# 15. Асинхронное программирование (asyncio)

Асинхронное программирование позволяет одной задаче уступить исполнение, пока она ждёт готовности данных, соединения, таймера или другой задачи. Освободившееся время event loop использует для остальных задач. Выигрыш появляется, когда ожидание действительно неблокирующее и число одновременно удерживаемых ресурсов ограничено.

В этой главе пройдём путь от `async def` до управления жизненным циклом приложения: владение задачами, структурированная конкурентность, отмена, дедлайны, очереди, streams, контекст запросов, взаимодействие с потоками и тестирование отказов. В конце находится законченный проект с ограниченной конкурентностью и проверкой остановки.

**Версии и формат примеров.** Базовая версия — Python 3.12+. Возможности новых версий помечены `# Python 3.13+` или `# Python 3.14+`. Учебные Python-блоки самодостаточны: сохраняйте каждый в отдельный `example.py` и запускайте `python example.py`. Блоки с пометкой `# pytest example` выполняются pytest; блоки проекта сохраняются по указанным путям. Внешние зависимости отмечены `# requires: ...`.

Большинство примеров использует только стандартную библиотеку и локальные данные. Сетевые демонстрации обращаются к собственному loopback-серверу, не требуют внешнего API и не отключают проверку TLS ради удобства. Учебные `assert` описывают ожидаемое поведение; в проекте runtime-валидация использует исключения.

Для отдельных библиотечных примеров в проверке использовались aiohttp 3.14.5, aiofiles 25.1.0 и HTTPX 0.28.1. Их можно установить в отдельное учебное окружение; эти зависимости не требуются runtime итогового проекта.

```bash
python -m pip install aiohttp==3.14.5 aiofiles==25.1.0 httpx==0.28.1
```

## Введение в асинхронность

### Проблема блокирующего I/O

Блокирующий вызов удерживает вызывающий OS-поток до завершения операции. Если это поток event loop, остальные корутины не получают исполнение, даже если их данные уже готовы.

Типичные источники блокировки — `time.sleep`, синхронный HTTP-клиент, обычные файловые операции, синхронный драйвер БД и запись в медленный logging handler. Наличие `async def` вокруг такого кода ничего не меняет.

```python
import asyncio


async def reader(ready: asyncio.Event) -> str:
    await ready.wait()
    return "data"


async def main() -> None:
    ready = asyncio.Event()
    task = asyncio.create_task(reader(ready))
    asyncio.get_running_loop().call_soon(ready.set)
    assert await task == "data"


asyncio.run(main())
```

Пока reader ждёт Event, поток event loop может исполнить callback. В реальном приложении так же ожидается готовность сокета. Для обычного файла portable asyncio API не предоставляет универсального неблокирующего `open/read`; часто используется пул потоков.

Сравнивайте не только время отдельного запроса, но и задержку остальных запросов. Один блокирующий вызов на секунду способен испортить tail latency всего сервиса.

### Конкурентность (Concurrency) vs Параллелизм (Parallelism)

Конкурентность — несколько работ продвигаются за пересекающиеся промежутки времени. Параллелизм — несколько работ физически исполняются одновременно.

В одном потоке loop обычно исполняет один Python-фрагмент за раз. Пока одна задача ждёт сеть, другие могут работать. Это конкурентность без одновременного исполнения нескольких Python-фрагментов в данном потоке.

Параллельный CPU получается через процессы, подходящие нативные библиотеки, несколько интерпретаторов или потоки free-threaded CPython. Создание тысячи asyncio.Task не создаёт тысячу вычислительных потоков.

Порядок запуска, окончания и выдачи результатов различается. `gather` возвращает результаты по входному порядку, а `as_completed` позволяет получать их по готовности.

### Процессы, потоки и асинхронность: сравнение подходов

| Модель | Ожидание I/O | Общие данные | Основная сложность |
| --- | --- | --- | --- |
| asyncio, один loop | Кооперативное переключение задач | Обычно один поток | Любая блокировка задерживает всех |
| Потоки | Блокирующий I/O допустим внутри worker | Общая память | Locks, гонки, жизненный цикл |
| Процессы | Независимые потоки процессов | Изолированная память | IPC, pickle, запуск и очистка |
| Гибрид | Async orchestration и выделенные workers | Границы нужно задать явно | Ограничения на обеих сторонах перехода |

Выбор определяется библиотеками и ресурсами. Если SDK предоставляет только синхронный API, ограниченный thread pool может оказаться естественным решением. Если клиент БД асинхронный, проще использовать его непосредственно.

В инженерии данных часто полезен гибрид: асинхронно получать ограниченные порции данных, выполнять тяжёлое преобразование в process pool и передавать результат ограниченному writer. Очередь между стадиями тоже должна иметь предел.

### Когда асинхронность нужна, а когда — вредна (CPU-bound задачи)

Asyncio удобно для большого числа независимых ожиданий: сетевые API, соединения БД, брокеры, streaming и таймеры. Оно усложняет простой последовательный скрипт, если тот почти всё время считает.

CPU-цикл внутри coroutine удерживает loop до явного освобождения исполнения. Добавление `await asyncio.sleep(0)` может улучшить отзывчивость, но не превращает работу в параллельную и не делает её автоматически быстрее.

Оценивайте затраты на scheduling, удержание Task, buffers, connection pools и cleanup. Асинхронный запрос на одну строку к локальному быстрому ресурсу не обязан быть быстрее синхронного.

Начинайте с последовательного oracle, затем измеряйте throughput, p95/p99 latency, loop lag, CPU и память при реалистичной нагрузке.

### Краткая история: от генераторов (yield) до async/await

Генераторы дали Python возможность приостанавливать и возобновлять функцию. `yield from` позволил делегировать выполнение другому генератору. Ранние асинхронные библиотеки строили coroutine-протоколы поверх этих механизмов.

Asyncio вошло в стандартную библиотеку в Python 3.4. Нативные `async def` и `await` появились в 3.5, асинхронные генераторы и comprehensions — в 3.6. Современные прикладные программы используют нативные корутины, TaskGroup и явное управление ресурсами.

Общий принцип сохранился: задача продвигается, пока может выполнить следующий шаг; затем передаёт управление планировщику при ожидании.

Изучать генераторные корутины полезно для понимания протоколов и старого кода. Копировать старые примеры с удалённым `@asyncio.coroutine` в новый проект не нужно.

## Основы asyncio

### Событийный цикл (Event Loop) — сердце асинхронности

Loop обслуживает готовые callbacks, шаги задач, таймеры и события I/O. Когда корутина действительно приостанавливается, loop может выбрать другую готовую работу.

Упрощённая последовательность: получить готовность → выполнить ограниченный фрагмент → зарегистрировать следующее ожидание → перейти к следующей готовой работе. Конкретные очереди и детали реализации не являются обещанием справедливого исполнения любого пользовательского кода.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    result = loop.create_future()
    loop.call_soon(result.set_result, "ready")
    assert await result == "ready"


asyncio.run(main())
```

Внутри coroutine используйте `get_running_loop`. Не создавайте loop на import библиотеки и не рассчитывайте, что `get_event_loop` всегда молча создаст его: поведение изменялось между версиями.

### Корутины (Coroutines): async def и объекты корутин

Вызов coroutine function создаёт coroutine object. Само тело функции при этом ещё не обязано исполниться. Исполнение начинается при await или передаче планировщику.

```python
import asyncio
import inspect


async def answer() -> int:
    return 42


async def main() -> None:
    coroutine = answer()
    assert inspect.iscoroutine(coroutine)
    assert await coroutine == 42
    try:
        await coroutine
    except RuntimeError:
        pass
    else:
        raise AssertionError("Нативную корутину нельзя использовать повторно")


asyncio.run(main())
```

Coroutine object одноразовый. Если один результат должны ожидать несколько потребителей, создайте Task: завершённую задачу можно await несколько раз.

Объект корутины, который не передан на выполнение, нужно закрыть, если вы сознательно отказываетесь от запуска. Иначе возможен `RuntimeWarning: coroutine was never awaited`.

### Ожидание: await и условия фактической приостановки корутины

`await` обращается к протоколу awaitable. Это потенциальная точка приостановки, но не обещание обязательного переключения на другую задачу.

Корутина без блокирующего await или уже завершённый Future могут вернуть результат немедленно. Аналогично `queue.get` для непустой очереди и свободный `lock.acquire` не обязаны дать другим задачам время исполнения.

```python
import asyncio


async def immediate() -> int:
    return 1


async def main() -> None:
    trace = []

    async def peer() -> None:
        trace.append("peer")

    task = asyncio.create_task(peer())
    assert await immediate() == 1
    trace.append("caller")
    assert trace == ["caller"]
    await task
    assert trace == ["caller", "peer"]


asyncio.run(main())
```

Пример использует стандартный отложенный запуск задач. Eager task factory может изменить порядок уже при `create_task`.

`asyncio.sleep(0)` явно уступает выполнение. Используйте его для обоснованной кооперативности, а не как случайный способ скрыть гонку или гарантировать окончание другой задачи.

### Запуск event loop: asyncio.run()

`asyncio.run` — синхронная граница приложения: создаёт loop, выполняет главную работу и завершает принадлежащие runner ресурсы. Обычно его вызывают один раз из точки входа.

```python
import asyncio


async def main() -> int:
    await asyncio.sleep(0)
    return 42


if __name__ == "__main__":
    assert asyncio.run(main(), debug=True) == 42
```

Нельзя вызвать `asyncio.run` в том же потоке, где уже работает loop. В notebook используйте top-level await, в ASGI-приложении — async API и lifespan хост-среды.

В 3.12 `asyncio.run` принимает coroutine; в 3.14 допускается любой awaitable. Для переносимого библиотечного API всё равно удобно предоставлять `async def`, а владение runner оставлять приложению.

### Создание задач: asyncio.create_task() и asyncio.ensure_future()

`create_task` планирует нативную корутину в текущем loop и возвращает Task. `ensure_future` поддерживает более общий набор awaitables и может вернуть уже переданный Future без создания нового Task.

```python
import asyncio


async def compute() -> int:
    await asyncio.sleep(0)
    return 7


async def main() -> None:
    task = asyncio.create_task(compute(), name="compute")
    assert asyncio.ensure_future(task) is task
    assert await task == 7
    assert await task == 7
    assert task.get_name() == "compute"


asyncio.run(main())
```

Для нового прикладного кода используйте TaskGroup либо `create_task` с явным владельцем. `ensure_future` полезен в адаптерах, где контракт действительно допускает Future.

Сохраняйте сильную ссылку на отдельную background Task, получайте её ошибку и задавайте завершение. Один набор `background_tasks` решает только удержание объектов; он не заменяет supervisor и shutdown.

### Конкурентное ожидание: asyncio.gather()

`gather` запускает переданные корутины конкурентно и возвращает список в порядке входных awaitables.

```python
import asyncio


async def double(value: int) -> int:
    await asyncio.sleep(0)
    return value * 2


async def main() -> None:
    result = await asyncio.gather(double(3), double(1), double(2))
    assert result == [6, 2, 4]


asyncio.run(main())
```

При обычном отказе одной задачи `gather` по умолчанию передаёт исключение ожидающему коду, но не отменяет остальных участников. Они могут продолжить работу после выхода вашего обработчика.

`return_exceptions=True` превращает исключения участников в элементы результата. Это удобно для контракта «собрать все исходы», если каждый элемент затем классифицируется. Это не автоматическая обработка ошибок.

Отмена самого gather распространяется на незавершённых участников. Отмена одного участника не равна отмене gather целиком. Для связанной партии с отменой siblings при отказе обычно удобнее TaskGroup.

## Ожидаемые объекты (Awaitables)

### Три типа awaitable объектов

Основные виды — coroutine, Task и Future. Все могут участвовать в await, но имеют разные обязанности.

| Объект | Кто продвигает работу | Повторный await | Типичное назначение |
| --- | --- | --- | --- |
| Coroutine object | Ожидающий код или Task | Нет | Реализация операции |
| Task | Event loop | Да | Запланированное исполнение coroutine |
| Future | Внешний producer результата | Да | Адаптация callback API |

`collections.abc.Awaitable` — общий протокол, а не гарантия принятия объекта любым asyncio API. Например, `create_task` ожидает coroutine, а `wait` требует уже созданные Tasks/Futures.

Пользовательский `__await__` — низкоуровневая возможность; прикладному коду чаще достаточно `async def`.

### Корутины

`await child()` обычно выполняет дочернюю coroutine внутри текущего Task. Отдельная Task при этом не появляется автоматически.

```python
import asyncio


async def child() -> asyncio.Task:
    return asyncio.current_task()


async def main() -> None:
    parent = asyncio.current_task()
    assert await child() is parent
    separate = asyncio.create_task(child())
    assert await separate is separate


asyncio.run(main())
```

Это влияет на отмену, ContextVar, stack introspection и владение. Async call graph может содержать много coroutine-вызовов внутри одной Task.

### Задачи (Tasks)

Task связывает coroutine с планировщиком, хранит исход и поддерживает отмену. Она может ожидать другой awaitable, оставаться готовой к продолжению или завершиться.

`done()` означает завершение с результатом, исключением или отменой. `cancelled()` истинно только для задачи, завершившейся отменой; `cancelling()` показывает число запросов отмены за вычетом соответствующих uncancel.

`task.result()` до завершения поднимает `InvalidStateError`. В отличие от concurrent.futures.Future, у asyncio Future/Task нет блокирующего `result(timeout=...)`: используйте await и async timeout.

Не создавайте Task конструктором без необходимости: высокоуровневые функции учитывают loop и фабрику задач.

### Футуры (Futures)

Future представляет будущий исход, но сама по себе не запускает coroutine. Производитель вызывает `set_result`, `set_exception` или отменяет Future.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    future = loop.create_future()

    def complete() -> None:
        if not future.done():
            future.set_result(42)

    loop.call_soon(complete)
    assert await future == 42


asyncio.run(main())
```

Создавайте Future через `loop.create_future`. Не завершайте его из чужого потока напрямую; перенесите callback в loop через `call_soon_threadsafe`.

Проверка `done` и установка результата выше выполняются без await в одном loop callback. Если между этими действиями появляется переход к другому потоку, прежнее обоснование безопасности перестаёт действовать.

### Иерархия и взаимосвязь между ними

Task использует Future-подобный интерфейс, но приложение не должно устанавливать результат Task вручную. Результат возникает из завершения её coroutine.

Типичная цепочка: приложение ожидает Task → Task выполняет coroutine → coroutine ожидает Future драйвера → callback готовности завершает Future → Task снова становится готовой.

Future привязан к loop. Объекты нельзя произвольно переносить между несколькими `asyncio.run` или threads. Ошибка может проявляться только при первой реальной блокировке, поэтому успешный короткий тест не доказывает корректность такого переноса.

Разделяйте asyncio.Future и concurrent.futures.Future. Для адаптации второго в loop есть `asyncio.wrap_future`; возвращаемый `run_coroutine_threadsafe` объект относится к concurrent.futures.

## Запуск и управление задачами

### Ожидание завершения: asyncio.wait()

`wait` получает непустой набор Tasks/Futures и возвращает два множества: завершённые и ещё ожидающие. Результаты и исключения нужно извлекать отдельно.

```python
import asyncio


async def main() -> None:
    gate = asyncio.Event()
    fast = asyncio.create_task(asyncio.sleep(0, result=1))
    slow = asyncio.create_task(gate.wait())
    tasks = {fast, slow}
    try:
        done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
        assert fast in done and slow in pending
        assert fast.result() == 1
    finally:
        gate.set()
        await asyncio.gather(*tasks, return_exceptions=True)


asyncio.run(main())
```

Начиная с Python 3.11 напрямую передавать coroutine objects в `wait` нельзя. Сначала создайте Task или используйте TaskGroup.

`wait` с timeout возвращает pending, а не поднимает TimeoutError и не отменяет участников. Отмена самого ожидания wait также не является автоматической отменой всех переданных задач.

### Параметры return_when: FIRST_COMPLETED, FIRST_EXCEPTION, ALL_COMPLETED

| Режим | Когда ожидание возвращается |
| --- | --- |
| FIRST_COMPLETED | Есть хотя бы один завершённый или отменённый участник |
| FIRST_EXCEPTION | Есть задача, завершившаяся исключением; без исключений — после всех |
| ALL_COMPLETED | Завершились все |

Несколько задач могут оказаться в done одновременно. Множество не задаёт входной порядок и не выбирает детерминированную «первую» ошибку.

FIRST_EXCEPTION — условие окончания ожидания, а не supervisor: оставшиеся задачи продолжают работу. Задача, завершившаяся отменой, не должна автоматически трактоваться как обычный бизнес-отказ.

### Обработка наборов завершенных и ожидающих задач

После wait обработайте каждый исход и решите судьбу pending. Для ожидающей задачи нужны продолжение, отмена с последующим await или передача другому явному владельцу.

```python
import asyncio


async def fail() -> None:
    raise ValueError("invalid data")


async def main() -> None:
    tasks = {
        asyncio.create_task(fail()),
        asyncio.create_task(asyncio.Event().wait()),
    }
    try:
        done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_EXCEPTION)
        errors = [task.exception() for task in done if not task.cancelled()]
        assert any(isinstance(error, ValueError) for error in errors)
        for task in pending:
            task.cancel()
    finally:
        await asyncio.gather(*tasks, return_exceptions=True)


asyncio.run(main())
```

`cancel` запрашивает отмену, а последующий await подтверждает, что задача дошла до завершения. Отсутствие этого await оставляет гонку с закрытием используемых ресурсов.

Если сама cleanup-последовательность может быть повторно отменена, нужно определить отдельную политику. Бесконечный shield без владельца не решает эту задачу.

### Ожидание с таймаутом: asyncio.wait_for()

`wait_for` ограничивает ожидание awaitable и при истечении времени обычно отменяет его. Если ему передана coroutine, она автоматически планируется как Task.

```python
import asyncio


async def main() -> None:
    cleaned = asyncio.Event()

    async def work() -> None:
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    try:
        await asyncio.wait_for(work(), timeout=0.01)
    except TimeoutError:
        pass
    else:
        raise AssertionError("Ожидалось истечение timeout")
    assert cleaned.is_set()


asyncio.run(main())
```

Timeout не является жёстким ограничением времени всей функции: wait_for дожидается обработки отмены. Долгий cleanup увеличивает фактическое время выхода. Если coroutine подавила CancelledError и вернула результат, исход тоже может отличаться от ожидаемого TimeoutError.

Для охвата нескольких await одной операцией удобнее `asyncio.timeout` или `timeout_at`. Дедлайн нужно рассчитывать по clock loop, а не по wall clock.

### Защита от отмены: asyncio.shield()

Shield отделяет отмену ожидающего от отмены внутреннего awaitable. Caller всё ещё может получить CancelledError, а защищённая Task продолжит исполняться.

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    finish = asyncio.Event()

    async def commit() -> str:
        started.set()
        await finish.wait()
        return "committed"

    inner = asyncio.create_task(commit())

    async def owner() -> str:
        return await asyncio.shield(inner)

    outer = asyncio.create_task(owner())
    await started.wait()
    outer.cancel()
    try:
        await outer
    except asyncio.CancelledError:
        pass
    assert not inner.done()
    finish.set()
    assert await inner == "committed"


asyncio.run(main())
```

В примере main сохраняет ссылку на inner и дожидается результата. Без такого владельца shield создаёт «продолжающуюся где-то» работу.

Shield не защищает от прямого `inner.cancel()`, закрытия процесса или внутренней ошибки. Не используйте его для сокрытия отмены всей бизнес-операции без явного контракта commit.

### Итерация по завершению: asyncio.as_completed()

На Python 3.12 переносимый вариант — обычный for, где каждый элемент затем нужно await. Эти элементы не являются исходными Task.

```python
import asyncio


async def main() -> None:
    tasks = [asyncio.create_task(asyncio.sleep(0, result=n)) for n in range(3)]
    try:
        values = []
        for completed in asyncio.as_completed(tasks):
            values.append(await completed)
        assert sorted(values) == [0, 1, 2]
    finally:
        await asyncio.gather(*tasks, return_exceptions=True)


asyncio.run(main())
```

С Python 3.13 доступен async iterator, который для явно переданных Tasks/Futures возвращает исходные объекты. Это удобно для сопоставления task → исходный запрос.

```python
# Python 3.13+
import asyncio


async def main() -> None:
    tasks = [asyncio.create_task(asyncio.sleep(0, result=n)) for n in range(2)]
    mapping = {task: index for index, task in enumerate(tasks)}
    async for task in asyncio.as_completed(tasks):
        assert await task == mapping[task]


asyncio.run(main())
```

Истечение timeout или прекращение итерации не отменяет оставшиеся задачи автоматически. Если прекращаете потребление, выполните собственную политику завершения.

<a id="structured-concurrency"></a>

## Структурированная конкурентность

### Владение задачами

У каждой Task должен быть владелец: request handler, компонент, TaskGroup, supervisor или приложение. Владелец определяет срок жизни, способ получения ошибки и shutdown.

Связь «создал Task и забыл» отсутствует в обычной лексической структуре программы. Родительская coroutine может вернуться, пока созданная Task продолжает пользоваться уже закрываемой session.

Структурированная конкурентность выражает зависимость явно: связанные задачи создаются внутри scope и не переживают его завершение.

Это не требует, чтобы в приложении не было долгоживущих workers. У таких workers владельцем становится долгоживущий scope приложения, а не случайный запрос.

### Ограничение времени жизни задач

Сначала определите scope: один HTTP-запрос, обработка сообщения, партия загрузки или lifespan приложения. Вложенные операции должны завершиться до выхода из scope либо быть переданы другому владельцу явно.

Ограничение lifetime не ограничивает число задач. TaskGroup с миллионом create_task всё ещё удерживает огромное количество Task. Для нагрузки нужны отдельные очереди и окна.

Успешный выход scope обычно означает, что связанная работа завершена. Abort означает: запрет новой работы → cancellation → cleanup → получение всех исходов → закрытие общих ресурсов.

### asyncio.TaskGroup

TaskGroup создаётся как async context manager. Его выход дожидается всех участников; отказ обычным исключением инициирует отмену остальных.

```python
import asyncio


async def square(value: int) -> int:
    await asyncio.sleep(0)
    return value * value


async def main() -> None:
    async with asyncio.TaskGroup() as group:
        first = group.create_task(square(3), name="first")
        second = group.create_task(square(4), name="second")
    assert (first.result(), second.result()) == (9, 16)


asyncio.run(main())
```

Не извлекайте result до завершения соответствующей задачи. Для больших потоков результатов используйте bounded queue или ограниченный completion window вместо накопления всех Task.

TaskGroup появился в 3.11. В 3.13 улучшено взаимодействие внешней и внутренней отмены; в 3.14 расширена передача параметров создания задач. Код, зависящий от тонких cancellation races, проверяйте на конкретных patch-версиях.

### TaskGroup vs gather()

| Вопрос | TaskGroup | gather |
| --- | --- | --- |
| Основная модель | Scope связанных задач | Awaitable, агрегирующий переданные операции |
| Обычный отказ участника | Отменяет siblings и ждёт их | По умолчанию передаёт ошибку без отмены остальных |
| Результаты | Из созданных Task или отдельного канала | Список во входном порядке |
| Несколько отказов | ExceptionGroup | По умолчанию первый наблюдаемый; другой режим — список исходов |
| Ограничение количества задач | Нужно реализовать отдельно | Нужно реализовать отдельно |

Выбирайте по контракту. Независимые best-effort проверки могут требовать «собрать все исходы». Согласованная партия, где результат без одной части бесполезен, естественно помещается в TaskGroup.

TaskGroup видит созданные через него задачи. Если участник сам вызвал голый create_task и потерял ссылку, структурированное владение этой дополнительной задачей автоматически не возникло.

### Ошибка одной задачи и судьба остальных

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()
    cleaned = asyncio.Event()

    async def dependent() -> None:
        started.set()
        try:
            await asyncio.Event().wait()
        finally:
            cleaned.set()

    async def fail() -> None:
        await started.wait()
        raise ValueError("failed")

    caught = []
    try:
        async with asyncio.TaskGroup() as group:
            group.create_task(dependent())
            group.create_task(fail())
    except* ValueError as errors:
        caught.extend(errors.exceptions)
    assert len(caught) == 1
    assert cleaned.is_set()


asyncio.run(main())
```

Отмена siblings кооперативная. Если участник заблокировал loop синхронным вызовом или подавляет отмену бесконечно, TaskGroup не может магически завершить его.

TaskGroup не откатывает внешние side effects. Для нескольких записей в разные системы нужен отдельный протокол согласованности, идемпотентность или компенсация.

### Группы исключений

ExceptionGroup хранит несколько исключений, сохраняя вложенную структуру. `except*` выделяет подходящие листья; остальные продолжают распространяться.

```python
def validate() -> None:
    raise ExceptionGroup("batch", [ValueError("bad value"), TypeError("bad type")])


handled = []
try:
    validate()
except* ValueError as group:
    handled.extend(type(error).__name__ for error in group.exceptions)
except* TypeError as group:
    handled.extend(type(error).__name__ for error in group.exceptions)
assert sorted(handled) == ["TypeError", "ValueError"]
```

`except*` не означает, что можно молча считать всю партию успешной. Сначала классифицируйте обработанные ошибки, затем определите судьбу результата.

Обычный except и except* нельзя смешать в одном try statement. При необходимости используйте вложенные try. KeyboardInterrupt и SystemExit TaskGroup обрабатывает особо: после остановки siblings исходное исключение поднимается отдельно.

### Вложенные группы задач

Вложенность выражает ресурсные границы: lifespan → batch → запросы одного источника. Внутренняя группа сначала завершает свой scope, а затем её ошибка становится отказом задачи внешней группы.

ExceptionGroup может содержать другие группы. Для анализа используйте except*, `subgroup` или `split`, а не предположение, что `group.exceptions` всегда состоит только из конечных бизнес-ошибок.

Не создавайте вложенность ради декоративной структуры. Граница полезна, когда у компонента собственные зависимости, deadline, политика повтора и ответственность за cleanup.

### Одновременная внешняя отмена и внутренний сбой

Одновременно могут произойти отмена запроса пользователем и отказ одного child. В таком случае важно сохранить и ошибку, и смысл внешней отмены, а не превратить отказ в успешный ответ.

В Python 3.13 поведение TaskGroup при внутренних и внешних cancellation-событиях улучшено, включая сохранение `Task.cancelling()`. Не используйте счётчик отмены как прикладной счётчик «числа нажатий Stop».

После except* обычных ошибок внешняя отмена может ещё требовать доставки на следующем await. Не сбрасывайте её через uncancel «для надёжности». Если компонент подавляет отмену намеренно, такой контракт должен быть узким и полностью завершать принадлежащую ему работу.

В тестах задавайте события в контролируемых точках. Один sleep на короткое время не доказывает, что вы воспроизвели конкретную гонку между отказом и отменой.

<a id="cancellation"></a>

## Отмена задач и обработка таймаутов

### Механизм отмены: task.cancel() и CancelledError

`cancel` запрашивает доставку CancelledError при следующей возможности продолжения Task. Он не является немедленным уничтожением стека.

```python
import asyncio


async def main() -> None:
    started = asyncio.Event()

    async def work() -> None:
        started.set()
        await asyncio.Event().wait()

    task = asyncio.create_task(work())
    await started.wait()
    assert task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        pass
    assert task.cancelled()
    assert task.done()


asyncio.run(main())
```

Если Task ожидает Future, отмена обычно передаётся этому awaitable. Shield может изменить границу распространения, поэтому граф await имеет значение.

Корутина, не уступающая loop, не получит отмену посреди произвольной Python-инструкции. Для длительной операции нужны checkpoints или изоляция в worker.

### Правильная обработка CancelledError в корутинах

CancelledError наследуется от BaseException. Обычный `except Exception` его не перехватывает, и это полезно для сохранения отмены.

```python
import asyncio


async def main() -> None:
    entered = asyncio.Event()
    cleaned = []

    async def operation() -> None:
        try:
            entered.set()
            await asyncio.Event().wait()
        except asyncio.CancelledError:
            cleaned.append("cancelled")
            raise
        finally:
            cleaned.append("closed")

    task = asyncio.create_task(operation())
    await entered.wait()
    task.cancel()
    try:
        await task
    except asyncio.CancelledError:
        pass
    assert cleaned == ["cancelled", "closed"]


asyncio.run(main())
```

Обычно достаточно finally, без отдельного except. Если отмену перехватывают для диагностики, после cleanup её поднимают снова.

Не оборачивайте тело coroutine в `except BaseException: return default`. Это скрывает отмену, KeyboardInterrupt и SystemExit, нарушая контракты runner и TaskGroup.

### Очистка ресурсов при отмене

Размещайте release, rollback и close в finally или async context manager. Сначала прекращайте использование общего ресурса всеми дочерними задачами, затем закрывайте ресурс.

Cleanup может содержать await. Уже доставленный CancelledError не означает, что каждое последующее await немедленно снова завершится отменой, но новый cancel во время cleanup возможен.

Для критичной финализации задайте отдельный ограниченный scope и владельца. Если применяете shield, удерживайте защищённую Task и решайте, кто дождётся её при повторной отмене.

Нельзя гарантировать успешный rollback после потери процесса или соединения. Отмена клиентской Task не подтверждает откат удалённой транзакции.

### Разница между таймаутом и отменой

Timeout — политика времени ожидания; cancellation — механизм прекращения задачи. `asyncio.timeout` использует cancellation текущей Task и преобразует свою отмену в TimeoutError при выходе из контекста.

```python
import asyncio


async def main() -> None:
    scope = None
    try:
        async with asyncio.timeout(0) as scope:
            await asyncio.Event().wait()
    except TimeoutError:
        assert scope is not None and scope.expired()
    else:
        raise AssertionError("Ожидался timeout")


asyncio.run(main())
```

Ловите TimeoutError снаружи соответствующего async with. Внутри coroutine обычно видит CancelledError.

Одинаковый класс TimeoutError может возникнуть и из самой операции. Если важно отличить причину, проверяйте timeout scope и классифицируйте ошибки зависимости отдельно.

### Отмена как часть контракта операции

Опишите, что означает отмена до отправки запроса, во время чтения ответа и после commit. Клиент мог перестать ждать, когда сервер уже сохранил данные.

Для безопасного повтора нужны idempotency key, уникальный бизнес-ключ, проверка статуса или транзакционный протокол. «Получили CancelledError» не означает «ничего не произошло».

В потоковом адаптере coroutine может завершиться отменой, а синхронный worker продолжить писать файл. В subprocess-коде отмена ожидания не означает, что дочерний процесс остановлен.

Полезно различать: запрос отмены принят, новые работы не принимаются, выполнение остановлено, ресурсы освобождены и результат операции известен.

<a id="synchronization"></a>

## Примитивы синхронизации

### Зачем нужны блокировки в асинхронном коде

Один loop не исключает логических гонок. Если между чтением и изменением общего состояния есть фактическая приостановка, другая Task может изменить это состояние.

```python
import asyncio


async def main() -> None:
    counter = 0
    barrier = asyncio.Barrier(2)

    async def increment() -> None:
        nonlocal counter
        previous = counter
        await barrier.wait()
        counter = previous + 1

    async with asyncio.TaskGroup() as group:
        group.create_task(increment())
        group.create_task(increment())
    assert counter == 1


asyncio.run(main())
```

Barrier делает потерю обновления воспроизводимой. Она не зависит от того, насколько «удачно» ОС переключила потоки.

Если весь фрагмент выполняется в одном loop без приостановки и не передаёт управление reentrant-коду, его обоснование отличается от многопоточного. Но вызов неизвестной функции, callback или перенос в другой поток может изменить это предположение.

### asyncio.Lock

Lock защищает прикладной инвариант между Tasks одного loop. Используйте async with, чтобы release произошёл и при исключении.

```python
import asyncio


async def main() -> None:
    lock = asyncio.Lock()
    counter = 0

    async def increment() -> None:
        nonlocal counter
        async with lock:
            previous = counter
            await asyncio.sleep(0)
            counter = previous + 1

    async with asyncio.TaskGroup() as group:
        for _ in range(10):
            group.create_task(increment())
    assert counter == 10
    assert not lock.locked()


asyncio.run(main())
```

Lock не reentrant: повторный acquire той же Task может привести к deadlock. Для нескольких locks задавайте единый порядок захвата.

Документация обещает справедливость ожидания acquire для asyncio.Lock. Это не обещание общей справедливости всего приложения и не универсальная гарантия для любых семафоров или сторонних примитивов.

Не удерживайте lock во время медленного I/O без необходимости. Иногда лучше зафиксировать короткое изменение состояния под lock, а долгую работу выполнить за его пределами.

### asyncio.Semaphore и BoundedSemaphore (ограничение конкурентности)

Semaphore ограничивает число одновременно вошедших операций. BoundedSemaphore дополнительно обнаруживает release сверх исходной ёмкости.

```python
import asyncio


async def main() -> None:
    semaphore = asyncio.BoundedSemaphore(2)
    active = peak = 0

    async def work() -> None:
        nonlocal active, peak
        async with semaphore:
            active += 1
            peak = max(peak, active)
            try:
                await asyncio.sleep(0)
            finally:
                active -= 1

    async with asyncio.TaskGroup() as group:
        for _ in range(8):
            group.create_task(work())
    assert active == 0
    assert peak <= 2


asyncio.run(main())
```

Семафор не ограничивает количество уже созданных Task и их аргументы. Миллион Task, ожидающих semaphore, остаются миллионом объектов с удерживаемым контекстом.

Лимит зависит от ресурса: connections, expensive queries, открытые файлы или CPU-stage. Смешивать разные ограничения одним глобальным semaphore не всегда правильно.

### asyncio.Event (оповещение между задачами)

Event хранит флаг. Set пробуждает ожидающих, clear сбрасывает флаг для последующих wait. Уже установленный Event ожидается без длительной блокировки.

```python
import asyncio


async def main() -> None:
    ready = asyncio.Event()
    observed = []

    async def waiter(index: int) -> None:
        await ready.wait()
        observed.append(index)

    async with asyncio.TaskGroup() as group:
        group.create_task(waiter(1))
        group.create_task(waiter(2))
        ready.set()
    assert sorted(observed) == [1, 2]


asyncio.run(main())
```

Event не является счётчиком событий или очередью сообщений. Несколько set не создают несколько отдельных доставок. Для каждого события с payload используйте Queue.

Из чужого OS-потока вызывайте `loop.call_soon_threadsafe(event.set)`, а не event.set напрямую.

### asyncio.Condition

Condition связывает ожидание изменения с проверкой предиката под lock. `wait` освобождает lock на время ожидания и захватывает его снова перед возвратом.

```python
import asyncio


async def main() -> None:
    condition = asyncio.Condition()
    state = {"ready": False}

    async def consumer() -> str:
        async with condition:
            await condition.wait_for(lambda: state["ready"])
            return "ready"

    task = asyncio.create_task(consumer())
    async with condition:
        state["ready"] = True
        condition.notify_all()
    assert await task == "ready"


asyncio.run(main())
```

Предикат важнее самого уведомления: состояние могло измениться до начала ожидания, а wait может завершиться без подходящего бизнес-состояния.

`condition.wait_for(predicate)` отличается от `asyncio.wait_for(awaitable, timeout)`. Первый ждёт предикат, второй ограничивает время ожидания.

### asyncio.Queue (обмен данными между задачами)

Queue позволяет передавать владение элементом между producer и consumer. Bounded queue при заполнении приостанавливает put и создаёт backpressure.

```python
import asyncio


async def main() -> None:
    queue = asyncio.Queue(maxsize=2)
    sentinel = object()
    result = []

    async def producer() -> None:
        for number in range(4):
            await queue.put(number)
        await queue.put(sentinel)

    async def consumer() -> None:
        while True:
            item = await queue.get()
            try:
                if item is sentinel:
                    return
                result.append(item * 2)
            finally:
                queue.task_done()

    async with asyncio.TaskGroup() as group:
        group.create_task(producer())
        group.create_task(consumer())
    await queue.join()
    assert result == [0, 2, 4, 6]


asyncio.run(main())
```

Sentinel тоже является элементом очереди и требует task_done. При нескольких consumers обычно требуется по одному сигналу завершения каждому.

`join` подтверждает соответствие put/task_done, а не успешность бизнес-операции. Если consumer умер, не вызывайте join бесконечно: используйте владельца задач и отдельную abort-политику.

### Типы очередей: FIFO, LIFO, Priority

| Тип | Порядок выдачи | Типичный сценарий |
| --- | --- | --- |
| Queue | Порядок помещения | Последовательный конвейер |
| LifoQueue | Последний помещённый первым | Обход или обработка свежей работы |
| PriorityQueue | По сравнению значений | Приоритетные задания |

У PriorityQueue одинаковые приоритеты заставляют сравнивать следующие элементы tuple. Если payload не сравним, получите TypeError. Используйте монотонный sequence number: `(priority, sequence, payload)`.

Приоритет не решает starvation автоматически. Для справедливости может потребоваться aging, квоты разных классов или отдельные очереди.

FIFO описывает извлечение из очереди, а не порядок завершения workers.

### Обработка переполнения и пустоты

`put_nowait` поднимает QueueFull, `get_nowait` — QueueEmpty. Async put/get позволяют ждать без блокировки OS-потока.

```python
import asyncio


async def main() -> None:
    queue = asyncio.Queue(maxsize=1)
    queue.put_nowait("one")
    try:
        queue.put_nowait("two")
    except asyncio.QueueFull:
        pass
    else:
        raise AssertionError("Ожидалась полная очередь")
    assert queue.get_nowait() == "one"
    queue.task_done()
    await queue.join()
    try:
        queue.get_nowait()
    except asyncio.QueueEmpty:
        pass
    else:
        raise AssertionError("Ожидалась пустая очередь")


asyncio.run(main())
```

У Queue нет аргумента timeout в get/put; ограничьте область через timeout или wait_for. Не выполняйте проверку `empty` и затем get как будто это одна атомарная операция с гарантией будущего результата.

`maxsize=0` означает отсутствие ограничения числа элементов. Даже положительный maxsize ограничивает элементы, а не суммарные bytes payload.

### Гонки между корутинами на точках await; asyncio-примитивы не потокобезопасны

Ищите последовательности «прочитал → await → изменил» и «проверил условие → await → выполнил действие». Между ними другая Task может изменить состояние.

Примитивы asyncio предназначены для взаимодействия внутри одного loop. В free-threaded Python это ограничение сохраняется: отсутствие GIL не делает Queue, Event и Lock межпоточными.

Для threads используйте threading-примитивы и безопасные переходы в loop. Не удерживайте обычный threading.Lock на await: другой callback того же OS-потока может попытаться захватить этот же lock и заблокировать весь loop.

Также не полагайтесь на threading.RLock для взаимного исключения Tasks: они могут исполняться в одном OS-потоке, которому разрешён повторный вход.

<a id="backpressure"></a>

## Управление нагрузкой и обратное давление — Backpressure

### Ограниченные очереди

Backpressure не позволяет upstream бесконечно опережать downstream. Ограниченная очередь превращает избыток поступления в ожидание, отказ, сброс или запись во внешнее хранилище — в зависимости от политики.

Ограничение должно покрывать все стадии: входную очередь, running операции, готовые результаты, network buffers и отложенные retries.

Если producer сначала создаёт миллион объектов, а затем кладёт их по одному в bounded queue, память уже израсходована. Источник тоже должен читаться постепенно.

В DE отдельно учитывайте размер партии: очередь на десять DataFrame или HTTP-ответов не означает десять маленьких объектов.

### Число созданных задач vs число активных операций

`TaskGroup` отвечает за lifetime, semaphore — за вход в критическую область, Queue — за количество элементов между стадиями. Ни один из них сам по себе не ограничивает все ресурсы.

Два типовых решения — фиксированное количество consumer Tasks с bounded Queue или completion window с ограниченным количеством созданных задач.

При сохранении входного порядка в предел окна должны входить и завершённые, но ещё не выданные результаты. Иначе медленный первый элемент вызывает неограниченный reorder buffer.

Проверяйте этот инвариант тестом с удерживаемой ранней задачей и быстро завершающимися поздними задачами.

### Ограничения семафора при массовом создании задач

Антипаттерн: создать список Tasks для всех записей, а внутри каждой ждать semaphore. Активных запросов мало, но число Task, аргументов и context snapshots остаётся большим.

Исправление начинается до create_task: producer получает следующий элемент только при свободном слоте окна или при возможности put в ограниченную очередь.

Условие завершения тоже должно быть ограничено. Список всех Future/results в конце способен вернуть линейный рост памяти даже при корректной рабочей очереди.

В проекте число живых операций ограничивается при создании, а общий объём результата ограничен контрактом конечной партии.

### StreamWriter.drain()

`writer.write` передаёт bytes в буфер транспорта и обычно возвращается без ожидания их отправки. `await writer.drain()` учитывает flow control: при достижении high watermark ждёт снижения буфера.

Drain не означает, что удалённое приложение прочитало сообщение, записало его в БД или подтвердило commit. Для этого нужен прикладной acknowledgement.

Один `writer.write(huge_payload)` уже способен резко увеличить память до drain. Пишите ограниченными chunks и ограничивайте исходный payload.

Drain тоже может завершиться исключением или быть отменён. Освобождение writer выполняется отдельно через close/wait_closed.

### Завершение producer-consumer конвейера

При нормальном EOF producer прекращает ввод и отправляет протокол завершения. Consumers заканчивают текущую работу и освобождают ресурсы. Владелец дожидается участников.

При ошибке порядок другой: остановить приём → отменить связанные задачи → дождаться finally → решить судьбу оставшихся элементов. Нельзя ожидать queue.join, если некому выполнить task_done для хвоста.

Sentinel удобен для переносимости, `Queue.shutdown` — для поддерживающих его версий. Ни один из них не заменяет семантику «задание успешно выполнено», «отклонено» и «доступно для повтора».

Закрытие входной очереди не доказывает завершения выходного writer. У каждой стадии должен быть владелец.

### Rate limiting vs ограничение конкурентности

Concurrency limit ограничивает одновременно активные операции; rate limit — число стартов или событий за интервал.

При concurrency=10 и очень быстрых ответах можно выполнить тысячи запросов в секунду. При rate=10/s и долгих ответах без отдельного concurrency limit количество живых запросов может расти.

Для внешнего API часто нужны оба ограничения, bounded очередь и общий timeout. Rate limiter может использовать token bucket, leaky bucket или планирование времени следующего старта.

Серверный Retry-After и backoff нужно учитывать в общем бюджете. Retry не должен обходить rate limiter и создавать новый неограниченный слой ожиданий.

### Политика обработки перегрузки

| Политика | Когда подходит | Что требуется |
| --- | --- | --- |
| Ждать | Upstream выдерживает задержку | Timeout ожидания и отмена |
| Отклонить | Интерактивный сервис | Явная ошибка и метрики |
| Сбросить старое или новое | Допустимы потери, например телеметрия | Документированный loss contract |
| Сохранить во внешнюю очередь | Важна надёжная доставка | Квоты storage, ack и recovery |
| Coalesce | Важно последнее состояние ключа | Корректная семантика объединения |

Наблюдайте queue age, объём bytes, количество отклонений и долю времени ожидания слота. Один qsize без возраста элементов не показывает, насколько система отстаёт.

Не делайте бесконечный retry на перегрузку: это удерживает ресурсы и усиливает отказ зависимости.

<a id="async-io"></a>

## Асинхронный ввод-вывод

### Работа с сетью: asyncio.open_connection(), asyncio.start_server()

Streams дают высокоуровневую пару StreamReader/StreamWriter. TCP передаёт поток bytes, а не отдельные сообщения: нужны длина, разделитель или другой framing-протокол.

```python
import asyncio


async def main() -> None:
    handlers = set()

    async def handle(reader, writer) -> None:
        try:
            async with asyncio.timeout(3):
                data = await reader.readexactly(4)
                writer.write(data.upper())
                await writer.drain()
        finally:
            writer.close()
            await writer.wait_closed()

    def accepted(reader, writer) -> None:
        task = asyncio.create_task(handle(reader, writer))
        handlers.add(task)

    server = await asyncio.start_server(accepted, "127.0.0.1", 0)
    try:
        port = server.sockets[0].getsockname()[1]
        reader, writer = await asyncio.open_connection("127.0.0.1", port)
        try:
            writer.write(b"ping")
            await writer.drain()
            assert await reader.readexactly(4) == b"PING"
        finally:
            writer.close()
            await writer.wait_closed()
    finally:
        server.close()
        await server.wait_closed()
        outcomes = await asyncio.gather(*handlers, return_exceptions=True)
        assert not [value for value in outcomes if isinstance(value, BaseException)]


asyncio.run(main())
```

Здесь серверные Task имеют владельца и их ошибки получены. Закрытие listening socket само по себе не завершает уже принятые соединения.

`read(n)` может вернуть меньше n; `readexactly(n)` ждёт заданное количество или поднимает IncompleteReadError. `readuntil` читает до separator с учётом лимита; `reader.read()` без размера может накопить весь ответ до EOF.

`limit` reader — часть управления буфером, а не общий предел размера бизнес-ответа для любого способа чтения. Отдельно ограничьте bytes сообщения, время подключения, чтения и полного запроса.

Для внешней сети используйте TLS с проверкой сертификата и hostname. Не переносите незашифрованный loopback-пример в Интернет как готовый протокол.

### Создание HTTP-клиентов: aiohttp (обзор)

ClientSession владеет connection pool и должна жить достаточно долго для переиспользования соединений. Создавайте её внутри работающего async scope и закрывайте после использующих её задач.

```python
# requires: aiohttp
import asyncio
import aiohttp
from aiohttp import web


async def main() -> None:
    async def respond(request):
        return web.json_response({"value": 42})

    app = web.Application()
    app.router.add_get("/value", respond)
    runner = web.AppRunner(app)
    await runner.setup()
    try:
        site = web.TCPSite(runner, "127.0.0.1", 0)
        await site.start()
        port = runner.addresses[0][1]
        timeout = aiohttp.ClientTimeout(total=3, connect=1, sock_read=1)
        connector = aiohttp.TCPConnector(limit=4, limit_per_host=2)
        async with aiohttp.ClientSession(
            connector=connector, timeout=timeout
        ) as session:
            async with session.get(f"http://127.0.0.1:{port}/value") as response:
                response.raise_for_status()
                assert await response.json() == {"value": 42}
    finally:
        await runner.cleanup()


asyncio.run(main())
```

JSON маленького собственного сервера в примере ограничен по конструкции. Для внешнего ответа проверяйте размер при потоковом чтении; Content-Length может отсутствовать, а распаковка способна увеличить объём.

У aiohttp `connect` включает ожидание свободного соединения из pool, `sock_connect` относится к установлению нового соединения, `sock_read` — к интервалу ожидания очередной порции. Total timeout и бизнес-дедлайн имеют собственные области действия.

Read timeout не защищает от бесконечного «медленно, но регулярно» отправляемого ответа без общего лимита времени и размера. HTTP-status, ошибки транспорта и ошибки содержимого классифицируйте отдельно.

### Асинхронная работа с файлами: aiofiles (почему обычные файлы блокируют event loop)

Aiofiles предоставляет async-интерфейс к обычным файловым операциям, делегируя их в executor. Это не означает, что файловая система стала нативно асинхронной для всех платформ.

```python
# requires: aiofiles
import asyncio
from pathlib import Path
import tempfile
import aiofiles


async def main(path: Path) -> None:
    async with aiofiles.open(path, "w", encoding="utf-8") as target:
        await target.write("python\n")
    async with aiofiles.open(path, "r", encoding="utf-8") as source:
        assert await source.read(128) == "python\n"


with tempfile.TemporaryDirectory() as directory:
    asyncio.run(main(Path(directory) / "example.txt"))
```

Частые очень маленькие await read/write могут проигрывать одному ограниченному вызову в to_thread. Сравнивайте размер chunks и scheduling overhead.

Отмена ожидающей coroutine не гарантирует остановку файлового вызова, который уже выполняется в thread. Не удаляйте или переиспользуйте ресурс, пока его фактический владелец ещё работает.

Для сложной файловой операции иногда лучше передать worker целое действие «открыть → обработать → закрыть», а не переносить владение открытым файлом через несколько независимых thread jobs.

### Работа с подпроцессами: asyncio.create_subprocess_exec() и asyncio.create_subprocess_shell()

Exec принимает программу и аргументы без shell-интерпретации. Shell нужен только для действительно shell-команд; пользовательские значения в строке shell требуют отдельного корректного quoting.

```python
import asyncio
import sys


async def main() -> None:
    process = await asyncio.create_subprocess_exec(
        sys.executable,
        "-I",
        "-c",
        "print('ready')",
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    try:
        async with asyncio.timeout(5):
            stdout, stderr = await process.communicate()
        assert process.returncode == 0
        assert stdout.strip() == b"ready"
        assert stderr == b""
    finally:
        if process.returncode is None:
            try:
                process.kill()
            except ProcessLookupError:
                pass
            await process.wait()


asyncio.run(main())
```

Нельзя просто ждать `process.wait`, если child заполняет stdout/stderr pipes, которые никто не читает. Communicate решает взаимную блокировку чтения, но собирает вывод в памяти.

Для недоверенного большого вывода нужны отдельные reader Tasks, лимиты bytes и политика прерывания. Отмена wait/communicate не убивает child автоматически; после сигнала нужен wait.

Пример завершает один непосредственный child. Группа процессов и потомки требуют отдельной платформенной политики. Поддержка subprocess зависит от loop и ОС; Windows SelectorEventLoop и ProactorEventLoop имеют разные возможности.

## Структуры данных в асинхронном коде

### Асинхронные итераторы: __aiter__() и __anext__()

`__aiter__` возвращает async iterator, `__anext__` возвращает awaitable следующего элемента. Окончание обозначается StopAsyncIteration.

```python
import asyncio


class AsyncRange:
    def __init__(self, stop: int) -> None:
        self.current = 0
        self.stop = stop

    def __aiter__(self):
        return self

    async def __anext__(self) -> int:
        if self.current >= self.stop:
            raise StopAsyncIteration
        value = self.current
        self.current += 1
        await asyncio.sleep(0)
        return value


async def main() -> None:
    assert [value async for value in AsyncRange(3)] == [0, 1, 2]


asyncio.run(main())
```

Async iterator не обязан создавать background Task. Он может получать следующую страницу данных только при очередном `anext`, что помогает ограничивать prefetch.

Не вызывайте одновременно anext одного stateful iterator без явно заявленной поддержки: многие источники и async generators этого не допускают.

### Асинхронные генераторы: async for и yield

Async generator объединяет yield значений и await между ними. Вызов возвращает async generator object; для получения элемента нужен async for/anext.

```python
import asyncio


async def numbers():
    for value in range(3):
        await asyncio.sleep(0)
        yield value


async def main() -> None:
    assert [value * 2 async for value in numbers()] == [0, 2, 4]


asyncio.run(main())
```

Async generator не возвращает итоговое значение через `return value`, как обычный generator. Для результата используйте выдаваемые значения или отдельный объект состояния.

Async comprehension не делает операции автоматически параллельными: источник запрашивается последовательно по его протоколу.

### Асинхронные контекстные менеджеры: __aenter__() и __aexit__(), async with

Async context manager позволяет ждать acquisition и cleanup. Синтаксис не гарантирует, что метод действительно отдаст управление, но разрешает это.

```python
import asyncio
from contextlib import asynccontextmanager


@asynccontextmanager
async def resource(events):
    events.append("open")
    try:
        yield "resource"
    finally:
        await asyncio.sleep(0)
        events.append("close")


async def main() -> None:
    events = []
    try:
        async with resource(events) as value:
            assert value == "resource"
            raise ValueError("body failed")
    except ValueError:
        pass
    assert events == ["open", "close"]


asyncio.run(main())
```

`__aexit__` получает информацию об исключении. Возврат truthy подавляет его, поэтому по умолчанию не подавляйте ошибки и cancellation.

Для динамического набора ресурсов используйте `contextlib.AsyncExitStack`. Порядок освобождения — обратный порядку успешного входа. Сначала остановите пользователей ресурса, затем освобождайте его.

### aiter()/anext(), asend()/athrow()/aclose() и очистка async generators

`aiter` получает async iterator, `anext` возвращает awaitable следующего элемента и допускает default. Async generator дополнительно поддерживает asend, athrow и aclose.

```python
import asyncio
from contextlib import aclosing


async def source(events):
    try:
        yield 1
        yield 2
    finally:
        await asyncio.sleep(0)
        events.append("closed")


async def main() -> None:
    events = []
    async with aclosing(source(events)) as stream:
        assert aiter(stream) is stream
        assert await anext(stream) == 1
    assert events == ["closed"]
    sentinel = object()
    assert await anext(stream, sentinel) is sentinel


asyncio.run(main())
```

Обычный break из async for не является универсальной гарантией немедленного закрытия произвольного источника. Aclosing задаёт детерминированный cleanup в текущем scope.

`asend(None)` запускает generator; ненулевое значение можно передавать после его первой приостановки на yield. `athrow(exception_instance)` доставляет исключение, `aclose` инициирует GeneratorExit. Не выдавайте новое значение в ответ на GeneratorExit.

Runner закрывает оставшиеся async generators при завершении, но это последний рубеж. Закрывать generator, владеющий соединением, лучше сразу после окончания его использования.

<a id="contextvars"></a>

## Контекст выполнения — contextvars

### ContextVar

ContextVar хранит значение, зависящее от контекста выполнения. Он полезен для request ID, trace ID, tenant и другой ограниченной метаинформации.

```python
import asyncio
from contextvars import ContextVar

request_id = ContextVar("request_id", default="unset")


async def handler(value: str) -> str:
    token = request_id.set(value)
    try:
        await asyncio.sleep(0)
        return request_id.get()
    finally:
        request_id.reset(token)


async def main() -> None:
    assert await asyncio.gather(handler("a"), handler("b")) == ["a", "b"]
    assert request_id.get() == "unset"


asyncio.run(main())
```

ContextVar не заменяет аргументы бизнес-функции и не является защищённым хранилищем. Если значение — mutable dict, копирование Context не делает deepcopy этого dict.

Объявляйте ContextVar на уровне модуля; долгоживущие Context могут удерживать ссылки на переменные и значения.

### Установка и восстановление значения

Set возвращает token предыдущего состояния. Восстанавливайте его в finally, особенно при вложенных request scopes.

Не восстанавливайте через `set(default)`, если перед входом могло быть другое значение. Reset возвращает именно предыдущее состояние, включая отсутствие локального значения.

Изменение ContextVar внутри дочерней Task не должно использоваться как способ вернуть результат родителю. Возвращайте результат явно.

### Tokens

Token относится к конкретному ContextVar и контексту; его нельзя произвольно переносить в другую Task или применять повторно.

```python
from contextvars import ContextVar

value = ContextVar("value", default="default")
outer = value.set("outer")
try:
    inner = value.set("inner")
    try:
        assert value.get() == "inner"
    finally:
        value.reset(inner)
    assert value.get() == "outer"
finally:
    value.reset(outer)
assert value.get() == "default"
```

В Python 3.14 Token также можно использовать как context manager для автоматического reset. Для кода 3.12+ явный try/finally остаётся переносимым вариантом.

### Context и copy_context()

Context — набор привязок ContextVar. Copy_context создаёт неглубокую копию текущих привязок; объекты-значения могут оставаться общими.

```python
from contextvars import Context, ContextVar, copy_context

variable = ContextVar("variable", default="unset")
token = variable.set("parent")
try:
    copied = copy_context()
    empty = Context()
    variable.set("changed")
    assert copied.run(variable.get) == "parent"
    assert empty.run(variable.get) == "unset"
finally:
    variable.reset(token)
```

Не пытайтесь одновременно входить в один и тот же Context из нескольких threads. Для независимых работ создавайте соответствующие копии.

Набор переменных контекста — инфраструктурная зависимость. Явно определите, какая информация переносится на background работу после окончания запроса.

### Наследование контекста задачами

По умолчанию create_task копирует текущий Context в момент создания Task. Последующее изменение привязки у родителя не перезаписывает копию ребёнка.

```python
import asyncio
from contextvars import ContextVar

identity = ContextVar("identity", default="unset")


async def read() -> str:
    await asyncio.sleep(0)
    return identity.get()


async def main() -> None:
    token = identity.set("before")
    try:
        task = asyncio.create_task(read())
        identity.set("after")
        assert await task == "before"
        assert identity.get() == "after"
    finally:
        identity.reset(token)


asyncio.run(main())
```

`context=...` позволяет задать другой Context явно. Если передать один и тот же mutable Context нескольким Task, это не равнозначно независимому copy_context для каждой.

При eager execution тело Task может начать работу уже внутри create_task; контекст должен быть подготовлен до этого вызова.

### Передача контекста при работе через потоки

`asyncio.to_thread` переносит текущий Context в thread-операцию. Это происходит при выполнении самой coroutine to_thread, а не обязательно при создании её объекта.

```python
import asyncio
from contextvars import ContextVar, copy_context

identity = ContextVar("identity", default="unset")


async def main() -> None:
    token = identity.set("first")
    try:
        operation = asyncio.to_thread(identity.get)
        identity.set("second")
        assert await operation == "second"
        context = copy_context()
        loop = asyncio.get_running_loop()
        assert await loop.run_in_executor(None, context.run, identity.get) == "second"
    finally:
        identity.reset(token)


asyncio.run(main())
```

Run_in_executor не обещает новый per-call copy текущего Context как to_thread. Для явного переноса используйте Context.run с отдельной копией.

В free-threaded Python настройки наследования Context при создании Thread могут влиять на первоначальное состояние worker. Это не замена явному переносу контекста каждого задания переиспользуемого пула.

Изменения привязок ContextVar в worker не автоматически сливаются обратно в контекст ожидающей Task.

### Изоляция контекста запросов

Изолируйте request-scoped данные отдельным task scope и сбрасывайте временные привязки. Не храните объект Request или большую session в ContextVar без необходимости: background Task может удержать их после ответа.

Для фонового задания перенесите только необходимые идентификаторы и неизменяемые параметры. Полный snapshot запроса может удерживать credentials, buffers и ссылки на уже закрытые ресурсы.

ContextVar с общим mutable dict не изолирует содержимое. Используйте неизменяемые значения или новое значение на request, а для общего состояния — соответствующую синхронизацию.

### Применение для логирования и трассировки

Logging filter или LogRecordFactory может читать request ID из ContextVar и добавлять его в записи. Сам handler при этом должен быть достаточно быстрым или передавать запись в ограниченную очередь.

Различайте trace propagation и бизнес-данные. ID корреляции можно передавать дальше, но он не является подтверждением авторизации.

При работе с очередью логирования снимайте необходимые значения до передачи записи другому потоку. В thread потребителя текущий ContextVar уже может относиться к другому контексту.

Измеряйте время ожидания queue/pool отдельно от времени транспорта и обработки: общий span без этих стадий плохо объясняет перегрузку.

<a id="advanced-asyncio"></a>

## Продвинутая работа с asyncio

### Вложенные event loop'ы: проблемы и решения (nest-asyncio)

Повторный run в потоке работающего loop нарушает модель владения. Обычно правильное решение — предоставить async API и await его в текущей среде.

```python
import asyncio


async def child() -> int:
    return 42


async def main() -> None:
    coroutine = child()
    try:
        asyncio.run(coroutine)
    except RuntimeError:
        coroutine.close()
    else:
        raise AssertionError("Вложенный run должен быть отклонён")
    assert await child() == 42


asyncio.run(main())
```

В notebook вызывайте `await child()`, в web framework используйте handler/lifespan. Для синхронного API из другого thread возможен run_coroutine_threadsafe; нельзя блокировать на его result поток самого loop.

[nest_asyncio](https://github.com/erdewit/nest_asyncio) патчит модель reentrancy, но исходный репозиторий архивирован с марта 2024 года. Для нового приложения не делайте его основой lifecycle; сначала проверьте, почему синхронная оболочка пытается владеть уже работающим loop.

### Создание собственных футур

Future полезен для адаптации одноразового callback API. Контракт должен обработать завершение, ошибку, отмену и удаление регистрации callback.

```python
import asyncio


async def from_callback() -> str:
    loop = asyncio.get_running_loop()
    future = loop.create_future()

    def completed() -> None:
        if not future.done():
            future.set_result("ready")

    handle = loop.call_soon(completed)
    try:
        return await future
    finally:
        handle.cancel()


assert asyncio.run(from_callback()) == "ready"
```

Проверка done не даёт complete второй раз и не позволяет set_result отменённому Future. Если callback приходит из чужого thread, сначала планируйте безопасную функцию завершения в loop.

Не возвращайте внутренний изменяемый Future наружу без необходимости: вызывающий сможет отменить его или вмешаться в состояние адаптера.

### Низкоуровневая работа с event loop: loop.call_soon(), loop.call_later(), loop.call_at()

Call_soon планирует обычный callback, call_later — через задержку, call_at — по абсолютному времени clock loop. Они не ожидают coroutine, возвращённую callback.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    first = loop.create_future()
    second = loop.create_future()
    loop.call_later(0, first.set_result, 1)
    handle = loop.call_at(loop.time(), second.set_result, 2)
    try:
        assert await first == 1
        assert await second == 2
    finally:
        handle.cancel()


asyncio.run(main())
```

Timer не гарантирует исполнение точно в указанную наносекунду: влияют разрешение clock и занятость loop. Не строите протокол корректности на предположении об идеальном порядке близких таймеров.

Храните handle, если таймер нужно отменить при закрытии ресурса. Иначе callback может сработать после окончания его жизненного цикла.

### Интеграция с потоками: asyncio.to_thread() и loop.run_in_executor()

To_thread удобен для ограниченной блокирующей функции и переноса contextvars. Run_in_executor позволяет выбрать явный executor и возвращает asyncio Future.

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor


def blocking_sum(values) -> int:
    return sum(values)


async def main(pool) -> None:
    assert await asyncio.to_thread(blocking_sum, [1, 2, 3]) == 6
    loop = asyncio.get_running_loop()
    assert await loop.run_in_executor(pool, blocking_sum, [4, 5]) == 9


with ThreadPoolExecutor(max_workers=2) as pool:
    asyncio.run(main(pool))
```

Явный pool здесь закрывается синхронным владельцем после выхода runner. Если закрывать busy pool прямо в loop через shutdown(wait=True), ожидание может блокировать loop.

Отмена asyncio Future не останавливает уже начатую thread-функцию. Семафор вокруг await to_thread тоже может освободиться при cancellation раньше фактического окончания worker — учитывайте реальное число продолжающихся операций.

### Проброс синхронного блокирующего кода в потоки

Выделяйте thread-операции целиком и назначайте владельца resources внутри worker. У функции должны быть timeouts зависимостей и, при необходимости, cooperative stop.

Не используйте default executor как безразмерную очередь. В него могут обращаться и другие компоненты, в том числе системные операции event loop. Собственный ограниченный pool помогает изолировать медленный legacy SDK.

Если thread после отмены продолжает изменять общий объект, coroutine не должна закрывать или переиспользовать этот объект как будто работа закончилась. Для строгого владения храните underlying concurrent Future или выделяйте worker scope, завершение которого подтверждается отдельно.

CPU-bound pure Python в обычной сборке чаще выносится в process pool. В free-threaded-сборке thread pool может использовать несколько ядер, но требует реальной потокобезопасности кода.

### Взаимодействие event loop с другими потоками

Используйте call_soon_threadsafe для callback и run_coroutine_threadsafe для coroutine. Второй возвращает concurrent.futures.Future с синхронным result, предназначенным для другого потока.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()

    async def compute() -> int:
        await asyncio.sleep(0)
        return 42

    def caller_in_thread() -> int:
        future = asyncio.run_coroutine_threadsafe(compute(), loop)
        return future.result(timeout=3)

    assert await asyncio.to_thread(caller_in_thread) == 42


asyncio.run(main())
```

Если вызвать future.result в потоке этого же loop, получится ожидание работы, которую заблокированный поток сам должен выполнить.

При shutdown другой thread может попытаться отправить callback в уже закрытый loop. Прекратите producers до закрытия loop и обработайте отказ при поздней отправке. Coroutine object, не принятый планировщиком, не должен остаться незакрытым.

### Семафоры для ограничения конкурентности

При сложном pipeline полезно несколько лимитов: глобальный предел операций, per-host HTTP limit, отдельный DB bulkhead и ограничение CPU-stage.

Задайте единый порядок захвата нескольких семафоров. Цикл «worker A держит глобальный слот и ждёт DB, worker B держит DB и ждёт глобальный слот» способен вызвать deadlock.

Не занимайте дорогой connection slot на весь backoff перед повтором, если контракт позволяет его освободить. Но общий бюджет числа попыток и живых jobs должен сохраняться.

Для лимита, охватывающего несколько процессов или хостов, локального asyncio.Semaphore недостаточно.

<a id="application-lifecycle"></a>

## Жизненный цикл асинхронного приложения

### Владение event loop

Обычно loop принадлежит точке входа CLI, web server, notebook или GUI integration. Библиотека предоставляет coroutine и не создаёт скрытый runner на каждый вызов.

Создавайте loop-bound clients внутри этого lifecycle. Глобальная session на import может попасть в другой loop теста, быть создана до запуска runtime или пережить момент закрытия.

Один loop не должен одновременно исполняться в нескольких OS-потоках. Несколько loops требуют независимых ресурсов и явных мостов между ними.

### asyncio.Runner

Runner позволяет выполнить несколько top-level async операций в одном принадлежащем ему loop и контексте.

```python
import asyncio
from contextvars import ContextVar

state = ContextVar("state", default="empty")


async def initialize() -> None:
    state.set("initialized")


async def read() -> str:
    return state.get()


with asyncio.Runner(debug=True) as runner:
    runner.run(initialize())
    assert runner.run(read()) == "initialized"
assert state.get() == "empty"
```

Runner — context manager с синхронным входом; `run` нельзя вызывать внутри работающего loop того же потока.

При использовании loop_factory определите создание и регистрацию loop согласно контракту runner. Не рассчитывайте, что новая factory повторит все исторические глобальные policies автоматически.

### Инициализация ресурсов

Ресурсы должны быть готовы до приёма запросов. Если инициализация третьего ресурса упала, первые два нужно закрыть.

```python
import asyncio
from contextlib import AsyncExitStack, asynccontextmanager


@asynccontextmanager
async def opened(name, events):
    events.append(f"open:{name}")
    try:
        yield name
    finally:
        events.append(f"close:{name}")


async def main() -> None:
    events = []
    async with AsyncExitStack() as stack:
        await stack.enter_async_context(opened("http", events))
        await stack.enter_async_context(opened("db", events))
    assert events == ["open:http", "open:db", "close:db", "close:http"]


asyncio.run(main())
```

Для сервиса такая область соответствует lifespan. Запросы получают ссылки на готовые dependencies; они не создают новый connection pool для каждого SQL-запроса.

### Завершение фоновых задач

Фоновые Tasks должны принадлежать приложению. На shutdown запретите новые задания, подайте stop, дайте завершить принятую работу и затем отмените оставшееся по политике.

Простой `task.add_done_callback(background.discard)` удаляет ссылку, но не получает исключение. Supervisor должен наблюдать исход, записывать отказ и решать, требуется ли остановка приложения.

Не переносите request-scoped Task в бессрочный фон после отправки HTTP-ответа, если ей нужны request session или транзакция, которые уже закрываются.

### Закрытие асинхронных генераторов

Закрывайте генераторы рядом с их использованием через aclosing или собственный async context manager. Не полагайтесь на garbage collection для сетевого соединения.

При ручном управлении loop существуют `shutdown_asyncgens` и другие стадии завершения. Высокоуровневый runner выполняет эти шаги за приложение, но не отменяет необходимость корректного resource scope.

Generator-finally может содержать await и зависеть от живой session. Порядок закрытия должен позволять ему выполнить cleanup до удаления этих dependencies.

### Завершение executors

Default executor принадлежит loop/runner. Явно созданный executor принадлежит создавшему компоненту; runner не обязан закрыть чужой pool.

Async cancellation и фактическое завершение thread job различаются. Закрытие runner может ждать default executor, поэтому «main был отменён» не означает «процесс вышел немедленно».

Для зависающего legacy SDK задайте transport timeout, cooperative stop или отдельную process boundary. Небезопасно решать это бесконечным увеличением shutdown timeout.

У custom executor завершайте приём jobs раньше закрытия loop, иначе worker может попытаться вернуть результат в уже завершённую среду.

### Graceful shutdown

Практический порядок: снять readiness → прекратить приём новой работы → дождаться или отклонить accepted work → остановить producers/workers → завершить использующие ресурсы Tasks → закрыть clients и pools → вернуть управление runner.

У shutdown должен быть бюджет времени и определённый исход для незавершённых работ. Нельзя одновременно обещать неограниченное ожидание зависшей зависимости и строго ограниченный выход.

Сигналы ОС обрабатываются с учётом платформы и обычно главного thread. Не выполняйте тяжёлый cleanup прямо внутри signal handler; перенесите запрос остановки в async lifecycle.

Повторный Ctrl+C или SIGKILL может прервать даже правильный graceful shutdown. Внешняя надёжность строится также на recovery и идемпотентности, а не только на finally.

### Интеграция с уже работающей средой выполнения

В notebook используйте await. В ASGI/framework — предоставленный lifespan и request scopes. В GUI — поддерживаемый адаптер loop и событий GUI, а не два конкурирующих владельца главного потока.

Для CLI обычно достаточно одного asyncio.run. Для синхронного приложения с выделенным loop-thread потребуется явный startup handshake, безопасная отправка работ и shutdown этого thread.

Не делайте универсальную функцию, которая при наличии loop «иногда возвращает Task», а без него «иногда возвращает готовое значение», если это скрыто от caller. Лучше два явных API: async операция и синхронная оболочка.

<a id="errors-and-debugging"></a>

## Обработка ошибок и отладка

### Исключения в корутинах и задачах

При `await operation()` исключение возникает в ожидающем коде обычным образом. У отдельной Task исход хранится до await/result/exception.

Если никто не получил исключение завершённой Task, loop может сообщить `Task exception was never retrieved`. Это потеря владельца, а не альтернативный нормальный канал обработки.

Обработка только успешных results из очереди тоже может скрыть смерть worker. Нужен TaskGroup, supervisor или наблюдение каждого Task.

Дополняйте ошибку индексом задания, стадией и безопасной метаинформацией. Не включайте в exception все credentials или полный payload ради удобной диагностики.

### Глобальная обработка необработанных исключений: loop.set_exception_handler()

Exception handler loop получает диагностический context. Он полезен для телеметрии callback/transport ошибок, но не заменяет получение Task results.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    previous = loop.get_exception_handler()
    messages = []

    def handler(loop, context) -> None:
        messages.append(context["message"])

    loop.set_exception_handler(handler)
    try:
        loop.call_exception_handler({"message": "controlled diagnostic"})
    finally:
        loop.set_exception_handler(previous)
    assert messages == ["controlled diagnostic"]


asyncio.run(main())
```

Handler должен быть обычной быстрой функцией. Созданная из него background coroutine тоже нуждается во владельце; не создавайте рекурсивный канал ошибок.

Если вы не полностью обработали диагностику, передайте context default_exception_handler. Не бросайте новое исключение из handler ради передачи бизнес-ошибки родителю.

### Включение отладки: PYTHONASYNCIODEBUG=1 и asyncio.run(debug=True)

Debug mode помогает находить медленные callbacks, неправильный thread доступа и предоставляет полезные сведения о создании задач.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    assert loop.get_debug()
    loop.slow_callback_duration = 0.1
    task = asyncio.create_task(asyncio.sleep(0), name="diagnostic-example")
    await task


asyncio.run(main(), debug=True)
```

Дополнительно полезны warnings и development mode: `python -X dev -W default example.py`. Получайте ошибки детерминированно, а не ждите, когда GC случайно напечатает предупреждение.

Debug mode добавляет overhead. Проверяйте корректность с ним, а производительность измеряйте также в обычном режиме.

### Поиск "забытых" await (coroutine never awaited)

Частая причина — вызвать async функцию как обычную и проигнорировать объект. Другая — передать async callback в API, которое ждёт обычную функцию и не await возвращаемое значение.

Статический анализ и строгие warnings помогают обнаружить такие места. Тест, который проверяет только отсутствие исключения, может пропустить, что полезная работа вообще не началась.

Не «исправляйте» каждый забытый await заменой на create_task. Сначала определите, нужна ли последовательная операция, конкурирующая Task или callback-адаптер.

Если запуск сознательно отменён до планирования, закройте coroutine object. Не закрывайте вручную coroutine, которой уже владеет исполняющаяся Task.

### Профилирование асинхронного кода

Разделяйте on-CPU время, ожидание внешней системы, ожидание pool/queue и scheduling delay. Обычный stack sampler не всегда показывает логическую цепочку await.

Полезны имена Tasks, current_task/all_tasks, Task.get_stack/print_stack и трассировка стадий. Не считайте количество Tasks равным числу активных сетевых операций.

В Python 3.14 добавлены инструменты introspection async call graph:

```python
# Python 3.14+
import asyncio
import io


async def main() -> None:
    output = io.StringIO()
    asyncio.print_call_graph(file=output)
    assert output.getvalue()


asyncio.run(main())
```

Graph текущих ожиданий не показывает всю историю и не доказывает отсутствие deadlock. Сопоставляйте его с метриками очередей, возрастом задач и состоянием зависимостей.

## Тестирование асинхронного кода

### pytest-asyncio: маркировка асинхронных тестов

Pytest-asyncio выполняет async test function в управляемом loop. В strict mode тесты маркируются явно, а async fixtures объявляются через `pytest_asyncio.fixture`.

```python
# pytest example
# requires: pytest, pytest-asyncio
import asyncio
import pytest


@pytest.mark.asyncio
async def test_task_result() -> None:
    async with asyncio.TaskGroup() as group:
        task = group.create_task(asyncio.sleep(0, result=42))
    assert task.result() == 42
```

Для standalone-файла сохраните блок как `test_example.py` и выполните `python -m pytest -q test_example.py`. В проекте ниже режим и loop scopes заданы в pyproject.toml.

Fixture scope и event-loop scope — разные вещи. Долгоживущий async client нельзя без проверки использовать в тестах с другим loop. Для простых тестов function scope даёт понятную изоляцию.

Не вызывайте asyncio.run внутри уже асинхронного теста. Альтернатива без внешнего plugin — unittest.IsolatedAsyncioTestCase.

### Мокирование асинхронных вызовов

AsyncMock предназначен для вызываемого объекта, результат которого await. Проверяйте `assert_awaited...`, если важно именно ожидание, а не создание coroutine object.

```python
import asyncio
from unittest.mock import AsyncMock


async def service(fetch) -> int:
    data = await fetch("key")
    return data["value"] * 2


async def main() -> None:
    fetch = AsyncMock(return_value={"value": 21})
    assert await service(fetch) == 42
    fetch.assert_awaited_once_with("key")


asyncio.run(main())
```

У async context manager фабрика может быть обычным методом, возвращающим объект с __aenter__/__aexit__. Например, механически заменить любой session.get на AsyncMock — не всегда корректно.

Мок не доказывает поведение реального pool, транспорта и cancellation cleanup. Для этого нужны ограниченные интеграционные тесты на локальном сервере или реальной тестовой зависимости.

### Тестирование таймаутов и отмен

Удерживайте операцию Event и отменяйте после подтверждения её старта. Это проверяет известное состояние и не требует гадать, достаточно ли короткого sleep.

```python
# pytest example
# requires: pytest, pytest-asyncio
import asyncio
import pytest


@pytest.mark.asyncio
async def test_cancellation_runs_cleanup() -> None:
    started = asyncio.Event()
    closed = asyncio.Event()

    async def operation() -> None:
        started.set()
        try:
            await asyncio.Event().wait()
        finally:
            closed.set()

    task = asyncio.create_task(operation())
    try:
        await asyncio.wait_for(started.wait(), timeout=3)
        task.cancel()
        with pytest.raises(asyncio.CancelledError):
            await task
        assert closed.is_set()
    finally:
        if not task.done():
            task.cancel()
        await asyncio.gather(task, return_exceptions=True)
```

Для дедлайна полезен уже истёкший timeout или управляемый scheduler/clock. Если проверяется сам реальный timer, утверждайте исход и cleanup, а не точное количество миллисекунд.

Проверяйте, что после теста не осталось принадлежащих операции Task и открытых соединений. Автоматическая отмена loop при teardown может скрыть утечку.

### Работа с асинхронными контекстными менеджерами в тестах

```python
# pytest example
# requires: pytest, pytest-asyncio
from contextlib import asynccontextmanager
import pytest


@pytest.mark.asyncio
async def test_resource_closes_on_error() -> None:
    events = []

    @asynccontextmanager
    async def resource():
        events.append("open")
        try:
            yield "ready"
        finally:
            events.append("close")

    with pytest.raises(ValueError):
        async with resource() as value:
            assert value == "ready"
            raise ValueError("failed")
    assert events == ["open", "close"]
```

Реальную session fixture создавайте и закрывайте в одном подходящем loop scope. Если fixture стартует server, её teardown должен закрыть listener и дождаться либо отменить принятые handler Tasks.

Тестируйте отказ между успешными acquisitions: rollback и закрытие уже открытых dependencies важны не меньше обычного happy path.

<a id="patterns-and-antipatterns"></a>

## Паттерны и антипаттерны асинхронного программирования

### Паттерны

Хороший паттерн делает видимыми ownership, предел нагрузки и границу отказа. Полезны ограниченный worker pool, structured fan-out/fan-in, request-scoped timeout и lifespan-scoped clients.

Компонент удобно описать как «получает ограниченный вход → выполняет ограниченную работу → возвращает ограниченный исход». Его error/cancel/cleanup пути должны быть частью того же интерфейса.

Не добавляйте конкурентность между операциями с зависимостью, например записью родительской строки и чтением сгенерированного ключа. Параллелизм не меняет бизнес-порядок.

### Producer-Consumer с asyncio.Queue

Используйте фиксированное число consumers и bounded queue. Producer читает вход постепенно, consumer получает один элемент, выполняет работу и обязательно завершает учёт элемента.

В нормальном сценарии каждый consumer получает EOF-сигнал. При ошибке TaskGroup отменяет связанные стадии, а владелец не ожидает невозможного join необработанного хвоста.

Если output sink медленнее workers, ограничьте и выходную очередь. Иначе backpressure заканчивается на середине pipeline.

Отдельно задайте delivery contract. Task_done локальной очереди не является ack брокеру, commit в БД или гарантией exactly-once.

### Пул соединений

Pool переиспользует дорогие соединения и ограничивает их число. Сессия/engine обычно принадлежит приложению, а конкретное соединение или transaction — операции.

Ожидание свободного слота входит в latency и должно иметь timeout. Не удерживайте соединение во время независимого сетевого запроса или backoff, если бизнес-транзакция этого не требует.

Для нескольких процессов размер pool умножается на число процессов. Десять web workers с pool size=20 могут открыть около двухсот соединений плюс overflow.

Потокобезопасность и task-safety конкретного клиента проверяйте отдельно. Connection pool не делает одну stateful DB session пригодной для конкурентного использования всеми Tasks.

### Retry с экспоненциальной задержкой

Повторяйте только классифицированные временные ошибки. Ошибка валидации, неверный пароль и нарушение бизнес-инварианта обычно не исправляются повтором.

У retry должны быть max attempts, общий deadline и ограничение задержки. Jitter уменьшает синхронные повторные волны большого числа клиентов.

```python
import asyncio


class TemporaryFailure(Exception):
    pass


async def retry(operation, *, attempts: int = 3, sleep=asyncio.sleep):
    if attempts <= 0:
        raise ValueError("attempts must be positive")
    for attempt in range(attempts):
        try:
            return await operation()
        except TemporaryFailure:
            if attempt + 1 == attempts:
                raise
            await sleep(min(0.01 * 2**attempt, 0.1))


async def main() -> None:
    count = 0
    delays = []

    async def operation():
        nonlocal count
        count += 1
        if count < 3:
            raise TemporaryFailure
        return 42

    async def controlled_sleep(delay):
        delays.append(delay)

    assert await retry(operation, sleep=controlled_sleep) == 42
    assert delays == [0.01, 0.02]


asyncio.run(main())
```

Пример намеренно детерминированный; для распределённого клиента добавляют jitter и учитывают Retry-After. CancelledError не ловится как TemporaryFailure.

Повтор записи требует идемпотентности. Timeout после отправки запроса оставляет неопределённость: сервер мог выполнить действие, а ответ потерялся.

### Bulkhead (изоляция с помощью семафоров)

Разные зависимости получают отдельные лимиты, чтобы медленный сервис не занял все ресурсы приложения. Например, отдельные слоты для API A, API B и фоновой загрузки.

Bulkhead не является полной изоляцией: все Tasks могут делить loop, память, default executor и outbound network. Для CPU/памяти иногда нужна process boundary.

Очередь ожидания bulkhead тоже должна быть ограничена. Иначе отказ зависимости превращается в накопление миллионов ожидающих запросов.

### Антипаттерны

| Ошибка | Последствие | Направление исправления |
| --- | --- | --- |
| create_task без владельца | Потерянные ошибки и ресурсы | Scope или supervisor |
| Неограниченный gather входа | Большое число Tasks и результатов | Окно или workers |
| Sync I/O в loop | Общая задержка всех Tasks | Async driver или ограниченный executor |
| Один timeout на всё без классификации | Неясная причина отказа | Стадии и общий deadline |
| Подавление CancelledError | Невозможность остановки | Cleanup с повторным raise |
| «Лечить» гонку sleep | Нестабильность | Event, predicate и инвариант |

### Блокирующий вызов в корутине (time.sleep() вместо asyncio.sleep())

Time.sleep приостанавливает OS-поток, а не только текущую coroutine. То же касается requests.get, синхронного cursor.execute и тяжёлого JSON преобразования.

Для обычной задержки используйте asyncio.sleep. Для sync I/O — async альтернативу или ограниченный thread boundary. Для длительного CPU — подходящую модель исполнения.

Не добавляйте sleep(0) после блокирующей операции и не считайте это устранением блокировки. Уже потраченное в заблокированном loop время вернуть невозможно.

### Массовое создание задач: семафор ограничивает работу, но не число задач

Перед созданием Task должен существовать свободный слот принятой работы. В противном случае вы ограничили только внутренний участок, оставив неограниченные stack/context/arguments.

List comprehension с create_task по всему iterator сначала исчерпывает вход. Если источник бесконечный, программа может вообще не перейти к ожидающему await.

Ограничивайте prefetch и завершённые результаты, ожидающие выдачи. Выбор порядка выдачи связан с верхней границей памяти.

### Фоновые задачи без владельца и контроля завершения

Task, которая переживает свой resource scope, может обратиться к закрытой session или писать уже после объявления операции успешной.

У долгоживущего worker должны быть startup acknowledgement, обработка отказа, stop и подтверждение окончания. Это часть lifecycle компонента, даже если полезная работа «фоновая».

Внешняя долговечная работа обычно требует брокера/планировщика и сохранённого задания. Task в памяти web process не переживёт рестарт приложения.

### Необработанные исключения в фоновых задачах

Лог с ошибкой GC недостаточен для бизнес-решения. Владелец должен получить исход вовремя, пока можно остановить siblings, сохранить состояние или сообщить об отказе.

Не вызывайте `task.exception()` только ради исчезновения warning, если полученная ошибка затем игнорируется. Сначала определите допустимые и недопустимые отказы.

У callback получения исхода должен быть собственный безопасный error path: cancelled Task поднимет CancelledError при запросе exception/result.

<a id="ecosystem"></a>

## Асинхронные библиотеки и экосистема

### HTTP: aiohttp, httpx (асинхронный клиент)

Aiohttp предоставляет клиент и серверный стек поверх asyncio. HTTPX имеет синхронный и асинхронный клиент, ASGI transport и интеграцию с async backends через свою инфраструктуру.

```python
# requires: httpx
import asyncio
import httpx


async def main() -> None:
    def respond(request):
        return httpx.Response(200, json={"value": 42})

    transport = httpx.MockTransport(respond)
    async with httpx.AsyncClient(transport=transport, timeout=3) as client:
        response = await client.get("https://example.test/value")
        response.raise_for_status()
        assert response.json() == {"value": 42}


asyncio.run(main())
```

MockTransport проверяет клиентский API, а не реальную сеть, TLS или pool contention. Сетевой пример aiohttp выше использует настоящий loopback transport.

Переиспользуйте AsyncClient/ClientSession. Для streaming-response гарантируйте закрытие response даже при прекращении чтения. Отдельно настраивайте connect/read/write/pool timeouts и предел ответа.

### Базы данных: asyncpg (PostgreSQL), aiomysql, databases, SQLAlchemy 2.x (асинхронный режим)

Asyncpg — PostgreSQL-клиент; aiomysql — async-интерфейс к MySQL. SQLAlchemy 2.x предоставляет async engine, connection и ORM session поверх подходящего async driver.

Для SQLAlchemy AsyncSession — изменяемый stateful объект транзакции; конкурентным Tasks обычно нужны отдельные sessions. Общий engine/pool и одна общая session — разные конструкции.

Избегайте неявного I/O при доступе к ORM attributes. Планируйте загрузку связей явно, учитывайте streaming результатов, transaction scope и rollback при cancellation.

`run_sync` SQLAlchemy адаптирует поддерживаемые synchronous SQLAlchemy-операции; он не превращает произвольный requests.get внутри callback в неблокирующий вызов.

[encode/databases](https://github.com/encode/databases) архивирован с августа 2025 года. Для сопровождения существующего проекта изучайте его фактические версии; для нового проекта оценивайте поддерживаемые драйверы и SQLAlchemy async API.

### Web-фреймворки: обзор FastAPI, aiohttp.web, Sanic

Async handler должен использовать совместимые неблокирующие dependencies. Объявление handler через async def не переносит его синхронные вычисления в thread pool автоматически.

FastAPI работает в ASGI-экосистеме; aiohttp.web и Sanic имеют собственные server APIs. Lifecycle clients, Task и background jobs согласовывайте с lifespan/событиями выбранного framework.

При disconnect клиента распространение cancellation определяется стеком и конкретной точкой обработки. Не считайте возврат HTTP-ответа доказательством завершения произвольно созданной background Task.

Запуск нескольких server workers создаёт несколько процессов, loops и pools. Общий лимит БД и локальный semaphore каждого worker различаются.

### Очереди: интеграция с aiokafka, aio-pika (RabbitMQ)

Aiokafka и aio-pika дают async APIs, но broker delivery semantics остаются частью прикладной архитектуры.

Для Kafka определите момент commit offset относительно durable side effect. Обработка нескольких сообщений partition конкурентно требует контроля порядка: commit позднего offset не должен подтверждать ещё не завершённые предыдущие сообщения.

Для RabbitMQ prefetch ограничивает unacked delivery; ack выполняется по контракту успешной обработки. Prefetch не ограничивает автоматически все локальные buffers и созданные Tasks.

При shutdown остановите получение, завершите или отклоните in-flight work и только затем закрывайте producer/consumer/channel. Reconnect не доказывает exactly-once; повторная доставка требует идемпотентности.

<a id="asyncio-and-gil"></a>

## asyncio и GIL

### Взаимодействие asyncio с GIL и ограничения CPU-вычислений

Asyncio-планировщик и GIL решают разные задачи. В одном loop-thread Python-код обработчиков исполняется последовательно независимо от возможности других threads работать без GIL.

В обычной сборке GIL ограничивает параллельный pure Python в threads одного interpreter. Нативная библиотека может освобождать GIL; процессы и изолированные interpreters дают другие границы исполнения.

Даже в free-threaded CPython один CPU-тяжёлый callback заблокирует свой loop-thread до возврата. Для параллелизма работу нужно действительно распределить по threads/processes/interpreters.

### Переключение контекста на точках await

В одном loop coroutine уступает управление при фактическом ожидании. Завершённый Future или мгновенно возвращающая coroutine не обязаны уступать время.

Это позволяет рассуждать об инварианте внутри участка без suspension, если исключены другие threads и reentrant вызовы. Но гарантия относится к конкретному scope и вызванному коду, а не ко всем объектам Python.

Проверка «в функции есть await» не доказывает справедливость длинного цикла. Если источник всё время готов, loop может долго не получать реальной приостановки.

### CPU-bound задачи и asyncio: использование run_in_executor с процессами

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp


def cpu_work(limit: int) -> int:
    return sum(value * value for value in range(limit))


async def main(pool) -> None:
    loop = asyncio.get_running_loop()
    values = [1000, 2000]
    result = await asyncio.gather(
        *(loop.run_in_executor(pool, cpu_work, value) for value in values)
    )
    assert result == [cpu_work(value) for value in values]


if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=2, mp_context=mp.get_context("spawn")) as pool:
        asyncio.run(main(pool))
```

Worker должен быть pickle-доступен, аргументы и результат — сериализуемы. Размер работы должен оправдывать IPC и startup; этот короткий пример проверяет интеграцию, а не ускорение.

Отмена asyncio await не уничтожает начатую process job. Для строгого прекращения нужна отдельная политика process pool и судьбы уже принятых заданий.

### asyncio в free-threaded сборке: один loop, несколько потоков и границы безопасности

В CPython 3.14 asyncio поддерживает free-threaded runtime. Это не разрешение запускать один loop одновременно из нескольких threads или свободно менять Task/Future из чужого потока.

Корректная модель — собственный loop у каждого соответствующего thread, thread-safe переходы и понятное владение clients. Asyncio.Lock/Event/Queue остаются внутрипетлевыми примитивами.

```python
import asyncio
from concurrent.futures import ThreadPoolExecutor


def run_independent_loop(value: int) -> int:
    async def main() -> int:
        await asyncio.sleep(0)
        return value * 2

    return asyncio.run(main())


with ThreadPoolExecutor(max_workers=2) as pool:
    assert list(pool.map(run_independent_loop, [1, 2])) == [2, 4]
```

Пример показывает независимые loop scopes, но не является benchmark многопроцессорного ускорения. Если зависимость повторно включает GIL, результаты масштабирования изменятся; проверяйте runtime после импортов.

Если разные loops используют общий mutable Python-объект, ему требуется межпоточная синхронизация. Локальный asyncio.Lock одного loop этого не обеспечивает.

<a id="other-models"></a>

## Сравнение с другими моделями

### asyncio vs threading (потоки)

Asyncio удобно при поддерживаемом async API и большом количестве ожиданий. Threads естественны для блокирующих библиотек и могут быть проще для небольшого ограниченного числа операций.

Переход на asyncio требует сквозного async call graph до владельца loop. Переход на threads требует thread-safety общего состояния и зависимостей.

В обоих подходах нужны timeouts, ограничение принятой работы, наблюдение ошибок и shutdown. Наличие GIL не отменяет ни одного из этих требований.

### asyncio vs multiprocessing (процессы)

Asyncio управляет конкурентными ожиданиями внутри runtime; multiprocessing создаёт отдельные OS-процессы. Они часто дополняют друг друга.

Process boundary помогает использовать CPU и изолировать некоторые нативные отказы, но добавляет startup, сериализацию и отдельный lifecycle.

Не переносите огромные DataFrame между процессами по одному мелкому заданию. Оценивайте locality, partition size и цену копирования вместе с async orchestration.

### asyncio vs greenlet/gevent

Greenlet предоставляет механизм переключения стеков; gevent строит на нём кооперативную систему и может патчить привычные blocking APIs.

Asyncio выражает async границы в синтаксисе await. В gevent границы могут быть менее явными из-за monkey patching; порядок импортов и совместимость библиотек имеют значение.

Отсутствие async/await в функции gevent не доказывает, что она никогда не уступит выполнение. И наоборот, неизвестный blocking C-вызов может блокировать scheduler.

Не смешивайте модели без поддерживаемого адаптера и измерения поведения. Объект coroutine одного runtime не автоматически является корректной операцией другого.

### asyncio vs trio (альтернативная модель)

Trio делает структурированную конкурентность, nurseries и cancellation scopes основой API. Asyncio предоставляет широкий стандартный стек и TaskGroup для связанных задач.

Отмена в Trio имеет другую модель scopes и checkpoints; нельзя механически переносить идиомы подавления CancelledError из asyncio.

AnyIO позволяет строить часть прикладного кода поверх поддерживаемых asyncio/Trio backends. Совместимость abstractions не означает, что конкретный asyncio-only driver начнёт работать с Trio без адаптации.

Сначала выбирайте ecosystem зависимостей и модель ownership, затем оценивайте синтаксическое удобство.

### asyncio vs curio

Curio — отдельная coroutine-based модель с собственным kernel и набором операций. Он интересен для изучения дизайна async runtime и сравнения механизмов задач и отмены.

Общий синтаксис async def не делает runtime-специфичные awaitables взаимозаменяемыми. Asyncio.Future ожидает asyncio-планировщик, а не произвольный kernel.

При выборе для production отдельно проверяйте состояние сопровождения, поддерживаемые Python/platforms и нужные драйверы. Размер стандартной asyncio-экосистемы сам по себе не описывает преимущества или ограничения каждого альтернативного runtime.

<a id="python-versions"></a>

## Нововведения в asyncio (по версиям Python)

### Python 3.7: asyncio.run()

Asyncio.run упростил владение loop в обычном приложении. В этой версии также появились create_task и поддержка contextvars, которые стали основой современного request context.

Исторические версии важны для чтения старого кода, но примеры главы рассчитаны на 3.12+. Не выбирайте устаревшую версию только ради совпадения с обучающей статьёй.

### Python 3.8: оптимизации

Среди существенных изменений — CancelledError как BaseException, имена Task, IsolatedAsyncioTestCase и ProactorEventLoop по умолчанию на Windows.

Оптимизации реализации не являются гарантией определённого ускорения приложения. Изменение наследования CancelledError имеет прямое отношение к корректности except-блоков.

Проверяя старый код, ищите обработчики, которые предполагали, что отмена попадёт в except Exception, и низкоуровневые зависимости от конкретного Windows loop.

### Python 3.9: asyncio.to_thread()

To_thread сделал перенос блокирующей функции с contextvars удобнее. Дополнительно развивалось штатное завершение default executor в lifecycle loop.

To_thread не отменяет ограничение очереди, thread-safety и невозможность безопасно убить уже работающий thread. Это удобный адаптер, а не отдельная гарантия завершения.

### Python 3.10: улучшенное сообщение об ошибках

Практически важны более явные требования к loop usage и удаление устаревших loop-параметров у многих высокоуровневых asyncio APIs.

Не рассматривайте текст ошибки как стабильный прикладной интерфейс. Проверяйте тип исключения и свой контракт, а не полную строку traceback.

При миграции удаляйте устаревшие `loop=...` из высокоуровневых primitives согласно документации конкретной функции. В работающей coroutine получайте текущий loop через get_running_loop.

### Python 3.11: TaskGroup, ExceptionGroup и контекстные таймауты

TaskGroup выразил ownership связанных задач. ExceptionGroup/except* дали механизм обработки нескольких отказов. Timeout/timeout_at позволяют задать deadline scope.

Также нельзя передавать голые coroutine objects в wait. Это помогает не смешивать создание задач и наблюдение уже запланированной работы.

Использование нового API не исправляет старую архитектуру автоматически: неограниченный fan-out внутри TaskGroup остаётся неограниченным.

### asyncio.TaskGroup — структурированная конкурентность

Создавайте группу вокруг одной связанной операции. На обычном отказе siblings отменяются, а выход ждёт cleanup всех участников.

Не скрывайте отказ в каждой child через return None, если группа должна остановиться. Для best-effort задайте явный тип исхода, а не смешивайте ошибку и законный None.

В Python 3.13 закрывается coroutine, переданная в неактивную группу; улучшены cancellation races. В 3.14 create_task группы передаёт дополнительные kwargs loop factory.

### asyncio.timeout() и asyncio.timeout_at()

Timeout принимает относительную длительность; timeout_at — абсолютное время clock loop. Один deadline удобно передавать вниз без обновления полного бюджета на каждой стадии.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    deadline = loop.time() + 3
    async with asyncio.timeout_at(deadline) as scope:
        await asyncio.sleep(0)
    assert not scope.expired()

    async with asyncio.timeout(None) as adjustable:
        adjustable.reschedule(loop.time() + 3)
        await asyncio.sleep(0)
    assert not adjustable.expired()


asyncio.run(main())
```

Нельзя передавать `time.time()` как deadline loop: у clocks разные начала отсчёта. После timeout cleanup может увеличить общее время возврата.

У операции должны оставаться отдельные ограничения соединения/чтения и общий бюджет. Набор независимых «по 30 секунд на каждую попытку» не равен общему deadline 30 секунд.

### Python 3.12: улучшения в профилировании

В Python 3.12 появился `sys.monitoring` из PEP 669 — инфраструктура наблюдения за исполнением Python. Она не является готовым async profiler и не делает обычный call stack полной цепочкой await.

Важные asyncio-возможности этой версии — eager task factory, loop_factory у asyncio.run и поддержка генераторов Tasks в некоторых ожиданиях.

Проверяйте, что выбранный profiler понимает версию интерпретатора, Tasks и ожидания. Wall-clock span, on-CPU samples и async call graph отвечают на разные вопросы.

### Eager task execution: eager_task_factory и изменение порядка выполнения

Eager factory начинает выполнение coroutine синхронно при создании Task и передаёт её планировщику, если возникает блокировка.

```python
import asyncio


async def main() -> None:
    loop = asyncio.get_running_loop()
    previous = loop.get_task_factory()
    events = []

    async def cached() -> int:
        events.append("inside")
        return 42

    loop.set_task_factory(asyncio.eager_task_factory)
    try:
        task = asyncio.create_task(cached())
        events.append("after")
        assert task.done()
        assert await task == 42
        assert events == ["inside", "after"]
    finally:
        loop.set_task_factory(previous)


asyncio.run(main())
```

Это изменение семантики, а не только скорости: callback может ещё не выполниться, но тело coroutine уже отработало до возврата create_task.

В 3.14 можно задать eager_start непосредственно:

```python
# Python 3.14+
import asyncio


async def cached() -> int:
    return 42


async def main() -> None:
    task = asyncio.create_task(cached(), eager_start=True)
    assert task.done()
    assert await task == 42


asyncio.run(main())
```

Не полагайтесь на присваивание `task = create_task(worker())` как на гарантию, что worker увидит уже присвоенную переменную task. При eager execution его тело может начаться раньше.

### Обновления TaskGroup, as_completed() и завершения очередей

| Версия | Существенное изменение |
| --- | --- |
| 3.13 | Async iteration as_completed с сопоставлением исходных Tasks |
| 3.13 | Queue.shutdown и QueueShutDown |
| 3.13 | Улучшения TaskGroup при внутренней/внешней отмене |
| 3.14 | Передача kwargs/eager_start при создании Tasks |
| 3.14 | Новые APIs async call graph introspection |

```python
# Python 3.13+
import asyncio


async def main() -> None:
    queue = asyncio.Queue(maxsize=2)
    await queue.put("accepted")
    queue.shutdown()
    assert await queue.get() == "accepted"
    queue.task_done()
    await queue.join()
    try:
        await queue.get()
    except asyncio.QueueShutDown:
        pass
    else:
        raise AssertionError("Очередь должна быть закрыта")


asyncio.run(main())
```

Graceful shutdown запрещает новые put, но позволяет извлечь уже принятый хвост. Immediate shutdown может отбросить queued items; join после такого abort не доказывает их бизнес-обработку.

Task_done для начатой работы и судьба её side effects остаются отдельной ответственностью consumer.

### Event loop factories, Runner и миграция от устаревающих policies

Policy API устаревает в 3.14; документация планирует удаление в 3.16. Для настройки loop используйте loop_factory у runner/run вместо глобальной подмены policy.

```python
import asyncio


def loop_factory():
    loop = asyncio.new_event_loop()
    asyncio.set_event_loop(loop)
    return loop


async def main() -> int:
    assert asyncio.get_running_loop().is_running()
    return 42


try:
    with asyncio.Runner(loop_factory=loop_factory) as runner:
        assert runner.run(main()) == 42
finally:
    asyncio.set_event_loop(None)
```

Фабрика должна соответствовать требованиям хост-среды и платформы. Нельзя выбирать loop только по benchmark, если он не поддерживает нужные subprocess, signals или транспорт.

В 3.14 get_event_loop без текущего loop поднимает RuntimeError. Код внутри async функции должен опираться на get_running_loop, а не на историческое неявное создание.

<a id="performance"></a>

## Производительность и оптимизация

### Измерение производительности асинхронного кода

Измеряйте всю операцию, включая ожидание slots/pool, сериализацию, retries и cleanup. Отдельно фиксируйте throughput и распределение latency.

При устойчивом потоке среднее число работ в системе связано с интенсивностью и средним временем пребывания: `L ≈ λ × W`. Это ориентир capacity planning, а не обещание оптимального semaphore для p99.

Генератор нагрузки должен сам не быть bottleneck. Closed-loop benchmark может скрыть перегрузку, если новые запросы создаются только после окончания предыдущих.

Сравнивайте одинаковые datasets, ограничения, warmup, retries и способ публикации результата. Синтетический sleep полезен для модели ожидания, но не доказывает ускорение настоящей сети/CPU.

### Диагностика event loop

Наблюдайте loop lag, медленные callbacks, количество Tasks, возраст queue items и ожидание connection pool.

Periodic heartbeat должен сравнивать ожидаемое и фактическое время по loop.time. Сам монитор не должен выполнять blocking logging или создавать больше работы, чем система выдерживает.

Снимки all_tasks/get_stack показывают состояние в момент наблюдения. Разделяйте полезное ожидание сети и невозможность продвижения из-за циклических зависимостей.

В free-threaded runtime диагностируйте каждый loop отдельно и сопоставляйте с CPU отдельных threads.

### Оптимизация количества переключений контекста

Один await на каждый байт или элемент может тратить больше времени на scheduling, чем на полезную обработку. Используйте ограниченные batches и chunks.

Слишком крупная порция ухудшает latency и отзывчивость отмены. Размер выбирается по измерениям и требованиям к остановке.

Eager execution помогает части синхронно завершающихся coroutine, но меняет порядок и не устраняет внешнее I/O. Сначала проверьте семантику, потом скорость.

Не удаляйте необходимые checkpoints из CPU-heavy обработки ради красивого throughput, если это нарушает deadline остальных запросов.

### Пул соединений и повторное использование

Переиспользование уменьшает DNS/TCP/TLS overhead и нагрузку на сервер. Pool limits должны согласовываться с semaphore, числом workers и лимитами зависимости.

Слишком большой pool увеличивает конкуренцию на сервере; слишком маленький создаёт очередь ожидания. Отдельно измеряйте время в этой очереди.

При HTTP streaming непрочитый и незакрытый response может удерживать connection slot. При БД незавершённая transaction удерживает больше, чем Python-объект cursor.

Если клиенты привязаны к loop, не перемещайте их между разными asyncio.run ради «экономии создания».

### Балансировка нагрузки между задачами

Крупные неоднородные jobs дают stragglers. Динамическая выдача из очереди распределяет работу лучше статического назначения одинакового числа элементов каждому consumer.

Входной порядок выдачи может ограничить throughput при bounded reorder buffer. Это осознанный контракт: память и детерминизм иногда важнее максимальной загрузки workers.

При нескольких источниках используйте справедливую диспетчеризацию или per-source квоты, иначе один большой tenant займёт всё окно.

Не делите работу на слишком мелкие units без оценки scheduling/IPC overhead. Для CPU-stage это особенно заметно на process boundary.

<a id="common-mistakes"></a>

## Частые ошибки

### Забытый await (корутина не выполняется)

Проверьте, где создаётся coroutine object и кто начинает её исполнение. Вызов async-функции из обычного callback не означает, что callback API выполнит await.

Тест должен подтверждать side effect или результат, а не только отсутствие traceback. Статический анализ и warnings дополняют такую проверку.

Правильное исправление определяется требуемым порядком: await для зависимой операции, TaskGroup для связанного fan-out или supervisor для долгоживущего background.

### Создание задачи и немедленный await: влияние на структуру выполнения

`await create_task(operation())` создаёт отдельную Task, но не даёт само по себе полезного перекрытия с последующей строкой. Для последовательной композиции обычно достаточно `await operation()`.

Отдельная Task всё же меняет ownership, context copy, cancellation и introspection. Поэтому конструкции не полностью семантически тождественны.

Если нужна конкурентность, сначала создайте ограниченный набор независимых работ, затем ожидайте их по выбранному контракту. Не превращайте все последовательные вызовы в create_task автоматически.

### Мутация общих данных без блокировок (да, это нужно и в асинхронности)

Проверяйте инвариант на всех suspension boundaries. Классический пример — прочитать баланс, дождаться внешней проверки и записать значение, не учитывая параллельное изменение.

Lock помогает только участникам, которые его соблюдают. Для БД нужны транзакции, constraints или optimistic locking; локальный lock одного process не защищает от другого server worker.

Для простого агрегата иногда лучше один coordinator-владелец, которому workers возвращают immutable результаты.

### Смешивание потокового и асинхронного кода без run_in_executor

Обычный I/O-вызов в coroutine блокирует loop. Asyncio-примитив в другом thread не становится thread-safe от отсутствия GIL.

Используйте async API зависимости, to_thread/run_in_executor для sync boundary и thread-safe APIs для обратной передачи.

Проверяйте не только успешный переход, но и остановку: что произойдёт, если loop закрывается, пока thread пытается вернуть результат или отправить callback?

### Ожидание корутины вместо создания задачи для фоновой работы

Await означает участие в текущем последовательном потоке выполнения. Если coroutine должна жить конкурентно, нужен планировщик и владелец отдельной Task.

Но «фоновая» не означает «никому не принадлежит». Для конечной партии используйте TaskGroup; для долгоживущего worker — application scope с supervisor.

Не маскируйте неверную зависимость запуском в фоне. Если следующий шаг требует результата, await выражает правильный порядок.

### Игнорирование CancelledError при очистке

Отмена должна проходить через cleanup и оставаться наблюдаемой вызывающим кодом. Return из finally может подавить и отмену, и обычную ошибку.

Не делайте blanket uncancel. Если операция намеренно заканчивает commit несмотря на отмену, задайте точную границу и владельца, который дождётся результата.

Cleanup тоже способен упасть. Сохраняйте причинную информацию, а не заменяйте исходный отказ безусловным «не удалось закрыть».

### Долгие вычисления в корутине (блокировка event loop)

Большая JSON-декодировка, сортировка, компрессия и Python-цикл могут блокировать loop не хуже time.sleep. Профилируйте время без checkpoints.

Для умеренной работы полезно ограничить размер входа. Для большой — выделить CPU-stage в подходящий executor или другую систему обработки.

Asyncio не заменяет Spark для распределённой обработки больших datasets. Оно помогает управлять I/O и orchestration, но не делает память и CPU одной машины безграничными.

<a id="faq"></a>

## Частые вопросы и ключевые выводы

### Что такое event loop простыми словами?

Это диспетчер, который продолжает готовые задачи и callbacks, обслуживает I/O и таймеры. Он эффективен, пока каждый исполняемый фрагмент вовремя возвращает управление.

Loop не читает мысли coroutine и не переносит blocking функцию в thread автоматически.

### В чем разница между asyncio.create_task() и asyncio.ensure_future()?

Create_task создаёт Task для coroutine в работающем loop. Ensure_future принимает более общий awaitable и может вернуть уже существующий Future.

Для прикладного fan-out обычно выбирают TaskGroup/create_task. Для адаптера общего awaitable может понадобиться ensure_future.

### Как выполнить синхронную функцию в асинхронном коде?

Небольшой неблокирующий вызов можно выполнить прямо. Sync I/O — через async alternative или ограниченный to_thread/thread pool. CPU-bound pure Python — через подходящий process/interpreter/thread backend с учётом GIL.

Для каждого варианта задайте передачу контекста, ограничения нагрузки и фактическое завершение после cancellation.

### Как ограничить количество одновременных запросов?

Ограничьте создание jobs/Tasks, одновременно выполняющиеся операции, connection pool и размер ответов. При необходимости добавьте rate limiter и per-host/per-tenant квоты.

Если сохраняется входной порядок, включайте завершённые, но ещё не выданные результаты в общий предел окна.

### Когда использовать asyncio, а когда — threading?

Когда зависимости асинхронные и много I/O-ожиданий, asyncio часто даёт удобную модель. Для blocking SDK и небольшого ограниченного fan-out threads могут быть проще.

Решение проверяйте по корректности, задержке, памяти и сложности эксплуатации. Само слово async не является характеристикой качества архитектуры.

### Итоговая шпаргалка по asyncio

| Задача | API или подход | Что ещё необходимо |
| --- | --- | --- |
| Запустить CLI | asyncio.run | Один владелец loop |
| Несколько top-level вызовов | asyncio.Runner | Общий согласованный lifecycle |
| Связанный fan-out | TaskGroup | Отдельный лимит числа jobs |

| Ограничить операцию по времени | timeout/timeout_at | Cleanup и semantics commit |
| Ограничить активный ресурс | Semaphore/pool | Bounded admission и bytes |

| Перенести blocking I/O | to_thread/executor | Реальное завершение worker |

Надёжный async-код делает видимыми не только успешные результаты, но и момент остановки, судьбу ошибок и верхние границы удерживаемой работы.

**Практический проект: ограниченная асинхронная партия запросов**

Соберём `bounded-async`: библиотеку и CLI для обработки конечной последовательности целых чисел. Для каждого числа worker получает квадрат от небольшого TCP-сервиса. Главная программа сохраняет входной порядок, ограничивает число Task и активных операций, выполняет ограниченный retry временных ошибок и возвращает отчёт только после полного успешного завершения.

Демонстрационный сервер запускается самим CLI по `--demo` на loopback и освобождает порт при выходе. Для проверки не нужен Интернет, внешний брокер или БД. Внешних runtime-зависимостей нет.

Упражнение посвящено orchestration, а не распределённому вычислению квадратов: арифметика намеренно проста, чтобы ошибки протокола и lifecycle не прятались за бизнес-алгоритмом.

**Контракт и пределы**

| Параметр | Контракт |
| --- | --- |
| Входной элемент | Именно int, от 0 до 1 000 000; bool не принимается |
| Результат worker | Именно int, от 0 до 10¹² |
| Порядок отчёта | Порядок входных элементов |
| Число входов | Не больше max_items; допустимый предел настройки — 10 000 |
| Число активных операций | Не больше concurrency |
| Созданная, но ещё не выданная работа | Не больше max_in_flight |
| Временная ошибка | OSError или timeout попытки; повторяется по RetryPolicy |
| Ошибка протокола | Не повторяется автоматически |
| Отмена | Передаётся вызывающему после cleanup Tasks |
| Ошибка участника | ExceptionGroup с индексированными ItemFailure |
| Успех CLI | Один полный JSON-отчёт в stdout |
| Отказ CLI | Диагностический JSON в stderr, без успешного префикса в stdout |

Максимумы настроек защищают от случайного безразмерного запуска. Они не заменяют admission control сервиса, который принимает множество партий одновременно.

Сводка содержит все результаты конечной партии, поэтому память результата имеет порядок `O(max_items)`. Рабочее окно ограничено отдельно. Для бесконечного источника нужен другой API: async iterator или ограниченный sink, с явным закрытием при прекращении чтения.

Iterable входов читается постепенно. Чтобы обнаружить превышение max_items, программа может запросить один дополнительный элемент. Синхронный `next` не должен выполнять долгий blocking I/O; ресурсным входным generator владеет передавший его caller.

**Как связаны два ограничения**

`max_in_flight` ограничивает число принятых элементов, результаты которых ещё не добавлены в упорядоченный отчёт. Внутри этого окна есть Tasks, ожидающие semaphore, выполняющиеся операции и готовые результаты в `ready`.

`concurrency` ограничивает работу внутри semaphore. Таким образом, одновременно можно удерживать шесть принятых элементов и исполнять не больше трёх обращений к зависимости.

Готовый последующий результат продолжает занимать слот окна, пока не готов более ранний. Это предотвращает бесконечный рост reorder buffer за одной медленной задачей.

Обратная сторона — возможный простой workers за медленным ранним элементом. Это осознанное сочетание ограниченной памяти и строгого порядка, а не ошибка, которую нужно исправлять бесконечным prefetch.

**Почему TaskGroup подходит для партии**

Ошибка worker отменяет siblings и прерывает ожидание coordinator. Выход TaskGroup дожидается finally участников. Только после успешного выхода формируется BatchReport.

Coordinator один изменяет pending, ready и output. Счётчики активных операций изменяются Tasks одного loop небольшими участками без suspension; межпоточного доступа в проекте нет.

Каждая операция задаёт item_index в ContextVar и сбрасывает token в finally. Это позволяет добавлять контекст в диагностику, не используя общий mutable request dict. У родительской Task значение не изменяется.

Некорректный вход, обнаруженный внутри TaskGroup, также входит в группу исключений. CLI рекурсивно извлекает листья для ограниченной диагностики. В библиотечном коде можно использовать except* для нужных классов ошибок.

Проект не выбирает детерминированную «первую» ошибку при нескольких одновременных отказах. Порядок успешных результатов детерминирован; порядок обнаружения отказов зависит от выполнения.

**Протокол TCP**

Один запрос и один ответ на соединение. Запрос — JSON `{"value": 3}` с завершающим LF, ответ — JSON `{"result": 9}` с LF.

Reader читает до разделителя и имеет предел буфера. Затем дополнительно проверяются размер полученного frame, UTF-8, JSON, schema, тип и диапазон результата. Клиент также проверяет, что число соответствует квадрату отправленного значения.

Ошибка framing, неполный ответ, неверный JSON и неверное значение считаются ошибкой протокола. Ответы не накапливаются до неограниченного EOF.

Демонстрационный сервер рассчитан на доверенный loopback. Для внешнего API потребуются TLS, аутентификация, серверный admission control и другие эксплуатационные условия; они не моделируются арифметическим demo.

**Retry и отмена**

Повтор разрешён для временных ошибок транспорта и timeout одной попытки. Число попыток ограничено, задержка растёт экспоненциально с full jitter и ограничена max_delay.

В этой модели вся логическая операция, включая backoff, занимает один concurrency slot. Это консервативно ограничивает количество одновременно живых retry sequences. Другой дизайн может освобождать слот на backoff, но тогда отдельно ограничивает число ожидающих повторов.

Сама операция read-only и идемпотентна. Для переноса такого retry на запись сначала определите idempotency key или другой способ не повторять side effect.

CancelledError не ловится обработчиком временных ошибок. При отмене соединение закрывается в finally, а TaskGroup завершает принадлежащие партии Tasks.

Close сначала инициирует закрытие writer, затем ограниченно ожидает wait_closed. При дополнительной отмене или отказе закрытия transport прерывается. Это не подтверждение удалённой транзакции; здесь сервер выполняет только вычисление.

**Дедлайны**

Timeout попытки охватывает установление соединения, отправку, чтение и связанную очистку. Общий timeout партии расположен снаружи TaskGroup и охватывает ожидание слотов, попытки и backoff.

Это кооперативные ограничения. Если переданный work блокирует loop синхронным вызовом, timer не сможет вовремя исполниться. Если ресурс требует cleanup после отмены, возврат может произойти позже nominal deadline.

Библиотека допускает `timeout=None`, если временем жизни владеет внешний scope. CLI задаёт конечный timeout по умолчанию.

```python
# project: src/bounded_async/core.py
from __future__ import annotations

import asyncio
import math
from collections.abc import Awaitable, Callable, Iterable
from contextvars import ContextVar
from dataclasses import dataclass

item_index: ContextVar[int] = ContextVar("item_index", default=-1)
Work = Callable[[int], Awaitable[int]]


class InputError(ValueError):
    pass


class ProtocolError(ValueError):
    pass


class ItemFailure(Exception):
    def __init__(self, index: int, code: str) -> None:
        super().__init__(index, code)
        self.index = index
        self.code = code


def positive_int(name: str, value: object, maximum: int) -> None:
    if type(value) is not int or not 1 <= value <= maximum:
        raise ValueError(f"{name} must be an integer in 1..{maximum}")


def positive_seconds(name: str, value: object) -> None:
    if (
        isinstance(value, bool)
        or not isinstance(value, (int, float))
        or not math.isfinite(value)
        or value <= 0
    ):
        raise ValueError(f"{name} must be finite and positive")


@dataclass(frozen=True)
class Options:
    concurrency: int = 3
    max_in_flight: int = 6
    max_items: int = 1000
    timeout: float | None = 10.0

    def __post_init__(self) -> None:
        positive_int("concurrency", self.concurrency, 64)
        positive_int("max_in_flight", self.max_in_flight, 128)
        positive_int("max_items", self.max_items, 10_000)
        if self.max_in_flight < self.concurrency:
            raise ValueError("max_in_flight must be at least concurrency")
        if self.timeout is not None:
            positive_seconds("timeout", self.timeout)


@dataclass(frozen=True)
class BatchReport:
    values: tuple[int, ...]
    peak_active: int
    peak_in_flight: int

    def as_dict(self) -> dict:
        return {
            "values": list(self.values),
            "count": len(self.values),
            "total": sum(self.values),
            "peak_active": self.peak_active,
            "peak_in_flight": self.peak_in_flight,
        }


@dataclass
class _Stats:
    active: int = 0
    peak_active: int = 0
    peak_in_flight: int = 0


async def _invoke(
    index: int, value: int, work: Work, semaphore: asyncio.Semaphore, stats: _Stats
) -> int:
    async with semaphore:
        stats.active += 1
        stats.peak_active = max(stats.peak_active, stats.active)
        token = item_index.set(index)
        try:
            result = await work(value)
            if type(result) is not int or not 0 <= result <= 1_000_000_000_000:
                raise ProtocolError("invalid_result")
            return result
        except ProtocolError as error:
            raise ItemFailure(index, "protocol_error") from error
        except TimeoutError as error:
            raise ItemFailure(index, "operation_timeout") from error
        except OSError as error:
            raise ItemFailure(index, "transport_error") from error
        finally:
            item_index.reset(token)
            stats.active -= 1


async def run_batch(
    values: Iterable[int], work: Work, *, options: Options = Options()
) -> BatchReport:
    """Return a complete ordered batch; child failures propagate as groups."""
    semaphore = asyncio.BoundedSemaphore(options.concurrency)
    stats = _Stats()
    pending: dict[asyncio.Task[int], int] = {}
    ready: dict[int, int] = {}
    output: list[int] = []
    submitted = next_emit = 0
    exhausted = False
    async with asyncio.timeout(options.timeout):
        async with asyncio.TaskGroup() as group:
            source = iter(values)
            while True:
                while (
                    not exhausted and len(pending) + len(ready) < options.max_in_flight
                ):
                    try:
                        value = next(source)
                    except StopIteration:
                        exhausted = True
                        break
                    if submitted >= options.max_items:
                        raise InputError("too_many_items")
                    if type(value) is not int or not 0 <= value <= 1_000_000:
                        raise InputError("invalid_input")
                    task = group.create_task(
                        _invoke(submitted, value, work, semaphore, stats),
                        name=f"bounded-async:item:{submitted}",
                    )
                    pending[task] = submitted
                    submitted += 1
                    stats.peak_in_flight = max(
                        stats.peak_in_flight, len(pending) + len(ready)
                    )
                while next_emit in ready:
                    output.append(ready.pop(next_emit))
                    next_emit += 1
                if not pending:
                    if exhausted:
                        break
                    continue
                done, _ = await asyncio.wait(
                    pending, return_when=asyncio.FIRST_COMPLETED
                )
                for task in done:
                    index = pending.pop(task)
                    ready[index] = task.result()
    return BatchReport(tuple(output), stats.peak_active, stats.peak_in_flight)
```

```python
# project: src/bounded_async/network.py
from __future__ import annotations

import asyncio
import json
import random
from collections.abc import Awaitable, Callable
from dataclasses import dataclass

from .core import ProtocolError, positive_int, positive_seconds


@dataclass(frozen=True)
class Endpoint:
    host: str = "127.0.0.1"
    port: int = 1
    attempt_timeout: float = 2.0
    max_response_bytes: int = 256
    close_timeout: float = 1.0

    def __post_init__(self) -> None:
        if not isinstance(self.host, str) or not self.host:
            raise ValueError("host must be nonempty")
        positive_int("port", self.port, 65535)
        positive_int("max_response_bytes", self.max_response_bytes, 65_536)
        positive_seconds("attempt_timeout", self.attempt_timeout)
        positive_seconds("close_timeout", self.close_timeout)


@dataclass(frozen=True)
class RetryPolicy:
    attempts: int = 2
    base_delay: float = 0.01
    max_delay: float = 0.1

    def __post_init__(self) -> None:
        positive_int("attempts", self.attempts, 5)
        positive_seconds("base_delay", self.base_delay)
        positive_seconds("max_delay", self.max_delay)
        if self.base_delay > self.max_delay:
            raise ValueError("base_delay must not exceed max_delay")


def parse_response(payload: bytes, maximum: int) -> int:
    if len(payload) > maximum or not payload.endswith(b"\n"):
        raise ProtocolError("invalid_frame")
    try:
        data = json.loads(payload.decode("utf-8"))
    except (ValueError, RecursionError) as error:
        raise ProtocolError("invalid_json") from error
    if not isinstance(data, dict) or set(data) != {"result"}:
        raise ProtocolError("invalid_schema")
    value = data["result"]
    if type(value) is not int or not 0 <= value <= 1_000_000_000_000:
        raise ProtocolError("invalid_result")
    return value


async def close_writer(writer: asyncio.StreamWriter, timeout: float) -> None:
    writer.close()
    try:
        async with asyncio.timeout(timeout):
            await writer.wait_closed()
    except asyncio.CancelledError:
        writer.transport.abort()
        raise
    except (OSError, TimeoutError):
        writer.transport.abort()


async def exchange(value: int, endpoint: Endpoint) -> int:
    reader, writer = await asyncio.open_connection(
        endpoint.host, endpoint.port, limit=endpoint.max_response_bytes
    )
    try:
        writer.write(json.dumps({"value": value}).encode("ascii") + b"\n")
        await writer.drain()
        try:
            response = await reader.readuntil(b"\n")
        except (asyncio.LimitOverrunError, asyncio.IncompleteReadError) as error:
            raise ProtocolError("invalid_frame") from error
        result = parse_response(response, endpoint.max_response_bytes)
        if result != value * value:
            raise ProtocolError("wrong_result")
        return result
    finally:
        await close_writer(writer, endpoint.close_timeout)


async def fetch_square(
    value: int,
    *,
    endpoint: Endpoint,
    policy: RetryPolicy = RetryPolicy(),
    perform: Callable[[int, Endpoint], Awaitable[int]] = exchange,
    sleep: Callable[[float], Awaitable[None]] = asyncio.sleep,
    jitter: Callable[[], float] = random.random,
) -> int:
    for attempt in range(policy.attempts):
        try:
            async with asyncio.timeout(endpoint.attempt_timeout):
                return await perform(value, endpoint)
        except (OSError, TimeoutError):
            if attempt + 1 == policy.attempts:
                raise
            cap = min(policy.base_delay * 2**attempt, policy.max_delay)
            await sleep(cap * jitter())
    raise RuntimeError("unreachable retry state")
```

```python
from __future__ import annotations

import asyncio
import json
from contextlib import asynccontextmanager

from .network import Endpoint, close_writer


@asynccontextmanager
async def demo_server():
    """A trusted loopback teaching server, owned by this context."""
    active: set[asyncio.Task] = set()
    async with asyncio.TaskGroup() as group:

        async def handle(reader, writer) -> None:
            try:
                async with asyncio.timeout(3):
                    payload = await reader.readuntil(b"\n")
                    data = json.loads(payload)
                    if not isinstance(data, dict) or set(data) != {"value"}:
                        return
                    value = data["value"]
                    if type(value) is not int or not 0 <= value <= 1_000_000:
                        return
                    writer.write(
                        json.dumps({"result": value * value}).encode("ascii") + b"\n"
                    )
                    await writer.drain()
            except (
                OSError,
                ValueError,
                TimeoutError,
                asyncio.IncompleteReadError,
                asyncio.LimitOverrunError,
            ):
                pass
            finally:
                await close_writer(writer, 1)

        def accepted(reader, writer) -> None:
            task = group.create_task(
                handle(reader, writer), name="bounded-async:demo-handler"
            )
            active.add(task)
            task.add_done_callback(active.discard)

        server = await asyncio.start_server(accepted, "127.0.0.1", 0, limit=128)
        try:
            yield Endpoint(port=server.sockets[0].getsockname()[1])
        finally:
            server.close()
            await server.wait_closed()
            for task in tuple(active):
                task.cancel()
```

```python
import argparse
import asyncio
import json
import sys
from functools import partial

from .core import ItemFailure, Options, run_batch
from .demo import demo_server
from .network import Endpoint, RetryPolicy, fetch_square


def leaves(error):
    if isinstance(error, BaseExceptionGroup):
        for child in error.exceptions:
            yield from leaves(child)
    else:
        yield error


async def execute(args, options, policy):
    if args.demo:
        async with demo_server() as endpoint:
            return await run_batch(
                args.values,
                partial(fetch_square, endpoint=endpoint, policy=policy),
                options=options,
            )
    endpoint = Endpoint(host=args.host, port=args.port)
    return await run_batch(
        args.values,
        partial(fetch_square, endpoint=endpoint, policy=policy),
        options=options,
    )


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(
        description="Bounded asynchronous batch of TCP square requests"
    )
    parser.add_argument("values", type=int, nargs="+")
    parser.add_argument("--demo", action="store_true")
    parser.add_argument("--host", default="127.0.0.1")
    parser.add_argument("--port", type=int, default=1)
    parser.add_argument("--concurrency", type=int, default=3)
    parser.add_argument("--max-in-flight", type=int, default=6)
    parser.add_argument("--timeout", type=float, default=10.0)
    parser.add_argument("--attempts", type=int, default=2)
    args = parser.parse_args(argv)
    try:
        options = Options(
            concurrency=args.concurrency,
            max_in_flight=args.max_in_flight,
            timeout=args.timeout,
        )
        policy = RetryPolicy(attempts=args.attempts)
        Endpoint(host=args.host, port=args.port)
    except ValueError as error:
        print(
            json.dumps({"error": "invalid_options", "detail": str(error)}),
            file=sys.stderr,
        )
        return 2
    try:
        report = asyncio.run(execute(args, options, policy))
    except TimeoutError:
        print(json.dumps({"error": "batch_timeout"}), file=sys.stderr)
        return 124
    except (asyncio.CancelledError, KeyboardInterrupt):
        print(json.dumps({"error": "cancelled"}), file=sys.stderr)
        return 130
    except ExceptionGroup as group:
        errors = [
            {"error": error.code, "index": error.index}
            if isinstance(error, ItemFailure)
            else {"error": type(error).__name__}
            for error in leaves(group)
        ]
        print(json.dumps({"error": "batch_failed", "causes": errors}), file=sys.stderr)
        return 1
    except (OSError, ValueError) as error:
        print(json.dumps({"error": type(error).__name__}), file=sys.stderr)
        return 1
    print(json.dumps(report.as_dict(), sort_keys=True))
    return 0
```

**Почему тесты проверяют поведение**

В тесте окна первый элемент удерживается Event, а два следующих завершаются. Тест ждёт, когда coordinator действительно перенёс результаты в буфер. До освобождения первого элемента источник не должен выдать четвёртый.

Это сильнее проверки только semaphore: число активных операций может быть ограничено даже в программе, которая создала весь вход и удерживает его в памяти.

Отдельный тест заставляет вторую задачу упасть, пока первая ждёт. После выхода TaskGroup первая обязана выполнить finally; принадлежащих партии Task не остаётся.

Тест внешней отмены дожидается начала операции и проверяет CancelledError у caller. Тест дедлайна удерживает незавершаемую операцию и проверяет timeout без утверждения о точном elapsed time.

Network-тесты открывают реальные loopback TCP-соединения. Они проверяют правильный ответ, неверное значение, слишком длинный frame, неполный frame и EOF на стороне сервера после отмены клиента.

Retry-тесты используют управляемые perform/sleep/jitter: можно точно проверить число попыток и задержки без реального ожидания. Ошибка протокола и CancelledError не должны вызывать повтор.

CLI-тесты запускают установленный wheel из постороннего каталога с `-I` и `-O`. Если runtime-валидация ошибочно спрятана в assert или импорт зависит от src в текущем каталоге, такой запуск это обнаружит.

Property-based-тест задаёт до 35 генерируемых наборов за запуск: значения, число активных операций и размер окна. Итог сравнивается с простым последовательным вычислением квадратов.

**Возможные расширения**

1. Добавьте streaming API выдачи по готовности с явным aclose и тестом досрочного прекращения чтения.
2. Реализуйте async-вход вместо синхронного iterable и ограничьте prefetch producer.
3. Добавьте bounded output sink. Медленная запись не должна приводить к накоплению неограниченных готовых результатов.
4. Добавьте HTTP-адаптер на ClientSession/AsyncClient с переиспользованием соединений, bytes limit и раздельными timeout стадий.
5. Добавьте per-host rate limiter, отдельный от concurrency limit, и тест расписания с управляемым clock.
6. Реализуйте bulkheads нескольких зависимостей и проверьте отсутствие циклического захвата лимитов.
7. Введите общий retry budget партии, чтобы каждый отдельный job не мог независимо израсходовать слишком много попыток.
8. Сделайте supervisor долгоживущих workers с startup acknowledgement, stop и политикой восстановления.
9. Добавьте AsyncExitStack для нескольких зависимостей и тест отказа в середине инициализации.
10. Сохраните отчёт в БД, определив transaction boundary, уникальный batch ID и поведение при отмене после commit.
11. Добавьте trace ID через ContextVar и logging queue, не выполняющую blocking I/O в loop.
12. Проверьте одновременные external cancel и child failure на поддерживаемых patch-версиях Python.
13. Добавьте реальный subprocess-adapter с ограничением stdout/stderr и явной судьбой дочерней process group.
14. Для blocking SDK реализуйте worker, реальное завершение которого подтверждается отдельно от отмены asyncio await.
15. Сравните тот же алгоритм на обычном и free-threaded runtime, сохранив одинаковые ограничения и проверив фактическое состояние GIL.
