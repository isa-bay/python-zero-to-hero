# 24. Нативные расширения, FFI и встраивание Python

Python часто работает вместе с кодом на C, C++, Rust и других языках. Так устроены многие библиотеки для вычислений, обработки изображений, работы с базами данных, криптографии и взаимодействия с операционной системой.

Такая интеграция позволяет использовать готовые библиотеки, ускорять отдельные операции и добавлять Python в существующие приложения. Одновременно она переносит в Python-приложение новые классы ошибок: повреждение памяти, несовместимость двоичного интерфейса, взаимные блокировки и аварийное завершение всего процесса.

Эта глава посвящена тому, как проектировать и проверять такую границу.

После изучения главы вы сможете:

- выбрать между отдельным процессом, FFI, extension module и embedding;
- описать сигнатуру C-функции для `ctypes` и CFFI;
- определить владельца памяти и момент освобождения ресурса;
- использовать основные правила Python/C API;
- объяснить различия между GIL, состоянием потока и потокобезопасностью;
- организовать состояние расширения без глобальных Python-объектов;
- разобраться в Limited API, Stable ABI и платформенных wheels;
- встроить интерпретатор в C-приложение.

Основные примеры рассчитаны на **CPython 3.12+**. Возможности, появившиеся позднее, отмечены отдельно. Это существенно: правила интеграции зависят не только от версии языка, но и от реализации Python, режима сборки и платформы.

В частности:

- обычный CPython и free-threaded CPython требуют отдельных проверок;
- поддержка subinterpreters и поддержка работы без GIL — разные свойства;
- в Python 3.15 появились новые API присоединения внешних потоков и Stable ABI для free-threaded сборок;
- объявления совместимости сами по себе не делают расширение безопасным.

Примеры в этой главе подготовлены по документации, но не прошли компиляцию и запуск в среде подготовки текста. Команды сборки и тесты приведены для воспроизведения.

## 24.1. Выбор способа интеграции

### 24.1.1. Отдельный процесс vs FFI vs extension module vs embedding

Сначала нужно решить, где проходит граница между Python и другим языком.

Есть четыре основных варианта.

| Подход | Кто запускает программу | Как передаются данные | Где выполняется нативный код |
|---|---|---|---|
| Отдельный процесс | Python или внешний оркестратор | stdin/stdout, файлы, сокеты, IPC | В другом адресном пространстве |
| FFI | Обычно Python | Через интерфейс внешней библиотеки | В процессе Python |
| Extension module | Python | Через Python-объекты и Python/C API | В процессе Python |
| Embedding | Приложение-хост | Через API интерпретатора и API хоста | Python работает внутри хоста |

#### Отдельный процесс

Python запускает самостоятельную программу и обменивается с ней данными.

```python
import json
import subprocess

completed = subprocess.run(
    ["native-worker", "--format=json"],
    input=json.dumps({"values": [10, 20, 30]}),
    text=True,
    capture_output=True,
    timeout=10,
    check=True,
)

result = json.loads(completed.stdout)
```

У такого решения есть собственный протокол:

- формат входа и выхода;
- версия сообщения;
- правила сообщения об ошибках;
- ограничения размера;
- тайм-аут;
- поведение при частичном выводе;
- код завершения процесса.

Главное архитектурное преимущество — изоляция адресного пространства. Если worker испортит собственную память, это не означает автоматического повреждения памяти родительского Python-процесса.

Но изоляция не устраняет необходимость ограничивать ресурсы, проверять сообщения и завершать зависшие процессы.

Этот вариант особенно полезен, если:

- библиотека нестабильна;
- обработка одного запроса достаточно тяжёлая;
- требуется независимый жизненный цикл;
- нужно ограничить последствия нативного падения;
- компонент должен использоваться из нескольких языков.

Стоимость включает запуск процесса или поддержку постоянного worker, сериализацию, передачу и разбор данных.

Для большого числа мелких запросов обычно лучше постоянный процесс с протоколом, чем новый процесс на каждую операцию.

#### FFI

FFI — Foreign Function Interface, механизм вызова функций другого языка.

В Python распространены `ctypes` и CFFI.

```python
import ctypes

library = ctypes.CDLL("/absolute/path/to/library.so")
```

Дальше Python вызывает экспортированные функции библиотеки.

Удобнее всего работать со стабильным C-интерфейсом:

```c
int calculate(
    const double *values,
    size_t count,
    double *result
);
```

FFI хорошо подходит, когда:

- библиотека уже существует;
- у неё есть документированный C API;
- интерфейс состоит из относительно простых функций;
- не требуется создавать сложную систему Python-типов.

При этом Python и библиотека находятся в одном процессе. Неверная сигнатура или обращение по недействительному указателю могут завершить весь процесс.

#### Extension module

Расширение импортируется как обычный модуль:

```python
import batchnative

result = batchnative.sum_bytes(b"hello")
```

Но его реализация скомпилирована в нативный код.

Расширение может:

- создавать Python-объекты;
- определять собственные классы;
- реализовывать протоколы Python;
- принимать буферы без промежуточного преобразования в список;
- вызывать Python-функции;
- управлять состоянием модуля.

Инструментами реализации могут быть:

- непосредственно Python/C API;
- Cython;
- pybind11;
- Rust и PyO3.

Такой подход даёт больше контроля над Python-интерфейсом. Взамен он требует аккуратной работы с моделью объектов, сборкой и совместимостью.

#### Embedding

При встраивании приложение на C, C++ или Rust запускает интерпретатор Python внутри себя.

Например, приложение может предоставлять пользователю Python для:

- сценариев автоматизации;
- описания правил;
- обработки событий;
- настройки поведения;
- анализа данных;
- расширения продукта плагинами.

Здесь именно хост определяет:

- когда создаётся интерпретатор;
- откуда импортируются модули;
- какие функции доступны сценариям;
- как передаются данные;
- когда прекращаются вызовы;
- как завершается интерпретатор.

Embedding не является способом получить песочницу для недоверенного Python-кода. Код внутри процесса может иметь доступ к возможностям этого процесса.

#### Как выбирать

| Ситуация | Разумная отправная точка |
|---|---|
| Нужно вызвать готовую C-библиотеку с небольшим API | `ctypes` или CFFI |
| Нужен компилируемый слой, проверяемый по заголовкам | CFFI API mode |
| Требуется удобная обёртка над большой C++-библиотекой | pybind11 |
| Нужно ускорить типизированный вычислительный цикл | Cython или расширение |
| Основная реализация пишется на Rust | PyO3 |
| Нативный компонент может падать и должен восстанавливаться отдельно | Отдельный процесс |
| Существующее приложение должно исполнять Python-сценарии | Embedding |
| Нужен тонкий контроль над Python-объектами и протоколами | Python/C API |

Выбор следует делать по контрактам и требованиям, а затем подтверждать измерениями.

### 24.1.2. Стоимость границы Python/C, копирования и преобразования данных

Сам факт выполнения функции на C не гарантирует ускорения.

Время операции удобно разложить на составляющие:

```text
общее время =
    подготовка аргументов
    + пересечение границы
    + копирование входных данных
    + нативная работа
    + копирование результата
    + создание Python-результата
```

Например, C-функция может складывать числа очень быстро. Но если для каждого числа Python отдельно:

1. вызывает функцию;
2. проверяет аргумент;
3. преобразует `int`;
4. получает C-результат;
5. создаёт новый Python `int`;

то стоимость границы может оказаться больше стоимости сложения.

#### Передавайте пакет данных

Менее удачный интерфейс:

```python
result = [native_transform(value) for value in values]
```

Более подходящий для тяжёлой обработки интерфейс:

```python
result = native_transform_many(values)
```

Во втором случае один переход обслуживает множество элементов.

Это особенно полезно для:

- обработки изображений;
- аудиосигнала;
- численных массивов;
- компрессии;
- хеширования;
- разбора больших блоков данных.

Однако пакетирование влияет на задержку одного запроса и потребление памяти. Размер пакета тоже нужно измерять.

#### Python-список и C-массив — разные представления

В Python:

```python
values = [1.0, 2.0, 3.0]
```

Это список ссылок на Python-объекты.

Функция:

```c
double sum_values(const double *values, size_t count);
```

ожидает последовательность значений `double` в определённом представлении памяти.

Между этими структурами нельзя поставить знак равенства. Обычно требуется преобразование.

Если данные уже находятся в подходящем массиве, например в объекте с buffer protocol, преобразование иногда удаётся избежать.

Но нужно проверить:

- тип элемента;
- размер элемента;
- порядок байтов;
- выравнивание;
- число измерений;
- strides;
- непрерывность;
- доступность записи;
- время жизни;
- возможность конкурентного изменения.

#### Zero-copy требует контракта

Zero-copy означает отсутствие определённого копирования на конкретном участке обработки.

Это не означает, что:

- данные нигде не копируются;
- функция принимает любой буфер;
- исходный объект можно сразу уничтожить;
- память нельзя переместить;
- другой поток не изменит содержимое;
- операция автоматически безопасна.

Например, получение представления без копирования может удерживать большой исходный объект ради небольшого фрагмента. Иногда отдельная копия уменьшает общее время удержания памяти и упрощает параллельную обработку.

#### Ограничение общего ускорения

Предположим, 90% времени программы занимает вычисление, которое удалось ускорить в 10 раз.

Оставшиеся 10% не изменились.

Тогда теоретическое ускорение всей программы:

```text
1 / (0.10 + 0.90 / 10) ≈ 5.26
```

Это полезный способ проверить ожидания до разработки расширения.

#### Что измерять

Сравнивайте одинаковую полезную работу:

- одинаковые входы;
- одинаковую точность;
- одинаковую семантику ошибок;
- одинаковый итоговый тип результата.

Отдельно измеряйте:

- подготовку данных;
- вызов на уже подготовленных данных;
- полную операцию от Python-входа до Python-результата;
- маленькие, средние и большие входы;
- один поток и несколько потоков;
- холодный запуск и повторные вызовы.

Ускорение внутреннего C-цикла может не ускорить пользовательский сценарий. Поэтому нужен и локальный benchmark, и измерение полной операции.

### 24.1.3. Владение памятью, временем жизни и ресурсами

Главный вопрос нативной интеграции:

> Кто обязан освободить ресурс и до какого момента разрешено им пользоваться?

Указатель сам по себе не содержит ответа.

```c
unsigned char *data;
```

Из этого объявления неизвестно:

- кто выделил память;
- какова её длина;
- можно ли её изменять;
- кто должен освободить память;
- какой функцией её освобождать;
- может ли адрес измениться;
- можно ли использовать его из другого потока;
- сохраняет ли библиотека переданный указатель после возврата.

#### Три независимых условия

Для безопасного доступа к указателю обычно нужны все три условия:

1. Владелец памяти продолжает существовать.
2. Адрес остаётся действительным.
3. Содержимое используется с разрешённой синхронизацией.

Удержание владельца не гарантирует стабильность адреса.

Например, C++-контейнер может оставаться живым, но после увеличения `std::vector` его внутренний массив может переехать.

Стабильный адрес не гарантирует отсутствие гонки.

Например, два потока могут одновременно обращаться к одной области памяти без согласования.

#### Заимствование и передача владения

Заимствование:

```c
int inspect(const unsigned char *data, size_t size);
```

Возможный контракт:

- функция читает данные;
- не сохраняет указатель;
- завершает чтение до возврата;
- не освобождает память.

Передача владения:

```c
int make_buffer(unsigned char **data, size_t *size);
void release_buffer(unsigned char *data);
```

Возможный контракт:

- при успехе библиотека возвращает новый ресурс;
- вызывающая сторона обязана вызвать `release_buffer`;
- использовать обычный `free` нельзя;
- после освобождения указатель недействителен.

Это нужно явно написать в документации. Сигнатура недостаточна.

#### Освобождайте тем же семейством API

| Выделение | Освобождение |
|---|---|
| `malloc` | `free` |
| `new T` | `delete` |
| `new T[n]` | `delete[]` |
| `PyMem_Malloc` | `PyMem_Free` |
| `PyObject_Malloc` | `PyObject_Free` |
| Функция конкретной библиотеки | Соответствующая функция этой библиотеки |

На Windows дополнительно важно не смешивать несовместимые runtime и границы DLL.

Практически удобный контракт внешней библиотеки: память всегда освобождается экспортированной функцией той же библиотеки, которая её выделила.

#### Непрозрачные дескрипторы

Для долгоживущих ресурсов удобны opaque handles:

```c
typedef struct engine engine;

engine *engine_create(void);
int engine_process(engine *instance, const void *data, size_t size);
void engine_destroy(engine *instance);
```

Python не должен знать внутреннее устройство `engine`.

Но документация должна определить:

- допустим ли `NULL`;
- можно ли вызвать `destroy` несколько раз;
- допускаются ли параллельные операции;
- может ли операция продолжаться после возврата;
- что происходит при закрытии с активными задачами.

Python-обёртку удобно сделать контекстным менеджером:

```python
with Engine() as engine:
    result = engine.process(data)
```

Финализатор можно использовать как дополнительную защиту, но освобождение дорогих или ограниченных ресурсов лучше делать явно.

#### Асинхронная операция меняет контракт

Если C-функция сохраняет указатель и возвращается до завершения работы, обычного локального Python-объекта может быть недостаточно.

Потребуется объект операции, который удерживает:

- входные данные;
- callback;
- пользовательский контекст;
- библиотеку или её дескриптор;
- механизм отмены;
- состояние завершения.

Уничтожение такого объекта должно учитывать незавершённую нативную работу.

«Отменить» и «все обращения к памяти закончились» — разные события.

Источник: [Memory management в Python/C API](https://docs.python.org/3.15/c-api/memory.html).

## 24.2. ctypes и CFFI

### 24.2.1. Сигнатуры, типы, структуры, указатели и соглашения вызова

`ctypes` позволяет описать функции динамической библиотеки непосредственно в Python.

Рассмотрим C API:

```c
int add_values(int left, int right);
```

Python:

```python
import ctypes
from pathlib import Path

library_path = Path("./libexample.so").resolve(strict=True)
library = ctypes.CDLL(str(library_path))

library.add_values.argtypes = [ctypes.c_int, ctypes.c_int]
library.add_values.restype = ctypes.c_int

print(library.add_values(10, 20))
```

#### Объявляйте `argtypes` и `restype`

По умолчанию `ctypes` предполагает для результата C-тип `int`.

Это опасно, если функция возвращает указатель:

```c
void *create_resource(void);
```

Правильное описание:

```python
library.create_resource.argtypes = []
library.create_resource.restype = ctypes.c_void_p
```

Если оставить результат как `int`, адрес на 64-битной платформе может быть усечён.

Неверное объявление сигнатуры не превращается в безопасную Python-ошибку во всех случаях. Оно может привести к повреждению памяти или падению процесса.

#### Соответствие типов

| C | Обычно в `ctypes` | Что проверить |
|---|---|---|
| `int` | `c_int` | Диапазон и знаковость |
| `unsigned int` | `c_uint` | Поведение при отрицательных значениях |
| `long` | `c_long` | Размер зависит от платформы |
| `size_t` | `c_size_t` | Беззнаковый размер |
| `double` | `c_double` | Ожидаемое представление |
| `void *` | `c_void_p` | Контракт указателя |
| `unsigned char *` | `POINTER(c_ubyte)` | Длина и доступ |
| `T *` | `POINTER(T)` | Время жизни и владение |
| `struct T` | `Structure` | Layout, alignment, padding |

Нельзя считать `long` универсальным 64-битным целым.

На 64-битной Windows `long` обычно имеет размер 32 бита, хотя указатель имеет размер 64 бита.

Отдельно различайте:

- `size_t`;
- `Py_ssize_t`;
- фиксированные типы вроде `uint32_t`;
- платформенные типы библиотек.

В Python число произвольной точности. Преобразование в C-число требует проверки диапазона на уровне вашего интерфейса.

#### Структуры

C:

```c
struct buffer {
    unsigned char *data;
    size_t size;
};
```

Python:

```python
import ctypes


class Buffer(ctypes.Structure):
    _fields_ = [
        ("data", ctypes.POINTER(ctypes.c_ubyte)),
        ("size", ctypes.c_size_t),
    ]
```

Порядок полей должен совпадать с C-заголовком.

Но одного порядка недостаточно. Нужно учитывать:

- padding;
- alignment;
- параметры упаковки;
- особенности компилятора;
- правила битовых полей.

Не добавляйте `_pack_ = 1` для исправления случайно обнаруженного несовпадения. Упаковка должна следовать реальному ABI библиотеки.

Полезно экспортировать диагностические функции:

```c
size_t buffer_sizeof(void);
size_t buffer_size_offset(void);
```

И сверять их с:

```python
ctypes.sizeof(Buffer)
Buffer.size.offset
```

Это обнаруживает часть несовпадений layout, но не доказывает корректность всего интерфейса.

#### Указатель и объект по адресу

```python
value = ctypes.c_int(42)

first = ctypes.pointer(value)
second = ctypes.byref(value)
```

`pointer()` создаёт ctypes-объект указателя.

`byref()` удобен для передачи адреса в вызов и обычно не нужен как самостоятельный долгоживущий указатель.

Оба варианта требуют понимания времени жизни исходного объекта.

Приведение через `cast()` меняет интерпретацию адреса. Оно не проверяет:

- действительно ли по адресу находится объект нужного типа;
- достаточно ли там памяти;
- выровнена ли память;
- не была ли она освобождена.

#### Соглашения вызова

Важны не только типы, но и calling convention.

В `ctypes`:

- `CDLL` используется для обычного C-интерфейса;
- `WinDLL` соответствует Windows API со `stdcall`, где это применимо;
- `PyDLL` предназначен для вызовов Python C API и имеет другое поведение относительно GIL и проверки ошибок.

Для callbacks также нужно выбирать соответствующий фабричный тип: например, `CFUNCTYPE` или `WINFUNCTYPE`.

Ошибка в calling convention особенно опасна на платформах и архитектурах, где она меняет правила передачи аргументов и очистки стека.

#### CFFI: ABI mode и API mode

CFFI предлагает два важных режима.

| Режим | Как работает | Основное свойство |
|---|---|---|
| ABI mode | `ffi.cdef()` + `ffi.dlopen()` | Библиотека загружается без компиляции обёртки |
| API mode | `ffi.cdef()` + `ffi.set_source()` | C-компилятор участвует в проверке интерфейса |

ABI mode:

```python
from cffi import FFI

ffi = FFI()
ffi.cdef("""
    int add_values(int left, int right);
""")

library = ffi.dlopen("/absolute/path/to/libexample.so")
print(library.add_values(10, 20))
```

API mode полезен, когда нужно компилироваться по настоящим заголовкам, учитывать платформенные определения и использовать более сложные конструкции C.

`cdef()` не является полноценным препроцессором C. Не следует ожидать, что туда можно без изменений вставить любой промышленный заголовок.

Источники:

- [ctypes](https://docs.python.org/3.15/library/ctypes.html).
- [CFFI overview](https://cffi.readthedocs.io/en/latest/overview.html).
- [CFFI reference](https://cffi.readthedocs.io/en/latest/ref.html).

### 24.2.2. Буферы, строки, callbacks и время жизни объектов

#### Строка Python и строка C

Python `str` — текст Unicode.

C `char *` — указатель на байты. Кодировка из такого типа не следует.

Для текстового API нужно явно договориться:

- о кодировке;
- о наличии завершающего нулевого байта;
- о допустимости встроенного `NUL`;
- о способе определения длины;
- о владельце результата.

Например:

```python
text = "Привет"
encoded = text.encode("utf-8")
```

Количество символов и количество байтов могут различаться:

```python
len(text)
len(encoded)
```

Для бинарных данных интерфейс `pointer + length` обычно точнее, чем строка с завершением по `NUL`.

#### Почему `c_char_p` не подходит для любого результата

Допустим, библиотека возвращает новую строку:

```c
char *make_message(void);
void release_message(char *message);
```

Если задать `restype = c_char_p`, `ctypes` может преобразовать результат в Python `bytes`.

Тогда исходный адрес, который нужно передать в `release_message`, не будет представлен как принадлежащий вам сырой указатель.

Для результата с отдельным освобождением лучше сохранить адрес:

```python
library.make_message.argtypes = []
library.make_message.restype = ctypes.c_void_p

library.release_message.argtypes = [ctypes.c_void_p]
library.release_message.restype = None

address = library.make_message()

if not address:
    raise MemoryError("make_message failed")

try:
    message = ctypes.string_at(address)
finally:
    library.release_message(address)
```

Для бинарных данных у `string_at` должна быть явная длина:

```python
payload = ctypes.string_at(address, size)
```

Без длины чтение продолжается до первого нулевого байта. Это другой контракт.

#### Копия и представление

Копия создаёт независимые данные.

Представление продолжает обращаться к исходной памяти.

Для представления нужно удерживать владельца до конца использования. Если память освобождена, представление становится опасным независимо от того, существует ли Python-объект представления.

В CFFI:

- `ffi.buffer(pointer, size)` создаёт интерфейс к существующей памяти;
- `bytes(ffi.buffer(pointer, size))` создаёт Python-копию;
- `ffi.from_buffer(...)` позволяет обратиться к буферу Python без отдельного копирования.

Пример:

```python
from cffi import FFI

ffi = FFI()

data = bytearray(b"abc")

with ffi.from_buffer("unsigned char[]", data) as pointer:
    pointer[0] = ord("A")

assert data == bytearray(b"Abc")
```

Пока используется указатель, необходимо сохранять исходный cdata, полученный от `from_buffer`.

Промежуточный `cast()` не следует считать универсальным механизмом удержания владельца.

CFFI также не превращает `const` в полноценную защиту от записи. Объявление C-типа не даёт права изменять Python `bytes`.

#### Callback — обратное пересечение границы

C может вызвать функцию Python через callback.

C:

```c
typedef int (*progress_callback)(size_t completed, void *context);
```

`ctypes`:

```python
import ctypes

ProgressCallback = ctypes.CFUNCTYPE(
    ctypes.c_int,
    ctypes.c_size_t,
    ctypes.c_void_p,
)
```

Созданный callback должен оставаться живым всё время, когда C может его вызвать.

Небезопасный жизненный цикл:

1. Python создаёт callback.
2. C сохраняет адрес callback.
3. Python теряет последнюю ссылку.
4. C вызывает уже недействительный адрес.

Для асинхронного API обычно нужно хранить callback в объекте регистрации.

Правильное завершение регистрации должно означать:

1. новые вызовы запрещены;
2. все уже начавшиеся вызовы закончились;
3. C больше не хранит используемый адрес;
4. Python может освободить callback и контекст.

Простой вызов `unregister()` не всегда гарантирует все эти условия. Нужно читать контракт библиотеки.

#### Исключение не должно пересекать C ABI

Нельзя рассчитывать, что исключение Python само корректно пройдёт через чужой C-стек и появится в вызывающем Python-коде.

Нужен явный мост:

- callback перехватывает исключение;
- сохраняет его в Python-контексте;
- возвращает C-код ошибки;
- C прекращает операцию;
- после возврата наружная Python-обёртка повторно поднимает исключение.

Полный пример приведён в практикуме.

Для сложных callbacks в CFFI API mode полезно рассмотреть `extern "Python"`: этот механизм позволяет связать скомпилированную обёртку с Python-реализацией функции.

#### Callback из внешнего потока

Библиотека может вызвать callback из собственного потока.

Нужно отдельно проверить:

- поддерживает ли это выбранная обёртка;
- как поток присоединяется к интерпретатору;
- можно ли использовать переданные объекты;
- когда заканчивается callback;
- как он синхронизируется с остановкой приложения.

В `ctypes` не следует строить контракт на предположении, что `threading.local()` сохранит ожидаемое состояние между callbacks из чужого потока. Механизм подключения такого потока может создавать временное Python-представление потока.

Источники:

- [ctypes: callbacks и указатели](https://docs.python.org/3.15/library/ctypes.html).
- [CFFI: работа с памятью и callbacks](https://cffi.readthedocs.io/en/latest/using.html).

### 24.2.3. Ошибки, освобождение памяти и thread safety внешней библиотеки

Внешняя библиотека может сообщать об ошибках несколькими способами.

| Способ | Пример | На что обратить внимание |
|---|---|---|
| Код результата | `0` — успех, другое — ошибка | Не потерять дополнительную диагностику |
| `NULL` | Не удалось создать объект | Узнать, где хранится причина |
| `errno` | POSIX-подобный API | Читать сразу и только по контракту |
| Windows last error | WinAPI | Правильно настроить доступ к ошибке |
| Выходной параметр | `error_info *error` | Владение строками и структурой |
| Состояние контекста | `engine_last_error(engine)` | Потокобезопасность и время жизни |

Не предполагайте, что любая неуспешная C-функция устанавливает `errno`.

Не предполагайте и обратное: ненулевой `errno` после успешного вызова не обязательно относится к этому вызову.

В `ctypes` для API с `errno` и Windows last error предусмотрены специальные настройки. Использовать их нужно в соответствии с документацией конкретной функции.

#### Освобождение должно работать на пути ошибки

Рассмотрим последовательность:

1. C выделил буфер.
2. Python начал создавать результат.
3. Создание Python-объекта завершилось `MemoryError`.

Освободить C-буфер всё равно нужно:

```python
resource = create_resource()

try:
    return convert_to_python(resource)
finally:
    release_resource(resource)
```

Особенно важны ошибки после частичного успеха:

- создан первый из нескольких ресурсов;
- зарегистрирован callback;
- открыт файл;
- запущен поток;
- выделена память результата.

Контракт должен определять состояние выходных параметров при каждом коде ошибки.

#### `ffi.gc` и детерминированное освобождение

CFFI позволяет связать указатель с деструктором:

```python
managed = ffi.gc(pointer, library.release_resource)
```

Это удобно, но время срабатывания сборки мусора не следует использовать как расписание освобождения дефицитного ресурса.

Для файлов, соединений, GPU-памяти и больших буферов обычно нужен явный `close`, контекстный менеджер или согласованное использование `ffi.release`.

Важно не соединить две независимые схемы освобождения так, чтобы один ресурс освободился дважды.

#### GIL не является блокировкой внешней библиотеки

`ctypes.CDLL` обычно освобождает GIL во время внешнего вызова.

Следовательно, два Python-потока могут одновременно оказаться внутри библиотеки.

Если библиотека использует:

- общий рабочий буфер;
- глобальную таблицу;
- process-global состояние;
- общий объект контекста без защиты;

то нужен её собственный механизм синхронизации или блокировка на стороне обёртки.

Например:

```python
import threading


class SerializedLibrary:
    def __init__(self, library):
        self._library = library
        self._lock = threading.Lock()

    def operation(self, argument):
        with self._lock:
            return self._library.operation(argument)
```

Такой код подходит только после анализа callbacks и повторного входа.

Если C-функция вызывает Python-callback, а callback снова пытается выполнить операцию под той же блокировкой, возможна взаимная блокировка.

Замена `Lock` на `RLock` не решает все случаи: callback может выполняться из другого потока.

#### Free-threaded Python требует отдельного анализа

Даже когда обёртка поддерживает работу без GIL, это не доказывает безопасность самой библиотеки.

Также нельзя считать два разных Python-объекта, указывающих на одну C-память, независимыми областями синхронизации.

Проверяйте реальные адреса и ресурсы, которыми совместно пользуются потоки.

Источник: [thread safety в ctypes](https://docs.python.org/3.15/library/ctypes.html).

## 24.3. Python/C API

### 24.3.1. Owned/borrowed references, reference counting и обработка ошибок

Python/C API позволяет работать с объектами Python из C.

Обычно включают:

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>
```

`Python.h` нужно подключать до стандартных заголовков, которым могут быть важны установленные им платформенные определения.

Для рассматриваемой базы 3.12 сохранение `PY_SSIZE_T_CLEAN` удобно; в новых версиях требования к некоторым старым форматам аргументов изменились.

#### Ссылка — это обязательство

Условно различают:

- owned reference — у вызывающего есть обязанность освободить ссылку;
- borrowed reference — пользоваться можно в рамках гарантированного времени жизни владельца;
- stolen reference — вызываемый API принимает обязанность по переданной ссылке.

Это не три вида Python-объектов.

Один объект может одновременно иметь множество ссылок с разными обязательствами у разных участников.

#### Owned reference

Функция возвращает новую сильную ссылку:

```c
PyObject *value = PyLong_FromLong(42);

if (value == NULL) {
    return NULL;
}

/* Использование value. */

Py_DECREF(value);
```

`PyLong_FromLong` может вернуть ссылку на уже существующий объект реализации. Для вашего кода это всё равно owned reference: обязанность определяется API, а не тем, была ли физически выделена новая память.

#### Borrowed reference

Например, традиционный `PyList_GetItem` возвращает borrowed reference.

В обычном однопоточном фрагменте она может использоваться, пока список удерживает элемент и не изменяется.

Но borrowed reference не должна сохраняться «на потом» без отдельного решения о времени жизни.

Для получения собственной сильной ссылки существует:

```c
PyObject *owned = Py_NewRef(borrowed);
```

В free-threaded коде этого недостаточно, если между получением borrowed reference и `Py_NewRef` другой поток может удалить объект.

Для подходящих операций следует использовать API, сразу возвращающие сильную ссылку. Например, `PyList_GetItemRef` и `PyDict_GetItemRef` появились в Python 3.13.

#### Stealing API

Некоторые функции принимают владение переданной ссылкой.

Известный пример — установка элемента списка через `PyList_SetItem`.

Нельзя автоматически добавлять `Py_DECREF` после любого вызова функции: при передаче владения это может привести к преждевременному уничтожению объекта.

Особенно внимательно читайте поведение функции на ошибке.

| API | Типичный контракт |
|---|---|
| `PyLong_FromLong` | Возвращает owned reference |
| `PyObject_GetAttrString` | Возвращает owned reference |
| `PyList_GetItem` | Возвращает borrowed reference |
| `PyList_GetItemRef`, с 3.13 | Возвращает owned reference |
| `PyTuple_Pack` | Возвращает owned reference, не крадёт ссылки аргументов |
| `PyList_SetItem` | Принимает ссылку по stealing-контракту |
| `PyDict_SetItem` | Не забирает владение ссылками вызывающего |

#### Один путь освобождения

Пример создаёт кортеж из двух объектов:

```c
static PyObject *
make_pair(void)
{
    PyObject *first = NULL;
    PyObject *second = NULL;
    PyObject *result = NULL;

    first = PyLong_FromLong(10);
    if (first == NULL) {
        goto done;
    }

    second = PyUnicode_FromString("ready");
    if (second == NULL) {
        goto done;
    }

    result = PyTuple_Pack(2, first, second);

done:
    Py_XDECREF(second);
    Py_XDECREF(first);
    return result;
}
```

Здесь:

- локальные переменные владеют `first` и `second`;
- `PyTuple_Pack` создаёт собственные ссылки;
- освобождение локальных ссылок не разрушает элементы возвращаемого кортежа;
- при ошибке результат остаётся `NULL`, а исключение устанавливает неуспешная API-функция.

#### `DECREF` может выполнить Python-код

Уничтожение объекта может вызвать финализатор и другие действия.

Поэтому перед `Py_DECREF` состояние структуры должно быть согласованным.

Для поля удобно:

```c
Py_CLEAR(state->cached_value);
```

Поле сначала обнуляется, затем освобождается прежняя ссылка.

Если финализатор повторно войдёт в код, он не увидит в поле указатель на уничтожаемый объект.

Не удерживайте обычную нативную блокировку вокруг потенциального выполнения Python-кода без анализа повторного входа.

#### Ошибка состоит из двух частей

Для большинства C-функций расширения ошибка означает:

1. установленное Python-исключение;
2. возвращённый признак ошибки.

Например:

```c
PyErr_SetString(PyExc_ValueError, "value must be positive");
return NULL;
```

Возврат `NULL` без исключения нарушает контракт.

Возврат нормального результата при оставленном исключении также нарушает контракт.

У функций, возвращающих число, нужно учитывать неоднозначный sentinel:

```c
long value = PyLong_AsLong(object);

if (value == -1 && PyErr_Occurred()) {
    return NULL;
}
```

`-1` может быть корректным значением. Поэтому проверяется состояние ошибки.

Не используйте значение счётчика ссылок как универсальное доказательство исключительного владения объектом. Immortal objects и free-threaded механизмы делают такие предположения особенно ненадёжными.

Источники:

- [Reference counting](https://docs.python.org/3.15/c-api/refcounting.html).
- [Exception handling](https://docs.python.org/3.15/c-api/exceptions.html).
- [List objects](https://docs.python.org/3.15/c-api/list.html).
- [Tuple objects](https://docs.python.org/3.15/c-api/tuple.html).
- [Dictionary objects](https://docs.python.org/3.15/c-api/dict.html).

### 24.3.2. Работа с объектами, buffer protocol и преобразованием типов

#### Проверка типа — часть Python-интерфейса

Допустим, расширение ожидает число.

Нужно решить, принимает ли оно:

- только `int`;
- подклассы `int`;
- объекты с `__index__`;
- произвольные объекты с `__int__`;
- `bool`.

Это разные контракты.

Аналогично для входных байтов:

- только точный `bytes`;
- `bytes` и подклассы;
- любой bytes-like объект;
- только непрерывный буфер;
- только writable buffer.

Чем шире контракт, тем больше условий нужно проверять.

#### Не путайте `str` и байты

Для текста:

```c
Py_ssize_t size = 0;
const char *utf8 = PyUnicode_AsUTF8AndSize(text, &size);

if (utf8 == NULL) {
    return NULL;
}
```

Полученный указатель связан с временем жизни Python-объекта. Это не новая независимо выделенная строка.

`size` измеряется в байтах UTF-8.

Если внешняя функция ожидает завершающуюся нулём строку и не принимает длину, нужно отдельно учитывать встроенные нулевые символы.

#### Buffer protocol

Buffer protocol позволяет получить описание памяти объекта без обязательного копирования.

Экспортёрами могут быть:

- `bytes`;
- `bytearray`;
- `memoryview`;
- `array.array`;
- многие массивы сторонних библиотек.

Минимальный пример получения длины непрерывного буфера:

```c
static PyObject *
buffer_size(PyObject *module, PyObject *object)
{
    Py_buffer view;

    if (PyObject_GetBuffer(object, &view, PyBUF_SIMPLE) < 0) {
        return NULL;
    }

    Py_ssize_t length = view.len;

    PyBuffer_Release(&view);

    return PyLong_FromSsize_t(length);
}
```

На каждое успешное получение буфера должен приходиться `PyBuffer_Release`.

Не вызывайте `PyBuffer_Release` для неуспешно полученного или неинициализированного `Py_buffer`.

#### Что содержится в `Py_buffer`

В зависимости от запрошенных флагов:

- адрес;
- длина в байтах;
- размер элемента;
- формат;
- число измерений;
- размеры измерений;
- strides;
- признак readonly;
- информация о косвенной адресации.

Нельзя получить произвольный `Py_buffer`, привести адрес к `double *` и считать задачу решённой.

Например:

- элементы могут быть не `double`;
- массив может быть strided;
- данные могут иметь другой byte order;
- адрес может не иметь нужного выравнивания.

`memcpy` в локальное значение иногда безопаснее прямого разыменования невыровненного указателя.

#### Readonly не означает immutable

Readonly-представление запрещает запись через конкретный интерфейс.

Но исходная память может оставаться изменяемой через другой объект.

Например, readonly `memoryview` над `bytearray` не превращает сам `bytearray` в неизменяемый объект.

Экспорт буфера может запрещать resize, сохраняя адрес. Это не означает запрета на изменение существующих элементов.

Поэтому перед освобождением GIL для чтения такого буфера нужно решить вопрос конкурентной записи.

В практикуме вычислительное расширение принимает только точный `bytes`. Это намеренно узкий контракт: неизменяемость входа упрощает безопасное чтение без GIL.

#### Преобразование целых

Для каждого C-типа нужно решить:

- диапазон;
- допустимость отрицательных значений;
- поведение при переполнении;
- допустимость `bool`;
- способ сообщения об ошибке.

Не превращайте отрицательную длину в `size_t` без проверки. После преобразования она может стать огромным положительным числом.

Не считайте переполнение signed integer в C аналогом поведения Python `int`: это разные модели вычислений.

Источники:

- [Buffer protocol](https://docs.python.org/3.15/c-api/buffer.html).
- [Bytes objects](https://docs.python.org/3.15/c-api/bytes.html).
- [Unicode objects](https://docs.python.org/3.15/c-api/unicode.html).

### 24.3.3. Освобождение GIL вокруг нативной работы и вход из внешнего потока

#### Два разных понятия

Нужно различать:

1. наличие GIL;
2. присоединённое к интерпретатору состояние потока.

В обычной сборке CPython эти понятия часто встречаются вместе.

В free-threaded сборке GIL может быть выключен, но Python/C API по-прежнему требует корректного присоединения потока к интерпретатору.

«GIL отсутствует» не означает «Python API разрешён из любого C-потока».

#### Освобождение вокруг нативного участка

```c
unsigned long long total = 0;

Py_BEGIN_ALLOW_THREADS

for (Py_ssize_t index = 0; index < length; index++) {
    total += data[index];
}

Py_END_ALLOW_THREADS
```

Этот участок должен работать исключительно с безопасными для такого использования нативными данными.

Внутри нельзя произвольно:

- создавать Python-объекты;
- вызывать Python-функции;
- менять Python-контейнеры;
- выполнять `Py_INCREF` и `Py_DECREF`;
- устанавливать Python-исключения.

Сначала поток возвращается в присоединённое состояние. Затем результат преобразуется в Python-объект или устанавливается исключение.

#### Жизненный цикл данных должен покрывать весь участок

Прежде чем отключить поток от интерпретатора, нужно:

- получить указатели;
- проверить типы и размеры;
- обеспечить время жизни владельцев;
- решить вопрос конкурентной записи;
- подготовить нативное состояние результата.

Нельзя рассчитывать, что GIL защитит данные после его освобождения.

Отсоединение полезно и в free-threaded сборках: оно позволяет интерпретатору корректно координировать некоторые операции и не означает простого «разблокирования несуществующего mutex».

#### Внешний поток

Нативная библиотека может создать собственный поток, который захочет вызвать Python.

Для этого требуется:

- выбрать нужный интерпретатор;
- обеспечить его существование;
- присоединить поток;
- выполнить Python API;
- корректно отсоединить поток;
- согласовать всё это с завершением хоста.

Исторически часто использовались:

```c
PyGILState_Ensure();
PyGILState_Release(...);
```

Но этот механизм имеет предположения о главном интерпретаторе и не является универсальным решением для subinterpreters.

В Python 3.15 семейство `PyGILState_*` получило статус soft deprecated в пользу новых механизмов работы с состоянием потока.

#### Новые API Python 3.15

Python 3.15 предоставляет механизмы с `PyInterpreterGuard` и `PyInterpreterView`.

Схематически работа с уже корректно полученным и живым guard выглядит так:

```c
/* Только Python 3.15+. guard подготовлен владельцем интерпретатора. */

PyThreadStateToken *token = PyThreadState_Ensure(guard);

if (token == NULL) {
    /*
     * Присоединиться не удалось.
     * Python-исключение здесь не устанавливается.
     * Нельзя обращаться к PyErr_* как к обычному пути ошибки.
     */
    return;
}

/* Здесь разрешён Python/C API для выбранного интерпретатора. */

PyThreadState_Release(token);
```

Этот фрагмент не описывает весь жизненный цикл guard.

Его должен контролировать хост:

- guard получают до запуска использующих его потоков;
- новые операции прекращают перед shutdown;
- активные операции завершают;
- guard закрывают по контракту API;
- интерпретатор не уничтожают при оставшихся пользователях.

Для старых версий и для некоторых постоянных worker требуется явное управление `PyThreadState`. Такую реализацию нужно проектировать под конкретную версию и выбранный интерпретатор.

#### Частая взаимная блокировка

Сценарий:

1. Python вызывает C.
2. C запускает worker.
3. Worker вызывает Python-callback.
4. Исходный поток делает `join`, продолжая удерживать GIL.
5. Worker ждёт GIL.
6. Исходный поток ждёт worker.

Разрыв такого цикла может требовать ожидания worker в отсоединённом состоянии.

Но это допустимо только при правильном владении всеми данными и при отсутствии запрещённых Python-вызовов в отсоединённом участке.

#### Проверки «Python ещё жив» недостаточно

Последовательность:

```text
проверили состояние интерпретатора
→ другой поток начал завершение
→ попытались войти в Python
```

содержит гонку жизненного цикла.

Нужен протокол остановки, а не одиночная проверка `Py_IsInitialized`.

Источники:

- [Thread state and the GIL](https://docs.python.org/3.15/c-api/threads.html).
- [PEP 788 — новые API работы с состоянием потока](https://peps.python.org/pep-0788/).

### 24.3.4. Module state, multi-phase initialization и subinterpreters

#### Почему глобальный `PyObject *` опасен

Наивное расширение может хранить состояние так:

```c
static PyObject *cached_result;
```

Но такая переменная принадлежит процессу, а Python-объект — конкретному интерпретатору и определённому жизненному циклу.

Проблемы возникают при:

- нескольких экземплярах модуля;
- subinterpreters;
- независимых GIL;
- повторной загрузке;
- завершении одного интерпретатора;
- конкурентном доступе.

Нельзя переносить Python-объект из одного интерпретатора в другой только потому, что его адрес доступен из C.

#### Состояние экземпляра модуля

Вместо глобального Python-объекта используют структуру:

```c
typedef struct {
    PyObject *InputTooLargeError;
} ModuleState;
```

Для модуля задают:

```c
.m_size = sizeof(ModuleState)
```

А состояние получают через:

```c
ModuleState *state = PyModule_GetState(module);
```

Так состояние связано с конкретным экземпляром модуля.

#### Multi-phase initialization

Инициализация разделяет создание модуля и его исполнение.

Обычно:

1. `PyInit_name` возвращает описание модуля через `PyModuleDef_Init`;
2. слот `Py_mod_exec` наполняет созданный модуль;
3. Python управляет жизненным циклом экземпляра.

Это позволяет лучше согласовать расширение с моделью импорта и изоляцией интерпретаторов.

#### `traverse`, `clear`, `free`

Если состояние содержит ссылки на Python-объекты, нужно объяснить их сборщику мусора.

Обычно:

- `m_traverse` перечисляет ссылки через `Py_VISIT`;
- `m_clear` освобождает их через `Py_CLEAR`;
- `m_free` завершает очистку и освобождает собственные нативные ресурсы.

Освобождение нативного ресурса и очистка Python-ссылок могут требовать разных действий.

Например, нативный worker сначала нужно остановить и дождаться его завершения. Простого `Py_CLEAR` для этого недостаточно.

#### Heap types

Если расширение определяет собственный тип, полезно рассматривать heap types, создаваемые для конкретного модуля.

API вроде `PyType_FromModuleAndSpec` помогает связать тип с модульным состоянием.

Для сложной иерархии нужно учитывать, как методы получают состояние определяющего модуля. Самостоятельное чтение произвольной глобальной переменной эту задачу не решает.

#### Subinterpreters

Subinterpreters позволяют иметь несколько интерпретаторов в одном процессе.

Но они не превращают процесс в набор полностью изолированных операционных сред.

Общими могут оставаться:

- нативные глобальные переменные;
- сторонние библиотеки;
- файловые дескрипторы;
- сигналы;
- другие ресурсы процесса.

Даже расширение с правильным module state может использовать внешнюю библиотеку, чьё process-global состояние делает независимую работу невозможной.

#### Объявления поддержки

Начиная с Python 3.12 слот `Py_mod_multiple_interpreters` позволяет объявлять свойства поддержки нескольких интерпретаторов.

Значение `Py_MOD_PER_INTERPRETER_GIL_SUPPORTED` означает более сильное обещание: расширение поддерживает интерпретаторы с независимыми GIL.

Это обещание нельзя выводить только из отсутствия одной глобальной переменной.

Источники:

- [Module objects](https://docs.python.org/3.15/c-api/module.html).
- [Isolating Extension Modules](https://docs.python.org/3.15/howto/isolating-extensions.html).
- [PEP 489 — multi-phase initialization](https://peps.python.org/pep-0489/).
- [PEP 684 — per-interpreter GIL](https://peps.python.org/pep-0684/).

### 24.3.5. Совместимость с free-threaded CPython

Free-threaded CPython позволяет выполнять Python-потоки без обычной глобальной блокировки интерпретатора.

Для расширения это меняет исходные предположения о синхронизации.

#### Что требуется проверить

1. Глобальное изменяемое состояние.
2. Состояние экземпляров расширения.
3. Borrowed references к изменяемым контейнерам.
4. Неатомарные последовательности операций.
5. Использование unchecked macros.
6. Сторонние C- и C++-библиотеки.
7. Callbacks.
8. Фоновую работу.
9. Освобождение ресурсов.
10. Параллельный shutdown.

#### Две безопасные операции не образуют безопасную транзакцию

Даже если отдельные операции контейнера защищены реализацией, последовательность:

```text
проверить наличие ключа
→ прочитать значение
→ изменить связанный ресурс
```

не обязательно атомарна.

Аналогично, проверка размера списка не гарантирует, что последующее обращение увидит тот же список.

Для некоторых участков нужны критические секции Python/C API или собственная синхронизация.

При использовании `PyDict_Next` нельзя предполагать, что вся итерация автоматически защищена от параллельных изменений.

#### Сильные ссылки вместо небезопасного повышения borrowed reference

В Python 3.13+ появились дополнительные API, сразу возвращающие сильную ссылку.

Пример:

```c
PyObject *item = PyList_GetItemRef(list, index);

if (item == NULL) {
    return NULL;
}

/* Работа с собственной ссылкой. */

Py_DECREF(item);
```

Это помогает избежать гонки между получением borrowed reference и её удержанием.

Но не защищает произвольную составную операцию вокруг элемента.

#### Объявление поддержки без GIL

В multi-phase модуле:

```c
#if PY_VERSION_HEX >= 0x030D0000
    {Py_mod_gil, Py_MOD_GIL_NOT_USED},
#endif
```

Это означает, что автор расширения заявляет поддержку работы без GIL.

Слот:

- не расставляет блокировки;
- не проверяет стороннюю библиотеку;
- не исправляет гонки;
- не делает небезопасные макросы безопасными.

Если расширение не объявляет такую поддержку, его импорт в free-threaded окружении может привести к включению GIL.

Поэтому тест «импортировалось в free-threaded Python» слабее теста «работает при фактически выключенном GIL».

#### Отдельные проверки

Нужны разные сценарии:

- обычный CPython;
- free-threaded CPython;
- один поток;
- несколько потоков;
- общий экземпляр объекта;
- разные экземпляры;
- одновременное закрытие;
- callback во время остановки.

Стресс-тест может обнаружить гонку, но отсутствие падения не доказывает её отсутствие.

Для поиска некоторых классов гонок полезен ThreadSanitizer в согласованной инструментированной сборке.

Источник: [C API Extension Support for Free Threading](https://docs.python.org/3.15/howto/free-threading-extensions.html).

## 24.4. ABI, сборка и распространение

### 24.4.1. Limited API, Stable ABI и приватные API CPython

#### API и ABI

API определяет, как исходный код вызывает библиотеку.

ABI определяет, как скомпилированные компоненты взаимодействуют на двоичном уровне:

- имена символов;
- соглашения вызова;
- размеры и layout структур;
- представление типов;
- набор доступных функций.

Исходный код может успешно пересобираться для нескольких версий Python, хотя один готовый бинарный файл между ними несовместим.

#### Обычный CPython API

Расширение, использующее полный публичный CPython API, обычно собирают отдельно для соответствующей minor-версии Python и режима сборки.

Например, wheel под CPython 3.14 не становится wheel для CPython 3.15 только потому, что обе версии поддерживают один и тот же Python-код.

#### Limited API

Limited API ограничивает используемую поверхность C API.

Перед `Python.h` задаётся целевая версия, например:

```c
#define Py_LIMITED_API 0x030C0000
#include <Python.h>
```

Но одного определения макроса недостаточно.

Нужно:

- использовать только разрешённые API;
- не обращаться к скрытому layout объектов;
- правильно настроить сборку;
- сформировать корректные wheel tags;
- проверить результат на поддерживаемых версиях.

Некоторые быстрые макросы полного API зависят от внутренних структур и недоступны в таком режиме.

#### Stable ABI и `abi3`

Stable ABI предназначен для двоичной совместимости определённого набора API между версиями CPython.

Для обычных сборок с ним связан ABI tag `abi3`.

Важные ограничения:

- это не переносимость между Windows и Linux;
- это не переносимость между архитектурами;
- это не автоматическое решение зависимостей на системные библиотеки;
- это не гарантия одинакового поведения всех версий;
- старый `abi3` не следует считать совместимым с free-threaded CPython.

#### Free-threaded Stable ABI в Python 3.15

В Python 3.15 появился Stable ABI для free-threaded сборок — `abi3t`.

Для кода, который действительно удовлетворяет условиям совместимости с обоими режимами, предусмотрено совместное обозначение ABI.

Например, соответствующий wheel может использовать сжатый ABI tag:

```text
abi3.abi3t
```

Новые настройки включают `Py_TARGET_ABI3T`.

Иллюстрация целевого уровня 3.15:

```c
#define Py_LIMITED_API 0x030F0000
#define Py_TARGET_ABI3T 0x030F0000
#include <Python.h>
```

Это иллюстрация выбора интерфейса, а не готовый рецепт преобразования любого расширения в совместимое.

В частности, учебное расширение из практикума использует полный API и не заявляет `abi3` или `abi3t`.

#### Публичное и приватное API

Имена `_Py...` обычно относятся к внутренним API CPython.

Опора на них может:

- нарушить совместимость даже при небольшом обновлении;
- усложнить free-threaded поддержку;
- потребовать постоянной адаптации;
- исключить использование Stable ABI.

API семейства `PyUnstable_...` явно допускают изменения между minor-версиями.

Если нужен такой интерфейс, зависимость должна быть осознанной и покрытой соответствующей матрицей сборки.

Источники:

- [C API Stability](https://docs.python.org/3.15/c-api/stable.html).
- [PEP 803 — Stable ABI для free-threaded CPython](https://peps.python.org/pep-0803/).

### 24.4.2. Платформенные wheels, внешние библиотеки и установка на чистой ОС

Wheel нативного расширения должен соответствовать сразу нескольким характеристикам окружения.

Имя wheel содержит совместимость с:

- Python;
- ABI;
- платформой.

Упрощённые примеры ABI-частей:

| Tag | Назначение |
|---|---|
| `cp314-cp314` | Обычный CPython 3.14 |
| `cp314-cp314t` | Free-threaded CPython 3.14 |
| `cp315-cp315t` | Free-threaded CPython 3.15 |
| `cp315-abi3.abi3t` | При выполнении требований — оба режима с целевого уровня 3.15 |

К этим частям обязательно добавляется платформенный tag.

Реальную совместимость определяют не примеры строк, а спецификация tags, содержимое wheel и требования сборки.

#### Что может зависеть от платформы

- архитектура CPU;
- ОС;
- libc;
- минимальная версия macOS;
- C++ runtime;
- внешние динамические библиотеки;
- набор процессорных инструкций;
- поддерживаемый ABI Python.

Для Linux различайте семейства `manylinux` и `musllinux`.

Совместимость с glibc не означает совместимость с musl.

Сборка на современной системе может случайно потребовать слишком новую версию системных символов.

Переименование wheel не исправляет такую зависимость.

#### Не используйте `-march=native` без продуманного ограничения аудитории

Этот флаг может включить инструкции, доступные на машине сборки, но отсутствующие на машине пользователя.

Для публичного wheel требуется понятная политика минимального CPU или механизм безопасного выбора реализации во время выполнения.

#### Внешние динамические библиотеки

Расширение может успешно импортироваться на машине разработчика, потому что там уже установлены нужные `.so`, `.dylib` или `.dll`.

На чистой системе импорт завершится ошибкой загрузчика.

Для анализа и подготовки зависимостей используются:

- Linux: `auditwheel`;
- macOS: `delocate`;
- Windows: `delvewheel`.

Эти инструменты помогают включать и корректировать допустимые зависимости. Они не исправляют произвольную несовместимость ABI и не снимают лицензионные ограничения.

Для матрицы wheels полезен `cibuildwheel`.

#### Проверяйте wheel, а не только исходную директорию

Корректный сценарий проверки:

1. Собрать wheel.
2. Создать чистое окружение.
3. Установить wheel.
4. Выйти из директории исходного проекта.
5. Импортировать модуль.
6. Выполнить контрактные тесты.
7. Проверить платформенные зависимости.

Иначе Python может случайно импортировать локальную копию, а установленный пакет останется непроверенным.

#### Установка из sdist

Если wheel для платформы отсутствует, `pip` может попытаться собрать sdist.

Пользователю тогда могут понадобиться:

- компилятор;
- Python development headers;
- C/C++ toolchain;
- Rust;
- системные библиотеки и заголовки;
- совместимый build backend.

Документация должна объяснять, где гарантирована установка готового wheel, а где требуется сборка.

Связь с предыдущей главой: сборка нативного wheel должна быть частью того же управляемого процесса доставки, что и остальные артефакты проекта.

Источники:

- [Platform compatibility tags](https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/).
- [setuptools: extension modules](https://setuptools.pypa.io/en/latest/userguide/ext_modules.html).
- [cibuildwheel](https://cibuildwheel.pypa.io/en/stable/).
- [auditwheel](https://pypi.org/project/auditwheel/).
- [delocate](https://github.com/matthew-brett/delocate).
- [delvewheel](https://github.com/adang1345/delvewheel).

### 24.4.3. Cython, pybind11 и Rust/PyO3: выбор инструмента

Эти инструменты уменьшают объём ручной работы, но не отменяют контрактов нативной интеграции.

| Инструмент | Хорошо подходит | Что остаётся ответственностью автора |
|---|---|---|
| Cython | Типизированные циклы, массивы, обёртки C | Типы, память, конкурентный доступ |
| pybind11 | C++-библиотеки и классы | Владение, lifetime policies, C++ thread safety |
| PyO3 | Расширения на Rust | Python-семантика, attachment, unsafe/FFI |
| Python/C API | Точный контроль | Практически все детали |
| CFFI | C API и компилируемые обёртки | Контракты внешней библиотеки |

#### Cython

Cython позволяет писать код, близкий к Python, с типами C и прямыми вызовами C API.

Иллюстрация:

```cython
# example.pyx

def sum_buffer(const unsigned char[::1] data):
    cdef Py_ssize_t index
    cdef unsigned long long total = 0

    with nogil:
        for index in range(data.shape[0]):
            total += data[index]

    return total
```

Здесь важны:

- тип элементов;
- непрерывность `::1`;
- отсутствие Python-операций в вычислительном участке;
- допустимость чтения памяти без конкурентной записи.

`const` запрещает запись через это представление, но не делает исходную память immutable.

Если буфер поддерживается изменяемым объектом, нужен отдельный контракт синхронизации.

Объявление Cython-функции как `nogil` означает возможность вызова без GIL. Само по себе оно GIL не освобождает. Для освобождения нужен соответствующий участок, например `with nogil`.

Выигрыш часто даёт переход от Python-операций к типизированным C-операциям, а не факт освобождения GIL.

#### pybind11

pybind11 связывает C++-типы и функции с Python.

Он помогает с:

- преобразованиями;
- исключениями;
- обёртками классов;
- RAII;
- NumPy;
- embedding.

Но возвращаемый C++-указатель всё равно требует ответа: кто владелец?

Политики возврата определяют, например:

- передать владение;
- вернуть заимствованную ссылку;
- связать время жизни результата с родительским объектом.

`reference_internal` может удерживать родителя, но не запрещает родителю переместить внутреннюю память.

Пример: ссылка на элемент `std::vector` может стать недействительной после realloc, хотя сам `vector` продолжает существовать.

Для освобождения GIL используется `py::gil_scoped_release`.

В его области нельзя выполнять Python-операции, включая неочевидные действия деструкторов Python-обёрток.

Поддержка без GIL и поддержка per-interpreter GIL объявляются отдельно и требуют аудита.

При работе с NumPy нужно помнить, что запрос преобразования типа или `forcecast` может создать копию. Приём массива не равен гарантированному zero-copy.

#### Rust и PyO3

Rust помогает отслеживать владение и заимствования в собственном коде.

Но граница с Python и внешним C всё равно требует понимания:

- Python-ссылок;
- присоединения потока;
- синхронизации;
- внутренней изменяемости;
- `unsafe`;
- сторонних библиотек.

В современных версиях PyO3:

- `Bound<'py, T>` связан с контекстом присоединения;
- `Py<T>` позволяет хранить Python-ссылку вне конкретного attachment-контекста;
- маркер `Python<'py>` не следует трактовать как доказательство эксклюзивного доступа при free-threading.

Поведение зависит от версии PyO3.

Начиная с PyO3 0.28, модуль по умолчанию рассматривается как поддерживающий работу без GIL. Это отличается от более старых примеров, где требовалось явно указывать `gil_used = false`.

Если модуль нуждается в GIL, это нужно явно объявить согласно документации используемой версии.

Rust не доказывает потокобезопасность внешней C-библиотеки и не исправляет ошибочно описанную FFI-сигнатуру.

#### Практический выбор

Выбирайте инструмент с учётом:

- существующей кодовой базы;
- компетенций команды;
- сложности интерфейса;
- требований к ABI;
- поддерживаемых платформ;
- процесса сборки;
- модели памяти;
- поддержки free-threaded CPython.

Источники:

- [Cython: typed memoryviews](https://docs.cython.org/en/latest/src/userguide/memoryviews.html).
- [Cython: nogil](https://docs.cython.org/en/latest/src/userguide/nogil.html).
- [pybind11: GIL и расширенные возможности](https://pybind11.readthedocs.io/en/stable/advanced/misc.html).
- [pybind11: return value policies](https://pybind11.readthedocs.io/en/stable/advanced/functions.html).
- [pybind11: NumPy](https://pybind11.readthedocs.io/en/stable/advanced/pycpp/numpy.html).
- [PyO3 0.30.1: free-threading](https://pyo3.rs/v0.30.1/free-threading.html).
- [PyO3: Python из Rust](https://pyo3.rs/v0.30.1/python-from-rust.html).

### 24.4.4. Native debugging, sanitizers и падения за пределами Python traceback

Python traceback показывает путь Python-вызовов.

Но он не объясняет автоматически:

- use-after-free;
- переполнение C-буфера;
- запись по недействительному адресу;
- гонку C++-потоков;
- ошибку выравнивания;
- несовместимый ABI;
- повреждение стека.

#### `faulthandler`

Для получения дополнительной диагностики:

```bash
python -X faulthandler program.py
```

Или:

```python
import faulthandler

faulthandler.enable()
```

Это диагностический механизм.

Он не превращает segfault в безопасно обрабатываемое Python-исключение и не восстанавливает повреждённую память.

Возможности вывода C-стека зависят от версии и платформы.

#### GDB

Для Linux-сценария:

```bash
gdb --args python -X faulthandler program.py
```

В отладчике полезны:

```text
run
bt
thread apply all bt
```

Если доступны Python debug helpers и подходящие символы:

```text
py-bt
```

Для расследования нужны символы не только Python, но и расширения и участвующих библиотек.

Для отладочной сборки часто полезны:

```text
-g
-O1
-fno-omit-frame-pointer
```

Конкретные параметры зависят от compiler/toolchain.

#### Sanitizers

| Инструмент | Что помогает находить |
|---|---|
| AddressSanitizer | Use-after-free, выход за границы и другие ошибки памяти |
| UndefinedBehaviorSanitizer | Некоторые формы undefined behavior |
| ThreadSanitizer | Некоторые гонки данных |

ASan и TSan обычно используют в отдельных сборках.

Нельзя считать, что добавление флага только к одному `.so` автоматически создаёт корректную инструментированную среду. Важны runtime sanitizer, загрузка библиотеки и совместимость с основным исполняемым файлом.

Практически удобно сначала тестировать чистое C-ядро отдельной C-программой, а затем интеграцию с Python.

#### Как уменьшать воспроизводящий пример

1. Зафиксировать вход.
2. Зафиксировать версии и режим сборки.
3. Убрать сеть и внешние сервисы.
4. Уменьшить число операций.
5. Проверить один поток.
6. Проверить несколько потоков.
7. Отделить нативное ядро от Python-обёртки.
8. Запустить под подходящим инструментом.

Если ошибка проявляется только после большого числа вызовов, отдельно проверьте:

- утечки;
- двойное освобождение;
- сохранённые borrowed references;
- callbacks после закрытия;
- использование временных буферов;
- конкурентный shutdown.

Опасные проверки с повреждением указателей выполняют в отдельном тестовом процессе, а не в основном процессе интерактивной сессии.

Источники:

- [faulthandler](https://docs.python.org/3.15/library/faulthandler.html).
- [GDB helpers](https://docs.python.org/3.15/howto/gdb_helpers.html).
- [AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html).
- [UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html).
- [ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html).

## 24.5. Встраивание интерпретатора

### 24.5.1. Инициализация, конфигурация, вызовы и завершение интерпретатора

При embedding Python становится частью жизненного цикла хоста.

Удобная модель:

1. Подготовить конфигурацию.
2. Инициализировать интерпретатор.
3. Зарегистрировать и загрузить необходимые модули.
4. Обслуживать вызовы.
5. Прекратить новые операции.
6. Остановить и дождаться фоновых операций.
7. Освободить Python-объекты.
8. Завершить интерпретатор.

#### Инициализация через `PyConfig`

Для базы 3.12+ используется конфигурационный API:

```c
PyConfig config;
PyConfig_InitIsolatedConfig(&config);

/* Настройка config. */

PyStatus status = Py_InitializeFromConfig(&config);

PyConfig_Clear(&config);

if (PyStatus_Exception(status)) {
    /* Обработать ошибку запуска. */
}
```

В реальном коде проверяют и промежуточные операции настройки, возвращающие `PyStatus`.

`PyConfig_InitIsolatedConfig` помогает получить контролируемый запуск, меньше зависящий от пользовательского окружения.

Это не security sandbox.

В новых версиях, начиная с 3.14, доступен также непрозрачный конфигурационный API `PyInitConfig`. Его не следует без отметки версии вставлять в пример для Python 3.12.

#### Вызов Python-функции

Типичный путь:

1. импортировать модуль;
2. получить атрибут;
3. проверить callable;
4. подготовить аргументы;
5. вызвать;
6. проверить результат;
7. преобразовать данные;
8. освободить owned references.

Для каждого шага нужен путь ошибки.

Не следует выполнять:

```c
PyObject_Call(...);
```

и продолжать работу, не проверив `NULL`.

#### Политика Python-исключений

Хост должен решить:

- превратить исключение в ошибку операции;
- записать traceback;
- вернуть структурированную диагностику;
- прекратить выполнение конкретного сценария;
- завершить приложение.

Для Python 3.12+ доступны `PyErr_GetRaisedException` и `PyErr_DisplayException`.

Это полезно и потому, что `PyErr_Print` имеет специальное поведение для `SystemExit`: такой вызов может завершить процесс.

Если хост хочет самостоятельно управлять завершением, нельзя бездумно использовать `PyErr_Print` как универсальный обработчик.

Это не защищает хост от кода, который прямо завершает процесс или вызывает опасный нативный код.

#### Не запускайте интерпретатор на каждый запрос

Постоянные циклы:

```text
initialize
→ один вызов
→ finalize
→ initialize
→ следующий вызов
```

создают сложный жизненный цикл.

Сторонние расширения и внешние библиотеки могут не поддерживать повторный запуск так, как ожидает хост.

Обычно разумнее иметь долгоживущий интерпретатор или выделенный процесс с понятным перезапуском.

#### Завершение

До `Py_FinalizeEx` должны закончиться внешние обращения к Python.

Особенно важно:

- отключить callbacks;
- дождаться worker;
- уничтожить объекты обёрток;
- освободить свои Python-ссылки;
- прекратить использование интерпретаторных дескрипторов.

После завершения нельзя выполнять обычные `Py_DECREF` для оставшихся Python-объектов.

В C++ это влияет на порядок RAII-деструкторов: объекты `py::object` должны уничтожаться до завершения `py::scoped_interpreter`.

Не смешивайте несколько независимых владельцев lifecycle, например ручную инициализацию и автоматически управляющий ею wrapper.

Источники:

- [Initialization configuration](https://docs.python.org/3.15/c-api/init_config.html).
- [Embedding Python](https://docs.python.org/3.15/extending/embedding.html).
- [Interpreter lifecycle](https://docs.python.org/3.15/c-api/interp-lifecycle.html).
- [pybind11: embedding](https://pybind11.readthedocs.io/en/stable/advanced/embedding.html).

### 24.5.2. Окружение, пути импорта и передача данных приложению-хосту

#### Что именно поставляется

Встроенному Python может требоваться:

- runtime Python;
- стандартная библиотека;
- пакет `encodings`;
- нативные стандартные модули;
- пользовательские модули;
- внешние динамические зависимости.

Наличие `libpython` само по себе не означает готовое работающее окружение.

Проверка на машине разработчика легко пропускает неявную зависимость от установленного системного Python.

#### Контролируйте import path

Если путь импорта зависит от текущей директории или произвольной переменной окружения, приложение может импортировать неожиданный модуль.

Хост должен определить:

- доверенные директории;
- версию встроенных пакетов;
- политику пользовательских модулей;
- допустимость `site`;
- влияние переменных окружения;
- поведение при отсутствии модуля.

Для промышленного приложения предпочтительны явно заданные и проверенные пути.

В практикуме путь к модулю добавляется явно для демонстрации. Это не полная схема поставки Python-runtime.

#### Конвертируйте данные на границе

Удобные типы обмена:

- числа;
- строки с явной кодировкой;
- bytes;
- списки и словари ограниченной структуры;
- буферы с контрактом;
- непрозрачные дескрипторы.

Если хост передаёт большой граф объектов, нужно решить, какие элементы копируются, какие разделяются и кто управляет lifetime.

#### Предоставление API хоста

Хост может:

- зарегистрировать built-in module до инициализации;
- импортировать расширение;
- передать callable или объект-контекст;
- предоставить opaque handle с API операций.

Для built-in module используется регистрация через `PyImport_AppendInittab` до запуска интерпретатора.

Дескриптор хостового объекта должен включать понятные правила действительности.

Не стоит передавать адрес как обычное целое и считать это полноценным безопасным интерфейсом.

Если Python хранит дескриптор после закрытия ресурса, последующий вызов должен обнаружить закрытое состояние, а не обращаться к уже освобождённой памяти.

#### Разделяйте ошибки сценария и ошибки хоста

Например:

- некорректные входные данные — ошибка запроса;
- Python `ValueError` — ошибка сценария;
- отсутствие встроенного пакета — ошибка поставки;
- недействительный native handle — нарушение lifecycle;
- повреждение памяти — авария нативного компонента.

Такое разделение помогает понять, что можно повторить, что нужно исправить пользователю, а что требует остановки компонента.

Если нужно исполнять недоверенный код, выбирайте архитектуру с отдельной изоляцией процесса и ресурсов.

Источники:

- [Python initialization configuration](https://docs.python.org/3.15/c-api/init_config.html).
- [Embedding Python in another application](https://docs.python.org/3.15/extending/embedding.html).

```c
#define BATCHFFI_H

#include <stddef.h>

#if defined(_WIN32)
#  if defined(BF_BUILD)
#    define BF_API __declspec(dllexport)
#  else
#    define BF_API __declspec(dllimport)
#  endif
#else
#  define BF_API
#endif

#ifdef __cplusplus
extern "C" {
#endif

enum {
    BF_OK = 0,
    BF_BAD_ARGUMENT = 1,
    BF_NO_MEMORY = 2,
    BF_TOO_LARGE = 3,
    BF_CALLBACK = 4
};

typedef struct bf_buffer {
    unsigned char *data;
    size_t size;
} bf_buffer;

typedef int (*bf_byte_callback)(
    unsigned char value,
    size_t index,
    void *context
);

BF_API unsigned int bf_abi_version(void);
BF_API size_t bf_buffer_sizeof(void);
BF_API size_t bf_buffer_size_offset(void);
BF_API size_t bf_max_input(void);

/*
 * out должен указывать на новый или уже освобождённый bf_buffer.
 *
 * Функция не сохраняет src после возврата.
 * При успехе out принадлежит вызывающему.
 * Освобождение — только через bf_buffer_free.
 *
 * При ошибке корректный out сбрасывается в {NULL, 0}.
 */
BF_API int bf_reverse_copy(
    const unsigned char *src,
    size_t size,
    bf_buffer *out
);

/*
 * Освобождает и обнуляет структуру.
 * NULL допустим.
 * Повторное освобождение той же обнулённой структуры допустимо.
 */

/*
 * Callback вызывается синхронно из вызывающего потока.
 * Указатели и callback не сохраняются.
 *
 * Ненулевой результат callback останавливает обход.
 */
BF_API int bf_visit_bytes(
    const unsigned char *src,
    size_t size,
    bf_byte_callback callback,
    void *context
);

}
#endif

#endif
```

Обратите внимание: присваивание одной структуры `bf_buffer` другой не создаёт второе владение.

После такого копирования два поля `data` будут содержать один адрес. Независимо освобождать обе копии нельзя.

### 24.6.2. Реализация `native/batchffi.c`

```c
#ifndef BF_BUILD
#define BF_BUILD
#endif

#include "batchffi.h"

#include <stdlib.h>

#define BF_MAX_INPUT ((size_t)1024 * 1024)

unsigned int
bf_abi_version(void)
{
    return 1;
}

size_t
bf_buffer_sizeof(void)
{
    return sizeof(bf_buffer);
}

size_t
bf_buffer_size_offset(void)
{
    return offsetof(bf_buffer, size);
}

size_t
bf_max_input(void)
{
    return BF_MAX_INPUT;
}

int
bf_reverse_copy(
    const unsigned char *src,
    size_t size,
    bf_buffer *out
)
{
    unsigned char *result;
    size_t index;

    if (out == NULL) {
        return BF_BAD_ARGUMENT;
    }

    out->data = NULL;
    out->size = 0;

    if (size > BF_MAX_INPUT) {
        return BF_TOO_LARGE;
    }

    if (size != 0 && src == NULL) {
        return BF_BAD_ARGUMENT;
    }

    if (size == 0) {
        return BF_OK;
    }

    result = malloc(size);

    if (result == NULL) {
        return BF_NO_MEMORY;
    }

    for (index = 0; index < size; index++) {
        result[index] = src[size - 1 - index];
    }

    out->data = result;
    out->size = size;

    return BF_OK;
}

void
bf_buffer_free(bf_buffer *buffer)
{
    if (buffer == NULL) {
        return;
    }

    free(buffer->data);
    buffer->data = NULL;
    buffer->size = 0;
}

int
bf_visit_bytes(
    const unsigned char *src,
    size_t size,
    bf_byte_callback callback,
    void *context
)
{
    size_t index;

    if (callback == NULL) {
        return BF_BAD_ARGUMENT;
    }

    if (size > BF_MAX_INPUT) {
        return BF_TOO_LARGE;
    }

    if (size != 0 && src == NULL) {
        return BF_BAD_ARGUMENT;
    }

    for (index = 0; index < size; index++) {
        if (callback(src[index], index, context) != 0) {
            return BF_CALLBACK;
        }
    }

    return BF_OK;
}
```

Свойства реализации:

- исходная память не сохраняется;
- результат выделяется отдельно;
- освобождение выполняет та же библиотека;
- пустой вход не требует выделения;
- callback синхронный;
- глобального изменяемого состояния нет.

Но функция не может проверить, действительно ли ненулевой указатель указывает на `size` доступных байтов. Это обязанность вызывающей стороны.

### 24.6.4. Обёртка `batchffi_wrapper.py`

```python
from __future__ import annotations

import ctypes
import sys
from collections.abc import Callable
from pathlib import Path


class NativeError(RuntimeError):
    def __init__(self, code: int):
        self.code = code
        super().__init__(f"Native operation failed: code={code}")


class Buffer(ctypes.Structure):
    _fields_ = [
        ("data", ctypes.POINTER(ctypes.c_ubyte)),
        ("size", ctypes.c_size_t),
    ]


ByteCallback = ctypes.CFUNCTYPE(
    ctypes.c_int,
    ctypes.c_ubyte,
    ctypes.c_size_t,
    ctypes.c_void_p,
)


class NativeLibrary:
    def __init__(self, path: str | Path):
        resolved = Path(path).resolve(strict=True)
        library = ctypes.CDLL(str(resolved))

        library.bf_abi_version.argtypes = []
        library.bf_abi_version.restype = ctypes.c_uint

        library.bf_buffer_sizeof.argtypes = []
        library.bf_buffer_sizeof.restype = ctypes.c_size_t

        library.bf_buffer_size_offset.argtypes = []
        library.bf_buffer_size_offset.restype = ctypes.c_size_t

        library.bf_max_input.argtypes = []
        library.bf_max_input.restype = ctypes.c_size_t

        library.bf_reverse_copy.argtypes = [
            ctypes.POINTER(ctypes.c_ubyte),
            ctypes.c_size_t,
            ctypes.POINTER(Buffer),
        ]
        library.bf_reverse_copy.restype = ctypes.c_int

        library.bf_buffer_free.argtypes = [
            ctypes.POINTER(Buffer),
        ]
        library.bf_buffer_free.restype = None

        library.bf_visit_bytes.argtypes = [
            ctypes.POINTER(ctypes.c_ubyte),
            ctypes.c_size_t,
            ByteCallback,
            ctypes.c_void_p,
        ]
        library.bf_visit_bytes.restype = ctypes.c_int

        if library.bf_abi_version() != 1:
            raise RuntimeError("Unsupported library ABI")

        if library.bf_buffer_sizeof() != ctypes.sizeof(Buffer):
            raise RuntimeError("bf_buffer size mismatch")

        if library.bf_buffer_size_offset() != Buffer.size.offset:
            raise RuntimeError("bf_buffer layout mismatch")

        self._library = library
        self.max_input = int(library.bf_max_input())

    @staticmethod
    def _check_status(code: int) -> None:
        if code == 0:
            return
        if code == 2:
            raise MemoryError("Native allocation failed")
        raise NativeError(code)

    def _input_copy(self, data: bytes):
        if type(data) is not bytes:
            raise TypeError("Expected exact bytes")

        if len(data) > self.max_input:
            raise ValueError("Input is too large")

        if not data:
            return None

        array_type = ctypes.c_ubyte * len(data)
        return array_type.from_buffer_copy(data)

    def reverse(self, data: bytes) -> bytes:
        source = self._input_copy(data)
        output = Buffer()

        try:
            code = self._library.bf_reverse_copy(
                source,
                len(data),
                ctypes.byref(output),
            )
            self._check_status(code)

            if output.size == 0:
                return b""

            return ctypes.string_at(output.data, output.size)
        finally:
            self._library.bf_buffer_free(ctypes.byref(output))

    def visit(
        self,
        data: bytes,
        visitor: Callable[[int, int], None],
    ) -> None:
        source = self._input_copy(data)

        if not callable(visitor):
            raise TypeError("visitor must be callable")

        failure: BaseException | None = None

        def bridge(value: int, index: int, context) -> int:
            nonlocal failure

            try:
                visitor(index, value)
            except BaseException as exc:
                failure = exc
                return 1

            return 0

        callback = ByteCallback(bridge)

        code = self._library.bf_visit_bytes(
            source,
            len(data),
            callback,
            None,
        )

        if failure is not None:
            raise failure

        self._check_status(code)


def main() -> None:
    if len(sys.argv) != 2:
        raise SystemExit(
            "Usage: python batchffi_wrapper.py PATH_TO_LIBRARY"
        )

    library = NativeLibrary(sys.argv[1])

    payload = b"a\x00bc"

    assert library.reverse(payload) == payload[::-1]
    assert library.reverse(b"") == b""

    visited: list[tuple[int, int]] = []
    library.visit(
        payload,
        lambda index, value: visited.append((index, value)),
    )

    assert visited == list(enumerate(payload))

    def fail(index: int, value: int) -> None:
        if index == 1:
            raise ValueError("callback failed")

    try:
        library.visit(payload, fail)
    except ValueError as exc:
        assert str(exc) == "callback failed"
    else:
        raise AssertionError("Expected callback exception")

    print("Contract checks passed")


if __name__ == "__main__":
    main()
```

Запуск на Linux:

```bash
python batchffi_wrapper.py ./libbatchffi.so
```

#### Что здесь важно

1. Библиотека загружается по явно разрешённому абсолютному пути.
2. У всех функций заданы сигнатуры.
3. Проверяются версия API и часть layout.
4. Вход копируется в закрытый для внешних пользователей ctypes-массив.
5. Этот массив жив до завершения C-вызова.
6. Выходная память всегда освобождается через `finally`.
7. `string_at` получает явную длину.
8. Callback остаётся жив в течение синхронной операции.
9. Исключение callback передаётся через отдельный Python-контекст.

Здесь сознательно есть копирование входа и результата. Это упрощает контракт.

Убирать копирование нужно после измерений и проектирования lifetime, а не только ради слова zero-copy.

Callback на каждый байт обычно слишком дорог для вычислительного интерфейса. Он добавлен для демонстрации обратного вызова и передачи ошибки.

### 24.6.5. CFFI ABI mode: `ffi_demo.py`

```python
from __future__ import annotations

import sys
from pathlib import Path

from cffi import FFI


CDEF = """
typedef struct bf_buffer {
    unsigned char *data;
    size_t size;
} bf_buffer;

unsigned int bf_abi_version(void);
size_t bf_max_input(void);

int bf_reverse_copy(
    const unsigned char *src,
    size_t size,
    bf_buffer *out
);

void bf_buffer_free(bf_buffer *buffer);
"""


def reverse(ffi, library, data: bytes) -> bytes:
    if type(data) is not bytes:
        raise TypeError("Expected exact bytes")

    if len(data) > library.bf_max_input():
        raise ValueError("Input is too large")

    def invoke(source) -> bytes:
        output = ffi.new("bf_buffer *")

        try:
            code = library.bf_reverse_copy(
                source,
                len(data),
                output,
            )

            if code == 2:
                raise MemoryError("Native allocation failed")

            if code != 0:
                raise RuntimeError(f"Native error: {code}")

            if output.size == 0:
                return b""

            return bytes(ffi.buffer(output.data, output.size))
        finally:
            library.bf_buffer_free(output)

    if not data:
        return invoke(ffi.NULL)

    with ffi.from_buffer("const unsigned char[]", data) as source:
        return invoke(source)


def main() -> None:
    if len(sys.argv) != 2:
        raise SystemExit("Usage: python ffi_demo.py PATH_TO_LIBRARY")

    ffi = FFI()
    ffi.cdef(CDEF)

    path = Path(sys.argv[1]).resolve(strict=True)
    library = ffi.dlopen(str(path))

    if library.bf_abi_version() != 1:
        raise RuntimeError("Unsupported library ABI")

    assert reverse(ffi, library, b"a\x00bc") == b"cb\x00a"
    assert reverse(ffi, library, b"") == b""

    print("CFFI contract checks passed")


if __name__ == "__main__":
    main()
```

Здесь вход передаётся через `from_buffer` без промежуточного массива.

Безопасность основана на узком контракте:

- принимается точный `bytes`;
- библиотека только читает вход;
- библиотека не сохраняет указатель;
- cdata жив до завершения вызова.

Результат копируется в Python `bytes`, затем C-память освобождается.

### 24.7.1. `native/batchnative.c`

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>

#define BATCH_MAX_INPUT ((Py_ssize_t)1024 * 1024)

typedef struct {
    PyObject *InputTooLargeError;
} ModuleState;

static ModuleState *
get_state(PyObject *module)
{
    return (ModuleState *)PyModule_GetState(module);
}

static PyObject *
sum_bytes(PyObject *module, PyObject *argument)
{
    char *raw = NULL;
    Py_ssize_t length = 0;
    unsigned long long total = 0;
    Py_ssize_t index;
    ModuleState *state;

    if (!PyBytes_CheckExact(argument)) {
        PyErr_SetString(
            PyExc_TypeError,
            "sum_bytes expects exact bytes"
        );
        return NULL;
    }

    if (PyBytes_AsStringAndSize(argument, &raw, &length) < 0) {
        return NULL;
    }

    if (length > BATCH_MAX_INPUT) {
        state = get_state(module);

        if (state == NULL) {
            return NULL;
        }

        PyErr_SetString(
            state->InputTooLargeError,
            "input exceeds one MiB"
        );
        return NULL;
    }

    const unsigned char *data = (const unsigned char *)raw;

    Py_BEGIN_ALLOW_THREADS

    for (index = 0; index < length; index++) {
        total += data[index];
    }

    Py_END_ALLOW_THREADS

    return PyLong_FromUnsignedLongLong(total);
}

static PyMethodDef module_methods[] = {
    {
        "sum_bytes",
        sum_bytes,
        METH_O,
        "Return the sum of bytes; input is limited to one MiB."
    },
    {NULL, NULL, 0, NULL}
};

static int
module_exec(PyObject *module)
{
    ModuleState *state = get_state(module);
    PyObject *error;

    if (state == NULL) {
        return -1;
    }

    if (state->InputTooLargeError != NULL) {
        return 0;
    }

    error = PyErr_NewException(
        "batchnative.InputTooLargeError",
        PyExc_ValueError,
        NULL
    );

    if (error == NULL) {
        return -1;
    }

    if (
        PyModule_AddObjectRef(
            module,
            "InputTooLargeError",
            error
        ) < 0
    ) {
        Py_DECREF(error);
        return -1;
    }

    state->InputTooLargeError = error;
    return 0;
}

static int
module_traverse(PyObject *module, visitproc visit, void *arg)
{
    ModuleState *state = get_state(module);

    if (state != NULL) {
        Py_VISIT(state->InputTooLargeError);
    }

    return 0;
}

static int
module_clear(PyObject *module)
{
    ModuleState *state = get_state(module);

    if (state != NULL) {
        Py_CLEAR(state->InputTooLargeError);
    }

    return 0;
}

static void
module_free(void *module)
{
    (void)module_clear((PyObject *)module);
}

static PyModuleDef_Slot module_slots[] = {
    {Py_mod_exec, module_exec},

#if PY_VERSION_HEX >= 0x030C0000
    {
        Py_mod_multiple_interpreters,
        Py_MOD_PER_INTERPRETER_GIL_SUPPORTED
    },
#endif

#if PY_VERSION_HEX >= 0x030D0000
    {Py_mod_gil, Py_MOD_GIL_NOT_USED},
#endif

    {0, NULL}
};

static struct PyModuleDef module_definition = {
    PyModuleDef_HEAD_INIT,
    .m_name = "batchnative",
    .m_doc = "A small native extension with per-module state.",
    .m_size = sizeof(ModuleState),
    .m_methods = module_methods,
    .m_slots = module_slots,
    .m_traverse = module_traverse,
    .m_clear = module_clear,
    .m_free = module_free
};

PyMODINIT_FUNC
PyInit_batchnative(void)
{
    return PyModuleDef_Init(&module_definition);
}
```

### 24.7.2. Почему контракт допускает чтение без GIL

Вход — точный `bytes`.

На время вызова аргумент остаётся живым. Содержимое `bytes` по Python-контракту неизменяемо.

В вычислительном участке используются:

- локальный указатель;
- локальная длина;
- локальный аккумулятор;
- чтение неизменяемых байтов.

Там нет Python API.

Лимит входа также ограничивает сумму:

```text
1 048 576 × 255 = 267 386 880
```

Она помещается в используемый `unsigned long long`.

Если убрать лимит, арифметику и максимальную длину нужно анализировать заново.

Объявления поддержки subinterpreters и работы без GIL основаны на этих свойствах конкретной реализации. При добавлении кэша, внешней библиотеки или фонового worker анализ нужно повторить.

### 24.7.3. Владение исключением

`PyErr_NewException` возвращает owned reference.

`PyModule_AddObjectRef` создаёт ссылку в словаре модуля, не забирая owned reference вызывающего.

После успешного добавления:

- одна ссылка принадлежит module state;
- другая удерживается атрибутом модуля.

`module_clear` освобождает ссылку состояния.

Даже если пользователь изменит атрибут:

```python
batchnative.InputTooLargeError = RuntimeError
```

внутреннее состояние продолжит хранить исходный класс.

Это свойство нужно учитывать при проектировании публичного интерфейса.

### 24.7.6. Тесты `test_batchnative.py`

```python
import unittest
from concurrent.futures import ThreadPoolExecutor

import batchnative


class SumBytesTests(unittest.TestCase):
    def test_empty(self):
        self.assertEqual(batchnative.sum_bytes(b""), 0)

    def test_binary_data(self):
        payload = bytes(range(256)) * 16

        self.assertEqual(
            batchnative.sum_bytes(payload),
            sum(payload),
        )

    def test_embedded_zero(self):
        self.assertEqual(
            batchnative.sum_bytes(b"a\x00b"),
            ord("a") + ord("b"),
        )

    def test_rejects_mutable_input(self):
        with self.assertRaises(TypeError):
            batchnative.sum_bytes(bytearray(b"abc"))

    def test_rejects_text(self):
        with self.assertRaises(TypeError):
            batchnative.sum_bytes("abc")

    def test_rejects_oversized_input(self):
        payload = b"x" * (1024 * 1024 + 1)

        with self.assertRaises(batchnative.InputTooLargeError):
            batchnative.sum_bytes(payload)

    def test_parallel_calls(self):
        payload = bytes(range(256)) * 4096
        expected = sum(payload)

        with ThreadPoolExecutor(max_workers=4) as executor:
            results = list(
                executor.map(
                    batchnative.sum_bytes,
                    [payload] * 32,
                )
            )

        self.assertEqual(results, [expected] * 32)


if __name__ == "__main__":
    unittest.main()
```

Эти тесты проверяют контракт и воспроизводимый параллельный сценарий.

Они не доказывают отсутствие всех гонок.

### 24.7.7. Установка собранного wheel

В каталоге `dist` могут лежать файлы от прежних сборок. Перед выбором wheel нужно убедиться, что используется актуальный артефакт для текущего интерпретатора.

Пример для каталога, в котором находится ровно один нужный wheel:

```python
from pathlib import Path
import subprocess
import sys

wheels = list(Path("dist").glob("*.whl"))

if len(wheels) != 1:
    raise SystemExit("Expected exactly one wheel")

subprocess.run(
    [
        sys.executable,
        "-m",
        "pip",
        "install",
        "--force-reinstall",
        str(wheels[0]),
    ],
    check=True,
)
```

Затем выполните тесты из директории вне исходного проекта, используя установленный wheel.

Отдельно проверьте:

- обычную сборку CPython;
- free-threaded сборку;
- фактическое состояние GIL после импорта;
- несколько интерпретаторов, если эта поддержка заявляется;
- установку на чистой целевой ОС.

Для проверки subinterpreters используйте API и инструменты, соответствующие конкретной версии Python. Внутренние тестовые модули не следует представлять как стабильный переносимый интерфейс приложения.

```python
def transform(value: int) -> int:
```

### 24.8.2. `embed_demo.c`

```c
#define PY_SSIZE_T_CLEAN
#include <Python.h>

#include <stdio.h>

static void
display_python_error(void)
{
    PyObject *exception = PyErr_GetRaisedException();

    if (exception == NULL) {
        fprintf(stderr, "Python operation failed without an exception\n");
        return;
    }

    PyErr_DisplayException(exception);
    Py_DECREF(exception);
}

static int
run_policy(const char *policy_directory)
{
    PyObject *directory = NULL;
    PyObject *module = NULL;
    PyObject *function = NULL;
    PyObject *argument = NULL;
    PyObject *result = NULL;

    int return_code = 1;
    long output;

    directory = PyUnicode_DecodeFSDefault(policy_directory);

    if (directory == NULL) {
        goto done;
    }

    /*
     * Borrowed reference.
     * В этом примере другие потоки Python ещё не запущены.
     */
    PyObject *path = PySys_GetObject("path");

    if (path == NULL || !PyList_Check(path)) {
        PyErr_SetString(
            PyExc_RuntimeError,
            "sys.path is unavailable or invalid"
        );
        goto done;
    }

    if (PyList_Append(path, directory) < 0) {
        goto done;
    }

    module = PyImport_ImportModule("policy");

    if (module == NULL) {
        goto done;
    }

    function = PyObject_GetAttrString(module, "transform");

    if (function == NULL) {
        goto done;
    }

    if (!PyCallable_Check(function)) {
        PyErr_SetString(
            PyExc_TypeError,
            "policy.transform must be callable"
        );
        goto done;
    }

    argument = PyLong_FromLong(7);

    if (argument == NULL) {
        goto done;
    }

    result = PyObject_CallOneArg(function, argument);

    if (result == NULL) {
        goto done;
    }

    output = PyLong_AsLong(result);

    if (output == -1 && PyErr_Occurred()) {
        goto done;
    }

    printf("Result: %ld\n", output);
    return_code = 0;

done:
    if (return_code != 0) {
        display_python_error();
    }

    Py_XDECREF(result);
    Py_XDECREF(argument);
    Py_XDECREF(function);
    Py_XDECREF(module);
    Py_XDECREF(directory);

    return return_code;
}

int
main(int argc, char **argv)
{
    PyConfig config;
    PyStatus status;
    int return_code;

    if (argc != 2) {
        fprintf(
            stderr,
            "Usage: embed_demo TRUSTED_POLICY_DIRECTORY\n"
        );
        return 2;
    }

    PyConfig_InitIsolatedConfig(&config);

    config.parse_argv = 0;
    config.use_environment = 0;
    config.site_import = 0;

    status = PyConfig_SetBytesString(
        &config,
        &config.program_name,
        argv[0]
    );

    if (PyStatus_Exception(status)) {
        goto initialization_failed;
    }

    status = PyConfig_SetBytesArgv(&config, argc, argv);

    if (PyStatus_Exception(status)) {
        goto initialization_failed;
    }

    status = Py_InitializeFromConfig(&config);

    if (PyStatus_Exception(status)) {
        goto initialization_failed;
    }

    PyConfig_Clear(&config);

    return_code = run_policy(argv[1]);

    /*
     * В этом примере все собственные Python-ссылки
     * освобождены внутри run_policy.
     */
    if (Py_FinalizeEx() < 0) {
        return_code = 120;
    }

    return return_code;

initialization_failed:
    if (PyStatus_IsExit(status)) {
        return_code = status.exitcode;
    } else {
        fprintf(
            stderr,
            "Python initialization failed: %s\n",
            status.err_msg != NULL
                ? status.err_msg
                : "unknown error"
        );
        return_code = 1;
    }

    PyConfig_Clear(&config);
    return return_code;
}
```

### 24.8.5. Что нужно добавить в реальный хост

#### Контроль поставки

Пример рассчитывает на доступное Python-окружение, которое соответствует используемой установке.

Для самостоятельной поставки требуется отдельно определить расположение:

- стандартной библиотеки;
- `encodings`;
- расширений;
- пользовательских пакетов;
- динамических зависимостей.

#### Контроль путей

`argv[1]` должен поступать от доверенного владельца приложения.

В реальном продукте нужны проверенные абсолютные пути и политика загрузки модулей.

#### Протокол остановки

Если появятся callbacks или worker:

1. прекратить приём операций;
2. отменить или завершить активные операции;
3. дождаться потоков;
4. снять регистрации callbacks;
5. освободить объекты;
6. завершить интерпретатор.

#### Политика исключений

Вместо печати в stderr хост может вернуть:

```text
тип ошибки
сообщение
контекст операции
идентификатор сценария
traceback
```

Но извлечение и сериализация диагностики тоже требуют Python API и должны выполняться до завершения интерпретатора.

### 24.9.1. Матрица контрактов

| Область | Примеры проверок |
|---|---|
| Пустые данные | Нулевая длина, `NULL` там, где допустим |
| Бинарные данные | Встроенный `NUL`, все значения байта |

| Завершение | Активные задачи, callbacks во время shutdown |

### 24.9.2. Проверяйте инварианты владения

Для каждого ресурса можно составить таблицу:

| Ресурс | Где создаётся | Кто владелец | Где освобождается |
|---|---|---|---|
| Вход ctypes | `_input_copy` | Локальная переменная | После завершения вызова |
| Результат C | `bf_reverse_copy` | Python-обёртка | `bf_buffer_free` в `finally` |
| Callback | `ByteCallback` | Локальная переменная | После синхронного возврата |
| Класс ошибки | `module_exec` | Module state и модуль | Очистка модуля |
| Импортированный модуль хоста | `PyImport_ImportModule` | `run_policy` | Путь `done` |

Если для строки нельзя заполнить владельца или освобождение, контракт ещё не закончен.

### 24.9.3. Разделяйте уровни тестирования

1. **Нативное ядро.** Проверка без Python.
2. **Обёртка.** Типы, исключения, lifetime.
3. **Конкурентность.** Совместный доступ и остановка.
4. **Packaging.** Содержимое wheel и зависимости.
5. **Установка.** Чистая целевая среда.
6. **Производительность.** Полный полезный сценарий.

Так проще определить, где возникла ошибка.

### 24.9.4. Наблюдаемость

- версию Python;

- архитектуру;

## 24.10. Типичные ошибки

### «Раз GIL есть, C-библиотека защищена»

Вызов может освобождать GIL, а библиотека может создавать собственные потоки.

Защищённость проверяется по реальному ресурсу и контракту библиотеки.

### «Я сохранил указатель — значит, сохранил объект»

Сырой адрес обычно не удерживает владельца.

Нужна отдельная сильная ссылка или другой механизм lifetime.

### «Readonly memoryview делает данные immutable»

Она ограничивает запись через представление.

Исходная память может изменяться через другой alias.

### «`cast` проверяет правильность типа»

Он меняет интерпретацию адреса.

Корректность адреса, длины, выравнивания и lifetime остаётся вашей обязанностью.

### «После `free` достаточно обнулить любую копию указателя»

Обнуление одной переменной не обнуляет другие aliases.

Они продолжают содержать недействительный адрес.

### «Callback можно освободить сразу после unregister»

Только если контракт гарантирует завершение всех активных вызовов.

### «Модуль импортируется в free-threaded Python, значит GIL выключен»

Импорт неподготовленного расширения может включить GIL.

Нужно проверять фактическое состояние.

### «Поддержка subinterpreters равна поддержке free-threading»

Это разные свойства.

Расширение может удовлетворять одному набору требований и нарушать другой.

### «Для `abi3` достаточно переименовать wheel»

Tag должен соответствовать реально использованным API и настройкам сборки.

### «Sanitizer ничего не нашёл, значит ошибок нет»

Инструмент обнаруживает определённые ошибки на выполненных путях и при конкретной конфигурации.

### «Segfault можно обработать как обычное исключение»

Повреждение памяти может сделать состояние процесса недостоверным.

Диагностический обработчик не восстанавливает корректность программы.

### «Embedding означает безопасную среду для любого сценария»

Python внутри хоста работает с полномочиями процесса в рамках доступных механизмов.

Для недоверенного кода требуется другая архитектура изоляции.

17. Почему ASan-расширению нужна согласованная runtime-конфигурация?
18. Почему `PyErr_Print` требует осторожности в хостовом приложении?
19. Что должно завершиться до `Py_FinalizeEx`?
20. Почему isolated configuration не является security sandbox?

### Краткие ориентиры для ответов

1. Стоимость переходов, преобразований и создания объектов может преобладать.
2. Живой объект может переместить внутреннюю память.
3. Автоматическое преобразование может скрыть адрес, нужный деструктору.
4. Явная сильная ссылка до завершения всех возможных вызовов.
5. Исключения Python не являются частью C ABI.
6. Различается обязанность удержания и освобождения ссылки.
7. Уничтожение объекта может выполнить пользовательский код.
8. Между чтением borrowed reference и удержанием объект может исчезнуть.
9. Другой alias может записывать в ту же память.
10. Нельзя выполнять обычные Python API-операции.
11. Поток всё равно должен быть связан с правильным интерпретатором.
12. Состояние связано с экземпляром модуля и его lifecycle.
13. Изоляция интерпретаторов и конкурентность внутри интерпретатора — разные задачи.
14. ABI Python не заменяет платформенный ABI.
15. Появился `abi3t` с собственными требованиями совместимости.
16. Иначе проверяется случайная локальная копия.
17. Инструментированному коду нужен корректно подключённый sanitizer runtime.
18. Для `SystemExit` возможно завершение процесса.
19. Внешние вызовы, callbacks, worker и использование Python-объектов.
20. Конфигурация запуска не изолирует полномочия процесса.

## 24.13. Что должно остаться после изучения главы

Перед написанием нативной интеграции полезно подготовить небольшой документ с ответами:

- Где проходит граница процесса?
- Какие типы пересекают границу?
- Какие данные копируются?
- Кто владеет каждым ресурсом?
- Когда заканчивается заимствование?
- Может ли адрес переместиться?
- Кто может изменять память?
- Как передаётся ошибка?
- Из каких потоков разрешены вызовы?
- Как останавливаются callbacks?
- Как завершается интерпретатор?
- Для каких Python, ABI и платформ поставляется артефакт?
- Как всё это проверяется?

Нативная интеграция становится управляемой, когда эти условия выражены в интерфейсе, реализации и проверках.
