# 14. Многопоточность и многопроцессность

Конкурентная программа должна не только выполнять несколько работ, но и владеть их временем жизни, передавать ошибки, ограничивать очередь и освобождать ресурсы. Ускорение имеет смысл, если сохранены корректность, предсказуемое потребление памяти и понятная остановка.

В этой главе разберём потоки, процессы, пулы и несколько интерпретаторов. Отдельно рассмотрим обычный CPython с GIL и free-threaded-сборки. В конце находится практический проект: ограниченная параллельная обработка JSONL-файлов с детерминированной выдачей и публикацией результата только после успешного завершения.

**Версии и запуск.** Базовые примеры рассчитаны на Python 3.12+. Возможности 3.13 и 3.14 отмечены комментариями `# Python 3.13+` и `# Python 3.14+`. Каждый учебный Python-блок самодостаточен; сохраняйте его в отдельный `example.py` и запускайте `python example.py`. Примеры с процессами особенно важно запускать как обычный импортируемый файл, а не вставлять в REPL.

Учебные `assert` фиксируют ожидаемый результат. В практическом проекте runtime-валидация использует исключения и не зависит от `python -O`. В примерах нет намеренно бесконечного deadlock; опасные случаи объясняются без зависания рабочего процесса.

Проверка таймаута ожидания и проверка принудительного завершения — разные задачи. Даже программа, которая заметила дедлайн, может ещё ждать очистки выполняющегося I/O. Там, где нужен жёсткий предел времени, требуется отдельная граница изоляции и явная политика прерывания.

## Выбор модели конкурентного выполнения

### Конкурентность vs параллелизм

**Конкурентность** — несколько работ находятся в процессе выполнения за пересекающиеся промежутки времени. **Параллелизм** — несколько работ физически исполняются одновременно, например на разных ядрах.

Один поток event loop может конкурентно обслуживать много сетевых операций без параллельного исполнения Python-кода. Несколько процессов могут одновременно считать на разных ядрах. Потоки одного интерпретатора могут перекрывать I/O, даже когда GIL ограничивает исполнение Python-кода.

| Свойство | Пример |
| --- | --- |
| Перекрытие ожиданий | Пока один запрос ждёт сеть, другой обрабатывает ответ |
| Одновременное вычисление | Два worker-процесса считают независимые блоки |
| Координация | Producer не выдаёт больше работы, чем система удерживает |
| Владение | Родитель останавливает и дожидается созданных workers |

Не делайте порядок результатов неявным. Порядок подачи, начала, завершения и публикации — четыре разных порядка. Бизнес-контракт может требовать только один из них.

### CPU-bound vs I/O-bound

CPU-bound-задача тратит большую часть времени на вычисления; I/O-bound — на ожидание диска, сети или внешней системы. Конкретный конвейер может менять характер нагрузки на разных этапах.

| Нагрузка | С чего начать |
| --- | --- |
| Много блокирующих сетевых запросов | Ограниченный ThreadPoolExecutor и timeouts транспорта |
| Pure Python CPU-цикл в обычном CPython | ProcessPoolExecutor или отдельные интерпретаторы |
| Нативная библиотека, освобождающая GIL | Измерить потоки и внутреннюю параллельность библиотеки |
| Async-библиотека с большим числом соединений | Asyncio и ограниченная конкурентность |
| Pure Python в free-threaded CPython | Измерить потоки при реально отключённом GIL |

«Запрос к БД» может ожидать сеть, а затем тратить CPU на декодирование миллионов строк. «Хеширование» часто выполняется нативным кодом, который при подходящих условиях освобождает GIL. Название операции не заменяет измерение.

Сначала измерьте последовательную реализацию: время, CPU, память, размер данных и долю ожидания. Для DE дополнительно учитывайте диск, DB connection pool, лимиты API и количество внутренних потоков NumPy/BLAS.

### Потоки, процессы и несколько интерпретаторов

| Модель | Изменяемое состояние | Изоляция отказа | Передача данных |
| --- | --- | --- | --- |
| Потоки одного интерпретатора | Обычно общая память | Падение процесса затрагивает всех | Ссылки на объекты; нужна синхронизация |
| Отдельные процессы | Раздельные адресные пространства | Лучше на уровне процесса | IPC, сериализация, shared memory |
| Интерпретаторы одного процесса | Python-состояние в основном изолировано | Общий процесс остаётся общей границей отказа | Копирование, специальные каналы и разделяемые буферы |

Subinterpreter сам по себе не создаёт поток. Для одновременной работы нескольких интерпретаторов нужны соответствующие потоки или executor. У каждого изолированного интерпретатора обычной сборки может быть собственный GIL; это отличается от одного free-threaded-интерпретатора с общей памятью.

Ни поток, ни subinterpreter не являются безопасной sandbox для недоверенного нативного кода. Даже отдельный процесс без ограничений ОС не является полной системой изоляции.

### Стоимость создания исполнителей

У executor есть затраты на создание workers, импорт модулей, инициализацию соединений и закрытие. Для маленьких задач эти расходы могут быть больше полезной работы.

```python
from concurrent.futures import ThreadPoolExecutor


def square(value: int) -> int:
    return value * value


values = list(range(20))
# Один пул на связанную партию, а не новый пул на каждый элемент.
with ThreadPoolExecutor(max_workers=2) as pool:
    actual = list(pool.map(square, values))
assert actual == [value * value for value in values]
```

В этом примере не обещается ускорение: операция слишком мала для содержательного benchmark. Его цель — показать lifecycle.

Долгоживущий пул амортизирует запуск, но сохраняет imports, thread-local state и ресурсы между задачами. Нужны понятные границы переиспользования, health checks и обработка сломанного worker. Глобальный пул, созданный при импорте библиотеки, затрудняет управление жизненным циклом.

### Стоимость обмена данными

При процессном выполнении нужно передать аргументы и вернуть результат. Время включает сериализацию, копирование, IPC и десериализацию. Отправка большого DataFrame может оказаться дороже вычисления над ним.

```python
import pickle

payload = list(range(1000))
encoded = pickle.dumps(payload, protocol=pickle.HIGHEST_PROTOCOL)
decoded = pickle.loads(encoded)
assert decoded == payload
assert decoded is not payload
print({"items": len(payload), "serialized_bytes": len(encoded)})
```

Здесь pickle используется только для собственных данных. Десериализация недоверенного pickle может выполнять код; это не транспортный формат для произвольного внешнего ввода.

Часто выгоднее передать путь к локальному файлу, диапазон индексов или имя shared memory, чем копировать весь массив. Такой descriptor требует согласованного срока жизни данных и доступности ресурса каждому worker.

Ограничение числа Future не ограничивает байты автоматически. Учитывайте размер аргументов, результатов, промежуточных копий и reorder buffer.

### Влияние GIL — ссылка на «Фундамент»

Подробная объектная модель и GIL относятся к главе «Фундамент». Для выбора исполнителя важны три разных режима:

- обычный CPython: один GIL ограничивает одновременное исполнение Python-кода в одном интерпретаторе;
- несколько изолированных интерпретаторов: отдельное Python-состояние и собственные GIL;
- free-threaded CPython: потоки одного интерпретатора могут выполнять Python-код без общего GIL.

С Python 3.13 существует отдельная free-threaded-сборка; для 3.14 этот вариант получил поддерживаемый, но по-прежнему необязательный статус. Обычная сборка автоматически не становится сборкой без GIL.

```python
import sys
import sysconfig

query = getattr(sys, "_is_gil_enabled", None)
print(
    {
        "python": sys.version.split()[0],
        "free_threaded_build": sysconfig.get_config_var("Py_GIL_DISABLED") == 1,
        "gil_enabled": query() if query is not None else "API unavailable",
    }
)
```

Важна проверка **после импорта зависимостей**: несовместимое нативное расширение может повторно включить GIL в free-threaded-процессе. Есть и явные runtime-настройки `PYTHON_GIL` и `-X gil`.

Внутренние блокировки dict/list/set не превращают последовательность «проверить → изменить два поля» в транзакцию. Свои инварианты защищайте явно в любом режиме. Free-threading не отменяет contention, стоимость памяти, ограничения I/O и необходимость измерять реальное ускорение.

## Многопоточность — threading

### Создание и запуск потоков

Создание `Thread` ещё не запускает работу. `start` создаёт исполнение в отдельном потоке; прямой вызов `run` — обычный вызов в текущем потоке.

```python
from queue import Queue
from threading import Thread

results: Queue[str] = Queue()


def work(name: str) -> None:
    results.put(name.upper())


threads = [
    Thread(target=work, args=(name,), name=f"worker-{name}") for name in ("a", "b")
]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join(timeout=3)
    assert not thread.is_alive()
assert sorted(results.get_nowait() for _ in threads) == ["A", "B"]
```

Один экземпляр Thread можно запустить только один раз. Передавайте `target=work`, а не `target=work()`, если функция должна выполниться в worker.

Для множества коротких задач обычно удобнее ограниченный executor, чем отдельный поток на каждую запись. Имя потока помогает диагностике, но не является уникальным бизнес-идентификатором.

### join

`join` ждёт завершения потока и возвращает `None`. После ограниченного ожидания нужно проверить `is_alive`.

```python
from threading import Event, Thread

ready = Event()
release = Event()


def work() -> None:
    ready.set()
    release.wait()


thread = Thread(target=work)
thread.start()
try:
    assert ready.wait(3)
    thread.join(timeout=0)
    assert thread.is_alive()
finally:
    release.set()
    thread.join(timeout=3)
assert not thread.is_alive()
```

Нельзя join текущего потока или ещё не запущенного Thread: это `RuntimeError`. Возвращённое target-значение через join не передаётся. Для результата используйте очередь, управляемый объект или Future.

Timeout join прекращает ожидание вызывающего кода, а не работу worker. Нужен отдельный протокол остановки.

### Daemon threads

Daemon-флаг определяет, удерживает ли поток процесс от завершения. Он не означает «безопасная фоновая служба», не уменьшает приоритет и не выполняет автоматический commit.

Когда остаются только daemon-потоки, интерпретатор может завершить процесс без их нормальной уборки. `finally`, flush, закрытие транзакции и публикация файла не гарантированы.

Поэтому важные workers обычно недемонные: родитель прекращает приём работ, подаёт сигнал, разблокирует ожидания и дожидается завершения. `daemon` задаётся до `start`; по умолчанию он наследуется от создающего потока.

Не решайте зависший shutdown превращением потока в daemon: сначала выясните, какое ожидание нельзя завершить.

### Обработка ошибок потоков

Необработанное исключение target не возникает автоматически в родителе при join. Его нужно передать и проверить.

```python
from queue import Empty, Queue
from threading import Thread

errors: Queue[Exception] = Queue()


def work() -> None:
    try:
        raise ValueError("invalid record")
    except Exception as error:
        errors.put(error)


thread = Thread(target=work)
thread.start()
thread.join(timeout=3)
assert not thread.is_alive()
try:
    error = errors.get_nowait()
except Empty:
    raise AssertionError("Ошибка worker потеряна")
assert isinstance(error, ValueError)
assert str(error) == "invalid record"
```

Для production-обработки родитель обычно переводит ошибку в остановку партии или явный результат ошибки. Future делает перенос исключения удобнее через `result`.

Хранение исключения вместе с traceback может удерживать большие входные объекты и стек. Не накапливайте бесконечный список ошибок. Внешняя диагностика должна содержать ограниченные структурированные поля.

### Общее изменяемое состояние

Потоки видят ссылки на одни объекты. Простой способ уменьшить сложность — назначить владельца состоянию и передавать сообщения.

```python
from queue import Queue
from threading import Thread

queue: Queue[tuple[str, int]] = Queue()


def produce(name: str, value: int) -> None:
    queue.put((name, value))


threads = [
    Thread(target=produce, args=("orders", 3)),
    Thread(target=produce, args=("users", 2)),
]
for thread in threads:
    thread.start()
totals: dict[str, int] = {}
for _ in threads:
    name, value = queue.get(timeout=3)
    totals[name] = totals.get(name, 0) + value
for thread in threads:
    thread.join(timeout=3)
    assert not thread.is_alive()
assert totals == {"orders": 3, "users": 2}
```

Словарь здесь меняет только родитель. Очередь защищает передачу, но если передать изменяемый dict, producer и consumer получат один объект. Не изменяйте его одновременно после передачи без отдельного соглашения.

Неизменяемая структура упрощает обмен, однако tuple с изменяемым списком внутри не становится глубоко неизменяемым.

### Гонки данных

Race condition возникает, когда корректность зависит от неустановленного порядка действий. Проверить существование ключа, а затем вставить значение — уже составная операция.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Barrier

state = {"count": 0}
both_read = Barrier(2, timeout=3)


def unsafe_increment() -> None:
    previous = state["count"]
    both_read.wait()
    state["count"] = previous + 1


with ThreadPoolExecutor(max_workers=2) as pool:
    futures = [pool.submit(unsafe_increment) for _ in range(2)]
    for future in futures:
        future.result(timeout=5)
assert state["count"] == 1  # Намеренно воспроизведённая потеря обновления.
```

Барьер задаёт конкретный плохой interleaving без надежды на случайный `sleep`. Проверка демонстрирует дефект; правильный счётчик должен дать два.

Стабильно зелёный стресс-тест не доказывает отсутствие гонки. Формулируйте инвариант, определяйте владельца и критическую секцию, затем тестируйте существенные расписания.

### Lock

Lock защищает целую критическую секцию, а не только отдельную строку присваивания.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

lock = Lock()
state = {"count": 0}


def increment_many() -> None:
    for _ in range(1000):
        with lock:
            state["count"] += 1


with ThreadPoolExecutor(max_workers=2) as pool:
    futures = [pool.submit(increment_many) for _ in range(2)]
    for future in futures:
        future.result(timeout=5)
assert state["count"] == 2000
```

`with lock` освобождает блокировку и при исключении. Самая важная часть — все участники используют один и тот же lock для одного инварианта.

Обычный Lock нерекурсивен: повторный захват тем же потоком может заблокировать его. Не рассчитывайте на fairness или конкретный порядок пробуждения ожидающих потоков.

С Python 3.13 `threading.Lock` оформлен как класс; в более ранних версиях это был factory-интерфейс. Для прикладной синхронизации обычно не нужно зависеть от этой детали типа.

### RLock

RLock допускает повторный захват тем же потоком и хранит глубину. Освободить его нужно столько же раз, сколько он был успешно захвачен.

```python
from threading import RLock

lock = RLock()
state = {"value": 0}


def add_one() -> None:
    with lock:
        state["value"] += 1


def add_two() -> None:
    with lock:
        add_one()
        add_one()


add_two()
assert state["value"] == 2
```

RLock полезен при действительно реентерабельном интерфейсе, но не исправляет конфликт порядка двух разных locks. Иногда лучше иметь приватный метод «lock уже захвачен», чем прятать архитектурную путаницу за рекурсивностью.

### Condition

Condition связывает ожидание с предикатом общего состояния. Предикат проверяется под тем же lock, который защищает его изменение.

```python
from threading import Condition, Thread

condition = Condition()
state: dict[str, int | None] = {"value": None}


def produce() -> None:
    with condition:
        state["value"] = 42
        condition.notify_all()


thread = Thread(target=produce)
thread.start()
try:
    with condition:
        ready = condition.wait_for(lambda: state["value"] is not None, timeout=3)
        assert ready
        result = state["value"]
finally:
    thread.join(timeout=3)
assert not thread.is_alive()
assert result == 42
```

`wait` освобождает связанный lock на время ожидания и снова захватывает его перед возвратом. `notify` не передаёт lock немедленно и не гарантирует, что предикат всё ещё истинен для конкретного consumer.

Проверяйте предикат в цикле или через `wait_for`, а не одним `if`. Пробуждение может быть ложным или предназначенное состояние уже забрал другой поток.

### Event

Event — флаг готовности или остановки. Он хранит состояние, поэтому set до wait не теряется.

```python
from threading import Event, Thread

ready = Event()
stop = Event()
finished = Event()


def worker() -> None:
    ready.set()
    try:
        stop.wait()
    finally:
        finished.set()


thread = Thread(target=worker)
thread.start()
try:
    assert ready.wait(3)
finally:
    stop.set()
    thread.join(timeout=3)
assert finished.is_set()
assert not thread.is_alive()
```

Event не является счётчиком сообщений: несколько set до clear не дают несколько независимых событий. Для передачи каждого элемента используйте очередь.

Если после clear возможен новый цикл, определите фазы протокола. Иначе старый сигнал может быть принят за новый или новый — случайно сброшен.

### Semaphore

Semaphore ограничивает число одновременных владельцев ресурса. BoundedSemaphore дополнительно обнаруживает release сверх начального лимита.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import BoundedSemaphore, Lock

gate = BoundedSemaphore(2)
metrics_lock = Lock()
metrics = {"active": 0, "peak": 0}


def work(value: int) -> int:
    with gate:
        with metrics_lock:
            metrics["active"] += 1
            metrics["peak"] = max(metrics["peak"], metrics["active"])
        try:
            return value * value
        finally:
            with metrics_lock:
                metrics["active"] -= 1


with ThreadPoolExecutor(max_workers=4) as pool:
    assert list(pool.map(work, range(8))) == [value * value for value in range(8)]
assert 1 <= metrics["peak"] <= 2
assert metrics["active"] == 0
```

Ограничение активных операций не ограничивает очередь уже созданных задач. Миллион Future может ждать два разрешения семафора и удерживать память.

Также различайте concurrency limit и rate limit: два одновременных запроса не означают «не больше двух запросов в секунду».

### Barrier

Barrier ожидает заданное число участников и отделяет фазы.

```python
from queue import Queue
from threading import Barrier, Thread

barrier = Barrier(2, timeout=3)
trace: Queue[tuple[str, int]] = Queue()


def work(number: int) -> None:
    trace.put(("ready", number))
    barrier.wait()
    trace.put(("after", number))


threads = [Thread(target=work, args=(number,)) for number in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join(timeout=5)
    assert not thread.is_alive()
events = [trace.get_nowait() for _ in range(4)]
assert [phase for phase, _ in events] == ["ready", "ready", "after", "after"]
```

Потерявшийся участник может заблокировать остальных; задавайте timeout и обрабатывайте `BrokenBarrierError`. `abort` переводит барьер в broken-состояние и будит ожидающих с ошибкой.

Barrier полезен для конкретного тестового interleaving и синхронной смены фаз. Он не подходит, если число динамических участников заранее неизвестно.

### Потокобезопасные очереди

`queue.Queue` синхронизирует put/get и умеет ограничивать размер. `SimpleQueue` проще, но не предоставляет bounded capacity и task tracking.

```python
from queue import Empty, Full, Queue

queue: Queue[str] = Queue(maxsize=1)
queue.put_nowait("e1")
try:
    queue.put_nowait("e2")
except Full:
    pass
else:
    raise AssertionError("Ожидалось ограничение очереди")
assert queue.get_nowait() == "e1"
queue.task_done()
queue.join()
try:
    queue.get_nowait()
except Empty:
    pass
else:
    raise AssertionError("Очередь должна быть пустой")
```

Не делайте `if not queue.empty(): queue.get()` как атомарную проверку: состояние может измениться между вызовами. Используйте blocking get с ограничением или обработку `Empty`.

`qsize`, `empty` и `full` пригодны для приблизительной диагностики, а не для доказательства, что следующий вызов не заблокируется.

### Thread-local storage

`threading.local` даёт отдельные атрибуты каждому потоку, но не отдельные значения каждому заданию пула.

```python
from queue import Queue
from threading import Barrier, Thread, local

state = local()
ready = Barrier(2, timeout=3)
results: Queue[str] = Queue()


def work(value: str) -> None:
    state.request_id = value
    try:
        ready.wait()
        results.put(state.request_id)
    finally:
        del state.request_id


threads = [Thread(target=work, args=(value,)) for value in ("a", "b")]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join(timeout=5)
    assert not thread.is_alive()
assert sorted(results.get_nowait() for _ in threads) == ["a", "b"]
```

Пул переиспользует поток: забытый request ID может попасть в следующую задачу. Удаляйте или восстанавливайте его в finally. Атрибуты `__slots__` подкласса local не становятся thread-local.

`contextvars` описывает контекст иначе. В Python 3.14 у Thread есть явный параметр `context`:

```python
# Python 3.14+
from contextvars import Context, ContextVar, copy_context
from queue import Queue
from threading import Thread

request_id = ContextVar("request_id", default="unset")
request_id.set("parent")
results: Queue[str] = Queue()

inherited = Thread(target=lambda: results.put(request_id.get()), context=copy_context())
isolated = Thread(target=lambda: results.put(request_id.get()), context=Context())
for thread in (inherited, isolated):
    thread.start()
for thread in (inherited, isolated):
    thread.join(timeout=3)
    assert not thread.is_alive()
assert sorted(results.get_nowait() for _ in range(2)) == ["parent", "unset"]
```

Значение по умолчанию для наследования зависит от runtime-настройки и типа сборки. Для request context задавайте нужное поведение явно; копирование контекста при создании worker не равно копированию для каждой последующей задачи.

### Кооперативная остановка потоков

Стандартный Thread не предоставляет безопасного kill. Worker должен проверять stop token и иметь возможность выйти из блокирующих операций.

Хороший протокол: прекратить приём задач → установить stop → разблокировать get/wait → завершить или отклонить текущую работу → закрыть собственные ресурсы → join.

Проверка флага только между задачами не остановит бесконечный сетевой read внутри задачи. Нужны timeouts транспорта, отменяемый API или отдельный процесс. Даже timeout ожидания Future не заменяет этот контракт.

Не пытайтесь внедрять произвольное исключение в другой поток через низкоуровневые хаки: он может находиться в середине изменения общего состояния.

### threading.excepthook, ошибки join и жизненный цикл недемонных потоков

`threading.excepthook` получает необработанное исключение обычного Thread. Это диагностика, а не автоматическая передача ошибки главному потоку.

```python
from queue import Queue
import threading

reported: Queue[tuple[str, str]] = Queue()
previous = threading.excepthook


def hook(args: threading.ExceptHookArgs) -> None:
    reported.put((args.exc_type.__name__, str(args.exc_value)))


def fail() -> None:
    raise ValueError("worker failed")


threading.excepthook = hook
thread = threading.Thread(target=fail)
try:
    thread.start()
    thread.join(timeout=3)
    assert not thread.is_alive()
finally:
    threading.excepthook = previous
assert reported.get_nowait() == ("ValueError", "worker failed")
```

Hook меняет состояние всего процесса; в библиотеке или параллельном тесте его подмена требует осторожности. Не храните бессрочно exc_value/traceback и сам Thread: это может создавать циклы ссылок и продлевать жизнь объектов.

В Python 3.14 join работающего daemon-потока на поздней стадии финализации может вызывать `PythonFinalizationError`. Основную уборку выполняйте до финализации, а не в позднем atexit.

Потоки ThreadPoolExecutor также удерживают завершение программы. Их служебная уборка выполняется до обычных atexit-handlers; нельзя рассчитывать, что только поздний handler подаст необходимый stop.

### Queue.task_done()/join(), ограниченные очереди и завершение работников

`Queue.join` ждёт, когда каждому put будет сопоставлен task_done. Это учёт принятых задач, а не подтверждение успешного бизнес-результата.

```python
from queue import Queue
from threading import Thread

stop = object()  # Один и тот же объект передаётся между потоками этого процесса.
queue: Queue[object] = Queue(maxsize=2)
results: Queue[int] = Queue()


def consume() -> None:
    while True:
        item = queue.get()
        try:
            if item is stop:
                return
            if not isinstance(item, int):
                raise TypeError("expected int")
            results.put(item * 2)
        finally:
            queue.task_done()


threads = [Thread(target=consume) for _ in range(2)]
for thread in threads:
    thread.start()
for value in range(4):
    queue.put(value)
for _ in threads:
    queue.put(stop)
queue.join()
for thread in threads:
    thread.join(timeout=3)
    assert not thread.is_alive()
assert sorted(results.get_nowait() for _ in range(4)) == [0, 2, 4, 6]
```

Этот пример использует известные корректные данные. Если consumer упал, оставшиеся элементы и sentinel могут навсегда заблокировать producer или join. Для production нужны отдельный канал ошибок, управление оставшимися заданиями и протокол остановки, который сохраняется при отказе.

Sentinel `object()` с проверкой `is` пригоден здесь для потоков, но не переносится автоматически в multiprocessing.Queue: pickle может создать другой объект. Для процессов используйте сериализуемый явный тип сообщения или значение, которое исключено из обычных данных.

С Python 3.13 Queue поддерживает shutdown:

```python
# Python 3.13+
from queue import Queue, ShutDown

queue: Queue[str] = Queue(maxsize=2)
queue.put("e1")
queue.shutdown()
assert queue.get_nowait() == "e1"
queue.task_done()
queue.join()
try:
    queue.get_nowait()
except ShutDown:
    pass
else:
    raise AssertionError("Закрытая и пустая очередь должна завершать чтение")
```

При `shutdown(immediate=True)` queued-элементы могут быть отброшены, и join больше не доказывает, что каждый put был обработан. У уже выполняемых задач остаётся собственный lifecycle. Это не универсальная замена политике отмены.

## Проблемы синхронизации

### Атомарность операции vs безопасность последовательности операций

Даже если одиночная операция контейнера защищена реализацией, несколько операций не становятся одной атомарной транзакцией.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

lock = Lock()
state = {"available": 1, "reserved": 0}


def reserve() -> bool:
    with lock:
        if state["available"] == 0:
            return False
        state["available"] -= 1
        state["reserved"] += 1
        return True


with ThreadPoolExecutor(max_workers=2) as pool:
    results = list(pool.map(lambda _: reserve(), range(2)))
assert sorted(results) == [False, True]
assert state == {"available": 0, "reserved": 1}
assert state["available"] + state["reserved"] == 1
```

Инвариант охватывает оба поля. Блокировка только вокруг одного присваивания не защищает проверку наличия ресурса и согласованность пары.

«На моей версии CPython append не ломается» недостаточно для переносимого протокола. Отдельно определяйте допустимые операции, владение и видимость результата.

### Deadlock

Deadlock — участники ждут друг друга так, что никто не может сделать следующий шаг. Типичный цикл: поток A держит lock 1 и ждёт lock 2, поток B держит lock 2 и ждёт lock 1.

Другой пример: единственный worker пула запускает новую задачу в том же пуле и ждёт её result. Свободного worker для новой задачи нет.

Признаки полезно искать через thread dump, `faulthandler.dump_traceback`, имена потоков и схему ожиданий. Не запускайте демонстрацию бесконечного deadlock в основном учебном процессе.

Timeout может помочь обнаружить ожидание и выйти из него, но не исправляет нарушенный порядок и не откатывает автоматически уже изменённое состояние.

### Livelock

При livelock участники активно меняют состояние, но полезного продвижения нет. Например, два worker постоянно уступают друг другу ресурс и немедленно повторяют тот же конфликт.

В отличие от deadlock, CPU может оставаться занятым. Проверяйте **progress metric**: число завершённых задач, движение offset, изменение фазы, а не только наличие живых потоков.

Ограниченные попытки, единый координатор и корректный backoff помогают, если они соответствуют протоколу. Случайная задержка уменьшает вероятность столкновения, но сама по себе не доказывает завершение.

### Starvation

Starvation — один участник долго не получает ресурс, хотя другие продвигаются. Обычный Lock не обещает строгого FIFO-порядка.

Причины: очень длинная критическая секция, постоянный поток приоритетной работы, занятый пул и неограниченная очередь. Метрика среднего времени может скрыть голодающий хвост.

Если fairness — часть требований, задайте явный порядок доступа или очередность в координаторе и тестируйте максимальное ожидание в объявленной модели. Не считайте её автоматическим свойством любого семафора.

### Порядок захвата блокировок

Один общий порядок захвата нескольких locks убирает соответствующий цикл ожидания.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Lock

locks = {name: Lock() for name in ("a", "b")}
counts = {"a": 0, "b": 0}


def update_pair(left: str, right: str) -> None:
    first, second = sorted((left, right))
    if first == second:
        raise ValueError("Нужны разные ресурсы")
    with locks[first]:
        with locks[second]:
            counts[left] += 1
            counts[right] += 1


with ThreadPoolExecutor(max_workers=2) as pool:
    futures = [
        pool.submit(update_pair, "a", "b"),
        pool.submit(update_pair, "b", "a"),
    ]
    for future in futures:
        future.result(timeout=5)
assert counts == {"a": 2, "b": 2}
```

Порядок должен быть общим для всех путей кода, включая error handling. Стабильный ID ресурса обычно понятнее случайного порядка появления объектов.

Протокол двухфазной операции может потребовать другого решения: скопировать состояние, отпустить lock, выполнить I/O и проверить версию перед commit. Тогда нужны тесты конкурентного изменения и повторов.

### Размер критической секции

Защищайте достаточно действий для инварианта, но не держите lock во время долгой несвязанной работы.

```python
from threading import Lock

lock = Lock()
state = {"version": 1, "name": "orders"}

with lock:
    snapshot = dict(state)
# Форматирование выполняется уже без lock.
message = f"{snapshot['name']}@{snapshot['version']}"
assert message == "orders@1"
```

Snapshot должен быть согласованным и достаточно независимым. Поверхностная копия dict не изолирует вложенные изменяемые значения.

Нельзя просто вынести проверку из lock ради ускорения, если между проверкой и изменением другой поток может нарушить предположение. Оптимизация должна сохранять границу атомарного решения.

### Reentrancy

Реентерабельный код допускает повторный вход до завершения предыдущего вызова. Повторный вход возможен не только из другого потока, но и через callback, logging handler, finalizer или вложенный публичный метод.

RLock решает только повторный захват одной блокировки тем же потоком. Он не делает промежуточное состояние объекта корректным для повторного вызова и не предотвращает рекурсивные побочные эффекты.

Разделяйте публичный метод и небольшие внутренние операции с явно описанными предусловиями. Не называйте объект thread-safe без указания поддерживаемых одновременных и повторных операций.

### Вызов пользовательского кода под блокировкой

Callback может ждать другой lock, обращаться к тому же объекту, выполнять I/O или выбрасывать исключение. Поэтому его выполнение под внутренним lock часто неожиданно расширяет критическую секцию.

```python
from threading import Lock


class Publisher:
    def __init__(self) -> None:
        self._lock = Lock()
        self._listeners = []

    def subscribe(self, listener) -> None:
        with self._lock:
            self._listeners.append(listener)

    def publish(self, value: str) -> None:
        with self._lock:
            listeners = tuple(self._listeners)
        for listener in listeners:
            listener(value)


publisher = Publisher()
received = []
publisher.subscribe(received.append)
publisher.publish("e1")
assert received == ["e1"]
```

Здесь список подписчиков фиксируется snapshot, а пользовательский код вызывается снаружи lock. Это задаёт конкретную семантику: новая подписка во время publish относится к следующему вызову.

Если callback должен быть частью атомарной операции, такой перенос бездумно делать нельзя. Лучше явно ограничить контракт callback или изменить архитектуру передачи событий.

### Почему GIL не заменяет синхронизацию

GIL относится к исполнению интерпретатора, а не к транзакциям приложения. Поток может смениться между чтением и записью, блокирующий вызов может освободить GIL, нативное расширение — выполнять работу без него.

Особенно опасны check-then-act, read-modify-write, согласованность нескольких контейнеров и публикация частично инициализированного объекта.

Пишите синхронизацию из инварианта: «не больше N активных операций», «каждый принятый элемент получает один результат», «все новые записи партии фиксируются вместе». Такую модель проще перенести в free-threaded-сборку, чем неявную надежду на случайную атомарность байткода.

## Многопроцессность — multiprocessing

### Создание и завершение процессов

Процесс имеет собственный Python runtime и адресное пространство. Родитель должен проверить не только завершение, но и exit code.

```python
import multiprocessing as mp


def calculate() -> None:
    result = sum(value * value for value in range(100))
    if result != 328350:
        raise ValueError("unexpected calculation")


if __name__ == "__main__":
    context = mp.get_context("spawn")
    process = context.Process(target=calculate, name="calculator")
    process.start()
    try:
        process.join(timeout=10)
        assert not process.is_alive()
        assert process.exitcode == 0
    finally:
        if process.is_alive():
            process.terminate()
            process.join(timeout=5)
        if process.is_alive():
            process.kill()
            process.join(timeout=5)
        process.close()
```

`join` не возвращает результат функции и не пробрасывает её исключение. Ненулевой exit code — отдельный сигнал ошибки. Для значения нужен IPC или Future.

Процесс с `daemon=True` имеет другую семантику, чем daemon thread: например, ему нельзя обычным способом создавать дочерние multiprocessing-процессы. Это не способ запуска самостоятельной фоновой службы.

### spawn, fork и forkserver

| Метод | Что происходит | Главный компромисс |
| --- | --- | --- |
| spawn | Запускается новый интерпретатор, нужное состояние передаётся явно | Больше стоимость запуска, яснее наследование |
| fork | Дочерний процесс получает snapshot адресного пространства родителя | Быстрый старт на поддерживаемых POSIX, опасность унаследованного состояния |
| forkserver | Workers форкаются от специального server-процесса | Меньше проблем fork сложного родителя, отдельный lifecycle сервера |

```python
import multiprocessing as mp

if __name__ == "__main__":
    print({"available": mp.get_all_start_methods()})
    context = mp.get_context("spawn")
    assert context.get_start_method() == "spawn"
```

Spawn не «копирует все globals»: модуль в новом процессе импортируется заново. Fork не создаёт безопасную общую Python-кучу: обычные изменения после fork не синхронизируются между процессами.

Forkserver обычно создаёт workers из более простого, однопоточного сервера. Но preload-модули сами могут запустить потоки; метод не отменяет требований к imports и ресурсам.

### Различия платформ и версий Python

Не полагайтесь на один default для всех систем.

| Среда | Ориентир |
| --- | --- |
| Windows | spawn; fork отсутствует |
| macOS современных CPython | spawn по умолчанию; fork считается небезопасным для многих сценариев |
| Linux в CPython 3.12 | Обычно fork по умолчанию |
| Поддерживаемые POSIX в CPython 3.14 | Обычно forkserver вместо fork; возможен spawn при ограничениях среды |

С Python 3.14 fork не является методом по умолчанию ни на одной платформе. Фактическую доступность и выбор проверяйте API текущего runtime; библиотека должна принимать context или создавать нужный явно.

С Python 3.12 fork в обнаруженном многопоточном процессе может выдавать DeprecationWarning. Для frozen-приложений и некоторых POSIX-упаковщиков spawn/forkserver имеют дополнительные ограничения.

В контейнере число видимых CPU и реально доступная квота могут различаться. Установка max_workers по «всем ядрам хоста» способна ухудшить время и память.

### Защита точки входа

При spawn дочерний процесс импортирует модуль. Создание новых процессов на верхнем уровне может вызвать рекурсивный запуск или RuntimeError.

```python
from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp


def square(value: int) -> int:
    return value * value


def main() -> None:
    context = mp.get_context("spawn")
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        assert list(pool.map(square, [1, 2, 3])) == [1, 4, 9]


if __name__ == "__main__":
    mp.freeze_support()
    main()
```

Под guard должны находиться запуск пула и другие entrypoint side effects. Объявления функций и классов, которые нужны workers, обычно остаются на уровне импортируемого модуля.

`freeze_support` полезен для соответствующих frozen-сценариев и не заменяет корректный guard. Код библиотеки не должен запускать executor просто вследствие import.

### Сериализация функций и аргументов

Стандартный pickle обычно передаёт функцию по доступному имени модуля, а не переносит произвольное замыкание с окружением.

```python
import pickle


def square(value: int) -> int:
    return value * value


restored = pickle.loads(pickle.dumps(square))
assert restored(4) == 16

try:
    pickle.dumps(lambda value: value * value)
except (pickle.PicklingError, AttributeError):
    pass
else:
    raise AssertionError("Ожидалась недоступность lambda для обычного pickle")
```

Проблемы часто вызывают локальные функции, lambda, lock, открытое соединение БД и объект, внутри которого они спрятаны. Доступность объекта для pickle и доступность его модуля в worker — разные условия.

Исключения тоже нужно сериализовать. У собственного исключения arguments должны позволять восстановить объект:

```python
import pickle


class RecordError(Exception):
    def __init__(self, record_id: str, code: str) -> None:
        self.record_id = record_id
        self.code = code
        super().__init__(record_id, code)


original = RecordError("e1", "invalid_value")
restored = pickle.loads(pickle.dumps(original))
assert restored.record_id == "e1"
assert restored.code == "invalid_value"
```

Если constructor требует два аргумента, а `Exception.args` содержит только одну форматированную строку, ошибка может сломать обратную передачу результата вместо нормальной доставки caller.

### Pipes

Pipe передаёт сообщения между концами соединения. В одностороннем `Pipe(duplex=False)` первый объект читает, второй пишет.

```python
import multiprocessing as mp
from multiprocessing.connection import Connection


def send_result(connection: Connection) -> None:
    try:
        connection.send_bytes(b'{"count":3}')
    finally:
        connection.close()


if __name__ == "__main__":
    context = mp.get_context("spawn")
    receive, send = context.Pipe(duplex=False)
    process = context.Process(target=send_result, args=(send,))
    process.start()
    send.close()
    try:
        assert receive.poll(10)
        assert receive.recv_bytes(maxlength=128) == b'{"count":3}'
        process.join(timeout=5)
        assert process.exitcode == 0
    finally:
        if process.is_alive():
            process.terminate()
            process.join(timeout=5)
        receive.close()
        process.close()
```

`send/recv` используют pickle для объектов; `send_bytes/recv_bytes` передают байтовые сообщения. Даже если recv готов, другая сторона может закрыться: учитывайте EOF и повреждение канала.

Не оставляйте ненужные копии концов Pipe открытыми. Они мешают корректно обнаружить завершение отправителей и удерживают ресурсы.

### Queues

`multiprocessing.Queue` сериализует объекты и использует служебную передачу. Окончание put не всегда означает, что данные уже дошли до другого процесса.

```python
import multiprocessing as mp


def produce(queue, value: int) -> None:
    queue.put((value, value * value))


if __name__ == "__main__":
    context = mp.get_context("spawn")
    queue = context.Queue(maxsize=2)
    processes = [
        context.Process(target=produce, args=(queue, number)) for number in (2, 3)
    ]
    for process in processes:
        process.start()
    try:
        results = [queue.get(timeout=10) for _ in processes]
        assert sorted(results) == [(2, 4), (3, 9)]
        for process in processes:
            process.join(timeout=5)
            assert process.exitcode == 0
    finally:
        for process in processes:
            if process.is_alive():
                process.terminate()
                process.join(timeout=5)
            process.close()
        queue.close()
        queue.join_thread()
```

Родитель сначала читает данные, затем join производителей. Иначе worker может ждать flush заполненного pipe, а родитель — завершения worker.

Сохраняется порядок сообщений одного производителя, но не общий порядок нескольких производителей. Не изменяйте mutable-объект сразу после put, рассчитывая на мгновенный snapshot.

У обычной multiprocessing.Queue нет `task_done/join` из threaded Queue; для task tracking есть `JoinableQueue`. `empty/qsize` также не подходят как атомарное условие решения.

### Managers

Manager держит объекты в server-процессе, а клиенты работают с proxy. Это удобный интерфейс, но каждое действие может быть IPC/RPC.

```python
import multiprocessing as mp
from multiprocessing.managers import SyncManager


def increment(counter, lock) -> None:
    for _ in range(50):
        with lock:
            counter["value"] += 1


if __name__ == "__main__":
    context = mp.get_context("spawn")
    with SyncManager(address=("127.0.0.1", 0), ctx=context) as manager:
        counter = manager.dict(value=0)
        lock = manager.Lock()
        processes = [
            context.Process(target=increment, args=(counter, lock)) for _ in range(2)
        ]
        for process in processes:
            process.start()
        try:
            for process in processes:
                process.join(timeout=10)
                assert process.exitcode == 0
            assert counter["value"] == 100
        finally:
            for process in processes:
                if process.is_alive():
                    process.terminate()
                    process.join(timeout=5)
                process.close()
```

Proxy-словарь не делает `counter["value"] += 1` атомарным: чтение и запись остаются отдельными действиями, поэтому нужен lock.

Здесь SyncManager явно использует loopback TCP и свободный порт. Обычный `context.Manager()` выбирает адрес сам; на POSIX это может быть Unix domain socket. Ни один вариант не обходит ограничения среды на создание соответствующих сокетов. Не открывайте pickle-based Manager для недоверенных клиентов.

Вложенный обычный list/dict внутри proxy не всегда передаёт локальное изменение автоматически: используйте подходящие вложенные proxy или явно присваивайте изменённое значение обратно.

Manager полезен для небольшого координационного состояния, а не для высокочастотной обработки каждого элемента большого массива.

### Shared memory

SharedMemory позволяет работать с общим байтовым блоком без копирования всего содержимого через pickle.

```python
import multiprocessing as mp
from multiprocessing import shared_memory
import struct


def double_values(name: str) -> None:
    block = shared_memory.SharedMemory(name=name)
    try:
        first, second = struct.unpack_from("!ii", block.buf)
        struct.pack_into("!ii", block.buf, 0, first * 2, second * 2)
    finally:
        block.close()


if __name__ == "__main__":
    context = mp.get_context("spawn")
    block = shared_memory.SharedMemory(create=True, size=8)
    process = context.Process(target=double_values, args=(block.name,))
    try:
        struct.pack_into("!ii", block.buf, 0, 3, 4)
        process.start()
        process.join(timeout=10)
        assert process.exitcode == 0
        assert struct.unpack_from("!ii", block.buf) == (6, 8)
    finally:
        if process.is_alive():
            process.terminate()
            process.join(timeout=5)
        process.close()
        block.close()
        block.unlink()
```

Формат `!ii` явно задаёт byte order и два целых. Shared memory не переносит произвольные Python-ссылки и не делает запись нескольких полей атомарной.

В примере владение передаётся фазами: parent заполняет → child изменяет → parent читает после join. Для одновременного доступа нужны locks, semaphores или отдельный протокол.

Храните layout, длину и версию данных отдельно от случайных догадок о размере буфера. Освобождайте экспортированные memoryview и NumPy-view перед закрытием блока.

### Межпроцессная синхронизация

Создавайте Process, Lock, Event, Queue и shared values из одного совместимого context.

```python
import multiprocessing as mp


def increment(counter) -> None:
    for _ in range(100):
        with counter.get_lock():
            counter.value += 1


if __name__ == "__main__":
    context = mp.get_context("spawn")
    counter = context.Value("q", 0)
    processes = [context.Process(target=increment, args=(counter,)) for _ in range(2)]
    for process in processes:
        process.start()
    try:
        for process in processes:
            process.join(timeout=10)
            assert process.exitcode == 0
        assert counter.value == 200
    finally:
        for process in processes:
            if process.is_alive():
                process.terminate()
                process.join(timeout=5)
            process.close()
```

`Value` с синхронизированным доступом защищает отдельные чтения и записи, но не делает += одной операцией. Внешний get_lock охватывает весь read-modify-write. Его default lock реентерабелен; замена на другой тип требует проверки вложенного захвата.

Использование одного lock для unrelated данных увеличивает contention. Использование разных locks для одного инварианта не защищает его вовсе.

### Copy-on-write

При fork страницы памяти первоначально могут разделяться, а запись создаёт частную копию страницы. Это оптимизация ОС, а не общая изменяемая Python-структура.

Даже обход большого Python-графа может менять служебное состояние, например reference counts, и влиять на фактическое разделение страниц. Результат зависит от представления данных и runtime.

Не суммируйте RSS процессов как точный объём уникальной физической памяти: shared pages могут учитываться несколько раз. Для анализа полезны PSS/USS, метрики контейнера и поведение под реальной нагрузкой.

Если архитектуре нужен общий массив, проектируйте memory mapping/shared memory и доступ явно, а не рассчитывайте на бесконечную выгоду от COW.

### Ограничения fork

В дочернем процессе остаётся только поток, который вызвал fork. Но snapshot может содержать locks, удерживаемые исчезнувшими потоками, состояние allocator, logging, DB-пулов и нативных библиотек.

Поэтому «сначала запустить потоки, затем fork ради экономии» опасно. Пересоздание одного Python-lock не чинит всё скрытое состояние сторонних библиотек.

Открытое DB-соединение или сетевой клиент не следует автоматически использовать одновременно из parent и child. Создавайте принадлежащий worker ресурс после запуска, например в initializer.

Если fork необходим, ограничения должны быть проверены для всей цепочки зависимостей. Для универсальной библиотеки безопаснее принимать explicit context и не навязывать глобальный start method.

### Завершение дочерних процессов

Предпочтительный путь — кооперативный stop, завершение собственной операции и проверка exit code. `terminate` и `kill` — аварийные действия с потерей нормального cleanup.

После terminate нужно join: посланный сигнал ещё не означает, что процесс завершился и был собран. Потомков worker эти методы автоматически не превращают в управляемую группу.

Прерывание во время работы с Queue/Pipe может повредить канал; во время удержания lock — оставить остальных участников заблокированными. После такой остановки часто требуется пересоздать весь пул и связанные IPC-ресурсы.

При проектировании вычисления разделяйте фазу получения результата и необратимую публикацию. Пусть worker возвращает данные, а единственный координатор решает, можно ли фиксировать общий результат.

### Освобождение ресурсов

Составьте список владельцев: кто закрывает Process handle, концы Pipe, Queue feeder, Manager, shared memory и открытые в worker файлы.

Процессу нужны завершение и join, затем close объекта Process. Queue обычно закрывается и дожидается feeder через join_thread после правильного drain. Manager удобно ограничить контекстным менеджером.

Не вызывайте `cancel_join_thread` просто ради исчезновения зависания: он может разрешить выход без flush и привести к потере сообщений. Сначала проверьте порядок «читать → join производителя».

Cleanup также может выбросить исключение. Сохраняйте исходную причину ошибки и не сообщайте «успешно», если ресурс не завершён по обещанному протоколу.

### get_context(), выбор start method и библиотечный код без глобальной настройки

`set_start_method` меняет глобальную политику процесса и обычно вызывается один раз в entrypoint. Библиотеке лучше получить context аргументом.

```python
from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp


def increment(value: int) -> int:
    return value + 1


def calculate(values: list[int], context) -> list[int]:
    with ProcessPoolExecutor(max_workers=2, mp_context=context) as pool:
        return list(pool.map(increment, values))


if __name__ == "__main__":
    context = mp.get_context("spawn")
    assert calculate([1, 2, 3], context) == [2, 3, 4]
```

Так вызывающий код может согласовать процессный executor с другими компонентами. Не вызывайте в reusable-модуле `set_start_method(..., force=True)`: вы можете нарушить контракты уже созданных locks и процессов.

### Pickle-доступность функций; fork многопоточного процесса и унаследованные ресурсы

Проверяйте полный путь задачи: import worker-модуля → загрузка callable → аргументы → выполнение → сериализация результата или исключения → получение в parent.

Успешный локальный `pickle.dumps` не доказывает, что файл модуля установлен в дочернем окружении. Работавший с fork скрипт с локальной функцией может перестать работать после перехода на spawn/forkserver.

REPL и notebook часто не предоставляют такой же импортируемый `__main__`, как файл. Выносите worker-функции в отдельный модуль.

Нельзя передавать объект с унаследованным thread pool или connection pool и ожидать корректного состояния после fork. Ресурс создаётся владельцем в новом процессе, а наружу передаётся его ограниченный результат.

### Resource tracker, shared_memory.close()/unlink() и аварийное завершение

На поддерживаемых POSIX с spawn/forkserver может работать resource tracker, следящий за некоторыми именованными ресурсами. Он помогает убирать остатки после выхода семейства процессов, но не заменяет нормальный lifecycle.

`close` освобождает handle текущего участника. `unlink` удаляет имя shared-memory-объекта; этот шаг должен иметь одного назначенного владельца. Семантика удаления различается на POSIX и Windows.

С Python 3.13 у SharedMemory есть параметр `track`. Для процессов одного multiprocessing-семейства обычно используется общий tracker. У независимо запущенных процессов trackers могут быть разными: завершение первого способно удалить ресурс раньше ожидаемого.

`track=False` у присоединяющегося участника применяют только при наличии другого явного владельца учёта. В Python 3.12 такого параметра нет; на Windows используется другой механизм срока жизни handles.

Аварийное завершение может оставить незавершённую бизнес-операцию даже при успешном удалении shared memory. Уборка ресурса и корректность результата — разные гарантии.

## Пулы и executors — concurrent.futures

### ThreadPoolExecutor

ThreadPoolExecutor переиспользует ограниченное число потоков и возвращает Future для каждого submit. Он удобен для блокирующего I/O и нативного кода с подходящей моделью GIL.

```python
from concurrent.futures import ThreadPoolExecutor
from pathlib import Path
import tempfile


def count_bytes(path: Path) -> int:
    return len(path.read_bytes())


with tempfile.TemporaryDirectory() as directory:
    paths = [Path(directory) / f"{index}.txt" for index in range(3)]
    for index, path in enumerate(paths):
        path.write_bytes(b"x" * (index + 1))
    with ThreadPoolExecutor(max_workers=2, thread_name_prefix="file-reader") as pool:
        assert list(pool.map(count_bytes, paths)) == [1, 2, 3]
```

Файлы здесь заведомо маленькие. Для внешнего файла `read_bytes` без лимита может потребить слишком много памяти.

Задавайте max_workers по доступным ресурсам. В Python 3.12 default основывался на `os.cpu_count`, с 3.13 используется `os.process_cpu_count`; ни одна формула автоматически не знает лимит вашего DB-пула.

Ошибка initializer ломает пул, а не просто одну задачу. Для долгоживущих бесконечных служб с собственным протоколом остановки обычные управляемые Thread иногда понятнее executor.

### ProcessPoolExecutor

ProcessPoolExecutor подходит для независимых CPU-задач и отдельного адресного пространства. Callable, аргументы, результаты и ошибки должны пройти через сериализацию.

```python
from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp


def sum_squares(limit: int) -> int:
    return sum(value * value for value in range(limit + 1))


if __name__ == "__main__":
    limits = [1000, 2000, 3000]
    with ProcessPoolExecutor(max_workers=2, mp_context=mp.get_context("spawn")) as pool:
        actual = list(pool.map(sum_squares, limits))
    expected = [n * (n + 1) * (2 * n + 1) // 6 for n in limits]
    assert actual == expected
```

Отдельно измеряйте запуск процессов и steady-state. Для короткой партии process overhead может перекрыть выигрыш.

`max_tasks_per_child` позволяет заменять worker после числа задач, но влияет на lifecycle и start method; он несовместим с fork. Проверяйте конкретную patch-версию Python и поведение вашей нагрузки.

Нельзя использовать методы того же process executor или его Future из выполняемой в нём задачи как общий механизм вложенной координации: это может привести к deadlock.

### submit

`submit(callable, *args, **kwargs)` планирует один вызов и возвращает Future. Сам возврат Future не означает, что задача уже началась.

```python
from concurrent.futures import ThreadPoolExecutor


def describe(name: str, *, count: int) -> str:
    return f"{name}:{count}"


with ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(describe, "orders", count=3)
    assert future.result(timeout=3) == "orders:3"
```

Ошибка может возникнуть при submit, например после shutdown или при сломанном пуле, а может прийти позже через Future, например при сериализации аргумента процессной задачи.

Не создавайте миллионы Future заранее только потому, что активных workers мало. У submit нет публичного аргумента bounded queue capacity.

### map

`Executor.map` возвращает результаты **в порядке входа**, даже если работы завершились иначе.

```python
from concurrent.futures import ThreadPoolExecutor


def transform(value: int) -> int:
    return value * 10


with ThreadPoolExecutor(max_workers=2) as pool:
    assert list(pool.map(transform, [3, 1, 2])) == [30, 10, 20]
```

Медленный ранний элемент задерживает выдачу поздних результатов: head-of-line blocking. Через as_completed можно выдавать по готовности, но порядок станет другим.

До Python 3.14 и при `buffersize=None` map обычно забирает вход и отправляет работы заранее. Не применяйте такой map к бесконечному iterable. Исключение задачи возникает при извлечении соответствующего результата из iterator; создание map само по себе не подтверждает успех.

### Ожидание результатов

`result` ожидает один Future. `wait` возвращает множества done/not_done, а `as_completed` выдаёт готовые Future.

```python
from concurrent.futures import FIRST_COMPLETED, ThreadPoolExecutor, wait
from threading import Event

release = Event()
pool = ThreadPoolExecutor(max_workers=2)
try:
    fast = pool.submit(lambda: "ready")
    slow = pool.submit(release.wait)
    done, not_done = wait([fast, slow], timeout=3, return_when=FIRST_COMPLETED)
    assert fast in done
    assert slow in not_done
finally:
    release.set()
    pool.shutdown(wait=True)
```

`FIRST_EXCEPTION` возвращает при обнаружении исключения; если исключений нет, ожидание похоже на ALL_COMPLETED. Оно не отменяет остальные задачи автоматически.

Обход списка futures с последовательным result сохраняет порядок, но может поздно обнаружить ошибку уже завершившейся дальней задачи. Выбор способа ожидания влияет на политику ошибок и buffering.

### Исключения

Future сохраняет исключение, а `result` поднимает его в вызывающем коде. Если никто не запросил результат или exception, ошибка может остаться незамеченной бизнес-логикой.

```python
from concurrent.futures import ThreadPoolExecutor


def parse_value(text: str) -> int:
    return int(text)


with ThreadPoolExecutor(max_workers=1) as pool:
    future = pool.submit(parse_value, "bad")
    try:
        future.result(timeout=3)
    except ValueError:
        assert isinstance(future.exception(), ValueError)
    else:
        raise AssertionError("Исключение worker должно дойти до caller")
```

Нормальная ошибка задачи и аварийное исчезновение процесса — разные ситуации. Второе может дать BrokenProcessPool и сделать непригодными остальные работы.

```python
from concurrent.futures import ProcessPoolExecutor
from concurrent.futures.process import BrokenProcessPool
import multiprocessing as mp
import os


def exit_without_cleanup() -> None:
    os._exit(7)


if __name__ == "__main__":
    with ProcessPoolExecutor(max_workers=1, mp_context=mp.get_context("spawn")) as pool:
        future = pool.submit(exit_without_cleanup)
        try:
            future.result(timeout=10)
        except BrokenProcessPool:
            pass
        else:
            raise AssertionError("Пул должен сообщить об исчезнувшем worker")
```

Это намеренно аварийная демонстрация в дочернем процессе без внешних бизнес-операций. После broken pool обычно создаётся новый executor; повтор задачи должен учитывать, могла ли она уже выполнить side effect до исчезновения.

### Таймауты

`Future.result(timeout=...)` ограничивает ожидание этого вызова. Он не останавливает функцию.

```python
from concurrent.futures import ThreadPoolExecutor
from threading import Event

started = Event()
release = Event()
pool = ThreadPoolExecutor(max_workers=1)


def work() -> int:
    started.set()
    release.wait()
    return 42


future = pool.submit(work)
try:
    assert started.wait(3)
    try:
        future.result(timeout=0)
    except TimeoutError:
        assert future.running()
    else:
        raise AssertionError("Worker ещё ждёт release")
finally:
    release.set()
    pool.shutdown(wait=True)
assert future.result() == 42
```

У map/as_completed timeout относится к их общему началу ожидания по правилам API, а не автоматически выделяется заново для каждого элемента. Для собственного дедлайна используйте monotonic clock и оставшееся время.

Выход из `with executor` всё равно выполняет shutdown с ожиданием. Поэтому измеренное время всей функции может превысить timeout Future. Если worker заблокирован навсегда, обычный executor не делает этот вызов жёстко ограниченным.

### Отмена

`cancel` отменяет Future только до перехода в выполняющееся состояние. Статус pending не следует читать и затем менять без самого cancel: между действиями есть гонка.

```python
from concurrent.futures import CancelledError, ThreadPoolExecutor
from threading import Event

started = Event()
release = Event()
pool = ThreadPoolExecutor(max_workers=1)


def occupy_worker() -> str:
    started.set()
    release.wait()
    return "finished"


first = pool.submit(occupy_worker)
try:
    assert started.wait(3)
    queued = pool.submit(lambda: "must not run")
    assert queued.cancel() is True
    assert first.cancel() is False
finally:
    release.set()
    pool.shutdown(wait=True, cancel_futures=True)
assert first.result() == "finished"
try:
    queued.result()
except CancelledError:
    pass
else:
    raise AssertionError("Ожидалась отменённая задача")
```

`shutdown(cancel_futures=True)` пытается отменить ещё не запущенную работу. Уже выполняющиеся задачи продолжаются. В ProcessPool часть работ может стать running до фактического начала пользовательского callable в worker, поэтому отмена не равна удалению элемента из вашей исходной очереди.

### Ограничение очереди работ

Backpressure означает, что producer не может бесконечно опережать обработку. Нужен предел всего окна, а не только числа активных workers.

```python
from collections import deque
from concurrent.futures import ThreadPoolExecutor
from contextlib import closing


def bounded_map(pool, function, values, limit: int):
    if limit <= 0:
        raise ValueError("limit must be positive")
    source = iter(values)
    pending = deque()
    try:
        for _ in range(limit):
            try:
                value = next(source)
            except StopIteration:
                break
            pending.append(pool.submit(function, value))
        while pending:
            future = pending.popleft()
            yield future.result()
            try:
                value = next(source)
            except StopIteration:
                continue
            pending.append(pool.submit(function, value))
    finally:
        for future in pending:
            future.cancel()


consumed = []


def source():
    for number in range(10):
        consumed.append(number)
        yield number


with ThreadPoolExecutor(max_workers=2) as pool:
    with closing(bounded_map(pool, lambda value: value * 2, source(), 3)) as results:
        assert next(results) == 0
        assert len(consumed) == 3
        assert list(results) == list(range(2, 20, 2))
```

Пример сохраняет входной порядок и ограничивает предварительное чтение. Он не является fail-fast по дальней задаче: ошибка обнаруживается при ожидании её позиции. Проект ниже использует отдельный completion loop и проверяет ошибки по готовности.

Если consumer досрочно прекращает чтение generator, явно закройте его, чтобы сработал finally. Cancel оставшихся Future всё равно не убивает уже выполняющуюся работу; lifecycle executor остаётся обязанностью владельца.

### Deadlocks при ожидании задач внутри того же пула

Классическая ошибка: все workers ждут результаты задач, которые должны исполняться теми же занятыми workers.

| Ситуация | Почему нет продвижения |
| --- | --- |
| max_workers=1, задача ждёт вложенный submit | Второй callable некому выполнить |
| A ждёт B, B ждёт A | Цикл зависимостей |
| Callback ждёт coordinator, coordinator ждёт callback | Неявный цикл управления |

Координатор должен находиться вне пула исполнителей. Для зависимостей задавайте DAG или выполняйте композицию в родителе. Увеличение max_workers иногда маскирует проблему, но не делает протокол правильным.

Для ProcessPoolExecutor дополнительно соблюдайте прямое ограничение API: не используйте его Executor/Future-методы внутри отправленного callable для управления этим же пулом.

### Размер порции данных

Слишком маленькие задачи тратят время на scheduling и IPC. Слишком большие ухудшают распределение нагрузки, задерживают первую выдачу и делают отмену менее отзывчивой.

Размер чанка зависит от стоимости элемента и разброса. Для skewed-данных одинаковое число строк не означает одинаковое время обработки.

Различайте:

- логическую партию данных;
- одну задачу, отправленную через submit;
- chunksize процессного map;
- размер байтового I/O-буфера;
- число задач в незавершённом окне.

Проверяйте как steady throughput, так и tail latency, память и время остановки. В DE одна огромная partition может определять время всего этапа.

### Стоимость сериализации

Process pool может проигрывать из-за копирования, даже если задача выглядит CPU-bound. Измеряйте весь путь, а не только функцию внутри worker.

Передавайте компактный descriptor и возвращайте небольшой результат. Для повторно используемых больших данных рассмотрите initializer, memory mapping или shared memory с ясным владельцем.

Не помещайте клиент БД в аргументы задачи ради удобства: создайте соединение в worker и ограничьте его lifecycle. Для thread pool тоже проверьте, допускает ли клиент одновременное использование.

Обратный путь также может быть большим. Ограниченное число заданий не защищает от результата на несколько гигабайт, который executor должен доставить и удержать.

### Future: состояния, result(), exception(), callbacks и as_completed()

Future проходит состояния ожидания, выполнения и завершения либо отмены. `done` истинно и для ошибки, и для cancellation; успех подтверждается получением результата.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from queue import Queue

callbacks: Queue[int] = Queue()


def finished(future) -> None:
    callbacks.put(future.result())


with ThreadPoolExecutor(max_workers=2) as pool:
    futures = {pool.submit(pow, value, 2): value for value in (3, 1, 2)}
    for future in futures:
        future.add_done_callback(finished)
    observed = {}
    for future in as_completed(futures, timeout=5):
        observed[futures[future]] = future.result()
    assert observed == {1: 1, 2: 4, 3: 9}
    assert sorted(callbacks.get(timeout=3) for _ in range(3)) == [1, 4, 9]
```

Callback получает Future и может выполняться не в main thread; если Future уже завершён, добавленный callback может быть вызван сразу. Не делайте в callback долгую блокирующую работу и не стройте циклы ожиданий.

`exception` ожидает завершения и возвращает исключение либо None; на cancelled Future он поднимает CancelledError. Обработка Future-результата должна быть ровно определена владельцем, а не оставлена «где-нибудь в callback».

### Отмена ожидающей задачи vs остановка уже выполняющейся работы

Нужны три отдельных уровня:

| Действие | Что меняется |
| --- | --- |
| Перестать ждать | Caller получает timeout/cancellation |
| Отменить ожидающую задачу | Callable не должен начать исполняться |
| Остановить начавшуюся работу | Worker обрабатывает stop либо процесс прерывается |

Для потоков используйте кооперативный stop и ограниченные blocking calls. Для процесса допустима аварийная остановка, но она теряет finally и может нарушить IPC.

С Python 3.14 ProcessPoolExecutor предоставляет terminate_workers и kill_workers:

```python
# Python 3.14+
from concurrent.futures import ProcessPoolExecutor
import multiprocessing as mp

if __name__ == "__main__":
    pool = ProcessPoolExecutor(max_workers=1, mp_context=mp.get_context("spawn"))
    try:
        assert pool.submit(sum, [1, 2, 3]).result(timeout=10) == 6
    finally:
        pool.terminate_workers()
    try:
        pool.submit(sum, [4, 5])
    except RuntimeError:
        pass
    else:
        raise AssertionError("Закрытый executor нельзя переиспользовать")
```

В примере вычисление завершено до остановки; опасная семантика прерывания описана отдельно. Методы пытаются завершить живых workers и выполняют shutdown связанных ресурсов. После этого новые задачи в пул не отправляют.

Эти методы не добавляют аналог kill для ThreadPoolExecutor и не превращают подпроцесс с внешними потомками в автоматически управляемую process group.

### map(): chunksize, buffersize и различия executors

`chunksize` управляет группировкой входов ProcessPoolExecutor.map; у ThreadPoolExecutor и InterpreterPoolExecutor он не даёт такого процессного batching-эффекта.

С Python 3.14 `buffersize` ограничивает предварительную отправку задач, результаты которых ещё не выданы. Это backpressure, а не число workers.

```python
# Python 3.14+
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor
import multiprocessing as mp


def square(value: int) -> int:
    return value * value


if __name__ == "__main__":
    expected = [number * number for number in range(10)]
    with ThreadPoolExecutor(max_workers=2) as pool:
        assert list(pool.map(square, range(10), buffersize=3)) == expected
    with ProcessPoolExecutor(max_workers=2, mp_context=mp.get_context("spawn")) as pool:
        assert list(pool.map(square, range(10), chunksize=2, buffersize=2)) == expected
```

У процессного map один отправляемый chunk включает несколько исходных элементов, поэтому buffersize нельзя бездумно интерпретировать как точное число записей исходного iterable.

При сохранении порядка ранний медленный chunk удерживает последующую выдачу. Ограничение элементов не является пределом байтов памяти, а timeout map не является прерыванием процессов.

<a id="interpreters"></a>

## Несколько интерпретаторов в одном процессе

### Subinterpreters

Subinterpreter — дополнительное состояние интерпретатора внутри того же процесса. Это не новый PID и не автоматически новый поток.

В CPython несколько интерпретаторов давно существовали через C API; с Python 3.14 появился публичный высокоуровневый модуль `concurrent.interpreters` и соответствующий executor.

Отдельные interpreter state, imports и GIL позволяют выполнять Python-код параллельно в нескольких интерпретаторах обычной сборки. При этом память процесса, некоторые системные ресурсы и граница аварийного завершения остаются общими.

Этот подход интересен для независимых задач с ограниченным обменом. Он не является полным drop-in replacement для кода, который ожидает общий глобальный dict и произвольные общие клиенты.

### Изоляция состояния

Импортированный модуль и его globals обычно принадлежат конкретному интерпретатору.

```python
# Python 3.14+
import builtins
from concurrent import interpreters

interpreter = interpreters.create()
try:
    interpreter.exec("import builtins; builtins.chapter14_marker = 'child'")
    assert not hasattr(builtins, "chapter14_marker")
finally:
    interpreter.close()
```

Изоляция Python-namespace не означает независимость всего состояния ОС. Current working directory и некоторые настройки библиотек могут быть process-global. Нативное расширение может хранить собственные глобальные данные.

Не используйте subinterpreters для защиты секретов от недоверенного кода того же процесса. Ошибка памяти в расширении способна повредить весь процесс.

### concurrent.interpreters

Модуль даёт создание, перечисление, запуск кода и закрытие интерпретаторов. Прямой call выполняется синхронно в вызывающем потоке.

```python
# Python 3.14+
from concurrent import interpreters

interpreter = interpreters.create()
try:
    assert interpreter.call(sum, [1, 2, 3]) == 6
    assert interpreter.id != interpreters.get_main().id
finally:
    interpreter.close()
```

`exec` запускает код в namespace __main__ выбранного интерпретатора. `prepare_main` подготавливает передаваемые значения. Для отдельных задач с результатами удобнее executor; ручное переключение interpreter context само по себе не даёт конкурентности.

`call_in_thread` создаёт поток для выполнения, но lifecycle этого потока и передача ошибки всё равно требуют управления. Не закрывайте interpreter, пока в нём продолжается выполнение.

### InterpreterPoolExecutor

Каждый worker этого executor имеет свой поток и отдельный интерпретатор. Он доступен с Python 3.14.

```python
# Python 3.14+
from concurrent.futures import InterpreterPoolExecutor

with InterpreterPoolExecutor(max_workers=2) as pool:
    assert list(pool.map(pow, [2, 3, 4], [3, 2, 1])) == [8, 9, 4]
```

Callable, аргументы и результаты передаются с участием сериализации. Не считайте, что одинаковый PID отменяет цену обмена данными. Initializer нужен для состояния конкретного worker-интерпретатора, а не для произвольного общего singleton.

Нормальные исключения передаются через Future, но при невозможности сохранить исходный объект используются дополнительные сведения ExecutionFailed. Тестируйте реальные типы возвращаемых значений и ошибки ваших зависимостей.

Для новых interpreter-моделей особенно важны совместимые версии нативных библиотек и фактическая проверка на целевой сборке.

### Передача данных между интерпретаторами

Большинство обычных объектов копируются; некоторые неизменяемые данные передаются эффективнее, а специальные очереди и буферы допускают управляемое разделение.

```python
# Python 3.14+
from concurrent import interpreters

messages = interpreters.create_queue(maxsize=2)
original = [1, 2]
messages.put(original)
interpreter = interpreters.create()
try:
    interpreter.prepare_main(messages=messages)
    interpreter.exec(
        "value = messages.get(timeout=3)\nvalue.append(3)\nmessages.put(value)\n"
    )
    assert messages.get(timeout=3) == [1, 2, 3]
    assert original == [1, 2]
finally:
    interpreter.close()
```

Cross-interpreter Queue не является полной копией `queue.Queue`: у неё нет task_done, join и shutdown. Поэтому протокол завершения и подтверждения работы нужно задавать отдельно.

Если передаётся действительно общий изменяемый буфер, изоляция globals больше не защищает его содержимое. Нужны владелец, фазы доступа или синхронизация, согласованная между участниками.

### Совместимость нативных расширений

У расширения есть как минимум два отдельных вопроса совместимости: работа в нескольких интерпретаторах и работа без GIL. Поддержка одного не доказывает другое.

Расширение может хранить process-global state, ожидать один interpreter, требовать GIL или не поддерживать выбранный ABI. Ошибка может проявиться на import, в конкурентном вызове или только при финализации.

Проверяйте документацию библиотеки, её build/wheel и фактический сценарий с imports, выполнением и cleanup. Не отключайте защитные проверки CPython ради принудительного запуска несовместимой библиотеки.

Если интеграция ненадёжна в subinterpreters, отдельный процесс может быть более подходящей границей, несмотря на дополнительные копии данных.

### Выбор между потоками, процессами и интерпретаторами

| Требование | Разумный кандидат | Что измерить или проверить |
| --- | --- | --- |
| Общие объекты и блокирующий I/O | Потоки | Thread-safety клиента, timeouts, число соединений |
| Pure Python CPU в обычной сборке | Процессы или интерпретаторы | Запуск, IPC, imports, распределение задач |
| Изоляция нативного падения | Процессы | Lifecycle и восстановление после broken worker |
| Меньше OS-процессов и явная изоляция Python-state | Интерпретаторы | C extensions и стоимость передачи |
| Параллельный общий Python-state без GIL | Free-threaded threads | Runtime GIL, locks, память и contention |
| Большой immutable набор данных | Зависит от представления | Mapping/shared memory, копии и locality |

Число workers не должно автоматически равняться числу элементов. Начните с последовательной версии, добавьте одну модель, измерьте end-to-end и сравните при одинаковом бюджете CPU и памяти.

Проверка результата и lifecycle важнее красивого графика ускорения на синтетической задержке.

<a id="practice"></a>

## Практические примеры

### Параллельные I/O-операции

Для независимых файлов или запросов потоковый пул удобен, если каждая операция имеет ограничения размера и времени. Порядок выдачи выбирайте отдельно.

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
from pathlib import Path
import tempfile


def inspect_file(path: Path) -> tuple[str, int]:
    with path.open("rb") as stream:
        payload = stream.read(1025)
    if len(payload) > 1024:
        raise ValueError("file too large")
    return path.name, len(payload)


with tempfile.TemporaryDirectory() as directory:
    paths = [Path(directory) / f"{number}.txt" for number in range(3)]
    for number, path in enumerate(paths):
        path.write_bytes(b"x" * number)
    with ThreadPoolExecutor(max_workers=2) as pool:
        futures = [pool.submit(inspect_file, path) for path in paths]
        result = dict(future.result() for future in as_completed(futures, timeout=5))
    assert result == {"0.txt": 0, "1.txt": 1, "2.txt": 2}
```

Ограничение `read(1025)` помогает обнаружить слишком большой обычный файл. Оно не добавляет timeout медленному файловому хранилищу.

Для HTTP нужны connect/read/write/pool timeouts клиента и ограничение bytes ответа. Лимит executor не заменяет лимиты retry и нагрузки на внешнюю систему.

### Параллельные CPU-вычисления

Разбейте вычисление на независимые задачи и возвращайте небольшой результат. Сравните итог с последовательным oracle, прежде чем сравнивать скорость.

В обычной сборке рассмотрите процессы/интерпретаторы. В free-threaded-сборке повторите измерение с потоками после проверки runtime GIL и корректной синхронизации.

Записывайте размер данных, способ запуска процессов, warmup, workers, доступные CPU и расходы на передачу. Если benchmark состоит из нескольких тысяч простых операций, основным результатом может оказаться стоимость запуска.

При использовании BLAS/OpenMP учитывайте вложенные нативные потоки: четыре процесса по восемь потоков не эквивалентны четырём вычисляющим workers.

### Producer-consumer

Producer получает вход, workers преобразуют его, coordinator собирает результаты. Для каждой границы нужен ограниченный буфер и собственник.

| Вопрос | Пример решения |
| --- | --- |
| Кто выдаёт новые задачи? | Один coordinator с ограниченным окном |
| Где живёт изменяемый агрегат? | Только в coordinator |
| Как передать отказ? | Future или отдельный ограниченный error channel |
| Как остановить получение? | Stop token и завершение producer |
| Как закрыть потребителей? | Sentinel, queue shutdown или lifecycle executor |
| Кто публикует результат? | Один владелец после успешной проверки |

Не ждите queue.join, если вы уже знаете, что consumer погиб и никто не обработает оставшийся хвост. Политика abort должна объяснять, какие задания завершены, отброшены и доступны для повтора.

### Ограниченный пул работников

Ограничивайте весь незавершённый цикл: submitted → running → completed → ещё не опубликованный результат.

Если освобождать слот сразу при завершении дальней задачи, а выдавать строго по порядку, медленный первый элемент может привести к неограниченному reorder buffer. Поэтому completed-but-not-emitted также должен занимать слот окна.

В проекте ниже инвариант имеет вид: `pending + ready <= max_in_flight`. Новое чтение входа разрешается только при свободном месте в этом общем окне. Дополнительно ограничен размер каждого файла и суммарный JSONL-результат.

### Завершение обработки после ошибки

После первой наблюдаемой ошибки прекратите submit, подайте stop выполняющимся задачам, отмените ещё ожидающие Future и дождитесь освобождения принадлежащих вам workers.

Если несколько задач упали одновременно, «первая обнаруженная» ошибка не обязательно имеет наименьший входной индекс. Для детерминированного выбора ошибки пришлось бы задать дополнительный контракт и, возможно, ждать другие задачи.

Не публикуйте успешный префикс как полный результат партии. Для файлового отчёта можно писать во временный файл, а окончательную замену выполнять только после успешного завершения всех задач.

Повтор после отказа требует отдельной идемпотентности, если workers выполняли внешние side effects. В показанном проекте они только читают вход и возвращают данные.

### Корректная остановка приложения

Назначьте координатору ответственность за приём работ, дедлайн, отмену и публикацию. Workers владеют локальными файлами/соединениями и проверяют stop в безопасных точках.

Порядок штатного завершения: прекратить submit → дождаться уже принятой работы → собрать результаты → закрыть executor → опубликовать итог. Порядок abort: прекратить submit → установить stop → отменить pending → дождаться cleanup → удалить staging.

KeyboardInterrupt главного потока следует обрабатывать с выполнением того же cleanup. Для child-процессов полезно централизовать SIGINT в parent, чтобы несколько workers не пытались независимо управлять остановкой.

Cooperative stop не гарантирует жёсткого deadline, если worker вошёл в неограниченный внешний I/O. В таком сценарии нужны timeouts зависимости либо отдельная принудительно завершаемая process boundary с согласованным восстановлением.

**Практический проект: ограниченный параллельный сканер JSONL**

Построим небольшую CLI-программу `bounded-scan`. Она получает несколько обычных файлов, в которых каждая строка содержит JSON-целое от `0` до `1_000_000`. Для каждого файла программа возвращает число записей, сумму и SHA-256 исходных байтов. Потоковый и процессный backend дают одинаковый отчёт в порядке входных файлов.

Это учебный проект про владение конкурентной работой. Хеширование и файловый I/O могут исполняться нативным кодом и освобождать GIL; наличие процессного backend само по себе не доказывает ускорение этой нагрузки.

**Контракт входа и результата**

| Случай | Поведение |
| --- | --- |
| Пустой файл | Ноль записей, сумма `0`, хеш пустых bytes |
| Последняя строка без LF | Допустима |
| LF и CRLF | Допустимы; SHA-256 сохраняет различия исходных bytes |
| Пустая строка среди записей | Ошибка `invalid_json` |
| `true`, `null`, строка, список, объект, дробное число | Ошибка `invalid_value` |
| Отрицательное число или число больше `1_000_000` | Ошибка `invalid_value` |
| Некорректные UTF-8 или JSON | Ошибка с индексом файла и номером строки |
| Превышен лимит файла, строки или числа записей | Ошибка worker |
| Превышен лимит числа файлов или размера отчёта | Ошибка coordinator |
| Партия завершилась успешно | Полный JSONL-отчёт заменяет destination |
| Ошибка, отмена или обнаруженный дедлайн | Staging удаляется; прежний destination сохраняется |

Значения `NaN` и `Infinity`, которые Python JSON-декодер умеет принимать как расширение, также отвергаются проверкой типа. `bool` не проходит, хотя является подклассом `int`: здесь используется `type(value) is int`.

Вход считается доверенным в отношении расположения файлов. Это не sandbox файловой системы: код не защищает от подмены путей другим процессом, блокирующего открытия FIFO или специально настроенного сетевого хранилища. Проверка обычного файла через `fstat` выполняется после открытия. В реальном сервисе отдельно задают допустимый каталог, права доступа, политику symlinks и timeouts транспорта.

**Основные инварианты**

1. Только coordinator читает последовательность путей, меняет агрегат и пишет отчёт.
2. Worker открывает и закрывает свой файл самостоятельно.
3. В процессе не передаются открытые файлы, executor или callback из локальной функции.
4. `pending + ready <= max_in_flight`, включая результаты, ожидающие выдачи по порядку.
5. Ошибки извлекаются по готовности Future; медленный первый вход не скрывает отказ последующего.
6. На abort устанавливается общий stop, отменяются ожидающие Future и выполняется `shutdown(wait=True, cancel_futures=True)`.
7. Публикация выполняется после завершения executor и закрытия staging.

`RunStats` изменяет только coordinator. Готовность worker ещё не доказывает, что coordinator обновил статистику после `submit`: тест должен дождаться соответствующего события coordinator. Это существенно и при включённом GIL, и особенно заметно без него.

**Почему память ограничена**

Каждый выполняющийся worker читает не более `max_file_bytes + 1` байта для обнаружения превышения. После проверки размера он декодирует строки; ограничение `split(..., max_records)` не создаёт неограниченный список отдельных строк. В IPC возвращается небольшая сводка, а не содержимое файла.

Объём памяти зависит от числа workers, лимита файла, Python-overhead объектов и размера общего окна. Лимит bytes входа не равен точному RSS: одновременно могут существовать chunks, объединённые bytes, список строк и временные объекты JSON.

Координатор ограничивает также общее число файлов и размер staging. Весь отчёт не собирается в список в памяти. Итератор путей читается постепенно, но его собственный `next()` должен завершаться: блокирующий producer требует самостоятельной политики остановки.

**Как устроено ограниченное окно**

`pending` хранит ещё не извлечённые Future, `ready` — успешно полученные результаты, которые пока нельзя выдать. `next_emit` обозначает следующий входной индекс.

Заполнение разрешено только до общей границы окна. После `wait(FIRST_COMPLETED)` coordinator сразу вызывает `result()` для готовых задач. Результат с последующим индексом остаётся в `ready` и продолжает занимать слот. Последовательный потребитель получает только непрерывный готовый префикс.

Существует неизбежный компромисс: при строгом порядке выдачи и ограниченной памяти workers могут простаивать за медленной ранней задачей. Для большей пропускной способности можно изменить контракт на выдачу по готовности или писать промежуточные результаты во внешнее ограниченное хранилище.

**Как работает остановка**

В потоковом backend workers получают один `threading.Event` через `partial`. Для процессов создаётся `Event` выбранного multiprocessing-контекста; он передаётся при запуске workers через initializer. Отправлять такой объект заново в каждом задании процесса не требуется.

Глобальные `_PROCESS_STOP` и `_PROCESS_LIMITS` относятся к состоянию конкретного дочернего процесса. Потоковый backend не использует эти globals, поэтому независимые потоковые запуски не перезаписывают stop друг друга.

Дедлайн рассчитывается по `time.monotonic()`. Ожидание Future разбито на короткие ограниченные интервалы, чтобы coordinator мог заметить внешний cancel. Это polling сигнала отмены, а не случайная задержка для «исправления» гонки.

После обнаружения отмены уже начатая операция может ещё завершаться. Блокирующий файловый вызов не прерывается установкой Event. Поэтому `--timeout` задаёт кооперативный дедлайн, а не гарантированный момент выхода процесса.

Пользователь API может передать `cancel=threading.Event()` и установить его из другого потока. CLI обрабатывает `KeyboardInterrupt` после выполнения cleanup; initializer дочерних workers игнорирует SIGINT, чтобы координатор управлял остановкой. Жёсткое убийство процесса и повторные прерывания во время cleanup требуют отдельной эксплуатационной политики.

**Публикация результата**

Staging создаётся в каталоге destination: это позволяет выполнить `os.replace` в пределах одной файловой системы. Перед заменой выполняются `flush`, `fsync` файла и закрытие дескриптора.

Это обеспечивает атомарную видимость замены на файловой системе с соответствующими гарантиями `replace`. Это не полная гарантия сохранности после потери питания: для неё нужны отдельный разбор файловой системы, синхронизация каталога и требования платформы.

Замена является точкой commit. Запрос отмены, пришедший после последней проверки и уже выполненного commit, не откатывает опубликованный отчёт. При нескольких независимых запусках с одинаковым destination действует «последний commit победил»; межпроцессного lock для destination в проекте нет.

Новый файл получает права временного файла; проект не сохраняет ACL, владельца и исходные permissions прежнего отчёта. Для конфигурационных файлов с особыми требованиями эту политику следует задавать явно.

```python
def _checkpoint(
    stop: StopSignal | None,
    cancel: StopSignal | None,
    deadline: float | None,
    now: Callable[[], float] = time.monotonic,
) -> None:
    if (cancel is not None and cancel.is_set()) or (stop is not None and stop.is_set()):
        raise BatchCancelled("cancelled")
    if deadline is not None and now() >= deadline:
        raise BatchTimeout("deadline exceeded")


def analyze(job: Job, *, limits: ScanLimits, stop: StopSignal) -> ScanResult:
    _checkpoint(stop, None, None)
    chunks: list[bytes] = []
    size = 0
    with Path(job.path).open("rb") as source:
        if not stat.S_ISREG(os.fstat(source.fileno()).st_mode):
            raise JobError(job.index, "not_regular_file")
        while True:
            _checkpoint(stop, None, None)
            chunk = source.read(min(65_536, limits.max_file_bytes - size + 1))
            if not chunk:
                break
            size += len(chunk)
            if size > limits.max_file_bytes:
                raise JobError(job.index, "file_too_large")
            chunks.append(chunk)
    payload = b"".join(chunks)
    lines = payload.split(b"\n", limits.max_records) if payload else []
    if lines and lines[-1] == b"":
        lines.pop()
    total = 0
    for line_number, line in enumerate(lines, 1):
        _checkpoint(stop, None, None)
        if line_number > limits.max_records:
            raise JobError(job.index, "too_many_records", line_number)
        if line.endswith(b"\r"):
            line = line[:-1]
        if len(line) > limits.max_line_bytes:
            raise JobError(job.index, "line_too_large", line_number)
        try:
            value = json.loads(line.decode("utf-8"))
        except (ValueError, RecursionError) as error:
            raise JobError(job.index, "invalid_json", line_number) from error
        if type(value) is not int or not 0 <= value <= 1_000_000:
            raise JobError(job.index, "invalid_value", line_number)
        total += value
    _checkpoint(stop, None, None)
    return ScanResult(
        job.index,
        Path(job.path).name,
        len(lines),
        total,
        hashlib.sha256(payload).hexdigest(),
    )


def bounded_results(

    try:
        source = iter(jobs)
        while True:
            _checkpoint(stop, cancel, deadline, now)
            while not exhausted and len(pending) + len(ready) < max_in_flight:
                _checkpoint(stop, cancel, deadline, now)
                try:
                    job = next(source)
                except StopIteration:
                    exhausted = True
                    break
                if job.index != stats.submitted:
                    raise ValueError(
                        "jobs must have contiguous indices starting at zero"
                    )
                future = executor.submit(work, job)
                pending[future] = job.index
                stats.submitted += 1
                stats.peak_in_flight = max(
                    stats.peak_in_flight, len(pending) + len(ready)
                )

            while next_emit in ready:
                _checkpoint(stop, cancel, deadline, now)
                result = ready.pop(next_emit)
                next_emit += 1
                stats.emitted += 1
                yield result

            if not pending:
                if exhausted:
                    return
                continue

            timeout = (
                0.05 if deadline is None else max(0.0, min(0.05, deadline - now()))
            )
            done, _ = wait(pending, timeout=timeout, return_when=FIRST_COMPLETED)
            _checkpoint(stop, cancel, deadline, now)
            for future in done:
                index = pending.pop(future)
                result = future.result()
                if result.index != index:
                    raise ValueError("worker returned an unexpected index")
                ready[index] = result
    finally:
        stop.set()
        for future in pending:
            future.cancel()


_PROCESS_STOP: StopSignal | None = None
_PROCESS_LIMITS: ScanLimits | None = None


def _initialize_process(stop: StopSignal, limits: ScanLimits) -> None:
    global _PROCESS_STOP, _PROCESS_LIMITS
    _PROCESS_STOP = stop
    _PROCESS_LIMITS = limits
    # The coordinator owns Ctrl+C and requests cooperative worker cancellation.
    signal.signal(signal.SIGINT, signal.SIG_IGN)


def _process_work(job: Job) -> ScanResult:
    if _PROCESS_STOP is None or _PROCESS_LIMITS is None:
        raise RuntimeError("worker was not initialized")
    return analyze(job, limits=_PROCESS_LIMITS, stop=_PROCESS_STOP)


def _backend(
    options: Options, limits: ScanLimits
) -> tuple[StopSignal, Executor, Callable[[Job], ScanResult]]:
    if options.backend == "thread":
        stop = Event()
        pool = ThreadPoolExecutor(
            max_workers=options.workers, thread_name_prefix="bounded-scan"
        )
        return stop, pool, partial(analyze, limits=limits, stop=stop)
    context = mp.get_context(options.start_method)
    process_stop = context.Event()
    process_pool = ProcessPoolExecutor(
        max_workers=options.workers,
        mp_context=context,
        initializer=_initialize_process,
        initargs=(process_stop, limits),
    )
    return process_stop, process_pool, _process_work


def _jobs(paths: Iterable[Path], output: Path, limits: ScanLimits) -> Iterator[Job]:
    destination = output.resolve()
    for index, path in enumerate(paths):
        if index >= limits.max_files:
            raise BatchLimitError("too_many_files")
        absolute = Path(path).absolute()
        if absolute.resolve() == destination:
            raise ValueError("output must differ from every input")
        yield Job(index, str(absolute))


def run_scan(
    paths: Iterable[Path],
    output: Path,
    *,
    options: Options = Options(),
    limits: ScanLimits = ScanLimits(),
    cancel: StopSignal | None = None,
) -> RunSummary:
    """Publish one complete report; preserve the old destination on failure."""
    deadline = None if options.timeout is None else time.monotonic() + options.timeout
    _checkpoint(None, cancel, deadline)
    output = Path(output).absolute()
    staging: Path | None = None
    stats = RunStats()
    files = records = total = written = 0
    try:
        with tempfile.NamedTemporaryFile(
            mode="wb",
            prefix=".bounded-scan-",
            suffix=".tmp",
            dir=output.parent,
            delete=False,
        ) as target:
            staging = Path(target.name)
            stop, executor, work = _backend(options, limits)
            try:
                results = bounded_results(
                    executor,
                    work,
                    _jobs(paths, output, limits),
                    max_in_flight=options.max_in_flight,
                    stop=stop,
                    stats=stats,
                    cancel=cancel,
                    deadline=deadline,
                )
                with closing(results):
                    for result in results:
                        encoded = (
                            json.dumps(
                                result.as_dict(),
                                ensure_ascii=True,
                                separators=(",", ":"),
                            )
                            + "\n"
                        ).encode("ascii")
                        written += len(encoded)
                        if written > limits.max_output_bytes:
                            raise BatchLimitError("output_too_large")
                        target.write(encoded)
                        files += 1
                        records += result.records
                        total += result.total
            finally:
                stop.set()
                executor.shutdown(wait=True, cancel_futures=True)
            _checkpoint(None, cancel, deadline)
            target.flush()
            os.fsync(target.fileno())
        _checkpoint(None, cancel, deadline)
        os.replace(staging, output)
        staging = None
        return RunSummary(files, records, total, stats.peak_in_flight)
    finally:
        if staging is not None:
            staging.unlink(missing_ok=True)
```

```python
import argparse
import json

from pathlib import Path

from .core import BatchCancelled, BatchTimeout, JobError, Options, run_scan


def main(argv: list[str] | None = None) -> int:
    parser = argparse.ArgumentParser(
        description="Scan bounded JSONL integer files in input order"
    )
    parser.add_argument("inputs", type=Path, nargs="+")
    parser.add_argument("--output", type=Path, required=True)
    parser.add_argument("--backend", choices=("thread", "process"), default="thread")
    parser.add_argument("--workers", type=int, default=2)
    parser.add_argument("--max-in-flight", type=int, default=4)
    parser.add_argument("--timeout", type=float)
    parser.add_argument(
        "--start-method", choices=("spawn", "forkserver"), default="spawn"
    )
    args = parser.parse_args(argv)
    try:
        options = Options(
            backend=args.backend,
            workers=args.workers,
            max_in_flight=args.max_in_flight,
            timeout=args.timeout,
            start_method=args.start_method,
        )
    except ValueError as error:
        print(
            json.dumps({"error": "invalid_options", "detail": str(error)}),
            file=sys.stderr,
        )
        return 2
    try:
        result = run_scan(args.inputs, args.output, options=options)
    except BatchTimeout:
        print(json.dumps({"error": "deadline_exceeded"}), file=sys.stderr)
        return 124
    except (BatchCancelled, KeyboardInterrupt):
        print(json.dumps({"error": "cancelled"}), file=sys.stderr)
        return 130
    except JobError as error:
        print(
            json.dumps(
                {"error": error.code, "job": error.index, "line": error.line_number}
            ),
            file=sys.stderr,
        )
        return 1
    except (OSError, ValueError, BrokenExecutor) as error:
        print(json.dumps({"error": type(error).__name__}), file=sys.stderr)
        return 1
    print(json.dumps(result.as_dict(), sort_keys=True))
    return 0
```

**Файл `tests/test_properties.py`**

```python
# project: tests/test_properties.py
import hashlib
import json
import tempfile
from pathlib import Path

from hypothesis import given, settings
from hypothesis import strategies as st

from bounded_scan import Options, run_scan


@settings(max_examples=40, deadline=None)
@given(
    batches=st.lists(st.lists(st.integers(0, 1_000_000), max_size=20), max_size=5),
    window=st.integers(1, 5),
    workers=st.integers(1, 3),
    final_lf=st.booleans(),
)
def test_parallel_report_matches_serial_oracle(batches, window, workers, final_lf):
    with tempfile.TemporaryDirectory() as directory:
        root = Path(directory)
        paths = []
        expected = []
        for index, values in enumerate(batches):
            path = root / f"данные-{index}.jsonl"
            payload = "\n".join(map(str, values)).encode("ascii")
            if values and final_lf:
                payload += b"\n"
            path.write_bytes(payload)
            paths.append(path)
            expected.append(
                {
                    "index": index,
                    "name": path.name,
                    "records": len(values),
                    "total": sum(values),
                    "sha256": hashlib.sha256(payload).hexdigest(),
                }
            )
        output = root / "report.jsonl"
        options = Options(workers=workers, max_in_flight=window)
        report = run_scan(paths, output, options=options)
        first = output.read_bytes()
        assert [json.loads(line) for line in first.splitlines()] == expected
        assert (report.files, report.records, report.total) == (
            len(batches),
            sum(map(len, batches)),
            sum(map(sum, batches)),
        )
        assert report.peak_in_flight <= window
        run_scan(paths, output, options=options)
        assert output.read_bytes() == first
```

`python -m bounded_scan` запускается как обычный модуль с защищённой точкой входа. Не переносите вызов `run_scan(..., backend="process")` на верхний уровень импортируемого скрипта. В собственном приложении используйте `if __name__ == "__main__":` и передавайте backend через `Options`.

**Exit codes и эксплуатационный контракт**

| Код | Значение |
| --- | --- |
| `0` | Полная партия опубликована |
| `1` | Ошибка входных данных, I/O, ограничений партии или сломанный executor |
| `2` | Неправильные аргументы или значения параметров |
| `124` | Coordinator обнаружил истечение дедлайна и выполнил cleanup |
| `130` | Отмена или KeyboardInterrupt с выполнением cleanup |

Стандартный вывод содержит только успешную JSON-сводку; диагностический JSON направляется в stderr. У ошибки записи есть индекс задания и номер строки. Для случайных исключений программа не публикует содержимое исходных строк.

Это коды контролируемых путей завершения программы. `SIGKILL`, падение нативной библиотеки, ошибка импорта и отказ самого cleanup могут завершить её по правилам ОС и Python.

**Что проверяют тесты**

Тест «медленная первая задача» удерживает первый worker через Event и дожидается, когда coordinator уже перенёс два последующих результата в буфер. До освобождения первого worker источник должен прочитать только размер окна.

Недостаточно дождаться события worker и сразу прочитать `RunStats`: worker может начать работу ещё до возврата `executor.submit`. В тесте есть отдельная наблюдаемая точка `wait` coordinator. Это позволяет проверять инвариант по состоянию, а не надеяться на удачную задержку.

Тест «ошибка второй задачи» удерживает первую до stop. Coordinator обязан обнаружить отказ второй, установить stop и завершить владельца пула. Реализация, которая просто ждёт `result()` первой Future, этот сценарий не пройдёт.

Для дедлайна используется управляемый clock: время меняется после начала работы, без ожидания случайного количества миллисекунд. Значения `Event.wait(timeout=...)` и `Thread.join(timeout=...)` в тестах служат ограничителями неисправного сценария.

Интеграционные тесты запускают настоящий spawn-пул и проверяют передачу `JobError`, отсутствие оставшихся workers, сохранность прежнего destination, удаление staging и поведение при `fsync/replace`-ошибках. Сценарий KeyboardInterrupt моделируется исключением из producer; это проверка cleanup, а не полноценный тест доставки сигналов всеми ОС.

CLI запускается из установленного wheel, с `-I` и `-O`. Это помогает обнаружить случайную зависимость от рабочего каталога и runtime-валидацию, ошибочно написанную через `assert`.

Property-based-тест генерирует значения, размеры партий, число workers и размер окна. Он сравнивает итог с последовательным oracle и проверяет повторную публикацию идентичного отчёта. `deadline=None` относится к таймингу Hypothesis, а не отключает дедлайны программы.

`forkserver`-тест запускается только при поддержке платформы и возможности создать Unix socket. Перечень `get_all_start_methods()` описывает платформенную поддержку, но не отменяет ограничения контейнера.

**Как осмысленно измерять производительность**

1. Подготовьте воспроизводимый набор неизменяемых файлов и последовательный oracle.
2. Сначала проверьте равенство отчётов, затем измеряйте время.

Один интеграционный тест `forkserver` пропущен на каждом интерпретаторе: проверочная среда запрещает Unix sockets, необходимые этому start method. `spawn` проверен настоящими дочерними процессами; пример Manager проверен через loopback TCP. Windows и macOS в эту локальную матрицу не входили.

Успешные тесты не доказывают отсутствие всех возможных interleavings. Здесь они проверяют конкретные инварианты управляемыми сценариями, настоящий IPC и сравнение с последовательным результатом.
