# 6. Статическая типизация и система типов

Типизация помогает описывать допустимые значения, связи между входом и результатом, возможности зависимостей и варианты состояния. Хорошие аннотации делают ошибки заметными до запуска и сохраняют информацию при передаче данных между функциями. Они особенно полезны на границах большого проекта, где один разработчик уже не может держать все контракты в памяти.

Python остаётся динамически типизированным языком. Аннотация сама по себе не проверяет HTTP-запрос, не преобразует JSON в модель и не блокирует неверное присваивание. Статическая проверка, runtime-валидация и тестирование дополняют друг друга и дают разные гарантии.

Глава сохраняет все семь тем и 36 пунктов README. Основные примеры рассчитаны на Python 3.12–3.14. Новый синтаксис параметров типов требует 3.12, значения параметров типов по умолчанию в новом синтаксисе — 3.13, `annotationlib` — 3.14. Для переносимых примеров с `TypeIs` и `ReadOnly` используется `typing_extensions`; это отдельная зависимость. Поддержка синтаксиса интерпретатором и поддержка правила анализатором проверяются независимо.

Короткие блоки независимы. Метка `# typing: negative` обозначает намеренно неверный код для проверки диагностики: такой блок не нужно запускать как программу. Метка `# typing: runtime` обозначает эксперимент с runtime-поведением, который может намеренно противоречить статическому контракту. `# typing: stub` отмечает описание `.pyi`, а не исполняемый модуль. Остальные короткие примеры предназначены для исполнения и проверки типов. Связанные файлы практического проекта отмечены путями; его `negative_*.py` также предназначены только для анализаторов.

## Основы постепенной типизации

### Статическая проверка vs runtime-валидация

**Статическая проверка** анализирует исходный код без обычного выполнения программы. Она проверяет совместимость аргументов, возвращаемых значений, присваиваний и операций, используя аннотации, вывод типов, stubs и правила выбранного инструмента.

**Runtime-валидация** проверяет реальные значения во время работы. Она отвечает на вопросы «действительно ли пришёл словарь», «существует ли поле», «положительно ли число», «не равен ли пароль пустой строке». Статический тип `int` не выражает произвольный числовой диапазон и не проверяет внешнее значение автоматически.

```python
def twice(value: int) -> int:
    return value * 2


assert twice(3) == 6
```

```python
# typing: negative
def twice(value: int) -> int:
    return value * 2


result = twice("3")  # error: передана строка вместо int.
```

В runtime такая функция со строкой могла бы вернуть `"33"`: оператор умножения существует и для строк. Статический контракт запрещает этот вызов независимо от случайной работоспособности выражения.

```python
def positive_count(value: object) -> int:
    if not isinstance(value, int) or isinstance(value, bool) or value <= 0:
        raise ValueError("Ожидается положительное целое число без bool")
    return value


assert positive_count(5) == 5
for invalid in (True, 0, -1, "5", None):
    try:
        positive_count(invalid)
    except ValueError:
        pass
    else:
        raise AssertionError(f"Принято некорректное значение: {invalid!r}")
```

Проверка `bool` нужна потому, что `bool` — подкласс `int`. Статический тип `int` обычно допускает `True`, хотя предметная область количества может это запрещать. Аналогично числовая совместимость аннотаций допускает передачу `int` там, где ожидается `float`; это правило типизации, а не преобразование объекта в runtime.

| Механизм | Что проверяет | Чего сам по себе не гарантирует |
|---|---|---|
| mypy / Pyright | Совместимость операций и заявленных типов | Достоверность внешних данных, отсутствие всех ошибок |
| Валидатор | Конкретные значения и инварианты на границе | Правильность всех дальнейших вызовов |
| Тесты | Наблюдаемое поведение на выбранных сценариях | Исчерпывающий перебор входов |
| Аннотации без анализатора | Описание намерения для людей и инструментов | Принудительное соблюдение контракта |

Система Python является **постепенной**: типизированные и динамические участки могут сосуществовать. Она намеренно допускает выходы вроде `Any` и `cast`; поэтому успешная проверка не является математическим доказательством безопасности произвольной программы.

Аннотируйте границы, где информация особенно важна: публичные функции, результаты парсинга, зависимости сервиса, возвращаемые значения из инфраструктуры. Для локального `count = 0` анализатор обычно сам выводит `int`. Избыточная ручная аннотация каждого промежуточного выражения редко полезна.

### Any vs object; строгая проверка и распространение Any

`object` означает: «значение может быть любым Python-объектом, поэтому использовать можно только известные общие операции». `Any` означает: «для этого участка разрешаем операции без обычной проверки совместимости». Это принципиально разные контракты.

```python
def describe(value: object) -> str:
    if isinstance(value, str):
        return value.upper()
    if isinstance(value, int):
        return f"number:{value}"
    return type(value).__name__


assert describe("python") == "PYTHON"
assert describe(5) == "number:5"
assert describe(None) == "NoneType"
```

```python
# typing: negative
def uppercase(value: object) -> str:
    return value.upper()  # error: object не обещает метод upper.
```

С `Any` аналогичный доступ разрешается, даже если реальный объект не имеет нужного метода. `Any` присваивается точным типам и принимает их значения без обычных ограничений; его нельзя понимать как обычный общий надтип наподобие `object`.

```python
# typing: runtime
from typing import Any


payload: Any = {"count": "three"}
count: int = payload["count"]
assert isinstance(count, str)

try:
    count + 1
except TypeError:
    pass
else:
    raise AssertionError("Аннотация не преобразовала строку в число")
```

**Откуда появляется `Any`:** неаннотированные функции, непараметризованные generics, некоторые API стандартной библиотеки вроде `json.loads`, неполные stubs, игнорируемые импорты и намеренные casts. Если функция возвращает `Any`, операции над её результатом тоже часто теряют проверяемость.

```python
import json


def read_json(text: str) -> object:
    # Широкий безопасный контракт: после чтения значение ещё не проверено.
    result: object = json.loads(text)
    return result


raw = read_json('{"count": 3}')
assert isinstance(raw, dict)
```

Возврат `object` не валидирует JSON, но не позволяет потребителю автоматически считать его проверенной схемой. `dict[str, Any]` уже обещает словарь со строковыми ключами и оставляет значения динамическими; `Any` вообще не обещает даже внешний словарь. Выбирайте честную степень знания.

`list[Any]` и `list[object]` также различаются. Во втором случае элементы нужно сужать перед специфическими операциями. В первом `Any` участвует в постепенной совместимости и способен обходить ограничения, которые обычная инвариантность наложила бы на `list[int]` и `list[object]`.

**Strict не означает запрет любого Any.** Набор флагов зависит от анализатора и версии. mypy `strict` усиливает требования к аннотациям и ряду динамических путей, но не запрещает каждый явный `Any`. Pyright различает `Any` и `Unknown`; strict-режим обычно существенно усиливает диагностику неизвестных типов, однако это не тождественный набор проверок.

При миграции локализуйте динамическую границу, возвращайте из неё `object` или проверенную модель и не распространяйте `Any` через весь сервис. Простое добавление `-> Any` к каждому сложному месту делает отчёт анализатора тише, но уменьшает полезность контракта.

### Встроенные generics, объединения T | U и Optional

В современном коде используйте встроенные параметры коллекций: `list[int]`, `dict[str, float]`, `set[str]`, `tuple[int, str]`. Для интерфейсов полезны ABC из `collections.abc`: `Iterable`, `Sequence`, `Mapping`, `Callable`.

```python
from collections.abc import Mapping, Sequence


def total_selected(names: Sequence[str], counts: Mapping[str, int]) -> int:
    return sum(counts.get(name, 0) for name in names)


assert total_selected(("a", "b"), {"a": 2, "b": 3}) == 5
```

| Аннотация | Смысл |
|---|---|
| `list[int]` | Изменяемый список целых значений |
| `tuple[int, str]` | Кортеж ровно из двух элементов указанных типов |
| `tuple[int, ...]` | Кортеж целых произвольной длины, включая пустой |
| `tuple[()]` | Только пустой кортеж |
| `dict[str, int]` | Конкретный изменяемый словарь |
| `Mapping[str, int]` | Интерфейс чтения отображения |
| `str \| bytes` | Значение одного из двух типов |
| `str \| None` | Строка либо None |
| `Optional[str]` | Та же объединённая форма `str \| None` |

`Optional` относится к **значению**, а не к обязательности аргумента. В `def f(x: str | None)` аргумент обязателен, но может быть `None`. В `def g(x: str = "")` аргумент можно не передать, хотя `None` не разрешён.

```python
def required_nullable(value: str | None) -> str:
    return "missing value" if value is None else value


def optional_argument(value: str = "default") -> str:
    return value


assert required_nullable(None) == "missing value"
assert optional_argument() == "default"
```

Аннотация `str` со значением по умолчанию `None` не должна использоваться как неявная замена `str | None`. Современная строгая проверка требует выразить nullable-состояние явно.

Объединение не является списком правил преобразования: `int | str` не пытается автоматически привести строку к числу. Для каждого допустимого варианта реализация должна иметь понятное поведение.

```python
def normalize_key(value: int | str) -> str:
    if isinstance(value, str):
        return value.strip()
    return str(value)


assert normalize_key(" a ") == "a"
assert normalize_key(12) == "12"
```

**Runtime и generics.** `list[int]` существует как параметризованное описание, но обычный список не хранит гарантию типов своих элементов. `isinstance(values, list[int])` не является валидатором содержимого и вызывает `TypeError`.

```python
# typing: runtime
values = [1, 2]
assert isinstance(values, list)
try:
    isinstance(values, list[int])
except TypeError:
    pass
else:
    raise AssertionError("Параметризованный list нельзя использовать так")
```

### None, отсутствующий аргумент и nullable-поле

Три разных ситуации часто ошибочно объединяют:

- аргумент вообще не передан;
- аргумент передан со значением `None`;
- ключ отсутствует в словаре.

В PATCH-подобной операции это могут быть разные команды: не менять поле, очистить поле и записать новое значение. Если использовать `None` одновременно как default и как команду очистки, различие исчезнет.

```python
from enum import Enum, auto


class Missing(Enum):
    TOKEN = auto()


def patch_title(value: str | None | Missing = Missing.TOKEN) -> str:
    if isinstance(value, Missing):
        return "unchanged"
    if value is None:
        return "clear"
    return f"set:{value.strip()}"


assert patch_title() == "unchanged"
assert patch_title(None) == "clear"
assert patch_title(" Python ") == "set:Python"
```

Enum-маркер даёт именованный отдельный тип и понятное сужение. У обычного `MISSING = object()` runtime-идентичность также работает, но анализатору может быть труднее вывести остаточный тип после проверки `is`. Нельзя объявлять всю входную величину просто `object`, а затем ожидать, что тип строки восстановится без дополнительных проверок.

Для словаря `{"title": None}` ключ присутствует. `data.get("title")` без отдельного маркера возвращает `None` и для этого случая, и для отсутствующего ключа. Если различие важно, проверяйте `"title" in data` либо используйте отдельный default-маркер.

В `TypedDict` обязательность ключа задают `Required`/`NotRequired`, а nullable-значение — `T | None`. Эти оси независимы: `NotRequired[str | None]` допускает отсутствие, строку и `None`, а `title: str | None` требует присутствия ключа.

**Отсутствие значения не всегда ошибка.** Иногда пустой результат естественен: поиск возвращает `User | None`. Если продолжение без пользователя недопустимо, вызывающий код должен обработать этот вариант, а не заставить анализатор замолчать через `cast(User, result)`.

### Type aliases, оператор type и NewType

Alias даёт существующему типу другое имя без создания нового статического домена. Он упрощает сигнатуры, но не отличает два идентификатора с одинаковым базовым типом.

```python
type UserName = str
type Coordinates = tuple[float, float]


def display(name: UserName, position: Coordinates) -> str:
    return f"{name}@{position[0]},{position[1]}"


assert display("Ada", (1.0, 2.0)) == "Ada@1.0,2.0"
```

Оператор `type` появился в Python 3.12 и создаёт `TypeAliasType`. Значение alias вычисляется лениво; это помогает описывать рекурсивные структуры и forward references. Для старых версий встречается `Alias = ...` и явное `Alias: TypeAlias = ...`.

```python
type JsonValue = (
    None | bool | int | float | str | list[JsonValue] | dict[str, JsonValue]
)


def is_scalar(value: JsonValue) -> bool:
    return not isinstance(value, (list, dict))


assert is_scalar({"id": 1}) is False
assert is_scalar("python") is True
```

Это описание формы Python-значения, а не полный контракт JSON: оно не запрещает `NaN`, не ограничивает глубину и размер, не проверяет входную строку. Рекурсивный тип не является автоматически рекурсивным валидатором.

`NewType` создаёт отдельное **статическое** имя для домена. `UserId` можно передать там, где нужен `int`, но обычный `int` не должен без явной маркировки попадать туда, где требуется `UserId`.

```python
from typing import NewType


UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)


def user_path(user_id: UserId) -> str:
    return f"/users/{user_id}"


identifier = UserId(42)
assert user_path(identifier) == "/users/42"
assert type(identifier) is int
assert UserId(identifier) is identifier
```

```python
# typing: negative
from typing import NewType


UserId = NewType("UserId", int)
OrderId = NewType("OrderId", int)


def user_path(user_id: UserId) -> str:
    return f"/users/{user_id}"


user_path(OrderId(42))  # error: OrderId не является UserId.
user_path(42)  # error: обычный int не является UserId.
```

В runtime вызов `NewType` возвращает исходный объект. Он не проверяет положительность ID, не создаёт новый подкласс `int` и не подходит как второй аргумент `isinstance`. Операция `UserId(1) + 1` обычно имеет тип `int`, а не автоматически `UserId`: сохранение предметного смысла нужно проектировать.

| Задача | Подход |
|---|---|
| Сократить длинную сигнатуру | Alias |
| Различать ID пользователя и заказа без runtime-обёртки | `NewType` |
| Проверять диапазон и сохранять собственное поведение | Валидатор и/или объект-значение |
| Получить настоящий runtime-подкласс | Обычный класс с осмысленным контрактом |

Alias из `type` не следует считать классом для `isinstance`: даже если он ссылается на класс, сам alias — иной runtime-объект. Для интроспекции существуют документированные средства, рассмотренные далее.

### Literal, LiteralString, Annotated, Final и ClassVar

Эти конструкции решают разные задачи; общий внешний вид квадратных скобок не делает их валидаторами.

**`Literal` — конкретные значения.**

```python
from typing import Literal


type Mode = Literal["strict", "lenient"]


def explain(mode: Mode) -> str:
    if mode == "strict":
        return "reject invalid data"
    return "collect rejected rows"


assert explain("strict") == "reject invalid data"
```

```python
# typing: negative
from typing import Literal


def configure(mode: Literal["strict", "lenient"]) -> None:
    pass


configure("strcit")  # error: опечатка не входит в набор Literal.
```

Литеральные типы удобны для режимов и tags объединения. Аннотация не меняет runtime: неподдерживаемая строка не будет автоматически отклонена, если реализация сама её не проверяет. Также анализатор может вывести обычный `str` вместо `Literal["strict"]`; при необходимости используйте явную аннотацию литерального значения.

**`LiteralString` — происхождение строки.** Он выражает строку, известную как литеральная или полученную допустимыми операциями над такими строками. Это не «строка без опасных символов» и не результат любого escape-фильтра.

```python
from typing import LiteralString


def build_template(template: LiteralString) -> str:
    return template


assert build_template("SELECT id FROM events WHERE kind = ?") == (
    "SELECT id FROM events WHERE kind = ?"
)
```

Поддержка проверок `LiteralString` зависит от анализатора и версии. Для SQL используйте параметризованные запросы: даже корректная литеральная аннотация не доказывает безопасность динамической вставки значения в запрос и не заменяет правила драйвера.

**`Annotated[T, ...]` — тип плюс метаданные.** Анализатор, не понимающий метаданные, рассматривает базовый `T`. Конкретный framework может прочитать дополнительные значения и реализовать собственное поведение.

```python
from typing import Annotated, get_args, get_origin


PositiveCount = Annotated[int, "must be positive"]
assert get_origin(PositiveCount) is Annotated
assert get_args(PositiveCount) == (int, "must be positive")
```

Строка `"must be positive"` не выполняет проверку. Pydantic, web framework или собственный валидатор могут договориться о трактовке метаданных, но это контракт потребителя, а не универсальная семантика Python. Порядок и содержимое метаданных могут быть значимыми для такой библиотеки.

**`Final` — ограничение перепривязки для статической проверки.** Оно не делает содержимое объекта неизменяемым.

```python
from typing import Final


DEFAULT_LIMIT: Final[int] = 100
ALLOWED: Final[list[str]] = ["read"]
ALLOWED.append("write")
assert ALLOWED == ["read", "write"]
assert DEFAULT_LIMIT == 100
```

```python
# typing: negative
from typing import Final


LIMIT: Final[int] = 100
LIMIT = 200  # error: переприсваивание Final.
```

Декоратор `@final` относится к классу или методу: запрещает наследование/переопределение на уровне анализатора. Для явного намерения переопределения есть `@override` с Python 3.12. Ни один из этих декораторов сам по себе не создаёт runtime-защиту от изменения класса.

**`ClassVar` — переменная класса.** Она отделяет общее состояние класса от поля экземпляра для анализатора и dataclass-генерации.

```python
from dataclasses import dataclass, fields
from typing import ClassVar


@dataclass
class Settings:
    namespace: ClassVar[str] = "service"
    retries: int = 3


assert [item.name for item in fields(Settings)] == ["retries"]
assert Settings.namespace == "service"
```

`ClassVar` не запрещает runtime-присваивание через экземпляр. Для общего изменяемого значения по-прежнему нужны политика владения, ограничения роста и синхронизация. Если комбинируете `Final` и `ClassVar`, учитывайте версию: вложение этих квалификаторов было расширено в Python 3.13.

### Self, Never и NoReturn

`Self` обозначает фактический тип текущего класса в контексте наследования. Он полезен для fluent-методов и альтернативных конструкторов, которые действительно сохраняют тип подкласса.

```python
from typing import Self


class Query:
    def __init__(self, clauses: tuple[str, ...] = ()) -> None:
        self.clauses = clauses

    def where(self, clause: str) -> Self:
        return type(self)((*self.clauses, clause))

    @classmethod
    def empty(cls) -> Self:
        return cls()


class SpecializedQuery(Query):
    pass


query = SpecializedQuery.empty().where("active")
assert type(query) is SpecializedQuery
assert query.clauses == ("active",)
```

Сигнатура конструктора подкласса должна оставаться совместимой. Если метод всегда возвращает базовый `Query`, аннотация `-> Self` будет нечестной. Используйте `-> Query`, когда результат намеренно имеет базовый тип. `Self` не является обычным типовым параметром, который можно объявлять в произвольной свободной функции.

`Never` — нижний тип: у него нет допустимых значений. Он полезен для ветвей, в которых уже исчерпаны все варианты, и функций, которые не возвращают управление обычным способом. `NoReturn` традиционно используется для последнего случая. Статически оба обозначают отсутствие нормального возвращаемого значения.

```python
from typing import Never, NoReturn


def fail(message: str) -> NoReturn:
    raise ValueError(message)


def impossible(value: Never) -> Never:
    raise AssertionError(f"Недостижимое значение: {value!r}")


def require_name(value: str | None) -> str:
    if value is None:
        fail("Имя отсутствует")
    return value


assert require_name("Ada") == "Ada"
```

`None` как тип результата означает нормальное завершение без полезного значения. `Never`/`NoReturn` означают отсутствие нормального завершения. Это различие помогает анализатору понять, что после вызова `fail()` не нужно дополнительно обрабатывать nullable-значение.

Аннотация `NoReturn` не обещает, что программа физически никогда не завершится: функция может выбросить исключение или завершить процесс. Если она иногда делает обычный `return`, реализация нарушает статический контракт. Исчерпывающую обработку вариантов далее проверим через `assert_never`.

**Документация:** [typing](https://docs.python.org/3.14/library/typing.html), [спецификация аннотаций](https://typing.python.org/en/latest/spec/annotations.html), [постепенная система типов](https://typing.python.org/en/latest/spec/concepts.html).

## Обобщённые функции и классы — Generics

### TypeVar: bounds, constraints и значения по умолчанию

Типовой параметр выражает связь между несколькими частями контракта. В `identity(value: T) -> T` результат сохраняет тип переданного значения. Если заменить оба `T` на `object`, связь исчезнет: потребитель будет знать только `object`.

```python
from typing import TypeVar, assert_type


T = TypeVar("T")


def identity(value: T) -> T:
    return value


def example(value: int) -> int:
    result = identity(value)
    assert_type(result, int)
    return result


assert example(5) == 5
assert identity("python") == "python"
```

Типовой параметр выбирается для отдельного вызова; он не становится навсегда `int` после первого использования. В generic-классе параметр, наоборот, связан с конкретной специализацией объекта и используется его методами согласованно.

**Bound — верхняя граница.** Он сообщает, какие операции допустимы над параметром, сохраняя возможность конкретного подкласса.

```python
from collections.abc import Sized
from typing import TypeVar


S = TypeVar("S", bound=Sized)


def longer(first: S, second: S) -> S:
    return first if len(first) >= len(second) else second


assert longer([1], [1, 2]) == [1, 2]
assert longer("abc", "x") == "abc"
```

Bound не означает точное совпадение runtime-классов двух аргументов. Анализатор может подобрать общий подходящий тип. Если алгоритм требует одинаковой кодировки, валюты или иной связи значений, bound сам этого не проверяет.

**Constraints — конечный набор разрешённых вариантов параметра.** Они полезны, когда все связанные позиции должны использовать один из заранее определённых типов.

```python
from typing import TypeVar


Text = TypeVar("Text", str, bytes)


def concatenate(first: Text, second: Text) -> Text:
    return first + second


assert concatenate("py", "thon") == "python"
assert concatenate(b"py", b"thon") == b"python"
```

```python
# typing: negative
from typing import TypeVar


Text = TypeVar("Text", str, bytes)


def concatenate(first: Text, second: Text) -> Text:
    return first + second


concatenate("py", b"thon")  # error: нельзя согласовать один Text для пары.
```

`TypeVar("T", str, bytes)` отличается от `T` с `bound=str | bytes`. Constraints выбирают один из вариантов и могут поднять пользовательский подкласс до типа ограничения. Bound допускает подходящий подтип и при необходимости общий тип. Нельзя одновременно задавать bound и constraints одному параметру; одно ограничение оформляется bound, а не списком constraints из одного элемента.

**Значение параметра типа по умолчанию** используется, когда его не удалось определить или он не указан. Это не default runtime-аргумента конструктора.

```python
# Python 3.13+: default в новом синтаксисе параметров типов.
from typing import assert_type


class Slot[T = int]:
    def __init__(self, value: T | None = None) -> None:
        self.value = value


default_slot = Slot()
assert_type(default_slot, Slot[int])
text_slot = Slot("python")
assert_type(text_slot, Slot[str])
assert default_slot.value is None
assert text_slot.value == "python"
```

```python
from typing import Generic, assert_type
from typing_extensions import TypeVar


T = TypeVar("T", default=int)


class Bucket(Generic[T]):
    def __init__(self) -> None:
        self.values: list[T] = []


bucket = Bucket()
assert_type(bucket, Bucket[int])
bucket.values.append(3)
assert bucket.values == [3]
```

Второй вариант использует backport; стандартный `typing.TypeVar` в Python 3.12 не принимает `default`. Параметр без default не может произвольно следовать после параметра с default. У вариативных параметров есть дополнительные правила; поддержка анализатора должна соответствовать выбранному синтаксису.

Типовой параметр только в результате, без связи с входом или фабрикой, часто является неверным обещанием: `def load[T]() -> T` не объясняет, откуда возьмётся любой запрошенный `T`. Более честный контракт — `def load[T](factory: Callable[[], T]) -> T`, где значение создаёт переданная зависимость.

### Современный синтаксис параметров типов — PEP 695

Python 3.12 позволяет объявлять параметры прямо рядом с функцией, классом или alias. Это сокращает служебные переменные и делает область параметра локальнее.

```python
from collections.abc import Sequence


def first[T](values: Sequence[T]) -> T:
    if not values:
        raise ValueError("Пустая последовательность")
    return values[0]


class Box[T]:
    def __init__(self, value: T) -> None:
        self.value = value

    def get(self) -> T:
        return self.value


type Pair[T] = tuple[T, T]

assert first([1, 2]) == 1
assert Box("data").get() == "data"
pair: Pair[int] = (1, 2)
assert pair == (1, 2)
```

| Новый синтаксис | Значение |
|---|---|
| `def f[T](x: T) -> T` | Generic-функция |
| `class Box[T]` | Generic-класс |
| `type Pair[T] = tuple[T, T]` | Generic-alias |
| `T: SomeProtocol` | Bound |
| `T: (str, bytes)` | Constraints |
| `**P` | ParamSpec |
| `*Ts` | TypeVarTuple |

```python
from collections.abc import Sized


def larger[T: Sized](left: T, right: T) -> T:
    return left if len(left) >= len(right) else right


def join[T: (str, bytes)](left: T, right: T) -> T:
    return left + right


assert larger("abc", "x") == "abc"
assert join(b"a", b"b") == b"ab"
```

Параметры из нового синтаксиса имеют особую область видимости. Не нужно заранее объявлять глобальный `T = TypeVar(...)` с тем же именем или добавлять `Generic[T]` к `class Box[T]`. Новый параметр — не обычная runtime-переменная аргумента функции.

Параметр должен сохранять полезную связь. Если функция только вызывает `len(value)` и возвращает `int`, достаточно `value: Sized`; отдельный `T` только в одной позиции не даёт потребителю дополнительного знания и может диагностироваться анализатором.

Вызов generic-функции остаётся обычным: `first(values)`. Функция не получает автоматически runtime-синтаксис `first[int](values)`. Параметризовать класс `Box[int](1)` можно, но runtime-тип экземпляра обычно остаётся `Box`.

```python
class Box[T]:
    def __init__(self, value: T) -> None:
        self.value = value


number = Box[int](1)
text = Box[str]("x")
assert type(number) is Box
assert type(text) is Box
assert number.value == 1
```

**Миграция требует трёх проверок:** исходник должен разбираться минимальным Python, runtime-импорты должны существовать, анализатор должен понимать используемые правила. `from __future__ import annotations` не позволяет старому парсеру прочитать `class Box[T]`: future-импорт не добавляет грамматику новой версии.

Новый синтаксис также вводит вывод вариантности для параметров generic-класса. Поэтому механическая замена старой формы не всегда равна изменению только внешнего вида: нужно повторно проверить совместимость API.

### Ковариантность, контравариантность и инвариантность

Пусть `Dog` — подтип `Animal`. Вариантность отвечает на вопрос: какое отношение существует между контейнерами или интерфейсами, параметризованными этими типами?

| Вариантность | Разрешённая подстановка | Типичная роль |
|---|---|---|
| Ковариантность | `Producer[Dog]` подходит вместо `Producer[Animal]` | Выдаёт значения |
| Контравариантность | `Consumer[Animal]` подходит вместо `Consumer[Dog]` | Принимает значения |
| Инвариантность | Ни одна такая подстановка не следует автоматически | Читает и изменяет значения |

**Почему список инвариантен.** Если бы `list[Dog]` разрешалось передать как `list[Animal]`, функция могла бы добавить туда `Cat`. После возврата исходный список собак содержал бы не собаку.

```python
# typing: negative
class Animal:
    pass


class Dog(Animal):
    pass


def add_animal(values: list[Animal]) -> None:
    values.append(Animal())


dogs: list[Dog] = [Dog()]
add_animal(dogs)  # error: list[Dog] не является list[Animal].
```

Для потребителя, которому достаточно чтения, выразите этот интерфейс через `Sequence[Animal]`, а не ослабляйте проверку cast-ом.

```python
from collections.abc import Sequence


class Animal:
    pass


class Dog(Animal):
    pass


def count_animals(values: Sequence[Animal]) -> int:
    return len(values)


dogs: list[Dog] = [Dog()]
assert count_animals(dogs) == 1
```

Ковариантный producer на старом синтаксисе задаёт намерение явно:

```python
from typing import Generic, TypeVar


class Animal:
    pass


class Dog(Animal):
    pass


T_co = TypeVar("T_co", covariant=True)


class ReadOnlyBox(Generic[T_co]):
    def __init__(self, value: T_co) -> None:
        self._value = value

    @property
    def value(self) -> T_co:
        return self._value


dogs: ReadOnlyBox[Dog] = ReadOnlyBox(Dog())
animals: ReadOnlyBox[Animal] = dogs
assert isinstance(animals.value, Dog)
```

Если добавить публичный setter, принимающий `T_co`, обещание ковариантности станет небезопасным. Запись `covariant=True` не разрешает игнорировать эту проблему: анализатор должен отклонять неподходящие использования параметра.

Контравариантный потребитель умеет принимать **более широкий** набор значений, чем требуется вызывающему коду:

```python
from typing import Protocol, TypeVar


class Animal:
    pass


class Dog(Animal):
    pass


T_contra = TypeVar("T_contra", contravariant=True)


class Sink(Protocol[T_contra]):
    def put(self, value: T_contra, /) -> None: ...


class AnimalSink:
    def __init__(self) -> None:
        self.values: list[Animal] = []

    def put(self, value: Animal, /) -> None:
        self.values.append(value)


storage = AnimalSink()
dog_sink: Sink[Dog] = storage
dog_sink.put(Dog())
assert len(storage.values) == 1
```

Так же устроены параметры `Callable`: функция, принимающая любой `Animal`, подходит туда, где будут передавать только `Dog`. Результат callable обычно ковариантен: функция, возвращающая `Dog`, подходит вместо возвращающей `Animal`.

В старой форме `Generic[T]` обычный `TypeVar` по умолчанию инвариантен. В `class Box[T]` вариантность выводится из использования параметра. Вариантность относится к конкретным позициям generic-класса, а не является глобальным свойством имени `T` во всех функциях.

### Изменяемые контейнеры vs неизменяемые интерфейсы

`Sequence[T]` и `Mapping[K, V]` ограничивают операции, доступные **через данный интерфейс**. Они не обещают, что за интерфейсом лежит физически неизменяемый объект или что другие владельцы не изменяют его.

```python
from collections.abc import Mapping, Sequence


values: list[int] = [1, 2]
view: Sequence[int] = values
values.append(3)
assert list(view) == [1, 2, 3]

source: dict[str, list[int]] = {"numbers": [1]}
mapping: Mapping[str, list[int]] = source
mapping["numbers"].append(2)
assert source["numbers"] == [1, 2]
```

Запрет `mapping["new"] = ...` не запрещает изменение вложенного списка. Для стабильного снимка нужен новый контейнер и подходящая политика вложенных значений: например, `tuple` из неизменяемых записей. Для конкурентной работы может потребоваться lock или передача исключительного владения.

`Sequence` ковариантен по элементу. `Mapping` ковариантен по **значению**, но не следует автоматически считать ковариантными его ключи. `list`, `dict` и другие изменяемые generic-контейнеры накладывают более строгие ограничения подстановки.

**Принцип сигнатуры:** принимайте минимальный интерфейс, который действительно нужен. Если функция только обходит элементы, достаточно `Iterable[T]`. Если нужны длина и индекс, полезен `Sequence[T]`. Если функция дописывает элементы, честно укажите изменяемый интерфейс.

```python
from collections.abc import Iterable, MutableSequence


def total(values: Iterable[int]) -> int:
    return sum(values)


def append_default(values: MutableSequence[int]) -> None:
    values.append(0)


assert total(iter([1, 2, 3])) == 6
items = [1]
append_default(items)
assert items == [1, 0]
```

Возвращаемый тип выбирают иначе: потребителю может быть полезен конкретный `list[T]`, если функция действительно создала независимый список. Не превращайте все сигнатуры в максимально абстрактные ради единообразия: контракт должен отражать возможности и владение.

### ParamSpec и Concatenate для обёрток и callback-функций

`Callable[..., R]` сохраняет знание о результате, но теряет проверяемую сигнатуру вызова. `ParamSpec` позволяет перенести **весь набор параметров**: типы, позиционность, keyword-only и обязательность.

```python
from collections.abc import Callable
from functools import wraps
from typing import ParamSpec, TypeVar


P = ParamSpec("P")
R = TypeVar("R")
calls: list[str] = []


def traced(function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        calls.append(function.__name__)
        return function(*args, **kwargs)

    return wrapper


@traced
def render(name: str, /, *, upper: bool = False) -> str:
    return name.upper() if upper else name


assert render("python", upper=True) == "PYTHON"
assert calls == ["render"]
```

`P.args` и `P.kwargs` используются парой для пересылки аргументов. Их нельзя произвольно разделить на независимые списки типов и ожидать сохранения связи. `functools.wraps` сохраняет runtime-метаданные и `__wrapped__`, но сам по себе не заменяет ParamSpec для статической сигнатуры.

В новом синтаксисе та же идея записывается `def traced[**P, R](function: Callable[P, R]) -> Callable[P, R]`. Не смешивайте в одном объявлении новый локальный `P` и старый `P = ParamSpec(...)` как будто это один объект.

`Concatenate` добавляет или убирает фиксированный префикс позиционных параметров. Например, можно привязать контекст и вернуть функцию, которая больше не требует его от пользователя.

```python
from collections.abc import Callable
from dataclasses import dataclass
from typing import Concatenate


@dataclass(frozen=True)
class Context:
    namespace: str


def bind_context[**P, R](
    function: Callable[Concatenate[Context, P], R], context: Context
) -> Callable[P, R]:
    def bound(*args: P.args, **kwargs: P.kwargs) -> R:
        return function(context, *args, **kwargs)

    return bound


def render(context: Context, /, name: str, *, upper: bool = False) -> str:
    result = f"{context.namespace}:{name}"
    return result.upper() if upper else result


render_team = bind_context(render, Context("team"))
assert render_team("isa", upper=True) == "TEAM:ISA"
```

`Concatenate` не является универсальным редактором произвольной сигнатуры. Добавление именованного параметра с потенциальной коллизией, удаление параметра из середины и преобразование каждого аргумента требуют другого API или более специальных средств. Callback-протокол удобен для фиксированной сложной сигнатуры; ParamSpec — для сохранения неизвестной заранее.

### TypeVarTuple и Unpack для variadic generics

Обычный `T` обозначает один тип. `TypeVarTuple` обозначает **последовательность типов**: например, `(int, str, bool)`. Он полезен, когда нужно сохранить разнородность и длину кортежа, а не превратить всё в `tuple[object, ...]`.

```python
def pack[*Ts](*values: *Ts) -> tuple[*Ts]:
    return values


def prepend[*Ts](head: bytes, tail: tuple[*Ts]) -> tuple[bytes, *Ts]:
    return (head, *tail)


assert pack(1, "a", True) == (1, "a", True)
assert prepend(b"tag", (1, "a")) == (b"tag", 1, "a")
```

Звёздочка в `tuple[*Ts]` распаковывает типовую последовательность. Это концептуально похоже на распаковку значений, но действует в системе типов. Без неё один `Ts` не становится обычным типом элемента.

На прежнем синтаксисе можно использовать `TypeVarTuple` и `Unpack`:

```python
from typing import TypeVarTuple, Unpack


Ts = TypeVarTuple("Ts")


def preserve(values: tuple[Unpack[Ts]]) -> tuple[Unpack[Ts]]:
    return values


assert preserve((1, "x")) == (1, "x")
```

У generic-класса последовательность параметров также может иметь переменную длину:

```python
class Row[*Columns]:
    def __init__(self, *values: *Columns) -> None:
        self._values: tuple[*Columns] = values

    def as_tuple(self) -> tuple[*Columns]:
        return self._values


row: Row[int, str, bool] = Row(1, "python", True)
assert row.as_tuple() == (1, "python", True)
```

Это не проверка схемы CSV в runtime. Неверные входные данные нужно валидировать отдельно. Типы, описывающие форму тензора, также не доказывают реальные числовые размеры массива, если конструктор и операции их не проверяют.

В одной последовательности типов нельзя произвольно использовать несколько независимых распаковок TypeVarTuple: граница между ними может стать неоднозначной. Для bounds, constraints и вариантности действуют отдельные ограничения и поддержка версий; не переносите все возможности обычного TypeVar автоматически.

Не путайте `Unpack[Ts]` для вариативной последовательности с `Unpack[SomeTypedDict]` для `**kwargs`: синтаксис похож, но модель параметров разная. Второй вариант разберём в следующей теме.

**Документация:** [Generics](https://typing.python.org/en/latest/spec/generics.html), [PEP 695](https://peps.python.org/pep-0695/), [PEP 696](https://peps.python.org/pep-0696/), [PEP 646](https://peps.python.org/pep-0646/).

## Структурная типизация и схемы словарей

### Protocol: методы, атрибуты и callback-протоколы

Структурная типизация проверяет, поддерживает ли тип нужные члены с подходящими сигнатурами. Обязательное наследование от интерфейса не требуется. Это особенно полезно для адаптеров сторонних библиотек и dependency injection.

```python
from typing import Protocol


class Clock(Protocol):
    def now(self) -> float: ...


class FixedClock:
    def __init__(self, value: float) -> None:
        self._value = value

    def now(self) -> float:
        return self._value


def timestamp(clock: Clock) -> str:
    return f"time:{clock.now():.1f}"


assert timestamp(FixedClock(12.5)) == "time:12.5"
```

`FixedClock` не наследуется от `Clock`, но подходит по форме. Аннотация описывает минимальное ожидание потребителя. Включать в протокол все методы текущей реализации не нужно: это затруднит альтернативные реализации без пользы для вызывающего кода.

**Сигнатура — больше, чем тип результата.** Анализатор учитывает число аргументов, их типы, позиционность и keyword-имена. Реализация должна принимать все вызовы, которые разрешает протокол. Если вызывающий код использует `timeout=`, переименование параметра без позиционного ограничения может нарушить совместимость.

Для атрибутов важно различать чтение и запись. `value: object` в протоколе обычно обещает возможность записать любое значение `object`, а не только прочитать существующий `int`.

```python
# typing: negative
from typing import Protocol


class MutableValue(Protocol):
    value: object


class IntValue:
    def __init__(self) -> None:
        self.value: int = 1


view: MutableValue = IntValue()  # error: через view разрешили бы записать str.
```

Если требуется только чтение, объявите read-only property:

```python
from typing import Protocol


class HasValue(Protocol):
    @property
    def value(self) -> object: ...


class IntValue:
    def __init__(self) -> None:
        self.value: int = 1


view: HasValue = IntValue()
assert view.value == 1
```

Реализация может иметь обычное поле с более точным типом: потребитель протокола не получает право его переприсвоить. Это позволяет безопаснее расширять совместимость и выводить вариантность.

**Callback-протокол** описывает сложный вызов через `__call__`, включая keyword-only параметры:

```python
from typing import Protocol


class Decoder(Protocol):
    def __call__(self, raw: bytes, /, *, strict: bool = True) -> str: ...


def utf8(data: bytes, /, *, strict: bool = True) -> str:
    return data.decode("utf-8", errors="strict" if strict else "replace")


def run_decoder(decoder: Decoder, payload: bytes) -> str:
    return decoder(payload, strict=True)


assert run_decoder(utf8, b"python") == "python"
```

Имя `raw` не обязано совпадать с `data`, потому что параметр позиционный-only. А keyword-only `strict` должен соответствовать. Для generic-протоколов действуют те же требования к вариантности: producer, consumer и изменяемый атрибут имеют разные позиции параметра типа.

Методы протокола могут иметь default-реализацию, но структурно подходящий сторонний класс её не наследует автоматически. Чтобы использовать общую реализацию через наследование, нужно действительно наследоваться от соответствующего класса; сама совместимость не внедряет методы.

### runtime_checkable и ограничения runtime-проверки

Обычный `Protocol` предназначен для статического анализа. Для ограниченных `isinstance`/`issubclass` проверок существует `@runtime_checkable`. Он проверяет наличие требуемых членов, но не доказывает подходящую сигнатуру, корректный результат и предметную семантику.

```python
# typing: runtime
from typing import Protocol, runtime_checkable


@runtime_checkable
class Reader(Protocol):
    def read(self) -> str: ...


class FakeReader:
    read = 42


candidate = FakeReader()
assert isinstance(candidate, Reader)
assert not callable(candidate.read)
```

Проверка может дать положительный ответ даже для невызываемого поля. Передача такого объекта как `Reader` должна быть отклонена статическим анализатором, если он видит реальный тип `FakeReader`. Runtime-проверка не превращает неверную реализацию в корректную.

Для протокола с полями экземпляра `issubclass` ограничен: по одному классу нельзя надёжно определить, что будет у его экземпляра.

```python
# typing: runtime
from typing import Protocol, runtime_checkable


@runtime_checkable
class HasName(Protocol):
    name: str


class User:
    name = "Ada"


assert isinstance(User(), HasName)
try:
    issubclass(User, HasName)
except TypeError:
    pass
else:
    raise AssertionError("Data protocol не поддерживает такую проверку класса")
```

Начиная с Python 3.12 runtime-проверка использует `inspect.getattr_static`, поэтому динамический `__getattr__` и свойства не ведут себя как простая ручная проверка `hasattr`. Набор членов фиксируется при создании протокола: позднее добавление нового требования не обязано менять runtime-проверку.

Проверка `isinstance(value, Reader[int])` не валидирует параметры generic-протокола и не является поддерживаемой заменой статического анализа. Для горячего пути runtime-протокол также может быть дороже простого вызова. Используйте его для осмысленной диагностики и совместимости, а не как универсальную границу доверия.

### TypedDict: Required, NotRequired и ReadOnly

`TypedDict` описывает форму обычного словаря со строковыми ключами: какие ключи возможны, обязательны ли они и какие значения им соответствуют. В runtime экземпляр остаётся `dict`.

```python
from typing import NotRequired, Required, TypedDict


class Patch(TypedDict, total=False):
    user_id: Required[int]
    title: NotRequired[str | None]


def describe_patch(patch: Patch) -> str:
    if "title" not in patch:
        return "unchanged"
    title = patch["title"]
    return "clear" if title is None else f"set:{title}"


assert describe_patch({"user_id": 1}) == "unchanged"
assert describe_patch({"user_id": 1, "title": None}) == "clear"
assert describe_patch({"user_id": 1, "title": "Python"}) == "set:Python"
```

| Поле | Ключ можно пропустить | Значение может быть None |
|---|---|---|
| `name: str` | Нет | Нет |
| `name: str \| None` | Нет | Да |
| `name: NotRequired[str]` | Да | Нет |
| `name: NotRequired[str \| None]` | Да | Да |

`total=False` влияет на поля, объявленные в данном теле, а не автоматически на всю унаследованную схему. Смешанные обязательные и необязательные поля можно выражать через квалификаторы либо наследование. `Required` и `NotRequired` у одного поля взаимоисключающие.

```python
# typing: negative
from typing import TypedDict


class User(TypedDict):
    name: str
    age: int


missing: User = {"name": "Ada"}  # error: отсутствует обязательный age.
wrong: User = {"name": "Ada", "age": "25"}  # error: age должен быть int.
```

**TypedDict не валидирует.** Вызов конструктора создаёт словарь, но не включает проверки схемы:

```python
# typing: runtime
from typing import TypedDict


class Payload(TypedDict):
    count: int


wrong = Payload(count="three")
missing = Payload()
assert type(wrong) is dict
assert wrong["count"] == "three"
assert missing == {}
```

Такой код намеренно противоречит аннотациям и должен давать статические ошибки. Для результата `json.loads` нельзя честно написать `Payload` без реальной проверки или доверенной внешней гарантии. `cast(Payload, raw)` только меняет мнение анализатора.

`ReadOnly` (в стандартном `typing` с Python 3.13; для старых версий через backport) запрещает изменение **поля через соответствующий типизированный интерфейс**. Он не замораживает настоящий словарь и вложенные значения.

```python
from typing_extensions import ReadOnly, TypedDict


class Event(TypedDict):
    event_id: ReadOnly[str]
    tags: ReadOnly[list[str]]


event: Event = {"event_id": "e-1", "tags": []}
event["tags"].append("python")
assert event["tags"] == ["python"]
```

```python
# typing: negative
from typing_extensions import ReadOnly, TypedDict


class Event(TypedDict):
    event_id: ReadOnly[str]


event: Event = {"event_id": "e-1"}
event["event_id"] = "e-2"  # error: поле доступно только для чтения.
```

Read-only поле может поддерживать более гибкую безопасную подстановку, чем изменяемое: потребитель не может записать значение неподходящего типа. Но принадлежность ключа, его обязательность и возможность записи нужно рассматривать вместе; правила не сводятся к «все TypedDict ковариантны».

TypedDict обычно совместим с `Mapping[str, object]` для общего чтения, но не является обычным `dict[str, object]` для произвольного изменения: иначе можно было бы удалить обязательное поле или присвоить ему произвольный объект.

**Дополнительные ключи — отдельная политика.** Лишний ключ в литерале, проверяемом как конкретный TypedDict, обычно диагностируется. При структурной совместимости более широкое значение может содержать дополнительные поля. Нельзя выводить из аннотации универсальную runtime-гарантию «в словаре нет ничего лишнего». Возможности закрытых схем и типизированных extra items имеют отдельную поддержку в спецификации, backports и анализаторах; для внешних данных проверяйте выбранную политику явно.

### Unpack[TypedDict] для типизированных **kwargs

Аннотация `**kwargs: int` означает, что **каждое значение** именованного аргумента — `int`. Она не описывает фиксированный набор имён. `Unpack[Options]` позволяет задать такой набор через TypedDict.

```python
from typing import NotRequired, TypedDict, Unpack


class Options(TypedDict):
    timeout: float
    retries: NotRequired[int]


def request(url: str, /, **options: Unpack[Options]) -> str:
    timeout = options["timeout"]
    retries = options.get("retries", 0)
    if timeout <= 0 or retries < 0:
        raise ValueError("Некорректные параметры")
    # Только формируем строку: сетевой запрос в примере не выполняется.
    return f"{url}; timeout={timeout}; retries={retries}"


assert request("https://example.invalid", timeout=2.0) == (
    "https://example.invalid; timeout=2.0; retries=0"
)
```

```python
# typing: negative
from typing import TypedDict, Unpack


class Options(TypedDict):
    timeout: float


def request(**options: Unpack[Options]) -> None:
    pass


request()  # error: обязательный timeout не передан.
request(timeout="soon")  # error: значение неверного типа.
request(timeout=1.0, timout=2.0)  # error: неизвестный именованный параметр.
```

Для передачи существующей конфигурации важно, чтобы анализатор знал её схему:

```python
from typing import NotRequired, TypedDict, Unpack


class Options(TypedDict):
    timeout: float
    retries: NotRequired[int]


def describe(**options: Unpack[Options]) -> str:
    return f"timeout={options['timeout']}"


options: Options = {"timeout": 1.5}
assert describe(**options) == "timeout=1.5"
```

Обычный `dict[str, object]` не гарантирует наличие обязательных ключей и тип каждого из них. На границе конфигурацию нужно проверить, а не просто распаковать. При forwarding также не пересылайте случайно лишние ключи в функцию с более узкой сигнатурой: лучше собрать аргументы явно либо согласовать оба интерфейса.

Имена из распакованного TypedDict не должны конфликтовать с обычными keyword-параметрами функции. Позиционный-only параметр может иметь отдельные правила сосуществования с одноимённым ключом, но такие API требуют особенно ясной документации. `Unpack` не выполняет runtime-фильтрацию и не изменяет правила вызова Python.

### Protocol vs ABC, TypedDict vs dataclass и модель валидации

| Инструмент | Основной вопрос | Runtime-форма |
|---|---|---|
| `Protocol` | Какие возможности нужны потребителю? | Обычный объект подходящей структуры |
| ABC | Какой номинальный контракт и общую реализацию поддерживают наследники? | Экземпляр иерархии |
| `TypedDict` | Какие ключи и типы значений есть у словаря? | Обычный dict |
| `dataclass` | Какие поля и стандартные методы нужны объекту? | Экземпляр отдельного класса |
| Валидатор / модель валидации | Соответствуют ли реальные данные правилам? | Зависит от реализации |

У ABC есть runtime-запрет создания неполного абстрактного класса, но нет автоматической проверки правильной сигнатуры и поведения его реализации. У dataclass есть генерация `__init__`, `repr`, равенства и других методов, но нет автоматической проверки типов каждого аргумента.

Выбирайте форму по границе: словарь удобно передать в JSON API, неизменяемый объект-значение — использовать внутри алгоритма, протокол — принять инфраструктурную зависимость. Не нужно делать один тип одновременно схемой HTTP, ORM-сущностью, mutable-кэшем и публичным DTO, если у них разные правила жизни.

Типичный поток выглядит так: **непроверенное значение `object` → явная валидация → проверенная запись/TypedDict → преобразование в доменную модель**. При необходимости обратная сериализация снова явно выбирает поля и формат. Система типов сохраняет знание, полученное валидатором, но не заменяет его работу.

У библиотек вроде Pydantic отдельно различайте strict-валидацию и преобразования. Принятие строки `"3"` как числа может быть полезной политикой, но не должно происходить неожиданно в каждом внутреннем методе. В этой главе практический проект использует явные проверки стандартными средствами.

**Документация:** [Protocols](https://typing.python.org/en/latest/spec/protocol.html), [TypedDict](https://typing.python.org/en/latest/spec/typeddict.html), [callables и kwargs](https://typing.python.org/en/latest/spec/callables.html), [typing_extensions](https://typing-extensions.readthedocs.io/).

## Типизация функций и асинхронного кода

### Callable, overload и различие перегрузки и реализации

`Callable[[A, B], R]` описывает вызываемый объект, принимающий два аргумента с соответствующими типами и возвращающий `R`. Подходят функции, bound methods и экземпляры с совместимым `__call__`.

```python
from collections.abc import Callable, Iterable


def transform[T, R](values: Iterable[T], function: Callable[[T], R]) -> list[R]:
    return [function(value) for value in values]


def label(value: int) -> str:
    return f"row-{value}"


assert transform([1, 2], label) == ["row-1", "row-2"]
```

Сигнатура сохраняет связь: элементы входа должны подходить callback, а элементы результата имеют тип результата callback. `Callable[..., R]` оставляет параметры неопределёнными и теряет эту часть проверки. Для keyword-only и других сложных форм используйте callback-протокол или ParamSpec.

`@overload` нужен, когда результат зависит от конкретного варианта входа и одна union-сигнатура теряет полезную информацию. Например, флаг определяет, будет результат строкой или байтами.

```python
from typing import Literal, assert_type, overload


@overload
def encode(value: str, *, binary: Literal[True]) -> bytes: ...


@overload
def encode(value: str, *, binary: Literal[False] = False) -> str: ...


@overload
def encode(value: str, *, binary: bool) -> str | bytes: ...


def encode(value: str, *, binary: bool = False) -> str | bytes:
    return value.encode("utf-8") if binary else value


assert_type(encode("python"), str)
assert_type(encode("python", binary=True), bytes)
assert encode("python", binary=True) == b"python"
```

Третий вариант нужен для переменной типа `bool`, значение которой заранее неизвестно. Реализация одна, и именно она выполняется в runtime. Python не выбирает тело функции по аннотациям overload.

Каждый заявленный вариант должен поддерживаться реализацией. Порядок overload имеет значение, если случаи пересекаются; ставьте более специфические варианты раньше общих и проверяйте совместимость результатов. Например, `bool` входит в `int`, поэтому две перегрузки для них требуют особого внимания.

Не добавляйте overload, если обычный `T` точнее выражает сохранение типа или все варианты всё равно возвращают один и тот же тип. Перегрузки — это публичные обещания, которые нужно сопровождать вместе с реализацией и тестами.

### Декораторы с сохранением параметров и возвращаемого типа

Декоратор должен описывать, что именно он сохраняет и меняет. Если обёртка принимает любые `*args: Any` и возвращает `Any`, неверные вызовы могут перестать замечаться после применения декоратора.

```python
from collections.abc import Callable
from functools import wraps
from time import perf_counter


durations: list[float] = []


def measured[**P, R](function: Callable[P, R]) -> Callable[P, R]:
    @wraps(function)
    def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        started = perf_counter()
        try:
            return function(*args, **kwargs)
        finally:
            durations.append(perf_counter() - started)

    return wrapper


@measured
def multiply(value: int, /, *, factor: int = 2) -> int:
    return value * factor


assert multiply(3, factor=4) == 12
assert len(durations) == 1
assert durations[0] >= 0
```

`finally` фиксирует длительность и при исключении, не подавляя его. Это учебный синхронный сборщик: список не ограничен и не является готовой системой метрик. Типизация не обеспечивает разумную кардинальность и контроль памяти.

Для `async def` синхронная обёртка вокруг вызова измерила бы в основном создание coroutine, а не её выполнение. Асинхронная обёртка должна дождаться результата:

```python
import asyncio
from collections.abc import Awaitable, Callable
from functools import wraps


events: list[str] = []


def traced_async[**P, R](
    function: Callable[P, Awaitable[R]],
) -> Callable[P, Awaitable[R]]:
    @wraps(function)
    async def wrapper(*args: P.args, **kwargs: P.kwargs) -> R:
        events.append("start")
        try:
            return await function(*args, **kwargs)
        finally:
            events.append("finish")

    return wrapper


@traced_async
async def fetch_count(*, value: int) -> int:
    return value


async def main() -> None:
    assert await fetch_count(value=3) == 3


asyncio.run(main())
assert events == ["start", "finish"]
```

Контракт результата обёрнутого вызова здесь — `Awaitable[R]`, а не конкретная coroutine для любого потребителя. Это сохраняет абстракцию, но может быть слишком широким для API, требующего именно coroutine. Выбирайте возвращаемый интерфейс в соответствии с тем, как объект будет использоваться.

`wraps` сохраняет метаданные исходной функции и связь `__wrapped__`, но не доказывает статическую корректность обёртки. Если декоратор меняет возвращаемый тип или параметры, его аннотации должны честно описывать новое API; runtime-интроспекция сигнатуры также может потребовать отдельной настройки.

### Iterator, Iterable и Generator: yield, send и return

`Iterable[T]` обещает возможность получить итератор, `Iterator[T]` — сам последовательный источник с `__next__`. Генераторный объект является итератором, но имеет дополнительные каналы `send`, `throw`, `close` и результат завершения.

```python
from collections.abc import Iterable, Iterator


def positive(values: Iterable[int]) -> Iterator[int]:
    for value in values:
        if value > 0:
            yield value


source = positive([-1, 0, 2, 3])
assert list(source) == [2, 3]
assert list(source) == []
```

Входной `Iterable` не обещает повторный обход. Если функция проходит его дважды, это нужно изменить, документировать или материализовать данные. Тип `Sequence` даёт более сильные структурные возможности, но не сам по себе фиксированный снимок.

`Generator[YieldType, SendType, ReturnType]` описывает три разных направления данных:

```python
from collections.abc import Generator


def accumulator() -> Generator[int, int, str]:
    total = 0
    while True:
        value = yield total
        if value < 0:
            return f"total={total}"
        total += value


generator = accumulator()
assert next(generator) == 0
assert generator.send(2) == 2
assert generator.send(3) == 5
try:
    generator.send(-1)
except StopIteration as finished:
    assert finished.value == "total=5"
else:
    raise AssertionError("Генератор должен завершиться")
```

`YieldType` идёт к потребителю, `SendType` — от потребителя, `ReturnType` доступен при завершении и через `yield from`. Для простого генератора без `send` и полезного `return` достаточно `Iterator[T]` либо явного `Generator[T, None, None]`.

Тип `SendType` контравариантен: генератор, принимающий более широкий набор значений, может обслуживать потребителя с узким набором отправляемых значений. Проверка типов не отменяет runtime-правило: до первого `yield` нельзя отправить произвольное не-None значение.

В Python 3.13 появились defaults для части параметров `Generator`/`AsyncGenerator`; форма `Generator[T]` в старой среде может быть неподдерживаемой. Для матрицы с 3.12 используйте полную форму или `Iterator[T]`, чтобы не путать доступность типовых defaults с поведением самого генератора.

### Awaitable, Coroutine, AsyncIterator и AsyncGenerator

Аннотация результата `async def f() -> T` описывает значение **после `await`**, а не непосредственный результат вызова `f()`. Вызов возвращает coroutine, исполнение которой нужно организовать.

```python
import asyncio
from typing import assert_type


async def fetch_count() -> int:
    return 3


async def main() -> None:
    result = await fetch_count()
    assert_type(result, int)
    task = asyncio.create_task(fetch_count())
    assert await task == 3


asyncio.run(main())
```

| Тип | Что обещает |
|---|---|
| `Awaitable[T]` | Объект можно ожидать и получить `T` |
| `Coroutine[Any, Any, T]` | Coroutine с результатом `T` и дополнительным низкоуровневым протоколом |
| `asyncio.Task[T]` | Запланированная задача, чей результат имеет тип `T` |
| `AsyncIterable[T]` | Поддерживает асинхронный обход |
| `AsyncIterator[T]` | Выдаёт значения через `__anext__` |
| `AsyncGenerator[Y, S]` | Async-генератор с выдаваемым `Y` и каналом `asend` типа `S` |

Два `Any` в обычном описании native-coroutine относятся к внутренним каналам `send`/`yield`; результат после `await` остаётся конкретным `T`. Их наличие не означает, что функция возвращает произвольный результат.

Не любой `Awaitable` является coroutine: это может быть `Future` или пользовательский объект. Например, `asyncio.create_task` требует coroutine; для другого awaitable можно написать маленькую coroutine-обёртку либо использовать подходящее API планирования.

```python
import asyncio
from collections.abc import Awaitable


async def await_result[T](value: Awaitable[T]) -> T:
    return await value


async def main() -> None:
    future: asyncio.Future[int] = asyncio.get_running_loop().create_future()
    future.set_result(7)
    task = asyncio.create_task(await_result(future))
    assert await task == 7


asyncio.run(main())
```

Асинхронный генератор не аннотируется как `Coroutine[..., AsyncIterator[T]]`, если сама функция содержит `yield`: её вызов сразу возвращает объект async-итерации.

```python
import asyncio
from collections.abc import AsyncGenerator, AsyncIterator


async def numbers() -> AsyncIterator[int]:
    for value in range(3):
        yield value


async def echo() -> AsyncGenerator[str, str]:
    message = yield "ready"
    yield message.upper()


async def main() -> None:
    assert [value async for value in numbers()] == [0, 1, 2]
    stream = echo()
    try:
        assert await anext(stream) == "ready"
        assert await stream.asend("python") == "PYTHON"
    finally:
        await stream.aclose()


asyncio.run(main())
```

У async-генератора нет отдельного `ReturnType`, и `return value` в нём запрещён. В протоколах async-источников часто правильно писать обычный `def rows(...) -> AsyncIterator[T]: ...`, чтобы описать результат вызова; `async def rows` без `yield` обозначил бы ожидание перед получением итератора.

Аннотация `Awaitable[T]` не выражает deadlines, отменяемость, повторное ожидание или владение task. Обычную coroutine нельзя повторно `await` после завершения; Task имеет другой жизненный цикл. Эти свойства нужно документировать и тестировать вместе с async-кодом.

### Типизация методов, properties и фабрик классов

Обычным `self` и `cls` обычно не нужны явные аннотации. `__init__` имеет результат `None`. Для fluent API подходит честный `Self`; для объекта класса — `type[T]`, а не `T`.

```python
from typing import Self, override


class Config:
    def __init__(self, value: str) -> None:
        self._value = value

    @property
    def value(self) -> str:
        return self._value

    @classmethod
    def from_text(cls, text: str) -> Self:
        return cls(text.strip())

    def label(self) -> str:
        return self.value


class UpperConfig(Config):
    @override
    def label(self) -> str:
        return self.value.upper()


assert UpperConfig.from_text(" data ").label() == "DATA"
```

Getter аннотирует читаемое значение, setter — принимаемое значение и `-> None`. Если чтение и запись допускают разные типы, это нужно поддержать явно и проверить выбранным анализатором; простой атрибут с одной аннотацией не выражает произвольный конвертер.

`type[T]` полезен для фабрики, которая сохраняет тип переданного класса:

```python
class Item:
    def __init__(self) -> None:
        self.ready = True


class SpecialItem(Item):
    pass


def build[T: Item](item_type: type[T]) -> T:
    return item_type()


item = build(SpecialItem)
assert type(item) is SpecialItem
assert item.ready is True
```

Такой контракт предполагает совместимый конструктор наследников. Система типов Python не даёт автоматического доказательства, что любой будущий подкласс сохранит конкретную сигнатуру конструктора базы. Для общего конструктора с параметрами часто точнее `Callable[P, T]` либо фабричный протокол.

```python
from collections.abc import Callable


def construct[**P, T](factory: Callable[P, T], *args: P.args, **kwargs: P.kwargs) -> T:
    return factory(*args, **kwargs)


class User:
    def __init__(self, name: str, *, active: bool = True) -> None:
        self.name = name
        self.active = active


user = construct(User, "Ada", active=False)
assert user.name == "Ada"
assert user.active is False
```

Сохраняйте подстановку методов: переопределение не должно сужать допустимые входы относительно базы и расширять результат до неподходящего типа. Статический анализ помогает проверить сигнатуры, но не доказывает прежние исключения, транзакционность и отсутствие новых побочных эффектов.

**Документация:** [Callables](https://typing.python.org/en/latest/spec/callables.html), [overload](https://typing.python.org/en/latest/spec/overload.html), [аннотации генераторов и корутин](https://docs.python.org/3.14/library/typing.html#annotating-generators-and-coroutines), [Self](https://typing.python.org/en/latest/spec/generics.html#self).

## Сужение типов — Type Narrowing

### isinstance(), проверки None и управляющий поток

Сужение типов уточняет известный тип выражения в конкретной ветви программы. Если `value: str | None` прошёл проверку `value is not None`, внутри соответствующей области анализатор может использовать `str`.

```python
from typing import assert_type


def normalized_name(value: str | None) -> str:
    if value is None:
        return "anonymous"
    assert_type(value, str)
    return value.strip()


assert normalized_name(None) == "anonymous"
assert normalized_name(" Ada ") == "Ada"
```

Ранний `return` исключает nullable-ветвь из дальнейшего потока. Аналогично работают известное выбрасывание исключения и вызов функции с результатом `NoReturn`.

```python
from typing import assert_type


def length_or_double(value: str | int) -> int:
    if isinstance(value, str):
        assert_type(value, str)
        return len(value)
    assert_type(value, int)
    return value * 2


assert length_or_double("data") == 4
assert length_or_double(3) == 6
```

`isinstance` учитывает подклассы. Если проверяется `int`, возможен и `bool`. У `type(value) is int` более узкая runtime-семантика, но нужно учитывать выразимость результата в системе типов и поведение анализатора.

**Truthiness не равна проверке None.** В условии `if value` строка `""` и число `0` попадают в ложную ветвь вместе с `None`. Это может быть ошибкой предметной логики даже при успешной типизации.

```python
def choose_port(value: int | None) -> int:
    return 8080 if value is None else value


assert choose_port(None) == 8080
assert choose_port(0) == 0
```

Если типы двух переменных логически связаны, анализатор не всегда способен восстановить эту связь из сложного условия. Явная проверка `first is not None and second is not None` обычно понятнее, чем попытка закодировать её через поиск `None` в кортеже. Произвольные отношения между значениями система типов не доказывает.

`assert value is not None` также сужает тип, но валидацию публичного входа лучше выполнять явным `if ...: raise ...`: Python может удалить assert при `-O`. Для внутреннего проверенного инварианта assert полезен как диагностическая проверка, если последующая корректность не опирается на его обязательное выполнение.

Сужение не меняет исходный тип объекта и не является приведением. Оно меняет знание анализатора о доступных операциях в определённой точке потока.

### TypeGuard vs TypeIs; безопасность при мутации

Обычная функция `def is_text(x: object) -> bool` не всегда сообщает анализатору, что истинный результат означает `str`. `TypeGuard` и `TypeIs` делают это намерение частью статического контракта.

```python
from typing import TypeGuard, assert_type
from typing_extensions import TypeIs


def is_text_guard(value: object) -> TypeGuard[str]:
    return isinstance(value, str)


def is_text(value: object) -> TypeIs[str]:
    return isinstance(value, str)


def with_guard(value: int | str) -> str:
    if is_text_guard(value):
        assert_type(value, str)
        return value.upper()
    assert_type(value, int | str)
    return str(value)


def with_type_is(value: int | str) -> str:
    if is_text(value):
        assert_type(value, str)
        return value.upper()
    assert_type(value, int)
    return str(value)


assert with_guard(3) == "3"
assert with_type_is("python") == "PYTHON"
```

| Свойство | TypeGuard | TypeIs |
|---|---|---|
| Результат функции в runtime | bool | bool |
| Уточнение истинной ветви | Обещанный целевой тип | Пересечение исходного и целевого типов |
| Уточнение ложной ветви | Обычно отсутствует | Исключает целевой тип |
| Целевой тип обязан быть совместим с входным | Нет | Да |
| Пример `list[object] -> list[str]` | Возможен | Не подходит из-за инвариантности |
| Достоверность проверки | Ответственность автора | Ответственность автора, включая ложную ветвь |

`TypeGuard` доступен в стандартном `typing` с Python 3.10, `TypeIs` — с 3.13. В этой главе TypeIs импортируется из backport для совместимости с 3.12.

**TypeIs требует двусторонней правды.** Нельзя обозначить проверку «положительное int» как `TypeIs[int]`: отрицательное целое не перестаёт быть `int`, когда функция вернула False. По той же причине проверка `type(x) is int` не эквивалентна полноценной проверке принадлежности `int`, поскольку исключает `bool` и другие подклассы.

```python
# typing: runtime
from typing_extensions import TypeIs


def is_exact_int(value: object) -> TypeIs[int]:
    # Намеренно НЕВЕРНЫЙ TypeIs: False для некоторых настоящих int.
    return type(value) is int


def unsafe_size(value: int | str) -> int:
    if is_exact_int(value):
        return value
    return len(value)  # Анализатор считает, что осталась только строка.


try:
    unsafe_size(True)
except TypeError:
    pass
else:
    raise AssertionError("Неверный предикат разрушил обещание ложной ветви")
```

Анализатор проверяет допустимость типов в сигнатуре, но не доказывает, что тело предиката соответствует обещанию для всех значений. Для проверки диапазона используйте обычный `bool` либо возвращайте отдельный проверенный объект-значение; не подменяйте предметный предикат отношением типов.

**Мутация после проверки.** Даже корректный предикат устанавливает факт о состоянии в момент вызова. Если существует изменяемый alias, факт может устареть:

```python
from typing import TypeGuard


def all_text(values: list[object]) -> TypeGuard[list[str]]:
    return all(isinstance(value, str) for value in values)


values: list[object] = ["python"]
alias = values
if all_text(values):
    alias.append(42)
    try:
        " ".join(values)
    except TypeError:
        pass
    else:
        raise AssertionError("Другой владелец успел изменить список")
```

Ветвь типизируется как список строк, хотя мутация через другой путь уже нарушила это знание. TypeGuard не предоставляет владение, блокировку или постоянный сертификат схемы.

Если исходные элементы неизменяемы, безопаснее построить новый проверенный кортеж. Для произвольного графа требуется собственная политика копирования и владения. Между проверкой и использованием также может быть `await`, callback или другой поток: эти границы необходимо учитывать явно.

### Tagged unions, match/case и исчерпывающая обработка

Tagged union объединяет несколько форм значения с различающим полем-тегом. Каждая форма имеет собственные обязательные поля. Это точнее, чем один большой словарь с десятком независимых optional-полей.

```python
from typing import Literal, TypedDict, assert_never


class Created(TypedDict):
    kind: Literal["created"]
    entity_id: int


class Deleted(TypedDict):
    kind: Literal["deleted"]
    reason: str


type Event = Created | Deleted


def describe(event: Event) -> str:
    if event["kind"] == "created":
        return f"created:{event['entity_id']}"
    if event["kind"] == "deleted":
        return f"deleted:{event['reason']}"
    assert_never(event)


assert describe({"kind": "created", "entity_id": 1}) == "created:1"
assert describe({"kind": "deleted", "reason": "expired"}) == "deleted:expired"
```

Тег связывает наличие поля с вариантом. Если добавить новое событие в union, `assert_never` поможет обнаружить обработчики, которые не обновили. Обычный `else: return "unknown"` может скрыть такое расширение.

Для неизменяемых дата-классов удобно сопоставление с образцом:

```python
from dataclasses import dataclass
from typing import assert_never


@dataclass(frozen=True)
class Success:
    count: int


@dataclass(frozen=True)
class Failure:
    message: str


type Result = Success | Failure


def describe(result: Result) -> str:
    match result:
        case Success(count=count):
            return f"accepted:{count}"
        case Failure(message=message):
            return f"error:{message}"
        case _:
            assert_never(result)


assert describe(Success(3)) == "accepted:3"
assert describe(Failure("bad data")) == "error:bad data"
```

Не каждый сложный match-pattern одинаково хорошо поддерживается всеми анализаторами. При сомнении проверьте выведенные типы и используйте явную ветвь `isinstance`/тег, которую инструменты понимают устойчиво.

```python
# typing: negative
from dataclasses import dataclass
from typing import assert_never


@dataclass(frozen=True)
class Success:
    count: int


@dataclass(frozen=True)
class Failure:
    message: str


def describe(result: Success | Failure) -> str:
    if isinstance(result, Success):
        return str(result.count)
    assert_never(result)  # error: здесь всё ещё возможен Failure.
```

Исчерпывающая обработка действует относительно объявленного union. Непроверенный внешний dict не станет корректным событием из-за `cast(Event, raw)`. Сначала валидируйте, затем используйте полное покрытие вариантов.

### assert_never(), cast(), assert_type() и reveal_type()

| Инструмент | Задача для анализатора | Поведение в runtime |
|---|---|---|
| `assert_never(value)` | Потребовать недостижимый тип Never | Выбрасывает исключение, если вызван |
| `cast(T, value)` | Считать значение имеющим тип T | Возвращает исходное значение |
| `assert_type(value, T)` | Проверить ожидаемый статический тип | Возвращает значение без проверки типа |
| `reveal_type(value)` | Показать выведенный тип в диагностике | В стандартном typing печатает runtime-тип в stderr |

`assert_never` не равен инструкции `assert False`: его собственное поведение не исчезает просто из-за `-O`. Это одновременно проверяемая точка исчерпывания и защита от неожиданного runtime-пути, но не полноценный валидатор сложного значения.

**Cast не преобразует и не проверяет.**

```python
# typing: runtime
from typing import cast


original = 42
claimed = cast(str, original)
assert claimed is original
assert type(claimed) is int
assert str(original) == "42"  # Это уже настоящее преобразование.
```

Используйте cast, когда имеется конкретное обоснование, недоступное анализатору: проверенный формат стороннего API, документированный инвариант библиотеки или ограничение выразимости. Локализуйте его и объясните, на чём основано обещание. Cast из непроверенного JSON прямо в доменную схему такого обоснования не имеет.

`assert_type` полезен для статических регрессионных тестов библиотечного API: после рефакторинга runtime-результат может остаться прежним, а информация о типе — превратиться в `Any` или широкий union.

```python
from collections.abc import Sequence
from typing import assert_type, reveal_type


def first_or_none[T](values: Sequence[T]) -> T | None:
    return values[0] if values else None


def inspect_result(values: Sequence[int]) -> int:
    result = first_or_none(values)
    assert_type(result, int | None)
    reveal_type(result)
    return 0 if result is None else result


assert inspect_result([3]) == 3
```

Runtime-вывод `reveal_type` здесь может показать `int`, потому что фактический результат равен 3. Статический анализатор сообщает `int | None`, потому что функция должна работать и с пустым входом. Эти два сообщения отвечают на разные вопросы.

В рабочем коде `reveal_type` обычно оставляют временно. В typecheck-тесте допустимо зафиксировать ожидаемые типы через `assert_type`, а отрицательные сценарии держать отдельно и проверять ожидаемую диагностику. Полезность такого теста теряется, если CI просто игнорирует ненулевой exit code анализатора.

### Сужение атрибутов и разделяемое изменяемое состояние

Локальная переменная с неизменяемым значением обычно стабильнее повторного доступа к изменяемому атрибуту. Если между проверкой `obj.value is not None` и чтением значения вызывается чужой код, состояние может измениться. Анализаторы не выполняют полный межпроцедурный и конкурентный анализ всех мутаций.

```python
import asyncio


class Cell:
    def __init__(self, value: str | None) -> None:
        self.value = value


async def clear(cell: Cell) -> None:
    cell.value = None


async def stable_upper(cell: Cell) -> str:
    value = cell.value
    if value is None:
        return "empty"
    await clear(cell)
    return value.upper()


cell = Cell("python")
assert asyncio.run(stable_upper(cell)) == "PYTHON"
assert cell.value is None
```

Локальная ссылка удерживает исходную строку, и строка не меняется при переприсваивании атрибута. Если бы значение было списком или объектом с изменяемым состоянием, одна локальная ссылка не обеспечила бы независимый снимок.

Не переносите полученное сужение через `await` как доказательство неизменности общего графа. Для согласованного чтения нескольких полей может понадобиться одна блокировка, immutable snapshot, транзакция или передача владения. Проверить два поля отдельно и получить каждое «правильного типа» недостаточно, если между ними нарушена смысловая связь.

`frozen=True`, `ReadOnly` и `Sequence` помогают описывать ограничения, но имеют разную глубину и не дают универсальной конкурентной гарантии. Проверенный тип является частью контракта; корректность жизненного цикла, синхронизации и мутаций нужно обеспечивать проектированием.

**Документация:** [Type narrowing](https://typing.python.org/en/latest/spec/narrowing.html), [PEP 647](https://peps.python.org/pep-0647/), [PEP 742](https://peps.python.org/pep-0742/), [typing helpers](https://docs.python.org/3.14/library/typing.html#functions-and-decorators).

## Аннотации во время выполнения

### Forward references, TYPE_CHECKING и циклические импорты

Forward reference позволяет сослаться на тип до того, как он появился в обычном runtime-порядке выполнения. Для кода, работающего на Python 3.12, часто используют строку с полным выражением аннотации либо future-импорт.

```python
from dataclasses import dataclass


@dataclass
class Node:
    name: str
    parent: "Node | None" = None


root = Node("root")
child = Node("child", root)
assert child.parent is root
```

Строкой нужно делать корректное выражение целиком: `"Node | None"`, а не `"Node" | None`. Во втором случае строковый объект участвует в runtime-операции объединения, которая не означает ожидаемый тип.

`typing.TYPE_CHECKING` истинен для анализатора и ложен при обычном выполнении. Под ним можно импортировать тип, который нужен только для статического контракта, сокращая runtime-зависимости и некоторые циклы.

```python
# typing: runtime
from typing import TYPE_CHECKING, get_type_hints


if TYPE_CHECKING:
    from decimal import Decimal


def amount() -> "Decimal":
    raise NotImplementedError


assert TYPE_CHECKING is False
try:
    get_type_hints(amount)
except NameError:
    pass
else:
    raise AssertionError("Decimal отсутствует в runtime-пространстве имён")
```

Это важное ограничение: анализатор видит тип, но framework, читающий аннотации во время работы, может не суметь его разрешить. Если тип нужен runtime-интроспекции, обеспечьте его доступность обычным импортом или явно переданными пространствами имён. Строковая форма не создаёт отсутствующий объект.

При циклических импортах сначала проверьте архитектуру: можно ли выделить общий протокол, перенести общую модель в независимый модуль или поменять направление зависимости? `TYPE_CHECKING` помогает только для зависимости, которая действительно нужна исключительно типам. Если модулю нужен runtime-класс для наследования, регистрации или вызова конструктора, скрыть импорт без изменения логики нельзя.

Импорт модуля вместо конкретного класса и квалифицированное имя `module.Class` иногда помогают управлять порядком доступа. Но модуль всё равно должен завершить нужную часть инициализации к моменту реального использования.

### `__annotations__`, get_type_hints(), get_origin() и get_args()

`__annotations__` предоставляет аннотации объекта, но их runtime-представление зависит от версии и режима вычисления. Это не готовая нормализованная схема валидации.

`typing.get_type_hints` разрешает строковые ссылки и нормализует часть аннотаций. Для класса он также учитывает наследование; при нехватке имён или ошибке вычисления может выбросить исключение. Если метаданные важны, используйте `include_extras=True`.

```python
from typing import Annotated, get_args, get_origin, get_type_hints


def process(value: Annotated[int, "positive"]) -> list[str]:
    return [str(value)]


plain = get_type_hints(process)
with_extras = get_type_hints(process, include_extras=True)
assert plain["value"] is int
assert get_origin(with_extras["value"]) is Annotated
assert get_args(with_extras["value"]) == (int, "positive")
assert get_origin(plain["return"]) is list
assert get_args(plain["return"]) == (str,)
```

`get_origin` показывает внешнюю конструкцию, `get_args` — её параметры. Они не выполняют рекурсивную проверку данных и не должны использоваться как единственный источник правил сложного валидатора.

```python
from typing import Literal, get_args, get_origin


annotation = dict[str, list[int | None]]
assert get_origin(annotation) is dict
key_type, value_type = get_args(annotation)
assert key_type is str
assert get_origin(value_type) is list
assert get_args(Literal["read", "write"]) == ("read", "write")
```

Не полагайтесь на строку `str(annotation)` как на машинный формат и не разбирайте её регулярными выражениями: представление, aliases и порядок частей union могут отличаться. Для объединений также учитывайте изменение runtime-представления между версиями; при необходимости проверяйте публичные `get_origin`/`get_args` и поддерживаемые варианты, а не частные классы `typing`.

`type Alias = ...` создаёт отдельный объект alias. Вызов `get_origin(Alias)` не обязан автоматически раскрывать его определение. Для `TypeAliasType` есть публичное `__value__`, но его чтение вычисляет ленивое значение и может потребовать ещё не определённые имена. В Python 3.14 добавлены дополнительные средства ленивой оценки через `annotationlib`.

У `TypedDict` есть метаданные обязательных/необязательных полей. Если аннотации строковые или отложенные, часть runtime-метаданных и совместимость backport-конструкций требуют особой осторожности. Пользуйтесь документированными API и тестируйте конкретную комбинацию Python и `typing_extensions`; не стройте схему исключительно на предположении о внутреннем словаре класса.

### Отложенные аннотации, future annotations и annotationlib

Необходимо различать три режима:

| Режим | Что происходит | Следствие |
|---|---|---|
| Обычный Python 3.12/3.13 | Многие аннотации функций и модулей вычисляются при определении | Неопределённое имя может сразу вызвать ошибку |
| `from __future__ import annotations` | Аннотации сохраняются в строковой форме | Для получения объектов типов требуется разрешение имён |
| Обычный Python 3.14 | Используется новая отложенная модель | Вычисление аннотации может произойти при обращении к ней |

Таблица описывает основной режим; у локальных аннотаций, type aliases и параметров типов есть собственные правила. Аннотация локальной переменной не означает, что Python обязан вычислить и сохранить её как аннотацию функции.

```python
from __future__ import annotations

from typing import get_type_hints


def identity(value: int) -> int:
    return value


assert isinstance(identity.__annotations__["value"], str)
assert get_type_hints(identity)["value"] is int
```

В Python 3.14 future-импорт не становится синонимом нового default-поведения: строковый режим сохраняет свои особенности. Миграцию framework, который читает аннотации, нужно тестировать отдельно от обычного исполнения функций.

```python
# Python 3.14+: без future-импорта ссылка может разрешиться позднее.
from annotationlib import Format, get_annotations


def describe(value: Later) -> str:
    return value.name


class Later:
    name = "defined later"


assert get_annotations(describe, format=Format.VALUE)["value"] is Later
assert describe(Later()) == "defined later"
```

`annotationlib`, появившийся в Python 3.14, позволяет явно выбрать форму результата:

- `Format.VALUE` — реальные вычисленные значения; разрешение имён может завершиться ошибкой.
- `Format.FORWARDREF` — реальные значения, где возможно, и `ForwardRef` для неразрешённых ссылок.
- `Format.STRING` — строковое представление выражений, близкое к исходному, но не точная копия исходного текста.

```python
# Python 3.14+
# typing: runtime
from annotationlib import Format, ForwardRef, get_annotations


def accept(value: MissingType) -> None:
    pass


partial = get_annotations(accept, format=Format.FORWARDREF)
assert isinstance(partial["value"], ForwardRef)
text = get_annotations(accept, format=Format.STRING)
assert isinstance(text["value"], str)
try:
    get_annotations(accept, format=Format.VALUE)
except NameError:
    pass
else:
    raise AssertionError("Неизвестный тип нельзя разрешить в обычное значение")
```

Не рассматривайте `FORWARDREF` как обещание полностью пассивного анализа: он старается вычислять известные части и не превращает любое выражение в безопасную строку. `STRING` также имеет ограничения и не гарантирует точное восстановление исходника.

Для метакласса, читающего namespace до завершения создания класса, в 3.14 предусмотрен `get_annotate_from_class_namespace` и соответствующие функции вызова. Простое ожидание готового `namespace["__annotations__"]` больше не описывает все режимы. Если вы пишете инфраструктурную библиотеку, проверяйте создание класса, унаследованные аннотации, forward references и несколько версий Python.

### Оценка аннотаций может выполнять код: границы доверия

Аннотация — выражение Python, а не специальный безопасный язык схем. В старом eager-режиме выражение могло выполняться при определении, в future-режиме — при разрешении строки, в новой модели — при обращении к аннотации.

```python
# typing: runtime
from __future__ import annotations

from typing import get_type_hints


events: list[str] = []


def choose_type() -> type[int]:
    events.append("evaluated")
    return int


def process(value: choose_type()) -> None:
    pass


assert events == []
assert get_type_hints(process)["value"] is int
assert events == ["evaluated"]
```

Пример намеренно показывает runtime-возможность выражения, а не рекомендуемый синтаксис статической аннотации. Анализатор не обязан принимать произвольный вызов как допустимое type expression.

```python
# Python 3.14+
# typing: runtime
from annotationlib import Format, get_annotations


events: list[str] = []


def choose_type() -> type[int]:
    events.append("evaluated")
    return int


def process(value: choose_type()) -> None:
    pass


assert events == []
assert get_annotations(process, format=Format.VALUE)["value"] is int
assert events == ["evaluated"]
```

**Доверие к аннотациям — доверие к коду.** Не принимайте произвольную строку от пользователя и не передавайте её в `eval`, `ForwardRef.evaluate` или изменённый `__annotations__` в надежде получить безопасный тип. Если нужен внешний язык схем, используйте формат с определённой грамматикой и валидатором.

Даже запрос `Format.STRING` не является песочницей: пользовательский `__annotate__`, fallback-пути и выражения могут выполнять код. Импорт неизвестного Python-модуля тоже сам по себе выполняет код, поэтому режим интроспекции не исправляет небезопасную загрузку плагина.

В собственных публичных аннотациях избегайте I/O, изменения состояния и дорогих вычислений. Используйте стабильные имена типов и декларативные метаданные. Инструменту документации или DI-контейнеру полезно явно документировать, когда он вычисляет аннотации, какие имена доступны и какие ошибки передаются наружу.

**Документация:** [annotationlib](https://docs.python.org/3.14/library/annotationlib.html), [изменения аннотаций в 3.14](https://docs.python.org/3.14/whatsnew/3.14.html#changes-in-annotations-pep-649-and-pep-749), [PEP 649](https://peps.python.org/pep-0649/), [PEP 749](https://peps.python.org/pep-0749/).

### mypy и Pyright: конфигурация, strict mode и CI

В большом проекте важен воспроизводимый контракт проверки: какие каталоги проверяются, какая версия Python считается целевой, какие зависимости доступны и какие отклонения допустимы. Зелёная строка «no issues» мало значит, если анализатор не увидел половину исходников или получил `Any` вместо всех внешних API.

**mypy** и **Pyright** реализуют общий язык типизации, но различаются выводом типов, диагностикой, поддержкой новых возможностей и настройками. Не ожидайте одинаковых сообщений и полностью одинакового набора принятых программ. Для проекта обычно выбирают основной обязательный анализатор; второй полезен для библиотечного API и проверки переносимости сложных аннотаций.

| Настройка | Зачем нужна |
|---|---|
| Целевая версия Python | Проверять доступность синтаксиса и API под поддерживаемый runtime |
| Strict mode | Усилить проверки неизвестных типов и неполных контрактов |
| Явные include/files | Зафиксировать проверяемую область |
| Окружение зависимостей | Использовать правильные пакеты и stubs |
| Фиксация версий инструментов | Отделить изменение кода от изменения правил анализатора |
| Проверка неиспользуемых suppressions | Удалять уже не нужные исключения |

`strict` — набор правил, который может развиваться. После обновления анализатора изучайте release notes и изменения диагностики, а не отключайте новые ошибки одним глобальным флагом. Для результатов `reveal_type` проверяйте смысл, а не точное форматирование строк во всех инструментах.

**Файл `src/zerohero_typing/models.py`.**

```python
# project: src/zerohero_typing/models.py
import re
from dataclasses import dataclass, field
from typing import Final, Literal, NewType, NotRequired

from typing_extensions import ReadOnly, TypedDict

EventId = NewType("EventId", str)
UserId = NewType("UserId", str)
MAX_AMOUNT: Final[int] = 1_000_000_000
_ID_PATTERN = re.compile(r"[A-Za-z0-9_-]{1,64}")


class SchemaError(ValueError):
    """Значение не соответствует схеме события."""


def _identifier(value: object, field_name: str) -> str:
    if not isinstance(value, str):
        raise SchemaError(f"{field_name}: ожидается строка")
    normalized = value.strip()
    if _ID_PATTERN.fullmatch(normalized) is None:
        raise SchemaError(f"{field_name}: недопустимый формат ID")
    return normalized


def make_event_id(value: object) -> EventId:
    return EventId(_identifier(value, "event_id"))


def make_user_id(value: object) -> UserId:
    return UserId(_identifier(value, "user_id"))


def checked_amount(value: object) -> int:
    if not isinstance(value, int) or isinstance(value, bool):
        raise SchemaError("amount_minor: ожидается int без bool")
    if not 0 <= value <= MAX_AMOUNT:
        raise SchemaError("amount_minor: значение вне диапазона")
    return value


def checked_note(value: object) -> str | None:
    if value is None:
        return None
    if not isinstance(value, str) or len(value) > 256:
        raise SchemaError("note: ожидается строка до 256 символов либо null")
    return value


class PaymentInput(TypedDict):
    # Это проверенное внутреннее представление, не сырой результат json.loads.
    event_id: ReadOnly[EventId]
    user_id: ReadOnly[UserId]
    amount_minor: int
    note: NotRequired[str | None]


@dataclass(frozen=True, slots=True)
class Payment:
    event_id: EventId
    user_id: UserId
    amount_minor: int
    note: str | None = None

    def __post_init__(self) -> None:
        # NewType и аннотации не проверяют конструктор в runtime.
        object.__setattr__(self, "event_id", make_event_id(self.event_id))
        object.__setattr__(self, "user_id", make_user_id(self.user_id))
        checked_amount(self.amount_minor)
        checked_note(self.note)


@dataclass(frozen=True, slots=True)
class Accepted:
    payment: Payment
    kind: Literal["accepted"] = field(default="accepted", init=False)


@dataclass(frozen=True, slots=True)
class Rejected:
    code: Literal["json", "schema", "limit"]
    message: str
    kind: Literal["rejected"] = field(default="rejected", init=False)


type DecodeResult = Accepted | Rejected
```

Фабрики ID действительно проверяют значения; NewType сохраняет различие уже после проверки. `Payment` повторно защищает собственный инвариант, потому что его можно создать напрямую. Поля frozen-объекта содержат строки и целое, поэтому здесь нет скрытого изменяемого вложенного списка.

Схема разрешает отсутствие `note` и явный `null`. В `Payment` эти два случая намеренно нормализуются в `None`: для данного домена они равнозначны. Если приложение обрабатывает PATCH и должно различать «не менять» и «очистить», такую нормализацию делать нельзя.

**Файл `src/zerohero_typing/decoding.py`.**

```python
# project: src/zerohero_typing/decoding.py
import json
from collections.abc import Mapping
from typing import cast

from .models import (
    Accepted,
    DecodeResult,
    Payment,
    PaymentInput,
    Rejected,
    SchemaError,
    checked_amount,
    checked_note,
    make_event_id,
    make_user_id,
)


def _unique_object(pairs: list[tuple[str, object]]) -> dict[str, object]:
    result: dict[str, object] = {}
    for key, value in pairs:
        if key in result:
            raise SchemaError("Повторяющийся ключ JSON")
        result[key] = value
    return result


def _object_mapping(value: object) -> dict[str, object]:
    if not isinstance(value, dict):
        raise SchemaError("Ожидается JSON object")
    # После isinstance известна только общая структура словаря.
    # Здесь НЕ обещаются типы конкретных полей: читаем object -> object,
    # затем проверяем ключи и строим новый словарь.
    mapping = cast(Mapping[object, object], value)
    result: dict[str, object] = {}
    for key, item in mapping.items():
        if not isinstance(key, str):
            raise SchemaError("Ключ должен быть строкой")
        result[key] = item
    return result


def validate_payload(value: object) -> PaymentInput:
    data = _object_mapping(value)
    required = {"event_id", "user_id", "amount_minor"}
    allowed = required | {"note"}
    if not required <= data.keys():
        raise SchemaError("Отсутствует обязательное поле")
    if not data.keys() <= allowed:
        raise SchemaError("Неизвестное поле")
    result: PaymentInput = {
        "event_id": make_event_id(data["event_id"]),
        "user_id": make_user_id(data["user_id"]),
        "amount_minor": checked_amount(data["amount_minor"]),
    }
    if "note" in data:
        result["note"] = checked_note(data["note"])
    return result


def _positive_limit(value: object) -> int:
    if not isinstance(value, int) or isinstance(value, bool) or value <= 0:
        raise ValueError("max_chars должен быть положительным int")
    return value


def decode_line(text: str, *, max_chars: int = 10_000) -> DecodeResult:
    limit = _positive_limit(max_chars)
    if len(text) > limit:
        return Rejected("limit", "Превышен лимит длины строки")
    try:
        raw: object = json.loads(text, object_pairs_hook=_unique_object)
        payload = validate_payload(raw)
        payment = Payment(
            payload["event_id"],
            payload["user_id"],
            payload["amount_minor"],
            payload.get("note"),
        )
    except json.JSONDecodeError:
        return Rejected("json", "Некорректный JSON")
    except SchemaError as error:
        return Rejected("schema", str(error))
    return Accepted(payment)
```

Единственный cast здесь локален и не утверждает схему платежа. После проверки внешнего словаря он даёт read-only интерфейс чтения произвольных Python-объектов; затем все конкретные типы проверяются до создания нового TypedDict. Cast в `PaymentInput` вместо этих проверок был бы совсем другим, необоснованным обещанием.

Дубликаты ключей JSON отклоняются явно, а не молча заменяются последним значением. Дополнительные поля тоже отклоняются. Лимит задан в символах Python-строки; это не лимит сетевых байтов и не полная защита от любых затрат парсинга. Ошибки программы, исчерпание памяти и произвольные сбои не превращаются широким `except Exception` в «неверный JSON».

**Файл `src/zerohero_typing/pipeline.py`.**

```python
# project: src/zerohero_typing/pipeline.py
from collections.abc import Callable, Iterable, Iterator
from dataclasses import dataclass
from typing import Protocol, assert_never

from .decoding import decode_line
from .models import Accepted, Payment, Rejected


class PaymentSink(Protocol):
    def write(self, payment: Payment, /) -> None:
        """Сохранить одно событие либо выбросить исключение."""
        ...


class MemorySink:
    def __init__(self) -> None:
        self._payments: list[Payment] = []

    def write(self, payment: Payment, /) -> None:
        self._payments.append(payment)

    def snapshot(self) -> tuple[Payment, ...]:
        return tuple(self._payments)


@dataclass(frozen=True, slots=True)
class ImportReport:
    accepted: int
    errors: tuple[Rejected, ...]

    @property
    def rejected(self) -> int:
        return len(self.errors)


def map_values[T, R](values: Iterable[T], function: Callable[[T], R]) -> Iterator[R]:
    for value in values:
        yield function(value)


def process_lines(lines: Iterable[str], sink: PaymentSink) -> ImportReport:
    accepted = 0
    errors: list[Rejected] = []
    for result in map_values(lines, decode_line):
        match result:
            case Accepted(payment=payment):
                sink.write(payment)
                accepted += 1
            case Rejected():
                errors.append(result)
            case _:
                assert_never(result)
    return ImportReport(accepted, tuple(errors))
```

Обход ленивый, но отчёт накапливает все ошибки в памяти. Для очень большого потока нужна другая политика: ограниченный sample ошибок, callback или отдельное хранилище. Тип `Iterator` не гарантирует ограниченную память всего приложения.

Каждая запись сохраняется отдельно; общей транзакции пакета здесь нет. Если sink завершился ошибкой после нескольких успешных вызовов, исключение передаётся наружу, а ранее сохранённые данные могут остаться. Для повторов потребуются идемпотентность и отдельный контракт. Типизация намеренно не выдаёт `write(Payment)` за гарантию exactly-once.

### Постепенная миграция и контроль исключений из проверки

Для существующего проекта начните с карты границ: где читаются внешние данные, какие модули имеют устойчивый API, где находятся динамические библиотеки и метапрограммирование. Типизация проще распространяется от небольшого проверяемого ядра с точными результатами, чем от сотен внутренних переменных без контракта входа.

Практический порядок:

1. Зафиксировать анализатор, конфигурацию и текущий набор ошибок.
2. Аннотировать публичные входы и результаты проверяемого модуля.
3. Вывести непроверенный ввод в `object` и добавить реальные валидаторы.
4. Описать нужные зависимости узкими Protocol вместо глобальных Any.
5. Включить строгие правила для готового модуля и постепенно расширять область.
6. Не допускать новых подавлений без понятной причины и владельца.

**Suppressions должны быть локальными.** `# type: ignore[code]` в mypy точнее безымянного ignore; Pyright имеет свои диагностические правила и адресные комментарии. Коды двух инструментов не являются общим стандартом, поэтому не копируйте их между анализаторами механически.

`cast` и ignore решают разные задачи. Cast меняет заявленный тип конкретного выражения; ignore подавляет диагностику на участке. Ни один вариант не проверяет runtime-значение. Если причина — настоящая ошибка входной схемы, исправлять нужно валидатор, а не комментарий.

`ignore_missing_imports = true` на весь проект может скрыть большую часть API за Any. Если внешняя библиотека не типизирована, ограничьте исключение её пространством имён и напишите типизированный адаптер с небольшим контрактом. Проверьте, какие типы действительно выходят из адаптера.

В mypy `check_untyped_defs` проверяет тела неаннотированных функций, но не создаёт точные аннотации параметров автоматически. В строгом проекте функция с неизвестными входами всё равно остаётся слабой границей. У Pyright вывод может быть другим; ориентируйтесь на фактическую диагностику и типы.

Отслеживайте не только число ошибок, но и покрытие публичных контрактов, распространение Any/Unknown, причины подавлений и наличие статических тестов критичного API. Нельзя улучшать метрику уменьшением области проверки или объявлением всего результата как Any.

### .pyi, typeshed, py.typed и поставка типов библиотеки

Файл `.pyi` описывает публичные типы без обычной реализации. В нём допустимы сигнатуры с `...`, overload и объявления экспортов. Когда рядом есть stub, анализатор обычно использует его как интерфейс вместо чтения соответствующего `.py` для потребителя.

```python
# typing: stub
# Пример содержимого api.pyi; это описание, а не исполняемый модуль.
from collections.abc import Iterable
from typing import overload


@overload
def total(values: Iterable[int]) -> int: ...


@overload
def total(values: Iterable[float]) -> float: ...
```

Пример показывает форму stub, но пересечение числовых overload требует согласованной реализации и проверки порядка: `int` статически совместим с `float`. Не создавайте stub, который обещает другой результат, чем реально возвращает пакет.

`typeshed` содержит типовые описания стандартной библиотеки и многих сторонних API. Анализаторы используют свои поставки/версии этих описаний; обновление typeshed может изменить вывод даже при неизменном исходнике приложения.

| Способ поставки | Что включается | На что обратить внимание |
|---|---|---|
| Inline-типы | Аннотации в `.py` и маркер `py.typed` | Маркер должен попасть в установленный wheel |
| `.pyi` рядом с реализацией | Stubs в пакете | Следить за соответствием runtime |
| Stub-only distribution | Пакет типов, часто с суффиксом `-stubs` | Версия и покрытие относительно настоящей библиотеки |
| Локальные stubs | Дополнение проекта для зависимости | Область override и поддержка после обновлений |

`py.typed` сообщает инструментам, что установленный пакет поставляет типовую информацию по правилам распространения. Это не сертификат качества: в коде всё ещё могут быть Any и неверные аннотации. Для namespace packages важны расположение маркера и реальные части дистрибутива; не кладите его бездумно в общий корень чужого namespace.

В практическом проекте проверьте три уровня:

- файл `py.typed` существует в исходном пакете;
- он включён в wheel;
- анализатор из независимой папки видит точный публичный API после установки wheel.

Проверка только исходников может пройти благодаря `mypy_path`, `extraPaths` или особенностям checkout, а пользователь библиотеки получит Any. Внешний consumer-тест должен выполняться без случайного доступа к `src`.

Для stub-пакетов и C-расширений полезен `stubtest` из mypy: он сравнивает часть stub-интерфейса с реальными объектами. Он не доказывает все overload-связи и предметные инварианты. Дополняйте его runtime-тестами и примерами положительной/отрицательной типизации.

**Типизация также является API.** Сужение принимаемого типа, изменение default, потеря overload, удаление экспортируемого alias и появление Any в результате могут ломать пользователей при прежнем runtime-поведении. Рассматривайте такие изменения на code review и в политике совместимости.

### Типы сторонних зависимостей и поддержка нескольких версий Python

Для каждой зависимости выясните: есть ли inline-типы, отдельный официальный или сторонний stub-пакет, совпадает ли его версия с runtime-библиотекой, нужен ли plugin конкретному анализатору. Mypy plugin не становится автоматически plugin для Pyright; код с такой зависимостью может проверяться по-разному.

Локальный адаптер полезен, когда внешний API динамический или слишком широкий. Он принимает непроверенные значения, выполняет необходимые проверки и возвращает небольшой устойчивый тип. Так внешний Any остаётся локальным, а основной алгоритм зависит от собственного проверяемого контракта.

**Матрица совместимости имеет несколько независимых осей:**

| Ось | Пример вопроса |
|---|---|
| Парсер Python | Разбирает ли Python 3.11 синтаксис `type Alias = ...`? Нет |
| Runtime API | Есть ли `TypeIs` в стандартном typing версии 3.12? Нет |
| Backport | Есть ли нужная конструкция в установленном `typing_extensions`? |
| Анализатор | Поддерживает ли его версия PEP 695/696/705/742? |
| Целевая настройка | Проверяем ли мы код как 3.12 или как 3.14? |
| Runtime-интроспекция | Умеет ли framework работать с моделью аннотаций 3.14? |
| Упаковка | Доступны ли типы установленному потребителю? |

Backport может добавить объект `ReadOnly` или `TypeIs`, но не научить старый Python разбирать новый синтаксис параметров типов. Future-импорт тоже не решает проблему грамматики. Укажите честный `requires-python` и проверьте минимальную версию реальным запуском.

`typing_extensions` лучше объявлять runtime-зависимостью, если пакет действительно импортирует его при обычной работе, как практический проект. Если зависимость нужна только проверяющим инструментам, можно рассмотреть отдельную dev-группу и TYPE_CHECKING, но тогда отдельно проверьте runtime-чтение аннотаций.

В CI полезны runtime-тесты на минимальной и одной из новых поддерживаемых версий, статическая проверка целевых версий, сборка и установка wheel, а также consumer-тест публичных типов. Для платформозависимых импортов добавляется целевая ОС. Обновления анализаторов и зависимостей лучше делать отдельным обозримым изменением.

В поддерживаемом проекте непроверенный ввод локализован, полезные связи между типами сохраняются, Any и suppressions имеют объяснение, статические негативные тесты действительно ловят нарушение, а установленные пользователи получают те же типы, что разработчики в checkout. Точность этих границ полезнее максимально сложных аннотаций во всех внутренних выражениях.

**Документация:** [mypy configuration](https://mypy.readthedocs.io/en/stable/config_file.html), [Pyright configuration](https://github.com/microsoft/pyright/blob/main/docs/configuration.md), [распространение типов](https://typing.python.org/en/latest/spec/distributing.html), [typeshed](https://github.com/python/typeshed), [stubtest](https://mypy.readthedocs.io/en/stable/stubtest.html), [typing_extensions](https://typing-extensions.readthedocs.io/).
