# Интроспекция, AST и инструменты анализа кода

Python позволяет исследовать работающие объекты, читать исходный текст, разбирать его структуру, создавать новые деревья и компилировать код. Эти возможности лежат в основе отладчиков, documentation generators, linters, type checkers, IDE и инструментов миграции.

Для каждого инструмента важно выбрать уровень представления. Объект функции содержит сведения о текущем окружении; исходный текст сохраняет комментарии; AST показывает синтаксическую структуру; bytecode отражает решения конкретного компилятора. Эти представления не взаимозаменяемы.

| Представление | Что хорошо видно | Что теряется или остаётся неизвестным |
| --- | --- | --- |
| Runtime objects | Реальные типы, атрибуты, bindings и состояние | Исходник может отсутствовать; доступ способен исполнять код |
| Tokens | Лексемы, комментарии и позиции | Связи между именами и смысл выражений |
| AST | Структура программы и роли синтаксических узлов | Обычные комментарии, исходное форматирование, runtime bindings |
| CST | Структура вместе с конкретной записью | Полная семантика динамического исполнения |
| Code object | Скомпилированный блок и его metadata | Самостоятельное окружение функции и исходное форматирование |
| Bytecode | Инструкции реализации и переходы | Переносимость между версиями и высокий уровень исходного замысла |

Основные примеры рассчитаны на Python 3.12+. Особенности Python 3.14 отмечены отдельно. Проверенный практический проект использует стандартную библиотеку для анализа и дополнительный LibCST для codemod.

Разбор текста сам по себе не исполняет анализируемую программу. Импорт модуля, получение динамического атрибута, вычисление annotation и `exec` могут выполнять код. Это различие определяет архитектуру инструментов разработчика.

## Интроспекция во время выполнения

### inspect: классы, модули, члены, frames и stack

**Интроспекция исследует уже существующие объекты**

`inspect` объединяет сведения о типах объектов, сигнатурах, исходниках, связях вызовов и execution frames. Это удобно для diagnostics, dependency injection, adapters, registration и документации.

Перед исследованием полезно уточнить вопрос: «какой объект передали?», «какие аргументы принимает callable?», «где определена функция?» или «кто сейчас вызывает этот код?». Один общий обход всех атрибутов редко является лучшим ответом на каждую задачу.

```python
import inspect


class Service:
    def run(self, value: int) -> int:
        return value + 1

    async def fetch(self) -> int:
        return 42


service = Service()
assert inspect.isclass(Service)
assert inspect.isfunction(Service.run)
assert inspect.ismethod(service.run)
assert inspect.iscoroutinefunction(Service.fetch)
assert inspect.getmodule(Service) is not None

methods = inspect.getmembers(Service, predicate=inspect.isfunction)
print([name for name, _ in methods])
```

Связанному методу доступны `__self__` и `__func__`. У `service.run` первый параметр уже связан с экземпляром, поэтому его вызывающая сигнатура отличается от `Service.run`.

Проверки формы объекта не гарантируют его поведение. `callable(x)` не доказывает, что следующий вызов завершится успешно; `iscoroutinefunction` не означает отсутствие блокирующего I/O внутри функции.

Обычная функция может возвращать awaitable. Async generator отличается от coroutine и не вызывается через простой `await` результата. Выбирайте `isawaitable`, `isgeneratorfunction`, `isasyncgenfunction` по конкретному протоколу.

**Сигнатура — структурированное описание вызова**

`inspect.signature` даёт объект `Signature`, а не строку, которую нужно разбирать регулярным выражением. Он учитывает positional-only, keyword-only, defaults и varargs.

```python
import inspect


def build_report(
    source: str, /, limit: int = 100, *, strict: bool = True
) -> tuple[str, int, bool]:
    return source, limit, strict


signature = inspect.signature(build_report)
bound = signature.bind("events", strict=False)
bound.apply_defaults()

assert bound.arguments == {"source": "events", "limit": 100, "strict": False}
assert build_report(*bound.args, **bound.kwargs) == ("events", 100, False)

try:
    signature.bind(source="events")
except TypeError:
    print("positional-only argument rejected")
else:
    raise AssertionError("binding must reject this call")
```

`bind` проверяет соответствие сигнатуре. Он не проверяет значения по type annotations и не исполняет тело функции. `bind_partial` допускает отсутствие обязательных аргументов и полезен для частичного связывания.

После `apply_defaults` в binding появляются значения по умолчанию. Если default mutable, это та же ссылка на объект, а не автоматически созданная копия. Интроспекция не исправляет контракт вызываемой функции.

У некоторых builtins и extension objects сигнатура отсутствует или ограничена. Обрабатывайте `TypeError/ValueError` и решайте, что должен делать ваш инструмент при неизвестной сигнатуре.

**Декораторы меняют наблюдаемый объект**

`functools.wraps` переносит metadata и задаёт `__wrapped__`. По умолчанию `inspect.signature` следует этой цепочке. Для исследования самой обёртки используйте `follow_wrapped=False`.

```python
from functools import wraps
import inspect


def observed(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        return function(*args, **kwargs)

    return wrapper


@observed
def calculate(value: int, *, scale: int = 2) -> int:
    return value * scale


public = inspect.signature(calculate)
implementation = inspect.signature(calculate, follow_wrapped=False)
assert list(public.parameters) == ["value", "scale"]
assert list(implementation.parameters) == ["args", "kwargs"]
assert inspect.unwrap(calculate).__name__ == "calculate"
assert calculate(3) == 6
```

Metadata может быть задана вручную, включая `__signature__`. Поэтому отображённая сигнатура — описание, предоставленное объектом и механизмом introspection, а не доказательство фактической реализации.

Проверяйте циклы `__wrapped__` и учитывайте ошибки `unwrap`. Собственный framework должен явно определять, доверяет ли он пользовательской metadata.

**Аннотации не всегда являются пассивными данными**

В старом режиме annotations могли вычисляться при определении функции; с `from __future__ import annotations` они хранятся в строковой форме. В Python 3.14 стандартная модель включает отложенное вычисление.

Получение значения annotation может вызвать вычисление выражения. `typing.get_type_hints` также выполняет разрешение имён и другие преобразования. Не исследуйте недоверенный plugin через импорт и вычисление annotations, ожидая чисто статического чтения.

Для текстового представления в Python 3.14:

```python
# Python 3.14+
import annotationlib
import inspect


def endpoint(value: NotImportedYet) -> list[int]:
    return [1]


signature = inspect.signature(endpoint, annotation_format=annotationlib.Format.STRING)
assert isinstance(signature.parameters["value"].annotation, str)
assert "NotImportedYet" in signature.parameters["value"].annotation
print(signature)
```

Пример не вызывает endpoint и не требует, чтобы имя annotation было разрешено как реальный тип. Форматы annotations нужно выбирать по задаче. Это не превращает introspection произвольного объекта с пользовательскими hooks в sandbox.

**Frames и stack**

Frame хранит состояние исполнения code block. Через него можно получить code object, локальные значения, номер строки и вызывающий frame. Stack — цепочка таких frames.

Для короткой диагностики лучше извлечь нужные данные и сразу удалить ссылки:

```python
import inspect


def describe_caller() -> tuple[str, int] | None:
    frame = inspect.currentframe()
    parent = None
    try:
        parent = frame.f_back if frame is not None else None
        if parent is None:
            return None
        return parent.f_code.co_name, parent.f_lineno
    finally:
        del parent
        del frame


def handler() -> tuple[str, int] | None:
    return describe_caller()


description = handler()
assert description is not None and description[0] == "handler"
```

Сохранённые frames и tracebacks удерживают локальные объекты. Список `inspect.stack()` может быть значительно дороже извлечения одного caller и тоже содержит ссылки на frames.

Не используйте глубокий обход stack на каждом шаге горячего цикла без измерения. Для tracing и profiling существуют специальные механизмы; подробности измерений рассмотрены в предыдущей главе.

### getattr_static() vs динамический доступ к атрибутам

**Обычный доступ включает протокол объекта**

`obj.name` и `getattr(obj, "name")` могут вызвать `__getattribute__`, descriptor и `__getattr__`. Property может читать файл, выполнять запрос и менять состояние.

`hasattr` тоже использует получение атрибута. Он подавляет `AttributeError`, но не все исключения. Поэтому «только проверить, есть ли поле» не всегда является пассивным действием.

```python
import inspect


class Record:
    def __init__(self) -> None:
        self.reads = 0

    @property
    def expensive(self) -> int:
        self.reads += 1
        return 42

    def __getattr__(self, name: str) -> str:
        if name == "virtual":
            return "created dynamically"
        raise AttributeError(name)


record = Record()
descriptor = inspect.getattr_static(record, "expensive")
assert isinstance(descriptor, property)
assert record.reads == 0
assert getattr(record, "expensive") == 42
assert record.reads == 1

missing = object()
assert inspect.getattr_static(record, "virtual", missing) is missing
assert getattr(record, "virtual") == "created dynamically"
```

`getattr_static` ищет атрибут без обычного descriptor resolution и обходится без пользовательского динамического доступа к самому искомому атрибуту. Это полезно для документации и tools, которым нужна декларация property.

Результат может быть descriptor object, а не значение, которое вернул бы обычный доступ. Такое различие является смыслом API.

**Slots и descriptors**

```python
import inspect


class Point:
    __slots__ = ("x",)

    def __init__(self, x: int) -> None:
        self.x = x


point = Point(7)
slot_descriptor = inspect.getattr_static(point, "x")
assert slot_descriptor is inspect.getattr_static(Point, "x")
assert point.x == 7

# Явное разрешение известного descriptor вновь выполняет его протокол.
assert slot_descriptor.__get__(point, Point) == 7
```

Если ваш инструмент автоматически вызывает `__get__` у любого найденного descriptor, пассивность снова теряется. Для произвольных объектов нельзя объявлять такое разрешение безопасным только потому, что первый поиск был static.

Статический доступ имеет ограничения при нестандартном устройстве классов, metaclasses и затенении `__dict__`. Он также может не увидеть виртуальные атрибуты, которые создаёт `__getattr__`.

**Получение списка членов — отдельная операция**

`inspect.getmembers_static` доступен с Python 3.11 и не разрешает descriptors обычным способом при получении значений. Но сбор списка имён связан с `dir`, а пользовательский `__dir__` может выполнять код.

Следовательно, «получить один объявленный атрибут» и «перечислить все члены произвольного объекта» имеют разные границы. Для статического анализа исходников ни один из этих подходов не заменяет чтение файла.

**Как выбирать**

| Задача | Подход |
| --- | --- |
| Получить значение по обычному контракту объекта | Обычный доступ или `getattr` |
| Исследовать объявление property/descriptor | `inspect.getattr_static` |
| Построить runtime API documentation доверенного модуля | `inspect` с обработкой ошибок |
| Найти зависимости неизвестного исходника | AST/CST без его импорта |
| Узнать, что действительно вернёт динамический объект | Выполнение его протокола в допустимой среде |

Пассивный анализ и runtime-проверка дополняют друг друга. Статический инструмент может видеть property в исходнике, а runtime adapter — реальную сигнатуру после установки декораторов.

### Получение исходника: ограничения REPL, builtins и сгенерированного кода

**Исходный текст не является обязательным свойством callable**

Python может работать с bytecode, native extension, динамически сгенерированной функцией и объектом, который вообще не был записан как `def` в файле.

`inspect.getsource` полезен, когда можно найти соответствующий исходник. Нужно обрабатывать отсутствие текста:

```python
import inspect


def transform(value: int) -> int:
    return value + 1


def source_or_none(value: object) -> str | None:
    try:
        return inspect.getsource(value)
    except (OSError, TypeError):
        return None


source = source_or_none(transform)
assert source is not None and "def transform" in source
assert source_or_none(len) is None
```

Самостоятельный пример нужно сохранить в `.py`-файл. В plain REPL исходника функции может не быть; IPython/Jupyter могут предоставлять собственный source cache, но это свойство среды.

**Разные инструменты дают разные сведения**

| API | Что пытается получить |
| --- | --- |
| `inspect.getfile` | Файл определения объекта, если известен |
| `inspect.getsourcefile` | Python source file, когда его можно определить |
| `inspect.getsourcelines` | Список строк и исходный номер начала |
| `inspect.getsource` | Исходный фрагмент строкой |
| `inspect.getdoc` | Нормализованную документацию |
| `linecache.getline` | Строку по имени файла и номеру |

Docstring не является исходником. Она может отсутствовать, быть заменена вручную или удалена режимом оптимизации `-OO`.

Для декорированной функции `getsource` может показать запись с декораторами, а runtime body находиться в wrapper. Сначала решите, нужен исходный объект или результат `inspect.unwrap`.

**Генерируемому коду можно дать реальное происхождение**

```python
import inspect
from pathlib import Path
from tempfile import TemporaryDirectory


source = "def generated(value):\n    return value * 2\n"

with TemporaryDirectory() as directory:
    path = Path(directory) / "generated_module.py"
    path.write_text(source, encoding="utf-8")
    namespace = {"__name__": "generated_demo"}
    code = compile(source, str(path), "exec")
    exec(code, namespace)
    generated = namespace["generated"]

    assert generated(5) == 10
    assert inspect.getsource(generated) == source
    assert generated.__code__.co_filename == str(path)
```

Выполняется только фиксированный учебный исходник, созданный в этом примере. Имя файла помогает `inspect` и traceback связать code object с текстом.

`compile(source, "<generated>", ...)` тоже принимает условное имя. Однако `co_filename` — metadata, а не подтверждение существования файла. Самостоятельно выбранное имя не делает исходник доступным для `getsource`.

`linecache` используется traceback и introspection. Интерактивные среды и loaders могут помогать находить исходник. Прямое заполнение внутренних cache entries требует знания реализации и не должно становиться универсальным API вашего пакета.

**Полученный текст может не совпасть с исполняемой версией**

Если файл изменился после импорта, runtime function продолжит исполнять старый code object, пока её не заменили. Читаемый сейчас файл может описывать другую ревизию.

Для воспроизводимой диагностики сохраняют версию artifact, revision и provenance исходников. В traceback путь к файлу полезен, но сам по себе не доказывает соответствие содержимого.

Упакованное приложение может не поставлять `.py` рядом с bytecode. ZIP loader иногда предоставляет source, native builtins — обычно нет. Не делайте получение исходника обязательным условием работы инструмента, если его контракт допускает такие объекты.

**Исходник и секреты**

API explorer или диагностический endpoint способен раскрыть пути, embedded credentials и внутреннюю реализацию. Если приложение публикует introspection, задайте доступные объекты и состав ответа явно.

Для анализа собственного репозитория обычно полезнее работать с versioned files напрямую. Это также позволяет проверить синтаксис, который пока не импортируется из-за отсутствующей зависимости.

### Code object vs function object; co_* и пространства имён

**Code object описывает блок, function object связывает его с окружением**

`function.__code__` содержит скомпилированное представление тела и metadata. Сам function object дополнительно связан с globals, defaults, closure, annotations, именем и атрибутами.

Один и тот же code object может использоваться несколькими функциями с разными глобальными окружениями:

```python
from types import FunctionType


def template(value):
    return value + offset


first = FunctionType(
    template.__code__, {"offset": 10, "__builtins__": {}}, name="first"
)
second = FunctionType(
    template.__code__, {"offset": 20, "__builtins__": {}}, name="second"
)

assert first.__code__ is second.__code__
assert first(3) == 13 and second(3) == 23
assert first.__globals__ is not second.__globals__
```

Пустой `__builtins__` здесь лишь делает пример окружения явным. Он не создаёт sandbox для произвольного code object.

Сам code object не содержит полного словаря globals функции. `co_names` перечисляет определённые использованные имена, но не даёт их текущие значения.

**Полезные поля**

| Поле | Что описывает |
| --- | --- |
| `co_name` / `co_qualname` | Имя и квалифицированное имя блока |
| `co_filename` | Metadata имени исходного файла |
| `co_firstlineno` | Номер начала определения/блока |
| `co_argcount` | Число позиционных параметров, включая positional-only |
| `co_posonlyargcount` | Число positional-only параметров |
| `co_kwonlyargcount` | Число keyword-only параметров |
| `co_varnames` | Имена аргументов и локальных переменных |
| `co_freevars` | Имена свободных переменных closure |
| `co_cellvars` | Локальные имена, используемые вложенными closures |
| `co_consts` | Константы, в том числе вложенные code objects |
| `co_names` | Имена, связанные с определёнными операциями обращения к именам/атрибутам |
| `co_flags` | Флаги вида и поведения code block |
| `co_lines()` / `co_positions()` | Связь кода с исходными позициями |

Не считайте `co_names` готовым списком импортов или зависимостей. Имя атрибута может не быть именем модуля, а динамический import может строить строку из данных.

Не восстанавливайте сигнатуру самостоятельно по tuple offsets, когда доступен `inspect.signature`. Публичный структурированный API лучше отражает callable, включая bound methods и decorators.

**Замыкания имеют отдельные cells**

```python
import inspect


def make_multiplier(factor: int):
    def multiply(value: int) -> int:
        return value * factor

    return multiply


double = make_multiplier(2)
triple = make_multiplier(3)
assert double.__code__ is triple.__code__
assert double(5) == 10 and triple(5) == 15

names = double.__code__.co_freevars
cells = double.__closure__ or ()
captured = {name: cell.cell_contents for name, cell in zip(names, cells)}
assert captured == {"factor": 2}
assert inspect.getclosurevars(triple).nonlocals == {"factor": 3}
```

Cells содержат ссылки на объекты. Если несколько closures разделяют одну cell, изменение через `nonlocal` видно всем соответствующим функциям.

Передача подходящих globals не заменяет closure. `FunctionType` для кода со свободными переменными требует корректного набора cells. Замена `__code__` у существующей функции также имеет ограничения совместимости.

**Code objects не являются стабильным форматом обмена**

Их структура и bytecode зависят от реализации и версии. Прямое создание `CodeType` позиционными аргументами особенно чувствительно к изменениям.

Если задача требует сгенерировать Python-программу, обычно проще построить AST и вызвать `compile` либо сгенерировать текст с понятным provenance. Для исследования инструкций используйте `dis`.

Модуль `marshal` и `.pyc` относятся к внутренним форматам исполнения. Не используйте их как доверенный переносимый протокол хранения произвольных пользовательских программ.

## Токенизация и синтаксическое дерево

### tokenize: позиции, комментарии, отступы и round-trip

**Tokens — лексическая форма программы**

`tokenize` разбивает текст на лексические элементы. Для инструмента важны тип токена, его текст, начальная/конечная позиция и исходная строка.

В отличие от AST, tokenizer предоставляет обычные комментарии. Это удобно для директив suppression, проверки заголовков и локальных изменений текста.

```python
import io
import token
import tokenize


raw = "if active:\n    значение = (1 +\n                2)  # комментарий\n".encode(
    "utf-8"
)
tokens = list(tokenize.tokenize(io.BytesIO(raw).readline))
comments = [item for item in tokens if item.type == tokenize.COMMENT]

assert len(comments) == 1
assert comments[0].string == "# комментарий"
assert any(item.type == tokenize.INDENT for item in tokens)
assert any(item.type == tokenize.DEDENT for item in tokens)
for item in tokens:
    if item.type in (tokenize.NAME, tokenize.COMMENT):
        print(token.tok_name[item.type], item.string, item.start, item.end)
```

`NEWLINE` завершает логическую строку. `NL` используется для незавершающего перевода строки, например внутри скобок и в определённых пустых/comment-only строках.

Отступы имеют синтаксическую роль через `INDENT/DEDENT`. Однако табуляция, число пробелов и визуальная ширина — разные понятия. Позиция tokenizer не является готовой координатой экранного курсора в любом редакторе.

Для операторов общий тип часто `OP`, а `exact_type` уточняет конкретный знак. Не сравнивайте все токены только с их печатным текстом: слово в строковом литерале не является identifier.

**Кодировка определяется на уровне исходных bytes**

`tokenize.tokenize` принимает `readline`, возвращающий bytes, и выдаёт `ENCODING`. `generate_tokens` работает с уже декодированным текстом и не выдаёт этот encoding token.

`tokenize.detect_encoding` учитывает UTF-8 BOM и encoding cookie. Для чтения обычного source file есть `tokenize.open`:

```python
from pathlib import Path
from tempfile import TemporaryDirectory
import tokenize


with TemporaryDirectory() as directory:
    path = Path(directory) / "latin_module.py"
    path.write_bytes(b"# coding: latin-1\nname = 'caf\xe9'\n")
    with tokenize.open(path) as stream:
        text = stream.read()
    assert "café" in text
```

Произвольный `read_text(encoding="utf-8")` не подходит для всех допустимых Python source files. Сохранение исходной кодировки и BOM особенно важно для codemod.

При работе с внешним большим файлом чтение и парсинг требуют лимитов. `tokenize.open` сам по себе не задаёт максимальный размер.

**Что гарантирует round-trip**

`untokenize` восстанавливает исходник по token pairs либо полным `TokenInfo`. Гарантия относится к типам и строковым значениям токенов, а не ко всем исходным bytes и пробелам.

```python
import io
import tokenize


raw = b"value=1+2  # keep this comment\n"
original = list(tokenize.tokenize(io.BytesIO(raw).readline))
rebuilt = tokenize.untokenize((item.type, item.string) for item in original)


def token_pairs(source: bytes):
    return [
        (item.type, item.string)
        for item in tokenize.tokenize(io.BytesIO(source).readline)
    ]


assert isinstance(rebuilt, bytes)
assert token_pairs(rebuilt) == token_pairs(raw)
assert b"# keep this comment" in rebuilt
print(rebuilt.decode("utf-8"))
```

Если передан `ENCODING`, результатом может быть bytes. При работе только со строковыми tokens результатом будет str. Уточняйте это в контракте преобразования.

Полные позиции помогают сохранить расположение, но не превращают tokenizer в универсальный форматирующий CST. Для перестановки больших синтаксических конструкций удобнее concrete syntax tree.

**Tokenization не равна проверке всей грамматики**

Поток токенов может быть получен для текста, который parser отвергнет. Незакрытые строки и скобки могут вызывать `TokenError`, но отсутствие этой ошибки не доказывает корректность программы.

Документация `tokenize` ориентирована на синтаксически корректный Python. Для обработки повреждённых файлов IDE нужны дополнительные правила восстановления.

В новых версиях меняются детали токенизации f-strings, template strings и других конструкций. Не фиксируйте список числовых token IDs в долгоживущем инструменте.

### ast.parse(), ast.dump() и типы узлов

**AST описывает синтаксическую структуру**

`ast.parse` строит дерево, не вызывая функции из анализируемого текста. Это позволяет исследовать модуль с отсутствующими зависимостями и даже опасными top-level выражениями, пока вы ограничиваетесь разбором.

```python
import ast


source = "total = price + 2\n"
tree = ast.parse(source, filename="invoice.py", mode="exec")

assignment = tree.body[0]
assert isinstance(assignment, ast.Assign)
assert isinstance(assignment.targets[0], ast.Name)
assert isinstance(assignment.targets[0].ctx, ast.Store)
assert isinstance(assignment.value, ast.BinOp)
assert isinstance(assignment.value.left.ctx, ast.Load)
print(ast.dump(tree, indent=2))
```

`ast.dump` предназначен для исследования структуры. `include_attributes=True` добавляет позиции и другие attributes. Точный полный dump не стоит использовать как стабильный контракт между версиями.

При `mode="exec"` корень обычно `Module`, при `eval` — `Expression`, при `single` — `Interactive`. Выбор режима ограничивает принимаемую грамматику.

**Основные семейства узлов**

| Конструкция | Примеры AST nodes |
| --- | --- |
| Константа | `Constant` |
| Имя, атрибут, индекс | `Name`, `Attribute`, `Subscript` |
| Арифметика и логика | `BinOp`, `UnaryOp`, `BoolOp`, `Compare` |
| Вызов | `Call`, `keyword`, `Starred` |
| Присваивание | `Assign`, `AnnAssign`, `AugAssign`, `NamedExpr` |
| Контейнеры | `List`, `Tuple`, `Dict`, `Set` |
| Comprehensions | `ListComp`, `SetComp`, `DictComp`, `GeneratorExp` |
| Определения | `FunctionDef`, `AsyncFunctionDef`, `ClassDef`, `Lambda` |
| Управление потоком | `If`, `For`, `While`, `Break`, `Continue`, `Return` |
| Контексты/исключения | `With`, `Try`, `ExceptHandler`, `Raise`, `TryStar` |
| Async | `Await`, `AsyncFor`, `AsyncWith` |
| Pattern matching | `Match`, `match_case` и семейство pattern nodes |
| Импорты | `Import`, `ImportFrom`, `alias` |
| Строковые интерполяции | `JoinedStr`, `FormattedValue`; в 3.14 также `TemplateStr/Interpolation` |
| Типовые объявления | `TypeAlias` и type parameter nodes в соответствующих версиях |

`Name(id="x", ctx=Load())` и `Name(id="x", ctx=Store())` имеют разные роли. Если заменить имя с неверным context, дерево может перестать компилироваться.

`obj.value` содержит `Attribute(attr="value")`: атрибут не является отдельным `Name`. `f(**mapping)` использует `keyword(arg=None, ...)`. `-5` обычно представлен как `UnaryOp(USub(), Constant(5))`.

`Constant` объединяет строки, bytes, числовые и некоторые другие константы. Для целых проверяйте при необходимости `type(value) is int`: `bool` является подклассом `int`, но может не подходить вашей трансформации.

**Поля AST нужно читать по модели грамматики**

У `FunctionDef` есть arguments, defaults, decorators, annotations и body. Позиционные defaults соответствуют последним позиционным параметрам; `None` в списке `kw_defaults` обозначает отсутствие default, а `Constant(None)` — явный default `None`.

У `Dict` возможен `None` среди keys для unpacking `**mapping`. У pattern matching имена захвата не обязательно выглядят как `Name(Store)`. Универсальная стратегия «ищем все Name» не охватывает все bindings.

`ast.iter_fields` и `ast.iter_child_nodes` помогают обойти структуру без предположений о внутреннем `__dict__`. У классов узлов есть `_fields`; в новых версиях дополнительно доступна `_field_types`.

**Версия grammar и версия среды**

```python
import ast


source = "type Box[T] = list[T]\n"
current_tree = ast.parse(source)
assert isinstance(current_tree.body[0], ast.TypeAlias)

try:
    ast.parse(source, feature_version=(3, 11))
except SyntaxError:
    print("type statement is unavailable in the selected grammar")
else:
    raise AssertionError("older grammar must reject a type statement")
```

`feature_version` — best-effort выбор грамматики. Он не превращает текущий компилятор в старый runtime и не проверяет доступность библиотечных API целевой версии.

Если tool поддерживает Python 3.12–3.14, тестируйте его на обеих границах и конкретных новых nodes. Поле `type_params` появилось раньше, чем некоторые параметры и default values внутри type parameter nodes.

**Template strings в Python 3.14**

```python
# Python 3.14+
import ast


tree = ast.parse('message = t"Hello, {name}!"\n')
template = tree.body[0].value
assert isinstance(template, ast.TemplateStr)
interpolations = [
    item for item in template.values if isinstance(item, ast.Interpolation)
]
assert len(interpolations) == 1
assert isinstance(interpolations[0].value, ast.Name)
assert interpolations[0].value.id == "name"
```

Здесь `name` не вычисляется: исходник только разбирается. Обработка AST новой конструкции не означает автоматической поддержки её runtime semantics вашим анализатором.

**Parse success — ещё не полная допустимость программы**

Parser может построить дерево для некоторых конструкций, которые отвергает последующая компиляция, например `return` вне функции. Полноценный инструмент должен различать syntax parsing, scope checks, type analysis и выполнение.

### NodeVisitor, NodeTransformer и обход вложенных областей

**Visitor отделяет обход от обработки узлов**

`NodeVisitor` вызывает `visit_ClassName` для соответствующего типа. Если переопределить метод и не вызвать `generic_visit`, его children автоматически не обходятся.

Это может быть как ошибкой, так и намеренным ограничением scope.

```python
import ast


source = """
def outer():
    def inner():
        pass
    return inner
class Service:
    def method(self):
        pass
"""
tree = ast.parse(source)


class TopLevelFunctions(ast.NodeVisitor):
    def __init__(self) -> None:
        self.names = []

    def visit_FunctionDef(self, node):
        self.names.append(node.name)
        # В тела определений намеренно не заходим.

    visit_AsyncFunctionDef = visit_FunctionDef

    def visit_ClassDef(self, node):
        return None


visitor = TopLevelFunctions()
visitor.visit(tree)
assert visitor.names == ["outer"]

all_names = {
    node.name
    for node in ast.walk(tree)
    if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef))
}
assert all_names == {"outer", "inner", "method"}
```

`ast.walk` даёт полный обход descendants, но не обещает удобный для вашей задачи порядок и не знает о границах имён. Он подходит для подсчёта форм, но не заменяет scope-aware анализ.

**Синтаксическая вложенность отличается от execution scope**

Тело вложенной функции исполняется при её вызове. Defaults и decorators вычисляются при создании функции в окружающем контексте. Правила annotations дополнительно зависят от версии и режима.

Тело класса исполняется при создании класса, а его методы имеют собственные scopes. Class namespace не является обычной enclosing function scope для method body.

У comprehensions есть правила изоляции имён, даже когда CPython 3.12+ инлайнит их исполнение по PEP 709. Исчезновение отдельного frame не означает исчезновение языковой границы bindings.

Если нужно найти «все вызовы, выполняемые при импорте», недостаточно исключить все nodes под `FunctionDef`: можно пропустить вызовы в defaults/decorators и ошибочно включить или исключить другие контексты.

**Scope-aware инструмент строит модель**

Для каждого блока определяют параметры, локальные bindings, global/nonlocal declarations, свободные имена и дочерние блоки. Затем учитывают точки связывания: assignments, imports, loop targets, with/except aliases, patterns и другие конструкции.

Для части такой работы полезен `symtable`, который использует правила компилятора текущего Python. Он не является готовым type checker и не разрешает произвольное динамическое поведение.

**Transformer заменяет nodes**

`NodeTransformer` использует возвращаемое значение `visit_*` как замену. Возврат исходного node сохраняет его; новый node заменяет; `None` может удалять элемент там, где это допустимо.

```python
import ast
import copy


class FoldIntegerAddition(ast.NodeTransformer):
    def visit_BinOp(self, node):
        node = self.generic_visit(node)
        if (
            isinstance(node.op, ast.Add)
            and isinstance(node.left, ast.Constant)
            and isinstance(node.right, ast.Constant)
            and type(node.left.value) is int
            and type(node.right.value) is int
        ):
            replacement = ast.Constant(value=node.left.value + node.right.value)
            return ast.copy_location(replacement, node)
        return node


original = ast.parse("value = (2 + 3) + (4 + 5)\n")
changed = FoldIntegerAddition().visit(copy.deepcopy(original))
changed = ast.fix_missing_locations(changed)

assert isinstance(original.body[0].value, ast.BinOp)
assert isinstance(changed.body[0].value, ast.Constant)
assert changed.body[0].value.value == 14

namespace = {}
exec(compile(changed, "folded-demo.py", "exec"), namespace)
assert namespace["value"] == 14
```

Это преобразование фиксированного доверенного примера. Bottom-up обход нужен, чтобы сначала свернуть дочерние additions, а затем родительскую.

Произвольные `a + b` нельзя заменить заранее вычисленным результатом: операнды могут вызывать пользовательский `__add__` и иметь побочные эффекты. Даже constant folding для больших выражений требует бюджета вычислений.

**Обязательные инварианты преобразования**

- Возвращаемый тип должен подходить позиции: statement нельзя вставить вместо expression.
- Контекст `Load/Store/Del` должен соответствовать роли.
- После удаления statements блок может потребовать `Pass`.
- Редактирование lists требует корректных последовательностей nodes.
- Нужно сохранять нужные type metadata и positions либо задавать новые.
- Scope, порядок вычислений и side effects нельзя считать второстепенными.

`NodeTransformer` обычно изменяет переданное дерево. Если исходный AST нужен для сравнения, создайте независимую копию. Несколько проходов должны иметь явный порядок и проверяемые промежуточные инварианты.

**Проверяйте поведение, а не только печать дерева**

Для transformation нужны fixtures, сравнение результата, повторное применение и отдельные негативные случаи. AST equivalence подходит не для любого codemod: перенос импорта намеренно меняет имя модуля, но не должен менять unrelated constructs.

Idempotence — полезное свойство миграции: повторный запуск не продолжает менять уже обработанный код. Оно не доказывает семантическую правильность, но обнаруживает ряд ошибок.

### Позиции узлов, fix_missing_locations() и ast.unparse()

**Три системы координат**

У AST номера строк начинаются с единицы, а column offsets — с нуля и измеряются в UTF-8 bytes. В tokenizer колонки относятся к декодированной строке. Редактор может дополнительно использовать visual columns или UTF-16 offsets.

Эти координаты расходятся на кириллице, emoji, combining characters и tabs. Нельзя напрямую использовать `col_offset` как Python string index.

```python
import ast


source = "имя = 'Иса'; результат = имя + '🐍'\n"
tree = ast.parse(source)
expression = tree.body[1].value

segment = ast.get_source_segment(source, expression)
assert segment == "имя + '🐍'"
assert expression.col_offset > source.index("имя +")
print(
    {
        "ast_utf8_byte_column": expression.col_offset,
        "python_character_column": source.index("имя +"),
        "segment": segment,
    }
)
```

`end_col_offset` указывает на позицию после конца span. У созданных вручную nodes end positions могут отсутствовать, и `get_source_segment` тогда не сможет восстановить фрагмент.

Для однострочного node можно декодировать UTF-8 prefix, чтобы получить code point column. Для нескольких строк нужны корректная обработка line endings и separate offsets начала/конца.

`str.splitlines` распознаёт больше разделителей, чем Python universal newlines. Например, U+2028 внутри строкового литерала не должен неожиданно увеличивать номер строки в вашем mapper. Практический проект содержит такой regression test.

**Locations для сгенерированного дерева**

```python
import ast


call = ast.Call(
    func=ast.Name(id="print", ctx=ast.Load()),
    args=[ast.Constant(value="generated AST")],
    keywords=[],
)
tree = ast.Module(body=[ast.Expr(value=call)], type_ignores=[])
tree = ast.fix_missing_locations(tree)

code = compile(tree, "generated-ast.py", "exec")
exec(code, {})
```

`fix_missing_locations` заполняет недостающие locations по окружающей структуре. Он не узнаёт, где текст «должен был находиться», и не восстанавливает исходное форматирование.

`copy_location(new, old)` полезен для замены, которая логически относится к исходному выражению. Новые children также должны иметь пригодные locations.

`increment_lineno` сдвигает позиции, например при вставке подготовленного блока. Для точных diagnostics после сложного codemod часто нужен source map, а не только общий сдвиг.

**Поля и attributes имеют разную роль**

`_fields` описывает синтаксические компоненты node; `_attributes` — такие сведения, как locations. Заполнение locations не исправляет отсутствующий `ctx`, неверное поле expression или пустой обязательный body.

Конструируйте nodes с явными обязательными полями. Поведение конструкторов становится строже в новых версиях Python; код, который случайно работал с неполным node, нельзя считать совместимым.

**`ast.unparse` генерирует новый исходник**

```python
import ast


source = "# comment to be lost\nvalue=(1+2)\n"
tree = ast.parse(source)
generated = ast.unparse(tree)
reparsed = ast.parse(generated)

assert ast.dump(reparsed, include_attributes=False) == ast.dump(
    tree, include_attributes=False
)
assert "# comment" not in generated
print(generated)
```

`unparse` стремится получить код с эквивалентной AST-структурой, но не возвращает исходные quote style, пустые строки и обычные комментарии. Скобки будут выбраны по необходимости записи выражения.

Type comments и `type_ignores` — специальные элементы, поддерживаемые отдельными режимами parser. Их наличие не означает сохранение всех комментариев программы.

Для глубоких деревьев возможны ограничения recursion. Если в инструмент поступают внешние данные, нужна граница размера/сложности; вызов `unparse` не является безусловно дешёвой операцией.

**Когда AST подходит для изменения кода**

AST удобно использовать для генерации нового модуля, эксперимента с компиляцией, analysis и transformation, где точная запись не является частью результата.

Если нужно изменить одну строку в большом пользовательском файле и сохранить comments, форматирование и line endings, рассмотрите CST или аккуратные локальные edits по диапазонам. Для production codemod важно, чтобы reviewer видел именно полезное изменение.

## Компиляция и динамическое исполнение

### compile(): режимы exec, eval и single

**Компиляция создаёт code object**

`compile` принимает исходный текст, bytes или подходящее AST и подготавливает код к выполнению. На этом шаге проверяются также ограничения, которые не сводятся к распознаванию tokens.

Функции из исходника здесь не вызываются. Defaults, decorators и top-level statements исполняются на следующем шаге, когда выполняется соответствующий code object.

| Режим | Что предназначено на вход | Типичное использование |
| --- | --- | --- |
| `exec` | Модуль или последовательность statements | Скрипт, generated module |
| `eval` | Одно выражение | Вычисление выражения доверенного происхождения |
| `single` | Интерактивный ввод | REPL-подобная обработка с display hook |

```python
import sys
from types import CodeType


expression = compile("6 * 7", "expression-demo.py", "eval")
assert isinstance(expression, CodeType)
assert eval(expression, {}) == 42

namespace = {}
module = compile("answer = 6 * 7\n", "module-demo.py", "exec")
assert exec(module, namespace) is None
assert namespace["answer"] == 42

displayed = []
previous_hook = sys.displayhook
sys.displayhook = displayed.append
try:
    interactive = compile("6 * 7\n", "interactive-demo.py", "single")
    exec(interactive, {})
finally:
    sys.displayhook = previous_hook
assert displayed == [42]
```

Все исходники в примере фиксированы. `single` нужен не для ограничения прав, а для семантики интерактивного ввода. Для определения «ввод ещё не закончен» REPL может использовать `codeop.compile_command`.

`filename` нужен для traceback и provenance. Он может быть условным, но реальный понятный путь или идентификатор generated artifact упрощает диагностику.

**Parser и compiler проверяют разные уровни**

```python
import ast


tree = ast.parse("return 42\n", filename="invalid-context.py")
assert isinstance(tree.body[0], ast.Return)

try:
    compile(tree, "invalid-context.py", "exec")
except SyntaxError:
    print("return outside a function rejected during compilation")
else:
    raise AssertionError("compilation must reject this context")
```

Аналогично scope rules могут отвергнуть некорректный `nonlocal` и другие контекстные нарушения. Построенный AST не следует автоматически выполнять только потому, что `ast.parse` завершился успешно.

Компиляция также не доказывает, что runtime imports разрешатся, выражение завершится или типы операндов подходят операциям.

**Flags и наследование настроек**

`flags` управляет специальными compiler options. `ast.PyCF_ONLY_AST` позволяет получить AST через `compile`; `ast.parse` предоставляет удобный интерфейс для похожей задачи.

`dont_inherit=True` помогает не наследовать некоторые compiler flags из вызывающего контекста. Это важно для генераторов, которым нужен явно заданный режим, а не случайные future flags framework.

`optimize` влияет на assertions, docstrings и другие предусмотренные оптимизации. Значение по умолчанию может учитывать запуск интерпретатора. Инструмент анализа должен понимать, исследует ли он исходную структуру или оптимизированное представление.

Не используйте `assert` для обязательной валидации пользовательского запроса: оптимизированный запуск может убрать такую проверку. В проекте ошибки конфигурации выражены явными исключениями.

**Top-level await**

Особый flag позволяет компилировать интерактивные конструкции с `await` вне обычного `async def`:

```python
import ast
import asyncio
import inspect


source = "await asyncio.sleep(0)\nanswer = 42\n"
namespace = {"asyncio": asyncio}
code = compile(
    source,
    "top-level-await-demo.py",
    "exec",
    flags=ast.PyCF_ALLOW_TOP_LEVEL_AWAIT,
    dont_inherit=True,
)
coroutine = eval(code, namespace)
assert inspect.iscoroutine(coroutine)
asyncio.run(coroutine)
assert namespace["answer"] == 42
```

Это интерфейс для специализированной среды выполнения, например интерактивной оболочки. Созданную coroutine нужно исполнить либо закрыть по контракту; простое получение объекта не выполняет асинхронную работу.

Пример также показывает, почему название `eval` нельзя считать ограничением возможностей code object. При передаче уже скомпилированного кода значение имеет его реальная структура и flags.

**Генерация требует отдельного качества**

Сохраняйте generated source/AST, его версию и понятный filename. Проверяйте compilation и поведение. Генератор должен исключать случайное включение произвольного текста в позиции кода.

Для подстановки обычных значений используйте data objects и runtime parameters, а не конкатенацию кода. Если же задача действительно состоит в создании программы, рассматривайте её как compiler/tooling project с определённой grammar и тестами.

### exec()/eval(): globals, locals и границы доверия

**Выполнение использует пространства имён**

При вызове с явными словарями можно управлять тем, откуда разрешаются имена и куда записываются bindings. Это управление окружением, а не автоматическое ограничение доступных эффектов.

Для generated module обычно удобен один namespace:

```python
source = "base = 40\n\ndef answer():\n    return base + 2\n"
namespace = {"__name__": "generated_demo"}

exec(compile(source, "namespace-demo.py", "exec"), namespace)
assert namespace["base"] == 40
assert namespace["answer"]() == 42
assert namespace["answer"].__globals__ is namespace
assert "__builtins__" in namespace
```

Если `globals` не содержит `__builtins__`, механизм исполнения добавляет доступ к builtins. Словарь вида `{"allowed_value": 1}` сам по себе не запрещает остальные возможности Python.

**Два namespace имеют неожиданную для многих семантику**

```python
source = "base = 40\n\ndef answer():\n    return base + 2\n"
global_names = {"__builtins__": {}}
local_names = {}

exec(source, global_names, local_names)
assert local_names["base"] == 40
assert "base" not in global_names

try:
    local_names["answer"]()
except NameError:
    print("function resolves globals, not the separate exec locals mapping")
else:
    raise AssertionError("base is unavailable to the generated function")
```

Top-level assignment попал в locals mapping, а созданная функция связана с globals. Это похоже на отдельные аспекты выполнения class body, но не должно использоваться как случайный способ «спрятать» переменные.

Если нужен доступный снаружи результат, передайте явный namespace и извлеките значение из него. Не пытайтесь управлять обычными function locals через неявный `exec`.

**`locals()` и `frame.f_locals` различаются**

В optimized function scope правила snapshot и write-through были уточнены в Python 3.13 по PEP 667. `locals()` возвращает snapshot, а `frame.f_locals` используется как представление с возможностью записи в реальное состояние frame.

Поведение старых версий отличалось. Framework, который рассчитывает на случайный эффект `locals()["x"] = ...`, оказывается зависимым от реализации и версии.

Для исполнения generated кода используйте отдельные словари. Для debugger, которому нужно менять живое состояние, ориентируйтесь на специальные API и поддерживаемые версии.

**Почему ограниченный globals не создаёт sandbox**

Python objects связаны с классами, descriptors, modules, callables и другими объектами. Разрешённый объект может предоставить доступ к дополнительным возможностям или выполнить код через собственный протокол.

Ограничение строки до «только выражение» тоже не исключает вызовы, attribute access, выделение огромных объектов и длительные вычисления. `eval` принимает выражения с побочными эффектами.

Запрет отдельных слов ненадёжен: существуют aliases, другие способы доступа и динамически вычисляемые значения. AST allowlist может определить маленький собственный язык, но проверка Python AST по нескольким признакам ещё не даёт доказанной изоляции полного Python.

**Выбирайте формат по задаче**

| Требование | Возможный подход |
| --- | --- |
| Передать настройки | JSON/TOML и schema validation |
| Описать ограниченное правило | Небольшой DSL с явной grammar и стоимостью операций |
| Зарегистрировать доверенный plugin | Обычный module/package API и управление жизненным циклом |
| Исполнить пользовательскую программу | Специализированная изоляция с отдельной моделью разрешений и ресурсов |
| Сгенерировать свой adapter | Compile доверенной конструкции и тест установленного artifact |

Отдельный subprocess помогает ограничить lifetime и сбой, но по умолчанию наследует права пользователя и доступ к ресурсам. Один `subprocess.run(..., timeout=...)` не создаёт полноценную среду изоляции.

Auditing и logging помогают наблюдать исполнение, а не отменяют необходимость модели доверия. Храните происхождение исходника, версию и решение, почему его выполнение разрешено.

**Не выполняйте исходник ради анализа**

Для списка imports не требуется импортировать модуль. Для поиска mutable defaults не нужно создавать функции. Для чтения объявленных annotations можно исследовать AST.

Практический проект этой главы читает файлы и строит деревья. Его тест с top-level записью marker-файла проверяет, что анализ не импортирует и не исполняет пользовательский модуль.

### ast.literal_eval(): ограничения формата и потребления ресурсов

**`literal_eval` разбирает значения ограниченного формата**

`ast.literal_eval` поддерживает определённые Python literals и контейнеры: строки, bytes, числа, tuples, lists, dicts, sets, boolean values, `None` и `Ellipsis`.

Он не разрешает произвольные имена и вызовы приложения. Это полезно для Python-представления небольших данных, но не является полной схемой валидации.

```python
import ast


value = ast.literal_eval("{'enabled': True, 'limits': (10, 20), 'labels': {'a', 'b'}}")
assert value["enabled"] is True
assert value["limits"] == (10, 20)
assert value["labels"] == {"a", "b"}

for invalid in ("unknown_name", "sum([1, 2])", "2 + 3"):
    try:
        ast.literal_eval(invalid)
    except (ValueError, SyntaxError):
        pass
    else:
        raise AssertionError("not an accepted literal form")
```

Отдельные формы, например представление пустого set и комплексных чисел, имеют специальную поддержку. Из этого не следует поддержка произвольной арифметики или исполнения функции с тем же именем.

Python literal format отличается от JSON: `True` вместо `true`, `None` вместо `null`, tuples и sets не имеют прямого эквивалента. Для публичного протокола обычно предпочтительнее явно выбранный формат со схемой.

**Нет произвольного исполнения — не значит нет DoS**

Большой или глубоко вложенный input расходует CPU, память и parser stack. Возможны `SyntaxError`, `ValueError`, `TypeError`, `MemoryError` и `RecursionError` в зависимости от входа и стадии.

Ограничение node count после `ast.parse` не ограничивает уже выполненную работу parser. Для враждебных входов нужны ограничения до разбора и, когда задача того требует, внешняя граница ресурсов.

Нельзя называть `literal_eval` безусловно безопасным для любого недоверенного текста только потому, что он не запускает обычные Python calls.

**Сначала ограничьте конкретный формат**

```python
import ast


def read_labels(text: str) -> tuple[str, ...]:
    if not isinstance(text, str) or len(text.encode("utf-8")) > 1_024:
        raise ValueError("label input is too large")
    try:
        tree = ast.parse(text, mode="eval")
    except (SyntaxError, ValueError) as error:
        raise ValueError("invalid label syntax") from error
    if not isinstance(tree.body, ast.List) or len(tree.body.elts) > 16:
        raise ValueError("a list of at most 16 strings is required")
    if any(
        not isinstance(item, ast.Constant) or type(item.value) is not str
        for item in tree.body.elts
    ):
        raise ValueError("only string labels are accepted")
    values = ast.literal_eval(tree)
    if any(len(value) > 40 for value in values):
        raise ValueError("label is too long")
    return tuple(values)


assert read_labels("['python', 'данные']") == ("python", "данные")
for invalid in ("[1]", "[str(1)]", "{'python'}"):
    try:
        read_labels(invalid)
    except ValueError:
        pass
    else:
        raise AssertionError("schema must reject the input")
```

Это небольшой validator фиксированного формата, а не универсальная защита parser. Для промышленного API стоит отдельно задать максимальный размер transport payload ещё до создания большой Python-строки.

Проверяются типы элементов, вместимость списка и длина labels. Прикладная схема может дополнительно запрещать дубликаты, нормализовать Unicode и проверять допустимый алфавит. Таких правил `literal_eval` не знает.

**Выбирайте сообщения об ошибках**

Пользователю полезно различать «неверная грамматика», «не тот контейнер» и «превышен лимит». При этом не стоит автоматически логировать весь input, если в нём могут быть секреты.

Не обрабатывайте нехватку памяти как обычную удобную ошибку поля без модели восстановления процесса. Границы ресурсов и lifetime parser заслуживают отдельного проектирования.

## Создание инструментов разработчика

### Статический анализатор, linter, codemod и проверка архитектурных правил

**У разных инструментов разные контракты**

Статический анализатор извлекает сведения без обычного выполнения программы. Linter превращает определённые наблюдения в diagnostics по правилам. Type checker строит дополнительную модель типов. Codemod предлагает или применяет конкретное преобразование.

Один проект может сочетать эти роли, но полезно отдельно определить, что он обнаруживает, что меняет и что гарантирует.

| Инструмент | Результат |
| --- | --- |
| Синтаксический анализатор | Дерево или ошибка grammar/context |
| Linter | Findings с rule ID, расположением и сообщением |
| Type checker | Diagnostics в рамках своей модели типов |
| Dependency analyzer | Граф известных import/reference edges |
| Architecture checker | Нарушения договорённостей о зависимостях |
| Codemod | Изменённый текст и объяснение преобразования |
| Formatter | Нормализованная запись по выбранным правилам |

**Pipeline должен быть явным**

Для source analyzer полезна последовательность: выбрать файлы, ограничить чтение, определить кодировку, разобрать AST, проверить compiler context, построить нужную модель, применить rules, отсортировать diagnostics и опубликовать отчёт.

Каждый этап имеет свои ошибки. «Файл не прочитан» не означает «нарушений нет». Синтаксически повреждённый файл нельзя молча исключать из denominator проверенного проекта.

Диагностике нужны стабильный code, relative path, определение единиц позиции и понятное сообщение. Для CI полезен machine-readable формат и документированные exit codes.

**Синтаксический сбор imports**

```python
import ast


source = """
import package.submodule
import math as mathematics
from json import loads as parse_json
"""
tree = ast.parse(source)
bindings = {}
for statement in tree.body:
    if isinstance(statement, ast.Import):
        for alias in statement.names:
            binding = alias.asname or alias.name.split(".")[0]
            bindings[binding] = alias.name
    elif isinstance(statement, ast.ImportFrom):
        for alias in statement.names:
            if alias.name != "*":
                bindings[alias.asname or alias.name] = (
                    f"{statement.module}.{alias.name}"
                )

assert bindings == {
    "package": "package.submodule",
    "mathematics": "math",
    "parse_json": "json.loads",
}
```

Здесь обрабатываются только top-level imports указанного примера. Это карта syntactic bindings на момент соответствующего statement, а не доказательство всех будущих значений этих имён.

У `import package.submodule` без alias локально связывается `package`. У relative imports нужен package context; одной строки `node.module` недостаточно.

**Архитектурная политика**

Можно задать правило: код под `app.domain` не должен явно импортировать `app.infrastructure`. Проверка prefix должна учитывать границу компонента: `app.infrastructure_extra` — другое имя.

Такое правило может намеренно распространяться на imports под `TYPE_CHECKING`, внутри функций и в недостижимых branches. Это политика исходного текста; для неё не обязательно доказывать исполнимость каждого branch.

Нужно определить, проверяются ли только прямые imports или транзитивные зависимости через re-exports. Динамические imports, namespace packages и конфигурация source roots требуют отдельной модели.

Для сложного графа разумно использовать готовый инструмент вроде Import Linter. Учебный checker в проекте реализует ограниченное правило явных imports и описывает слепые зоны.

**Autofix требует более сильного основания**

Найти mutable default сравнительно просто. Автоматически заменить его на `None` сложнее: надо вставить initialization, выбрать sentinel при допустимом `None`, сохранить annotations и не изменить контракт.

Предложить diagnostic можно при меньшей уверенности, чем требуется для автоматического изменения программы. Для rule с неоднозначной семантикой полезнее explainable warning, чем уверенный неверный fix.

В codemod задайте предусловие: какая старая API используется, какая новая ей соответствует, какие случаи поддерживаются и какие оставляются для ручного решения.

**Тестирование analyzer**

Проверяйте положительные и отрицательные fixtures, nested scopes, aliases, encodings, Unicode columns и syntax errors. Тест «здесь находится один Call» недостаточен для правила, которое заявляет разрешение настоящего symbol.

Golden tests полезны для human-readable diagnostics и diffs. При этом крупный snapshot должен позволять понять изменение, иначе его легко обновить вместе с ошибкой.

Проверяйте установленный wheel из другого каталога. Анализатор должен использовать собственный пакет, а не случайно импортированный `src` из текущего working directory.

**Производительность tool**

Храните разобранный файл и таблицы строк для повторных rules. Повторный decode/parse или пересчёт offsets на каждую diagnostic может превратить линейный анализ в существенно более дорогой.

Cache key должен учитывать содержимое, версию parser, конфигурацию, rules и окружение, влияющее на вывод. Один mtime не всегда достаточно надёжен; reuse старого результата после изменения settings приводит к неверному «зелёному» отчёту.

Для incremental analysis нужно знать, какие результаты зависят от изменённого модуля. При type inference изменения public API могут инвалидировать больше одного файла.

**Готовые инструменты**

| Задача | Примеры |
| --- | --- |
| Общие lint rules и форматирование | Ruff |
| Статическая типизация | mypy, Pyright |
| Security patterns | Bandit |
| Архитектурные import contracts | Import Linter |
| Сохраняющий форматирование codemod | LibCST |
| Связь AST с текстовыми диапазонами | asttokens |

Здесь перечислены роли, а не взаимозаменяемые продукты. Конфигурацию и совместимость нужно выбирать под поддерживаемый Python, layout и workflow.

Не стоит писать собственный полный linter ради уже решённой задачи. Собственное правило оправдано, когда оно выражает конкретный контракт вашей системы и его достаточно просто поддерживать.

### AST vs CST для сохранения комментариев и форматирования

**Abstract syntax намеренно абстрагируется от записи**

Для AST выражения `a+b` и `a + b` имеют одинаковую основную структуру. Для reviewer их текст различается. Комментарий о важном инварианте вообще может отсутствовать в AST.

CST сохраняет элементы concrete syntax: whitespace, comments, parentheses и другие детали. LibCST использует immutable nodes и возвращает новое дерево через visitor/transformer.

**Round-trip с LibCST**

```python
# requires: libcst
import libcst as cst


raw = b"# keep this\nvalue = (1000)  # important\r\n"
module = cst.parse_module(raw)
assert module.bytes == raw


class GroupThousands(cst.CSTTransformer):
    def leave_Integer(self, original_node, updated_node):
        if updated_node.value == "1000":
            return updated_node.with_changes(value="1_000")
        return updated_node


changed = module.visit(GroupThousands())
assert changed.bytes == raw.replace(b"1000", b"1_000")
assert b"# important\r\n" in changed.bytes
namespace = {}
exec(changed.code, namespace)
assert namespace["value"] == 1_000
```

Изменён только фиксированный доверенный пример. Здесь не требуется разрешение имён: меняется допустимая запись одного integer literal с сохранением значения.

Если передавать bytes, LibCST может учитывать исходную кодировку и выдавать `Module.bytes`. Для str используется `Module.code`. Не теряйте byte-level свойства до parser, если они входят в контракт migration.

**CST не решает автоматически семантику**

Замена всех `Name("old")` на `Name("new")` изменит параметры, locals, imports и другие роли. Сохранение comments не делает rename корректным.

Для реального symbol rename нужно выяснить bindings, scope и references. Для переноса API может потребоваться разрешение qualified names и знание сигнатур.

LibCST предоставляет metadata providers, но их результаты тоже имеют область применимости. Qualified name, полученное статически, не описывает любое будущее monkey patching.

**Metadata и identity nodes**

```python
# requires: libcst
import libcst as cst
from libcst.metadata import MetadataWrapper, PositionProvider


source = "# header\n\ndef calculate(value):\n    return value + 1\n"


class Definitions(cst.CSTVisitor):
    METADATA_DEPENDENCIES = (PositionProvider,)

    def __init__(self) -> None:
        self.definitions = []

    def visit_FunctionDef(self, node):
        position = self.get_metadata(PositionProvider, node)
        self.definitions.append((node.name.value, position.start.line))


wrapper = MetadataWrapper(cst.parse_module(source))
visitor = Definitions()
wrapper.visit(visitor)
assert visitor.definitions == [("calculate", 3)]
assert wrapper.module.code == source
```

`MetadataWrapper` управляет деревом, для которого рассчитаны metadata. По умолчанию он может копировать nodes, поэтому нельзя бездумно смешивать identity из исходного и обёрнутого дерева.

Используйте documented provider и его единицы позиций. AST byte offsets, CST positions и координаты LSP нельзя смешивать без преобразования.

**AST с привязкой к tokens**

Иногда нужно найти исходный segment по AST, но не изменять всю структуру. `asttokens` связывает nodes с текстовыми диапазонами:

```python
# requires: asttokens
import ast

from asttokens import ASTTokens


source = "результат = calculate(10, scale=2)  # keep\n"
tokens = ASTTokens(source, parse=True)
call = next(node for node in ast.walk(tokens.tree) if isinstance(node, ast.Call))
assert tokens.get_text(call) == "calculate(10, scale=2)"
start, end = tokens.get_text_range(call)
assert source[start:end] == "calculate(10, scale=2)"
```

Это удобно для diagnostics и локальных edits. Поддержка отдельных новых синтаксических форм и сложных embedded expressions зависит от версии библиотеки; проверяйте fixtures для своего syntax set.

**Выбор представления**

| Требование | Обычно подходит |
| --- | --- |
| Подсчитать синтаксические формы | AST |
| Проверить конкретный comment/directive | tokenize |
| Сгенерировать новый код без сохранения стиля | AST или generator текста |
| Изменить исходник с сохранением trivia | CST |
| Найти небольшой source span по AST | asttokens или аккуратная работа с positions |
| Понять уже исполняемый callable | inspect |

У локальных текстовых edits нужны отсутствие перекрытий, корректные offsets и проверка, что файл соответствует исходному snapshot. Иначе редактор может применить диапазон к уже изменённому тексту.

**Codemod должен быть reviewable**

По умолчанию полезно формировать diff. Отдельно проверяются compilation, tests, typing и повторный запуск transformation. Большая миграция делится на достаточно небольшие изменения.

Если инструмент не может уверенно преобразовать mixed import, пусть он явно сообщит об оставленном случае. Молчаливое изменение неподдерживаемой части хуже диагностируемого ограничения.

Старый `lib2to3` не подходит как универсальная основа для нового инструмента на современном Python; модуль удалён из стандартной библиотеки в Python 3.13. Grammar стороннего CST parser тоже нужно проверять отдельно от версии runtime.

### Ограничения статического анализа динамического языка

**Текст не содержит все будущие значения**

Имена могут получать новые bindings, modules — новые атрибуты, классы — методы, а import path — зависеть от environment. Decorators и metaclasses способны изменить созданный объект.

Статический инструмент выбирает модель: какие динамические действия известны, какие аппроксимируются, какие считаются неизвестными. Полезность анализа определяется не отсутствием динамики, а ясностью модели и её соответствием проекту.

**Простая проверка имени не разрешает symbol**

```python
import ast


source = """
def eval(value):
    return value
result = eval("plain data")
"""
tree = ast.parse(source)
calls_named_eval = [
    node
    for node in ast.walk(tree)
    if isinstance(node, ast.Call)
    and isinstance(node.func, ast.Name)
    and node.func.id == "eval"
]
assert len(calls_named_eval) == 1

namespace = {}
exec(compile(tree, "shadowed-name-demo.py", "exec"), namespace)
assert namespace["result"] == "plain data"
```

В этом фиксированном примере вызывается локально определённая функция, а не builtin. Diagnostic «в исходнике есть вызов с именем eval» точнее, чем безусловное утверждение «здесь исполняется строка как Python».

Обратная проблема — alias настоящей опасной функции. Анализ только одного spelling пропустит `executor = eval; executor(text)`. Для вывода о вызове нужен анализ bindings/dataflow и его пределы.

**Symbol table помогает с лексическими правилами**

```python
import symtable


source = """
rate = 2
def outer(value):
    captured = value
    def inner(extra):
        return captured + extra + rate
    return inner
"""
root = symtable.symtable(source, "scope-demo.py", "exec")
outer = next(child for child in root.get_children() if child.get_name() == "outer")
inner = next(child for child in outer.get_children() if child.get_name() == "inner")

assert outer.lookup("value").is_parameter()
assert outer.lookup("captured").is_local()
assert inner.lookup("captured").is_free()
assert inner.lookup("extra").is_parameter()
assert inner.lookup("rate").is_global()
```

`symtable` использует правила текущего компилятора. Он различает scopes и свойства symbols, но не знает фактическое значение глобального `rate` при каждом будущем вызове.

Новые версии языка добавляют annotation scopes, type parameters и другие особенности. Собственная модель scopes должна сопровождаться версионными тестами, а не только знакомыми примерами `def`.

**Control flow и dataflow**

Тип переменной может зависеть от branch. Объект может быть переопределён после import. Исключение может прервать initialization. Полезный analyzer различает возможные пути и объединяет сведения в точках слияния.

Для глубоких задач строят control-flow graph, def-use chains, reaching definitions и другие модели. Даже они требуют правил для вызовов неизвестных функций, aliasing и внешних эффектов.

`TYPE_CHECKING` влияет на анализ типов, но обычно не выполняется как обычная runtime ветка. Правило архитектуры может намеренно учитывать такие imports, а runtime dependency estimator — отдельно их классифицировать.

**Точность и полнота**

False positive — tool сообщил нарушение там, где выбранный контракт не нарушен. False negative — реальное нарушение не обнаружено.

Soundness и completeness всегда относятся к конкретной формальной модели. Отсутствие findings от практического linter не означает доказательство всех свойств произвольной Python-программы.

Type checker может допускать `Any`, использовать stubs, игнорировать часть модулей и зависеть от настроек. Зелёный отчёт имеет смысл только вместе с этой конфигурацией.

**Imports и граф проекта**

Влияют source roots, namespace packages, relative imports, re-exports, `__all__`, generated code и условные зависимости. Один путь файла не всегда однозначно задаёт importable module name.

В проекте ниже package context задаётся явно. Это ограничивает неоднозначность и позволяет разрешать обычные relative imports без импортирования модулей.

Он не строит полный транзитивный граф runtime-зависимостей. Например, `from app import *` и строка для `importlib.import_module` требуют дополнительной модели. Такие случаи названы ограничениями, а не молча объявлены корректными.

**Практические меры**

Используйте conventions, которые упрощают анализ: явные imports, устойчивые public APIs, ограниченные dynamic registries, типизированные границы и небольшие modules.

Suppression должна иметь объяснение и достаточный scope. Глобальное отключение rule из-за одного ложного срабатывания скрывает остальные случаи; тысячи необъяснённых suppressions тоже лишают правило смысла.

Сочетайте static checks, runtime tests, contracts и наблюдаемость. Они находят разные классы проблем.

Сам инструмент и его plugins — исполняемое ПО. То, что анализируемые файлы не импортируются, не означает автоматическую изоляцию любого config loader или plugin framework.

### Байт-код и внутренние API: привязка к версии реализации

**Bytecode находится ниже AST**

После разбора и контекстных проверок compiler выбирает инструкции, константы, переходы и служебные структуры. Это полезный уровень для изучения CPython и диагностики конкретной реализации.

`dis` даёт структурированное представление, с которым удобнее работать, чем с произвольным ручным разбором `co_code`.

```python
import dis


def calculate(value: int) -> int:
    return value * 2 + 1


instructions = list(dis.get_instructions(calculate))
assert instructions
assert calculate(5) == 11
for instruction in instructions:
    print(instruction.offset, instruction.opname, instruction.argrepr)
```

Список opcodes и их operands меняется между версиями. Не проверяйте бизнес-поведение утверждением «у этой функции ровно семь инструкций».

`Instruction` связывает opcode, argument и часть metadata с source positions. Для анализа jumps используйте сведения `dis` соответствующей версии, а не предположение, что offset всегда равен индексу в списке.

**Специализация и inline caches**

CPython может специализировать инструкции по наблюдаемым типам. Отображение исходного bytecode и реально адаптированной формы различается.

```python
import dis
import io


def add_one(value: int) -> int:
    return value + 1


for number in range(5_000):
    add_one(number)

stream = io.StringIO()
dis.dis(add_one, file=stream, adaptive=True, show_caches=True)
assert add_one(41) == 42
print(stream.getvalue())
```

Это диагностический пример для CPython с поддержкой указанных параметров. Он не требует конкретного spelling специализированной инструкции и не обещает, что любая сборка выберет одинаковую specialization.

`co_code` не обязательно является полным снимком того внутреннего представления, которое прямо сейчас исполняет адаптивный интерпретатор. Для объяснения поведения используйте documented view и точную версию.

Наличие специализации не означает, что ручная подмена bytecode станет хорошей оптимизацией. Внутренние invariants включают stack effects, caches, exception tables и source mapping.

**Исходная политика и скомпилированное поведение различаются**

```python
import ast
import dis


source = "if False:\n    import forbidden_dependency\n"
tree = ast.parse(source)
source_imports = [
    node for node in ast.walk(tree) if isinstance(node, (ast.Import, ast.ImportFrom))
]
compiled = compile(tree, "dead-branch-demo.py", "exec", optimize=0)
instruction_imports = [
    item for item in dis.get_instructions(compiled) if item.opname == "IMPORT_NAME"
]

assert len(source_imports) == 1
print(
    {
        "syntactic_imports": len(source_imports),
        "compiled_import_instructions": len(instruction_imports),
    }
)
```

В проверенных сборках compiler может убрать заведомо неисполняемую ветку. Архитектурное правило по исходнику всё равно увидит её import. Это не противоречие: проверяются разные свойства.

Для security и architecture checks заранее выберите уровень. Нельзя подменить политику «в исходнике не должно быть зависимости» анализом только реально оставшихся instructions.

**Внутренние форматы и совместимость**

| Механизм | Что учитывать |
| --- | --- |
| `co_code` и opcodes | Версию CPython, caches, jumps и stack effects |
| `CodeType` constructor | Изменения аргументов и внутренних invariants |
| `code.replace` | Согласованность заменяемых metadata и instructions |
| `marshal` | Внутренний формат; отсутствие гарантий обмена недоверенным кодом |
| `.pyc` | Header, magic number, invalidation и соответствие runtime |
| Приватные `sys._*` / C APIs | Ограниченную поддержку и отсутствие обычной стабильности |

Hash-based pyc invalidation не является подписью доверенного автора. Совпадение magic number не доказывает безопасность artifact.

Не переносите bytecode между CPython versions или в другую реализацию как обычные данные приложения. Для распространения библиотек используйте стандартный packaging workflow и совместимые artifacts.

**Когда стоит опускаться на этот уровень**

Для изучения compiler decisions, конкретной regression, instrumentation или работы над интерпретатором. Для большинства lint rules и codemods достаточно AST/CST.

Для event monitoring и profiling предпочтительнее поддерживаемые API и инструменты, а не собственная правка инструкций. Версионные тесты обязательны там, где внутренний API всё-таки является частью решения.

**Практический проект: анализатор и preview codemod**

Пакет `code-inspector-lab` выполняет две команды:

- `check` анализирует дерево одного явно заданного Python package и выдаёт JSON diagnostics.
- `migrate` предлагает diff для переноса одиночного `from legacy_utils import normalize` в `modern_utils`, сохраняя alias и оформление.

Анализируемые модули не импортируются. Исходник проходит decode, `ast.parse` и compiler context check через `compile`. Созданный code object не исполняется.

**Три правила**

| Code | Проверка | Граница |
| --- | --- | --- |
| `CI001` | Mutable literal/comprehension в default function/async function/lambda | Не выводит значение calls, aliases и содержимого tuple |
| `CI002` | Bare `except:` | Не запрещает все broad explicit handlers |
| `CI003` | Явный import из `package.domain` в `package.infrastructure` | Прямые синтаксические edges без runtime inference |

`CI001` учитывает positional-only, обычные positional и keyword-only параметры. `CI003` разрешает обычные relative imports по известному package context, включая `__init__.py`.

Imports под `TYPE_CHECKING` и внутри функций тоже проверяются: так определена политика. `from package import *`, dynamic imports и транзитивные re-exports полностью не моделируются.

**Диагностический контракт**

Пути в отчёте относительны указанному root. Line и column для findings начинаются с единицы; column измеряется в Unicode code points, а не в UTF-8 bytes и не в экранных ячейках.

Ошибки чтения, кодировки и grammar/compiler context находятся в `problems`. Для SyntaxError сохраняется parser message и line; неоднозначный column разных представлений сюда не переносится.

Exit code `0` означает завершённую проверку без findings, `1` — findings, `2` — ошибки входа/проверки. Если есть и problems, и findings, приоритет у `2`.

Лимит числа файлов, размера одного файла и общего прочитанного объёма задаётся явно. При превышении лимита полный отчёт не публикуется.

**Граница чтения**

Вложенные symlinks пропускаются с записью в отчёте; root должен быть существующим обычным directory. Source reader принимает regular files. Из обхода исключены `.git`, `.venv`, `__pycache__`, `build` и `dist`.

Эти проверки рассчитаны на обычный анализ собственного дерева. Они не обеспечивают защиту от конкурентной подмены filesystem, не ограничивают все расходы traversal и не являются sandbox parser для враждебного input.

Mapper колонок специально различает Python universal newlines и другие Unicode separators. Для большого production analyzer таблицу строк стоит подготовить один раз на файл.

**Контракт codemod**

Precondition миграции: `modern_utils.normalize` совместим с прежней API в вашем проекте. Это проверяется документацией и tests соответствующей библиотеки, а не самой формой import.

Поддерживается absolute import ровно одного `normalize`, в том числе с alias, parentheses и comments. Mixed imports и `*` остаются без изменения и подсчитываются как skipped.

Команда выводит preview diff и сохраняет исходный файл. Для сохранения diff можно указать `--output`. Она не применяет patch автоматически.

После transformation проверяются parse и compiler context, а tests проверяют byte-level сохранение unrelated текста и idempotence.

```python
# project: src/code_inspector/model.py
from dataclasses import asdict, dataclass


class ScanError(ValueError):
    """The requested scan cannot produce a complete report."""


@dataclass(frozen=True, slots=True, order=True)
class Finding:
    path: str
    line: int
    column: int
    code: str
    message: str


@dataclass(frozen=True, slots=True)
class Problem:
    path: str
    kind: str
    message: str
    line: int | None = None


@dataclass(frozen=True, slots=True)
class Report:
    files_seen: int
    files_analyzed: int
    bytes_read: int
    findings: tuple[Finding, ...]
    problems: tuple[Problem, ...]
    skipped_symlinks: tuple[str, ...]

    @property
    def exit_code(self) -> int:
        return 2 if self.problems else 1 if self.findings else 0

    def to_dict(self) -> dict:
        return {"schema_version": 1, "exit_code": self.exit_code, **asdict(self)}
```

**`src/code_inspector/source.py`**

```python
# project: src/code_inspector/source.py
import io
import json
import os
from pathlib import Path
import stat
import tempfile
import tokenize

from .model import ScanError


def read_limited(path: Path, maximum: int) -> bytes:
    if type(maximum) is not int or maximum <= 0:
        raise ScanError("positive byte limit required")
    if not stat.S_ISREG(path.stat(follow_symlinks=False).st_mode):
        raise ScanError("source must be a regular non-symlink file")
    with path.open("rb") as stream:
        raw = stream.read(maximum + 1)
    if len(raw) > maximum:
        raise ScanError("source file exceeds the byte limit")
    return raw


def decode_source(raw: bytes) -> str:
    encoding, _ = tokenize.detect_encoding(io.BytesIO(raw).readline)
    return raw.decode(encoding)


def character_column(text: str, line_number: int, utf8_column: int) -> int:
    # Python line numbering uses universal newlines, not every Unicode separator.
    line = text.replace("\r\n", "\n").replace("\r", "\n").split("\n")[line_number - 1]
    prefix = line.encode("utf-8")[:utf8_column]
    return len(prefix.decode("utf-8")) + 1


def write_text_atomic(path: Path, text: str) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    temporary = None
    try:
        with tempfile.NamedTemporaryFile(
            mode="w",
            encoding="utf-8",
            newline="",
            dir=path.parent,
            prefix=f".{path.name}.",
            delete=False,
        ) as stream:
            temporary = Path(stream.name)
            stream.write(text)
            stream.flush()
            os.fsync(stream.fileno())
        os.replace(temporary, path)
    finally:
        if temporary is not None:
            temporary.unlink(missing_ok=True)


def write_report(path: Path, value: dict) -> None:
    text = json.dumps(value, ensure_ascii=False, indent=2, allow_nan=False) + "\n"
    write_text_atomic(path, text)
```

```python
import ast
from importlib.util import resolve_name

from .model import Finding
from .source import character_column


MUTABLE_LITERAL = (
    ast.List,
    ast.Dict,
    ast.Set,
    ast.ListComp,
    ast.DictComp,
    ast.SetComp,
)


def within(module: str, prefix: str) -> bool:
    return module == prefix or module.startswith(prefix + ".")


class Analyzer(ast.NodeVisitor):
    def __init__(
        self,
        text: str,
        path: str,
        module: str,
        package_context: str,
        domain_prefix: str,
        infrastructure_prefix: str,
    ) -> None:
        self.text = text
        self.path = path
        self.module = module
        self.package_context = package_context
        self.domain_prefix = domain_prefix
        self.infrastructure_prefix = infrastructure_prefix
        self.findings: list[Finding] = []

    def add(self, node: ast.AST, code: str, message: str) -> None:
        self.findings.append(
            Finding(
                path=self.path,
                line=node.lineno,
                column=character_column(self.text, node.lineno, node.col_offset),
                code=code,
                message=message,
            )
        )

    def check_defaults(self, arguments: ast.arguments) -> None:
        positional = [*arguments.posonlyargs, *arguments.args]
        defaults = arguments.defaults
        pairs = list(zip(positional[-len(defaults) :], defaults))
        pairs.extend(
            (argument, default)
            for argument, default in zip(arguments.kwonlyargs, arguments.kw_defaults)
            if default is not None
        )
        for argument, default in pairs:
            if isinstance(default, MUTABLE_LITERAL):
                self.add(
                    default,
                    "CI001",
                    f"mutable literal default for parameter {argument.arg!r}",
                )

    def visit_FunctionDef(self, node: ast.FunctionDef | ast.AsyncFunctionDef) -> None:
        self.check_defaults(node.args)
        # Nested functions and class methods are intentionally checked as well.
        self.generic_visit(node)

    visit_AsyncFunctionDef = visit_FunctionDef

    def visit_Lambda(self, node: ast.Lambda) -> None:
        self.check_defaults(node.args)
        self.generic_visit(node)

    def visit_ExceptHandler(self, node: ast.ExceptHandler) -> None:
        if node.type is None:
            self.add(node, "CI002", "bare except catches BaseException subclasses")
        self.generic_visit(node)

    def check_import(self, node: ast.AST, target: str) -> None:
        if within(self.module, self.domain_prefix) and within(
            target, self.infrastructure_prefix
        ):
            self.add(
                node,
                "CI003",
                f"domain explicitly imports infrastructure: {target}",
            )

    def visit_Import(self, node: ast.Import) -> None:
        for alias in node.names:
            self.check_import(alias, alias.name)

    def visit_ImportFrom(self, node: ast.ImportFrom) -> None:
        base = node.module or ""
        if node.level:
            try:
                base = resolve_name("." * node.level + base, self.package_context)
            except ImportError:
                # The configured package context cannot resolve this import.
                return
        targets = [base]
        targets.extend(
            f"{base}.{alias.name}" for alias in node.names if alias.name != "*"
        )
        forbidden = next(
            (
                target
                for target in targets
                if within(target, self.infrastructure_prefix)
            ),
            None,
        )
        if forbidden is not None:
            self.check_import(node, forbidden)


def analyze(
    tree: ast.AST,
    text: str,
    path: str,
    module: str,
    package_context: str,
    package: str,
) -> tuple[Finding, ...]:
    visitor = Analyzer(
        text,
        path,
        module,
        package_context,
        package + ".domain",
        package + ".infrastructure",
    )
    visitor.visit(tree)
    return tuple(sorted(visitor.findings))
```

```python
# project: src/code_inspector/project.py
import ast
from dataclasses import dataclass
import keyword
import os
from pathlib import Path

from .analyzer import analyze
from .model import Problem, Report, ScanError
from .source import decode_source, read_limited


@dataclass(frozen=True, slots=True)
class Limits:
    max_files: int = 512
    max_file_bytes: int = 256 * 1_024
    max_total_bytes: int = 4 * 1_024 * 1_024

    def __post_init__(self) -> None:
        for value in (self.max_files, self.max_file_bytes, self.max_total_bytes):
            if type(value) is not int or value <= 0:
                raise ScanError("limits must be positive integers")


def module_context(relative: Path, package: str) -> tuple[str, str]:
    parts = list(relative.with_suffix("").parts)
    initializer = parts[-1] == "__init__"
    if initializer:
        parts.pop()
    module = ".".join([package, *parts])
    context = module if initializer else module.rpartition(".")[0]
    return module, context


def discover(root: Path, limits: Limits) -> tuple[list[Path], tuple[str, ...]]:
    if root.is_symlink() or not root.is_dir():
        raise ScanError("root must be an existing non-symlink directory")
    paths = []
    skipped = []
    ignored = {"__pycache__", ".git", ".venv", "build", "dist"}

    def fail_walk(error):
        raise ScanError("directory traversal failed") from error

    for directory, names, filenames in os.walk(
        root, followlinks=False, onerror=fail_walk
    ):
        current = Path(directory)
        kept = []
        for name in sorted(names):
            child = current / name
            if child.is_symlink():
                skipped.append(child.relative_to(root).as_posix() + "/")
            elif name not in ignored:
                kept.append(name)
        names[:] = kept
        for name in sorted(filenames):
            path = current / name
            if path.suffix != ".py":
                continue
            if path.is_symlink():
                skipped.append(path.relative_to(root).as_posix())
                continue
            paths.append(path)
            if len(paths) > limits.max_files:
                raise ScanError("project exceeds the file count limit")
    return sorted(paths), tuple(sorted(skipped))


def scan(root: Path, package: str, limits: Limits | None = None) -> Report:
    if not package or any(
        not part.isidentifier() or keyword.iskeyword(part)
        for part in package.split(".")
    ):
        raise ScanError("package must be a dotted Python identifier")
    bounds = Limits() if limits is None else limits
    paths, skipped = discover(root, bounds)
    findings = []
    problems = []
    total_bytes = 0
    analyzed = 0
    for path in paths:
        relative = path.relative_to(root)
        label = relative.as_posix()
        try:
            raw = read_limited(path, bounds.max_file_bytes)
        except OSError:
            problems.append(Problem(label, "io", "source could not be read"))
            continue
        total_bytes += len(raw)
        if total_bytes > bounds.max_total_bytes:
            raise ScanError("project exceeds the total byte limit")
        try:
            text = decode_source(raw)
        except (UnicodeError, SyntaxError, LookupError):
            problems.append(Problem(label, "encoding", "source encoding is invalid"))
            continue
        try:
            tree = ast.parse(text, filename=label, type_comments=True)
            compile(tree, label, "exec", dont_inherit=True, optimize=0)
        except SyntaxError as error:
            problems.append(Problem(label, "syntax", error.msg, error.lineno))
            continue
        except RecursionError:
            problems.append(
                Problem(label, "parser-limit", "parser recursion limit reached")
            )
            continue
        module, context = module_context(relative, package)
        findings.extend(analyze(tree, text, label, module, context, package))
        analyzed += 1
    return Report(
        files_seen=len(paths),
        files_analyzed=analyzed,
        bytes_read=total_bytes,
        findings=tuple(sorted(findings)),
        problems=tuple(sorted(problems, key=lambda item: (item.path, item.kind))),
        skipped_symlinks=skipped,
    )
```

```python
# project: src/code_inspector/codemod.py
import ast
from dataclasses import dataclass
import difflib

from .model import ScanError


@dataclass(frozen=True, slots=True)
class Migration:
    source: bytes
    changed_imports: int
    skipped_imports: int
    diff: str


def migrate_import(raw: bytes, label: str = "module.py") -> Migration:
    try:
        import libcst as cst
    except ImportError:
        raise ScanError("install the codemod extra to preview a migration") from None

    class MoveImport(cst.CSTTransformer):
        def __init__(self):
            self.changed = 0
            self.skipped = 0

        def leave_ImportFrom(self, original_node, updated_node):
            if (
                updated_node.relative
                or not isinstance(updated_node.module, cst.Name)
                or updated_node.module.value != "legacy_utils"
            ):
                return updated_node
            names = updated_node.names
            if (
                isinstance(names, cst.ImportStar)
                or len(names) != 1
                or not isinstance(names[0].name, cst.Name)
                or names[0].name.value != "normalize"
            ):
                self.skipped += 1
                return updated_node
            self.changed += 1
            return updated_node.with_changes(module=cst.Name("modern_utils"))

    try:
        module = cst.parse_module(raw)
        transformer = MoveImport()
        transformed = module.visit(transformer)
        output = transformed.bytes
        # Check parser and compiler context without executing the source.
        tree = ast.parse(output, filename=label, type_comments=True)
        compile(tree, label, "exec", dont_inherit=True, optimize=0)
    except (
        cst.ParserSyntaxError,
        SyntaxError,
        UnicodeError,
        LookupError,
        RecursionError,
    ):
        raise ScanError("source could not be parsed for migration") from None
    parts = difflib.unified_diff(
        raw.decode(module.encoding).splitlines(keepends=True),
        output.decode(module.encoding).splitlines(keepends=True),
        fromfile="a/" + label,
        tofile="b/" + label,
        lineterm="\n",
    )
    chunks = []
    for part in parts:
        chunks.append(part)
        if not part.endswith("\n"):
            chunks.append("\n\\ No newline at end of file\n")
    return Migration(
        source=output,
        changed_imports=transformer.changed,
        skipped_imports=transformer.skipped,
        diff="".join(chunks),
    )
```

```python
# project: src/code_inspector/cli.py
import argparse
import json
from pathlib import Path
import sys

from .model import ScanError
from .project import Limits, scan
from .source import read_limited, write_report, write_text_atomic


def parser() -> argparse.ArgumentParser:
    root = argparse.ArgumentParser(prog="code-inspector")
    commands = root.add_subparsers(dest="command", required=True)
    check = commands.add_parser("check")
    check.add_argument("root", type=Path)
    check.add_argument("--package", required=True)
    check.add_argument("--max-files", type=int, default=512)
    check.add_argument("--max-file-bytes", type=int, default=256 * 1_024)
    check.add_argument("--max-total-bytes", type=int, default=4 * 1_024 * 1_024)
    check.add_argument("--output", type=Path)
    migrate = commands.add_parser("migrate")
    migrate.add_argument("file", type=Path)
    migrate.add_argument("--max-file-bytes", type=int, default=256 * 1_024)
    migrate.add_argument("--output", type=Path)
    return root


def main(argv: list[str] | None = None) -> int:
    arguments = parser().parse_args(argv)
    try:
        if arguments.command == "check":
            limits = Limits(
                arguments.max_files, arguments.max_file_bytes, arguments.max_total_bytes
            )
            root = arguments.root.absolute()
            # A generated report must not replace a scanned Python source.
            if arguments.output is not None and (
                arguments.output.suffix == ".py"
                or arguments.output.resolve() == root.resolve()
            ):
                raise ScanError("choose a non-Python report file")
            report = scan(root, arguments.package, limits)
            value = report.to_dict()
            if arguments.output is None:
                print(json.dumps(value, ensure_ascii=False, indent=2))
            else:
                write_report(arguments.output, value)
            return report.exit_code
        from .codemod import migrate_import

        if arguments.file.is_symlink():
            raise ScanError("source must not be a symlink")
        if arguments.output is not None and (
            arguments.output.resolve() == arguments.file.resolve()
            or arguments.output.suffix == ".py"
        ):
            raise ScanError("patch output must differ from source")
        result = migrate_import(
            read_limited(arguments.file, arguments.max_file_bytes), arguments.file.name
        )
        if arguments.output is None:
            print(result.diff, end="")
        else:
            write_text_atomic(arguments.output, result.diff)
        if result.skipped_imports:
            print(
                f"code-inspector: {result.skipped_imports} mixed or unsupported imports skipped",
                file=sys.stderr,
            )
        return 1 if result.changed_imports else 0
    except ScanError as error:
        print(f"code-inspector: {error}", file=sys.stderr)
        return 2
    except OSError:
        print("code-inspector: source or output I/O failed", file=sys.stderr)
        return 2


if __name__ == "__main__":
    raise SystemExit(main())
```

При наличии предлагаемых изменений `migrate` возвращает `1`. Если изменений нет — `0`; при ошибке — `2`. Source сохраняется без изменения. В patch labels CLI используется имя выбранного файла; для групповой миграции потребуется собственная политика путей и применения.

После просмотра diff и проверки контракта библиотек примените нужное изменение обычным workflow проекта. Затем выполните tests и повторный запуск codemod.

**Как читать результат анализа**

У исходного `demo_app/domain/service.py` ожидаются:

- `CI003` на import инфраструктуры из domain.
- `CI001` на list default параметра `values`.
- `CI002` на bare except.

Отсутствие `legacy_utils` и `demo_app` среди установленных dependencies не мешает анализу: исходник не импортируется.

`files_seen` — число выбранных Python files. `files_analyzed` — число файлов, прошедших decode, parse и compiler context checks. `bytes_read` суммирует bytes успешно прочитанных входов, включая текст с последующей syntax/encoding problem.

`findings` и `problems` отсортированы для воспроизводимого отчёта. Если один файл не прошёл проверку, результаты остальных остаются доступны, а итоговый exit code равен `2`.

Превышение глобального лимита или лимита отдельного файла прерывает полный scan. Ранее сохранённый отчёт не заменяется частичным результатом.

**Разбор архитектуры**

`source.py` отвечает за ограниченное чтение, decoding, перевод offsets и публикацию output. Правила анализа не открывают файлы самостоятельно.

`project.py` определяет набор файлов и package context. Он разрешает обычные относительные imports по расположению файла и заданному полному package name.

`analyzer.py` работает с готовым AST. Для syntactic default rule он не выводит значения expressions, а для architecture rule не загружает module objects.

`codemod.py` имеет отдельную dependency. Команда `check` работает без LibCST; для `migrate` нужен extra `codemod`. Это позволяет сохранить маленькую обязательную поверхность инструмента.

`cli.py` переводит внутренние результаты в контракт exit codes и outputs. Она не перезаписывает исходный `.py` отчётом или patch output.

Конфигурация и лимиты проверяются явными исключениями, поэтому `-O` не убирает обязательные проверки.

**Почему compiler check допустим для статического инструмента**

`compile` проверяет контекст без обычного выполнения top-level statements. Это позволяет обнаружить, например, `return` вне функции после успешного `ast.parse`.

Полученный code object не передаётся в `exec/eval`. Imports, decorators, defaults и annotations анализируемой программы не исполняются этим шагом.

Но parsing/compilation потребляют ресурсы. Ограничение файлов до нескольких сотен килобайт — практический guard для собственного проекта, а не доказательство устойчивости к любому намеренно вредному входу.

**Что покрывают tests**

- Выравнивание defaults для positional-only, обычных и keyword-only параметров.
- Function, async function, nested definitions, methods и lambda.
- Прямые mutable literals и comprehensions; явно ограниченная обработка calls и nested mutability.
- Bare except отдельно от explicit exception handlers.
- Absolute/relative imports, aliases, package initializers, prefix boundaries и nested imports.
- Кириллица и Unicode separators в вычислении колонок.
- Encoding cookie, BOM, CRLF и отсутствие последнего newline.
- Parse errors, compiler context errors и продолжение проверки остальных файлов.
- Ограничения файлов/байтов и сохранение предыдущего отчёта при незавершённом scan.
- Пропуск обнаруженных symlinks.
- Отсутствие импорта source с top-level marker side effect.
- Сохранение комментариев и byte-level properties в поддерживаемых codemod cases.
- Пропуск mixed imports, idempotence и отказ от partial migration.
- Установка wheel и запуск из другого directory, включая `-I/-O`.

Property-based tests генерируют Unicode parameter names, comments и module prefixes. Они дополняют конкретные regression fixtures, а не заменяют их.

**Что остаётся ограничением**

Правило `CI001` не найдёт `items=list()`, default alias на существующий list и tuple, внутри которого находится mutable object. Оно намеренно проверяет определённые syntactic shapes.

`CI003` не является полным dependency graph. Transitive re-exports, import hooks и dynamic strings могут обойти эту модель. Не используйте его как механизм изоляции исполнения.

Обычное чтение файла и проверка symlink не дают atomic snapshot при конкурентных filesystem changes. Для worktree собственного репозитория этого достаточно как учебного протокола; инструмент для чужого изменяющегося дерева требует другой модели чтения.

Ограничения обрабатываемых bytes не ограничивают число пустых directories и всю стоимость traversal. Большому production tool нужны дополнительные budgets, cancellation и observability.

Позиции findings описывают Unicode code points. Для LSP клиента потребуется перевод в согласованную position encoding, а для подсветки tab/emoji — правила самого клиента.

Compatibility переносимой версии analyzer включает parser, compiler, AST schema, LibCST grammar и rules. Установка dependencies без version history не фиксирует эти компоненты навсегда.
